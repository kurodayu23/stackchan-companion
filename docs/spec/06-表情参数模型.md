# 06 · 表情参数模型（平台无关规范）

> 状态：**v1.0（2026-10-24）**
> 适用范围：App 端（iOS / SwiftUI）表情渲染器、后端表情保活调度器、设备轨对照
> 唯一事实来源：官方固件 `m5stack/StackChan`（`origin/main` = `eff0d6b`，固件 1.6.0）
> 交叉引用：`docs/research/53-固件表情引擎与动作合成通道取证.md`、`docs/spec/00-StackChan产品规格与技术规格.md` §6.4、`docs/spec/02-交付感与质感规范.md` §5

## §0 一句话结论

**小栈的脸 = 3 个元素 × 5 个整数参数。** 设备端与 App 端用**同一套参数、同一套几何公式**渲染 ⇒ 无覆盖时两轨**逐像素一致**；设备自身的 `blink` / `idle_expression` / `setEmotion` 会改写**同一批字段** ⇒ 这是两轨分叉的唯一原因。

本文是**平台无关**的：任何端（SwiftUI / HTML / 未来的 Android）照抄 §1–§6 就能得到与设备一致的脸。

## §1 对象模型：3 元素 × 5 参数

### §1.1 元素集合

表情通道（0x03 ControlAvatar）只解析 3 个元素，各 5 个字段：

| 元素 | JSON key | 类 | 出处 |
|---|---|---|---|
| 左眼 | `leftEye` | `DefaultEyes`（`isLeftEye=true`） | `firmware/main/stackchan/json/json_helper.cpp:54-57` |
| 右眼 | `rightEye` | `DefaultEyes`（`isLeftEye=false`） | `firmware/main/stackchan/json/json_helper.cpp:59-62` |
| 嘴 | `mouth` | `DefaultMouth` | `firmware/main/stackchan/json/json_helper.cpp:64-67` |

`speechBubble` **不被解析**（0x03 通道不能下发气泡）；`visible` / `emotion` / `ignoreEmotion` 也都不被解析；任何未知 key **静默忽略**、设备不报错。
（`firmware/main/stackchan/json/json_helper.cpp:41-68`；53 号 §3.1）

### §1.3 JSON 解析的硬规则（写 payload 必读）

| 规则 | 后果 | 出处 |
|---|---|---|
| **0x03**：`x` 与 `y` **必须同时是 int** 才调用 `setPosition` | 只给 `x` 不给 `y` ⇒ **位置整体不生效** | `json/json_helper.cpp:18-23` |

## §2 极性表与单位换算

### §2.1 ⚠️ 极性表（最容易写反的地方）

| 元素 | weight 的含义 | weight = 0 | weight = 100 | 方向 |
|---|---|---|---|---|
| `leftEye` / `rightEye` | **睁眼程度**（眼睑上移量） | 眼睑压住眼白**上部**、露出**下缘月牙 25.23%** ⇒ **不是全闭**（固件是容器内绝对定位，非同心盖板，见 §0.1 C-5） | 眼睑整体移出容器 ⇒ **全睁（100%）**（weight ≥ 70 即饱和） | **越大越睁开** |
| `mouth` | **张开度** | 90×6 圆角 0 的细线 ⇒ **闭嘴** | 60×50 圆角 16 ⇒ **大开口** | **越大越张开** |

**结论：眼睛与嘴的 weight 方向是「相同」的（都越大越"开"）。**
真正的「相反」在下面三处，任何端写渲染器时不要混淆：

| 对比 | 方向 | 出处 |
|---|---|---|
| 眼睑的**运动方向** vs weight 的**符号** | 相反：weight ↑ ⇒ 眼睑 y 偏移**变负**（向上移） | `avatar/skins/default/eyes.cpp:75`（`-map_range(...)`） |
| 嘴的**宽度** vs 嘴的**高度** | 相反：weight ↑ ⇒ 宽 90→60 **变窄**，高 6→50 **变高** | `avatar/skins/default/mouth.cpp:52-53` |
| 旧原型的写法 | **反的**：把 eye weight 当「眼睑盖住多少」 | 见 §0.1 C-1 |

> ⛔ **交付红线**：任何一端把「eye weight ↑ = 眼睑盖得更多」写进去，就是极性写反，必须打回。

### §2.2 单位换算

| 量 | 换算 | 出处 |
|---|---|---|
| `x` / `y` | JSON ±100 ↔ 像素 ±16 ⇒ **1 px = 6.25 JSON 单位**（等价：1 JSON 单位 = 0.16 px） | `avatar/skins/default/eyes.cpp:64-65`；`avatar/skins/default/mouth.cpp:42-43`；`map_range` 定义 `components/smooth_ui_toolkit/src/core/math/base.hpp:40-48` |
| `rotation` | **0.1 度** ⇒ 度 = 值 / 10；3600 = 360° | `avatar/avatar/elements/element.h:36-44`；53 号 §1.1 |
| `weight` | 0..100 ⇒ 归一化 0.0..1.0 | `avatar/avatar/elements/feature.h:22-25` |
| `size` | -100..100 ⇒ 归一化 -1.0..1.0 | `avatar/avatar/elements/feature.h:36-39` |
| 眼睛直径 | `8 + (size + 100) * 24 / 200` px（size=0 ⇒ 20 px，**整数截断**） | `avatar/skins/default/eyes.cpp:137` |
| 眼睑 y 偏移 | `-eyeDiameter * weight / 100` px | `avatar/skins/default/eyes.cpp:75` |
| 嘴 宽 / 高 / 圆角 | `90 + w*(60-90)/100` / `6 + w*(50-6)/100` / `0 + w*(16-0)/100` px（**整数截断**） | `avatar/skins/default/mouth.cpp:52-54` |

### §2.3 元素基准位置（320×240 设备画布内）

设备端头像面板 = **320×240**、居中（`avatar/skins/default/default.cpp:13-15`）。
LVGL v9 中 `LV_ALIGN_CENTER` + `setPos(x,y)` 的语义是「**居中 + 偏移**」
（`managed_components/lvgl__lvgl/src/core/lv_obj_pos.c:625-705`，其中 `LV_ALIGN_CENTER` 分支 `:697-700` 把 style x/y 加到居中位置上）。

| 元素 | 基准（相对面板中心） | 元素中心（画布坐标，偏移为 0 时） | 出处 |
|---|---|---|---|
| 左眼 | x = -70, y = -16 | (90, 104) | `avatar/skins/default/eyes.cpp:13, 63-65` |
| 右眼 | x = +70, y = -16 | (230, 104) | `avatar/skins/default/eyes.cpp:13, 63` |
| 嘴 | x = 0, y = +26 | (160, 146) | `avatar/skins/default/mouth.cpp:12, 42-43` |

> 眼睛容器恒为 32×32，变换锚点在 (16,16) = 眼心（`avatar/skins/default/eyes.cpp:29-30`）。

## §3 规范默认值（唯一真值）

**任何端在「没有下发任何表情」时，都必须渲染成下面这组值。**
这组值 = 固件构造函数自己的初始状态（眼睛 `setSize(0) / setWeight(100)`，嘴 `setWeight(0)`），**不是**我们另选的一套。

| 元素 | x | y | rotation | weight | size |
|---|---|---|---|---|---|
| `leftEye` | 0 | 0 | 0 | 100 | 0 |
| `rightEye` | 0 | 0 | 0 | 100 | 0 |
| `mouth` | 0 | 0 | 0 | 0 | 0 |

> 出处：`avatar/skins/default/eyes.cpp:46-49`（`setSize(0); setWeight(100); setPosition; setRotation(0)`）、`avatar/skins/default/mouth.cpp:28-30`（`setPosition; setWeight(0); setRotation(0)`）。
> 该值同时 = `Emotion::Neutral` 的眼睛部分（`eyes.cpp:103-105`），嘴在固件里**没有情绪表**（§5 已说明）。

### §4.3 Schema 决策说明

| 决策 | 理由 | 出处 |
|---|---|---|
| `additionalProperties: false` | 固件对未知 key **静默忽略**（设备不报错 ⇒ 拼错的 key 只会「什么都没发生」）。后端必须靠 schema 在**下发前**拦下来 | `json/json_helper.cpp:41-68`；53 号 §3.1 |
| `type: "integer"`（不是 number） | ArduinoJson 的 `is<int>()` 对 **float 变体返回 false**（`default: return false`）⇒ `12.0` 这种写法会被**静默丢弃** | `components/ArduinoJson/src/ArduinoJson/Variant/VariantData.hpp:376-399` |
| 0x03 用 `dependentRequired` 表达「x 与 y 同生共死」 | 0x03 的 `update_feature` 里 `x` 与 `y` **必须同时是 int** 才调 `setPosition` | `json/json_helper.cpp:18-23` |
| 0x14 **不用** `dependentRequired` | 0x14 的 `parse_feature` 里 `x` 与 `y` **各自独立**判 `is<int>()`，可以只给一个 | `json/json_helper.cpp:145-164` |
| `rotation` 上限 3600 / 下限 0 | 固件 `Element::setRotation` 钳位 0..3600。**负值在视觉上仍生效**（原始值直接交给 LVGL），但 `getRotation()` 读回是 0 ⇒ **不要下发负 rotation**，用 3600-θ 表达反向 | `avatar/avatar/elements/element.h:41-44`；`avatar/skins/default/eyes.cpp:80-85`；`avatar/skins/default/mouth.cpp:60-66` |
| `speed` 不写死范围 | 53 号 §5.4 已更正：`speed` 实际是**弹簧刚度**（`stiffness = 10 + (speed/1000)² × 640`），不是舵机速度 | 53 号 §5.4（该更正由 57 号真机扫参得出） |

## §5 表情语义表（6 种官方情绪）

固件情绪枚举只有 6 种，**没有**惊讶 / 害羞 / 困惑等更细的情绪（`avatar/avatar/elements/emotion.h:11-18`）。

### §5.1 表 A —— 固件事实部分（眼睛）

固件的 `setEmotion` 只改**眼睛的 weight 与 rotation**，且**右眼 = -左眼**（`avatar/skins/default/eyes.cpp:93-99`）。
嘴**没有**情绪表：`DefaultMouth` 未覆写 `setEmotion`，基类是空实现 ⇒ **固件情绪对嘴零影响**。

| 情绪 | 枚举 | `leftEye.weight` | `leftEye.rotation` | `rightEye.weight` | `rightEye.rotation` | 出处 |
|---|---|---|---|---|---|---|
| Neutral | 0 | 100 | 0 | 100 | 0 | `avatar/skins/default/eyes.cpp:103-105` |
| Happy | 1 | 72 | 1550 | 72 | -1550 | `avatar/skins/default/eyes.cpp:106-108` |
| Angry | 2 | 70 | 450 | 70 | -450 | `avatar/skins/default/eyes.cpp:109-111` |
| Sad | 3 | 70 | -400 | 70 | 400 | `avatar/skins/default/eyes.cpp:112-114` |
| Doubt | 4 | 75 | 0 | 75 | 0 | `avatar/skins/default/eyes.cpp:115-117` |
| Sleepy | 5 | 35 | -50 | 35 | 50 | `avatar/skins/default/eyes.cpp:118-120` |

> ⚠️ Sad 的 `-400` 是**视觉值**；`Element::setRotation` 把**存储值**钳成 0（见 §0.1 C-3）。我们下发时用 `3560` 表达 −40°。

### §5.2 表 B —— ⭐ 待用户拍板（非固件事实，当前**不填值**）

> 固件只给了**眼睛**的 6 组 weight/rotation（表 A）。**嘴在 6 种情绪下分别是什么样子，固件没有任何事实**（`DefaultMouth` 未覆写 `setEmotion`）。

| `leftEye.x` / `rightEye.x` | ±100 ↔ ±16 px | — | **待拍板** |

| # | 条件 | 为什么 |
|---|---|---|
| 1 | 6 种情绪在「3 元素 × 5 参数」空间里**两两可区分** | 否则情绪切换看不出区别 |

| 5 | 只在**参数空间**里做区分，不引入固件没有的通道 | 固件只认 3 元素 × 5 字段（§1.1） |

> 本仓库的调试视图（`prototype/components/expression-renderer.html`）正是这么做的。

### §5.3 App 端如何「设置情绪」

固件**没有**远程设置情绪的接口：`setEmotion` 的真实调用点只有「配网完成」与「文本含 hello/hi/love」两处（53 号 §2.1 事实 C）。
⇒ **App 端不能靠「让设备进入某个情绪」来表达情绪**，必须自己把参数**按 0x03 下发**。

| 情绪 | 设备侧实际会发生什么 | App 端正确做法 |
|---|---|---|
| 任意 6 情绪 | 设备只会「收到 15 个参数并渲染」 | 眼睛取**表 A**；其余 11 个参数取**表 B 拍板值**（未拍板前取 §3 默认值）→ 0x03 下发 → 保活重发 |
| 文本含 hello / hi / love | 设备额外进入 Happy **2000 ms**（`TimedEmotionModifier`），**覆盖**我们下发的眼睛 weight/rotation | 这 2000 ms 内两轨必然分叉；靠保活流在窗口结束后立即抢回 |

### §6.3 「App 是镜子」的可验证定义

依据产品原则「**设备是身体，App 是镜子**」（`docs/research/58-iOS端架构决策.md` §4）：

- **设备轨** = 设备真实显示 = 我们下发的参数 ⊕ 设备自身 modifier 的覆盖结果
- **App 轨** = 镜子 = 我们下发的参数本身
- 两者用**同一套几何公式**渲染 ⇒ **无覆盖时逐像素一致**；一旦发生覆盖（§8）就分叉

⇒ 这条「逐像素一致」是 App 端渲染器的**几何验收标准**：任何一端的渲染只要和 §6.2 对不上，App 就不再是镜子。
（这条只约束几何；配色 / 圆角 / 阴影 / 字体 / 动效见 §7.2 **待拍板**。）

> App 端渲染器**必须复用同一套几何函数**（先算整数像素，再整体缩放），**不许**在 App 端另算一套比例。

> 这条只约束**几何**，不约束配色 / 圆角 / 阴影 / 字体 / 动效。

## §8 三条覆盖事实的渲染含义

### §8.1 `blink` 覆盖远程表情

| 事实 | 细节 | 出处 |
|---|---|---|
| 节奏 | 睁 5200 ms（+ 0..500 ms 随机抖动） / 闭 200 ms | `modifiers/blink.h:25,88-89` |
| 闭眼时写的值 | 双眼 weight = **25**（**不是 0**） | `modifiers/blink.h:83` |
| 恢复 | 闭眼瞬间备份当前 weight，睁眼时写回 | `modifiers/blink.h:80-81,91` |
| 首次触发 | 构造后 5200 ms | `modifiers/blink.h:38` |

**渲染含义**：设备轨上会看到「双眼 weight 突然被压到 25（≈ 75% 闭）200 ms，然后跳回原值」。
因为 25 ≠ 0，**固件的眨眼不是完全闭眼**。App 轨若要镜像这次眨眼，必须知道 weight=25 这个具体值，而不是「闭眼」这个抽象。

> ⚠️ `resyncEyeWeights()`（`modifiers/blink.h:41-44`）**全仓没有调用点**（53 号 §10 待验证项 6）⇒ 远程 weight 与 blink 备份冲突时的最终行为**未验证**。

### §8.2 设备端情绪覆盖（hello / hi / love）

| 事实 | 细节 | 出处 |
|---|---|---|
| 触发 | 文本消息内容含 `hello` / `hi` / `love` | `apps/app_avatar/app_avatar.cpp:251-255`（53 号 §2.1 事实 C） |
| 动作 | `TimedEmotionModifier(Happy, 2000)` | 同上 |
| 覆盖字段 | `setEmotion` 写的就是**同一批 weight / rotation** ⇒ 后写者胜 | `avatar/skins/default/eyes.cpp:87-124`；53 号 §2.1 事实 A |
| 影响范围 | **只影响眼睛**；嘴的 `setEmotion` 是空实现 | `avatar/avatar/avatar.h:44-57` + `avatar/avatar/elements/element.h:55-57` |
| 恢复 | 2000 ms 后 `setEmotion(_prev_emotion)` | `modifiers/timed.h:83-90` |

**渲染含义**：这 2000 ms 内，**设备轨的眼睛被改写成 Happy（左 72 / 1550，右 72 / -1550）**，而 App 轨仍在显示我们下发的参数 ⇒ 两轨分叉，且**分叉的原因不在参数里，而在时序里**。
⇒ 结论：表情必须**保活重发**（周期 < 2000 ms，53 号 §4.3），否则窗口一过就被设备改回去。

### §8.3 关键帧硬切无插值

| 事实 | 细节 | 出处 |
|---|---|---|
| 播放 | `Timeline::update()` 到 `durationMs` 边界直接 `_current_index++` 并 `_apply_current_keyframe()` | `animation/animation.cpp:70-95` |
| 插值 | **没有**任何插值 | 同上；53 号 §5.4 |
| 绕过锁 | `Keyframe::apply()` 直接 set，**不查** modify lock | `animation/animation.cpp:12-34` |
| 例外 | `breath.h` **不查锁**（见 §0.1 C-2）⇒ 0x14 播放期间呼吸仍在叠加 | `modifiers/breath.h:37-40` |
| 呼吸幅度 | ±16 **JSON 单位**（不是像素）⇒ 换算后仅 ±2.56 px | `modifiers/breath.h:61,82-87` + §2.2 |

**渲染含义**：
1. 设备上每帧是一个**台阶**；要顺滑只有两条路 —— **生成阶段补密帧**，或**播放阶段插值**。前者是我们自己的编译器要做的事（53 号 §5.4 已指明方向）；后者会让 App 比设备顺 ⇒ 破坏「镜子」原则。**选哪条待拍板**。
2. `docs/spec/02` §5 D-7「表情切换不做过场动画 + 眼睑连续」与本条的张力，需要一次裁决（**待拍板**）。
3. 播放期间设备上的脸仍在上下浮动 ±2.56 px（呼吸），这是 App 端**无法从参数里得知**的设备私有行为。

#### §9.2b.1 ⭐ 公开订正（2026-10-25 夜间回源核验）——「逐像素一致」的原记录需要收窄

**订正前的原记录**（保留）：约束 3 写「**镜像模式必须输出整数像素、无抗锯齿**」。

**本轮回源发现的问题**（`firmware/main/stackchan/avatar/skins/default/eyes.cpp`）：

| 事实 | 出处 |
|---|---|
| 眼睛的 rotation 施加在 **eye 容器**上（`_container->setRotation`） | `eyes.cpp:80-85` |
| 容器 pivot = **容器中心**（`setTransformPivot(16,16)`，容器 32×32） | `eyes.cpp:29-30` |
| 容器里同时装着**眼白与眼睑** ⇒ **两者一起转** | `eyes.cpp:32-44` |
| 6 情绪里 **4 个带非零旋转**：Happy `1550`(155°) / Angry `450`(45°) / Sad `-400`(−40°) / Sleepy `-50`(−5°) | `eyes.cpp:103-122` |
| **左右眼镜像**：右眼是 `setRotation(-rotation)` | `eyes.cpp:93-98` |

**两个必须公开订正的判断**：

1. **「镜像模式 = 逐像素一致」当时是假的。**
   实装前 `FaceView` 的几何层算对了 `rotationTenths`，**但 Canvas 里从未应用** ⇒
   4/6 情绪的眼睛角度与设备不一致。已修（两种模式都加 `context.rotate(by:)`，
   绕眼睛中心），并加门禁 `check_face_geometry.py` 守住（新增 10 项检查：6 情绪表逐值 +
   左右眼镜像 + 下发值区间 + 渲染层真的旋转）。
2. **「无抗锯齿」这条对旋转过的眼睛不成立。**
   设备端（LVGL `transform_angle`）与 App 端（SwiftUI 矢量路径填充）
   **都是抗锯齿光栅化** ⇒ 旋转眼睛的边缘**不可能逐像素相同**。
   ⇒ **收窄为**：镜像模式保证**几何一致**（中心点 / 直径 / 旋转角 / 眼睑偏移 / 层级 / 设备原色），
   **逐像素相同仅对未旋转元素成立**（嘴、位置、以及 rotation == 0 的 Neutral / Doubt）。
   这不是放宽标准，而是把「可判的」与「不可判的」分开写清楚。

> **顺带记录一条固件侧的状态怪癖**（不影响渲染，但容易看错）：
> `Element::setRotation`（`avatar/elements/element.h:43`）把**存储值**钳到 `0..3600`，
> 负角读回是 0；但 `DefaultEyes::setRotation` 随后把**原始未钳位**的值传给
> `_container->setRotation(rotation)` ⇒ **渲染照常生效**，只是 `getRotation()` 读数失真。
> 这正是协议层「负角用 `3600 + θ` 表达」的原因（`docs/spec/06` §4.3）。

#### §9.2b.3 ⭐ 文献侧的三层一致判据（2026-10-25 07:00 后追加，出处等级 T4）

> 来源：[`docs/research/78-表情与身体表达决策证据提取.md`](../research/78-表情与身体表达决策证据提取.md)
> （DeepSeek 员工池逐条读 112 条文献记录产出，每条带逐字原文与语料行号，**已回源核验**）。
> ⚠️ 出处等级 **T4** = 论文「声称了什么」，**不等于**已被独立验证。

§9.2b.1 把对外承诺收窄为「几何一致」之后，还缺一句**可验收**的话：
「一致到什么程度，才算同一个表情」。按该文的三条侧证，可写成三层：

| 层 | 要求 | 机器可判？ | 依据（记录号见 78 号） |
|---|---|---|---|
| ① **参数层** | 同一组表情系数 / 关键帧数值**逐字节相同** | ✅ 可 | 表情的定义层级是**参数/系数**：avatar 由 neutral + blendshape 线性组合生成，渲染是下游（`parametric-face-animation.10` / `.7`） |
| ② **几何层** | 关键点位置 / 相对距离在**容差内**一致 | ⚠️ 容差必须**实测标定** | 情绪可由 landmark 的**几何与空间关系**承载（`robot-face.27`）；跨本体传递时中间表示被选成「3D landmark + 两两距离」且被偏好（`robot-face.29`） |
| ③ **像素层** | **不承诺**逐点相等，只承诺「同一拓扑下语义可辨识」 | ❌ 不可判 | 跨本体迁移只能保住 **coarse semantics**，细粒度一致性会被本体约束破坏（`robot-motion-expression.15`） |

⇒ **对外表述用 ①②，不用 ③ 的强承诺。**

⚠️ **反证，必须一起记**（`parametric-face-animation.18`）：即使输入**同一份**驱动信号 / 参数，
不同模型（不同渲染路径、不同本体）对它的**响应不同**，偏离训练分布时会 struggle。
⇒ 「参数一致 ⇒ 表情一致」在经验上**不是自动成立**的
⇒ ② 的容差**必须实测**，不能只写在文档里。

#### §9.2b.4 ⭐ 一条会打到我们管线的风险（2026-10-25 07:00 后追加，**未实测**）

文献里明确记录过一类失败：**强模态吞掉弱模态的条件信号**。
`robot-motion-expression.16` 的原话（78 号已核验，L5834）：

> 「a flow-matching model given both a rich audio embedding and a discrete emotion label
> suppresses the emotion, generating near-identical motion regardless of the specified emotion.」

⇒ **我们的管线正是这个形态**：「TTS 音频 + 情绪标签 → 表情 / 动作关键帧」。
⇒ 风险：**音频信息越丰富，情绪标签越可能被忽略** ⇒ 不同情绪最后生成几乎一样的动作。
⇒ 对策方向（**未实现、未验证**）：情绪必须**直接改写动作幅度 / 速度参数**，
而不是当成一个附加 embedding 拼进去 —— 让它在数值上**不可被音频淹没**。

⚠️ 这条目前**只是文献侧证（T4）+ 我们自己的推断**，**没有任何本项目实测**支撑
⇒ 已登记为本项目待验证项（`docs/spec/09` §九）。

#### §9.2b.5 ⭐ 一条与 D1 视觉终选直接相关的实测要求（2026-10-25 07:00 后追加）

78 号给出的最硬一条量化证据（`robot-motion-expression.1`，L5556）：

> 「Out of the 15 gestures presented, we found 6 robotic gestures that can be accurately
> recognized by the human observer.」

⇒ **15 个设计出来的表达，只有 6 个能被准确认出（40%）**；活下来的是
「点头 / 拍手 / 拥抱 / 生气 / 走路 / 飞」这类**原型级、单一意图**的表达。
⚠️ 它是**动作**模态、跨模态外推要打折；但它给出的**方法学**直接可用：
**可辨识度是被实测出来的，不是设计者自称的。**

⇒ 对 D1 的含义：4 套方案无论选哪套，都应补一轮**双端并排可辨识度测试**：
「这套风格下还剩几种表情能被认出」——**这件事目前没做过**（`docs/spec/09` §九）。
