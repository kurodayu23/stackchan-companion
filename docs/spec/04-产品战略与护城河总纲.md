## 一、一句话定位

> **玩具陪你玩，档案记住你是谁。**
> 玩具越玩越旧，档案越聊越厚；玩具丢了就丢了，档案丢了是**你的**、还在。

StackChan 不是"能说话的桌面摆件"，也不是"又一个 AI 陪伴 App 的硬件版"。

它是一个**关系载体**：硬件只是身体，**关系档案才是产品**。
App 是身体的遥控器 + 关系的查看器，**不是产品本体**。

这条定位直接决定了三件事：

| 决策 | 内容 | 依据 |
|---|---|---|
| 做什么 | 陪伴机器人（它有身体、会主动、有脾气、会有变化） | 00 号 §功能取舍 |
| **不做什么** | **不做订阅、不做云端锁定、不做"关系不可带走"** | 48 号 §6.1 候选 A |
| 为什么别人做不了 | 不是技术做不了，是**商业模式不让做**（订阅收入与"关系可带走"直接互斥） | 48 号 §6.1 |

## 二、护城河：三层结构

护城河不是"功能清单"。按**能不能被抄**分成三层，强度递减：

```
┌─────────────────────────────────────────────────────────────┐
│  第三层 · 商业结构层（最强 / 不可抄 / 靠决心）                │
│  「设备即档案 + 可审计来源」                                  │
│   关系存在用户自己拥有、可导出、可核对的东西里                 │
│   壁垒：订阅模式与之互斥，巨头收购只买技术不买关系              │
├─────────────────────────────────────────────────────────────┤
│  第二层 · 时间壁垒层（可追但追不上 / 靠数据积累）              │
│  ① 关系阶段（离散状态机，不是分数）                          │
│  ② 韵律 → 身体的映射参数（需真实人机对话语料 + 逐次调参）      │
│  ③ 身体感知的可靠性（连着 300 次不迟钝）                     │
│   壁垒：需要长期私密交互数据 —— 商用方不敢用、竞品买不到        │
├─────────────────────────────────────────────────────────────┤
│  第一层 · 工程能力层（可抄 / 靠时间与人）/ 也是入场券          │
│  · 端侧存在性检测 + 舵机闭环（在 ESP32-S3 上调到"不迟钝"）      │
│  · 三通道同步反馈（声音 + 表情 + 运动）                        │
│  · 官方协议的全栈实现（App ↔ 设备 ↔ 云）                       │
│   壁垒：开源栈里有半个实现（groki-bot），但依赖 Mac             │
└─────────────────────────────────────────────────────────────┘
```

**关键判断：第一层必须先做，但它不构成"别人做不了"。**
如果只做到第一层，我们就是一个做得更认真的开源项目。**护城河只在第二、三层成立。**

### 3.4 ⭐ 硬件能力的事实核正（2026-10-24 实读固件源码）

**这两条不是文案差异，是能力上限差异 —— 直接决定护城河②「别过头再转回来」能不能做。**

| 项 | 官方 README 说法 | **固件源码实读** | 裁决 |
|---|---|---|---|
| 水平舵机 | 「**360-degree continuous rotation** on the horizontal axis」 | `hal_servo.cpp:340`：`yaw_servo_config.angleLimit = Vector2i(-1280, 1280)` → **±128.0°**，且 `enablePwmMode = true` | ⭐ **以源码为准：±128°，不是 360°** |
| 垂直舵机 | 「90-degree movement on the vertical axis」 | `hal_servo.cpp:349`：`pitch_servo_config.angleLimit = Vector2i(30, 870)` → **3.0° ~ 87.0°** | 以源码为准 |
| NFC | 「a full-featured NFC module」 | **固件仓库里零 NFC 代码**（全仓 `grep -i nfc` 只命中 README 那一行） | ⚠️ **硬件有模组，官方固件没驱动** |
| IMU | 「a 9-axis IMU (accelerometer + gyroscope + magnetometer)」 | 固件用 **BMI270**（6 轴：加速度计 + 陀螺仪） | 以源码为准：6 轴 |
| 舵机单位 | README 未写 | 线上 `angle` 单位 **0.1 度**（App 侧 `/10.0` 同样处理） | 以源码为准 |

**App 侧 3D 预览与固件限幅一致**（`stackchan_robot_box.dart`：`clampedYaw` 同样夹在 ±128），说明官方自己也按 ±128 做预览 —— **进一步佐证 README 的 360° 是营销口径**。

#### 3.4.1 这对护城河②意味着什么

「别过头再转回来」原本被设想成：它把头转开 → 确认 → 再转回来面对你。**在 ±128° 的物理约束下这个设计反而更好**：

| 维度 | 若真能 360° 连续转 | **实际 ±128°（真实）** |
|---|---|---|
| "转开"的语义 | 可以转到任意角度 → **"背对你"这个状态需要额外编码** | **天然有边界** —— 转开就是转到一个有限角度，语义自明 |
| "转回来"的可信度 | 看起来像机械转台，**失去"人"的感觉** | 像**脖子有活动范围** → 更像生物，**更动人** |
| 竞品门槛 | 高 | 低 → **壁垒不在硬件，在关系绑定** |

⇒ ⭐ **修正后的护城河②表述**：
**不是"它能转 360° 所以厉害"，而是"它的脖子只有 ±128°，所以它『别过头再转回来』这件事才有人的重量 —— 而它转回来是因为你们有历史，不是因为看见一张脸"。**
**硬件约束从限制变成了表达力。**

⚠️ **必须同步 UI**：任何展示"360°"的文案都是错的（README 抄来的）。iOS 端姿态显示一律用 `yaw ∈ [-128°, +128°]`、`pitch ∈ [3°, 87°]`。

#### 3.4.2 NFC 的真实状态（2026-10-24 二次核正，见 52 号）

| 项 | 正确值 | 证据 |
|---|---|---|
| 芯片 | ⭐ **ST25R3916**（NFC-V 53 kb/s / NFC-A 848 kb/s，ST DS12484 Rev 8） | M5Stack 官方 StackChan 文档；**不是 PN532** |
| 总线 | **I2C，地址 0x50** | 同上 |
| 固件驱动 | **零** | 全仓 `grep -i nfc` 只命中 README 那一行；`grep -i st25r\|pn532` **0 命中** |
| 速率 | NFC-V 53 kb/s / NFC-A 848 kb/s | ST DS12484 Rev 8 |

- **官方固件没有 NFC 驱动** → 要用 NFC，**我们必须自己写固件**（违反"不改固件"红线）或**外挂模块**。
- ⇒ **NFC 人格卡降级为"可选增强"，不进 P0–P2 主线**。
- 若要做，优先方案：**外挂 NFC 模块接在扩展排针**，不动主控固件路径。
  ⚠️ **原写法「SPI 模块（PN532 类）」已作废** —— 芯片是 ST25R3916，走 I2C 0x50；PN532 是另一个产品线的模组（52 号 §1）。

**⭐ 52 号的核心裁决：NFC 卡 = 分享手段，不是迁移手段**（四条论证）：
① 私人层过卡 = 护城河自毁；② 容量差 2 个数量级；③ 卡无会话；④ 两种定位在「载荷-加密-导入」语义上互斥。
⇒ **换机分工**：**NFC 只搬公开层**（仪式感），**BLE / 加密文件搬私人层**。
⇒ **验签用 ECDSA P-256 + SHA-256**（**不是 Ed25519** —— Ed25519 在 ESP-IDF 5.x 的 mbedTLS 里根本不存在；S3 有 SHA/AES/RSA 加速器但**无 ECC 加速器**）。

### 3.5 ⭐ 表情与动作通道的事实边界（2026-10-24 实读固件表情引擎）

护城河②（韵律表达 / 身体表达）此前按「它能转 360°、表情丰富」来论证。实读固件后，边界如下：

| 事实 | 结论 | 影响护城河 |
|---|---|---|
| 远程表情只认 **3 元素 × 5 字段**（leftEye/rightEye/mouth） | 表情的表达空间**很窄**，不是「无限表情」 | 护城河不在「表情多」，在**在窄空间里做出时序** |
| 远程表情**撑不过 2 秒**（被 blink/idle/breath 覆盖） | 必须保活重发 + 与空闲动画仲裁 | ⭐ **护城河②的工程内核**：实时仲裁才是别人抄不走的 |
| 0x14 关键帧通道**绕过 modify lock**，含脸+脖+**双 RGB 灯** | 动作合成有官方载体，**不用发明格式** | 护城河是**「情绪→时间轴」映射资产**，不是通道本身 |
| 0x14 **硬切无插值**、舵机**无弹簧** | 自制动作必须自己插值 | 插值器 + 动作库 = 可积累资产 |
| 情绪**只有 6 种**且**不可远程设置**（只有 hello/hi/love 触发 Happy） | 情绪表达必须建在**参数连续空间**上，不是枚举态 | ⇒ 情绪建模搬到**服务端**，设备只当执行器 |
| 官方身体感知 = **IMU 摇晃 + 5 种触摸手势**；NFC / 红外**固件无驱动** | 「在场感知」若重复 IMU 必输 | 壁垒必须走**端侧人体存在/朝向**（P2-1），且必须先做 1 周可行性验证 |
| 装饰器（shy/sweat/heart/dizzy/angry）**不走远程通道** | 想用就得改固件 | 与「固件零改动」冲突，**已排除** |

**⇒ 护城河②的修正表述**：
不是「它有丰富表情」，而是「**它的表情通道只有 5 个旋钮、每 2 秒会被它自己抹掉一次，而我们在服务端做实时仲裁与时间轴编译**」——
**窄通道 + 强约束 ⇒ 表达密度成为稀缺品。**

**⇒ 护城河②从「韵律映射参数」升级为三件套**：
① **保活调度器**（< 2000 ms 周期 + 本地仲裁）② **关键帧编译器**（情绪+韵律 → 0x14 时间轴）③ **插值器**（把硬切变顺滑）。
三件都是**服务端**资产，不占固件、不占 App ⇒ **与 App 端竞品天然互斥**。

### 3.6 ⭐⭐ 护城河的重定位（2026-10-24 补充取证，来自 49 号开源生态扫描）

§3.1 的裁决基于 48 号的**竞品**取证。49 号把范围扩大到 **GitHub 同硬件开源项目**，结论比 §3.1 更严厉：

#### 3.6.1 被占据的四个位置（同一硬件，已有开源实现）

| 位置 | 已被谁占据 | 证据 |
|---|---|---|
| **好感度状态机** | `Corvelis/stackchan-pet-fw`（42★, **MIT**, 2026-08-10） | ⭐ **CoreS3 + StackChan，与我们同一硬件**。`affection` 0..1000 持久化 + `mood` -100..100 + `confusion` 0..100 + **5 级会话风格** + **逐事件权重表** + 冷却 + 迟滞 + `characterId` 增量同步 |
| **关系阶段成长** | `FlashCat-Jordan/OttoClaw`（82★, CC BY-NC-SA, 2026-06-15） | **22 种情绪 + 5 阶段关系成长**（陌生→认识→熟络→亲密→羁绊）+ **6 舵机 AI 自主控制** + 记忆/会话/技能全本地存储 |
| **LLM 直控舵机 + 表情** | `ideamark/desk-emoji`（594★, GPL-3.0, 2026-09-19） | ESP32-S3 2-DoF 云台 + emoji 屏 + PAJ7620 手势 + LLM 语音，LLM **直接输出动作名数组** |

| （对照）基线固件本身 | `stack-chan/stack-chan`（1811★, Apache-2.0） | M5Stack CoreS3，就是我们的官方基线 |

#### 3.6.2 ⭐ 唯一还空着的位置：**韵律 → 舵机/关键帧**

`desk-emoji`（594★，最接近的对手）经**源码逐行核查**：
- 它的动作由 **LLM 直接输出动作名数组**驱动；
- **全仓无任何韵律（prosody）提取代码**（零 pitch/energy/语速分析）；
- 记忆只存 **10 轮**（`MAX_MEM_LEN=10`）。

`stackchan-pet-fw` 的正向情绪判定也是**文本判定**（`positive_talk`），不是韵律。

学术侧的现状（**2026-10-24 第 2 轮 55 号复核后订正**）：
- arXiv 上**唯一**相关的是 #16 `2603.09324v1`《Reading the Mood Behind Words: Integrating Prosody-Derived Emotional Context into Socially Responsive VR Agents》（**CHI EA 2026 接收**）—— 但它是 **VR 智能体**，管线是 **prosody → 语音情绪识别 → 离散情绪标签 → 注入 LLM 对话上下文**，**不产生任何运动**。它证明的是「韵律信息该被怎么用」，**不是**「韵律驱动身体动作」。
- 55 号复核结论：arXiv `all:"CHI EA 2026"` 10 篇命中**全部**为 VR / LLM / HCI 方向；**不存在**「语音韵律驱动桌面表情机器人舵机」的直接先例（`EmoGesture` / `Emote` 正文 `dl.acm.org` 403，其 GitHub 实现 `total_count=0`，`eGeMAPS` 官方特征集连接超时 ⇒ 三项**未取得**）。

> ⚠️ **本条订正了此前的一处错误表述**：先前写作时把 #16 描述成「韵律驱动桌面表情机器人论文」并附了一个「93.3% 偏好」数字 —— **该数字全仓无来源、该描述与原论文不符**（原论文不产生运动），现已删除并按 49 号 / 55 号的原始取证改写。
> **订正后结论不变、且更强**：不仅「无开源实现」，而是**学术侧与产业侧都没有直接先例** —— 这正是「唯一空位」的准确含义。

> **⇒ 护城河②的最终裁决：不是「我们能做韵律映射」，而是「**整个生态里只有我们做韵律→身体**」。**
> 这条从「壁垒从技术降级为时间」**上调为「唯一空位」**，并与 §3.5 的三件套（保活调度器 / 关键帧编译器 / 插值器）合流。
> 学术 + 竞品双侧都没有直接先例 ⇒ 这是本项目**最值得押的**一条。

> ⭐ **2026-10-27 补充（87 号）：这条空位现在有了机器判据。** 韵律→身体的算法层早已实现（`server/stackchan_ai/prosody.py`：YIN → 7 维 → 42 参数 → PCHIP → 0x14 关键帧），本轮用**合成韵律语料**离线跑真实管线，把它变成 10 项可判阈值（门禁 `tools/check_prosody.py`）：**情绪没被音频淹没**（淹没比 0.41）、**6 情绪跨韵律变体可辨识度 83.3%**、编译逐字节可复现、单帧 320 B、零越界。⚠️ 过程中**抓到并修掉 1 个真缺陷**（`env` 边界补零 ⇒ 每句话第一帧嘴/眼/灯弹到满量程）—— ⇒ 「韵律→身体」从「只有实现」升级为「**实现 + 可判 + 已自证不会骗自己**」。

> ⭐⭐ **2026-10-27 补充（88 号）：这条空位的「算法层」现在同时是「可标定的」，而且第一次量出了它自己的短板。** 用**真实 MiniMax TTS**（32 次调用、18 条语料入库）跑同口径测量，得到三个对护城河有直接影响的数：
>
> 1. ⭐ **护城河的边界被量化了**：10 维输出特征里只有 **3 维**真正携带情绪信息（`pitch_mean` / `pitch_max` / `mouth_mean`，比值 3.3~5.9），其余 7 维基本在动但不携带情绪
>    ⇒ **「韵律→身体」不是「把 42 个参数都映射出去」，而是「用少数几维承载情绪，其余维只负责生气动」**。
> 2. ⚠️ **纯音频韵律只能分出 33.3%**（跨文本留一）⇒ **韵律本身不是情绪的主载体**，情绪的主载体是**标签基线**（6/6 完美可分）⇒ ⇒ **「韵律→身体」这条路的天花板是「情绪 + 韵律协同」，不是「纯韵律」** ⇒ 这恰好是我们要的定位（LLM 给标签 + 韵律做调制），但**必须承认韵律是配角**。
> 3. ⚠️ **当前实现里，韵律调制是净负贡献**：标签基线 6/6 ⇒ 加真实韵律后只剩 **61.1%**（能量通道与情绪基线争夺同一个「嘴」通道 ⇒ SNR 0.19）⇒ ⇒ **这条护城河现在有一个已量化的短板**，已登记为待拍板 **Q21**（口径 + 增益 + 基线必须一起调）。
>
> ⇒ **诚实结论**：「唯一空位」这个判断**依然成立且更强**（整个生态仍无人做），**但空位不等于自动成立** ⇒ 本项目的优势在于**它现在有了机器判据**，能在真实语料上持续暴露自己的短板 —— 这比「看起来做了很多」更有护城河价值。

#### 3.6.4 存在感知的可行性证据（正面，对 R2）

ESP-DL 官方在 ESP32-S3 上的实测延迟（49 号取证）：

| 模型 | 延迟 | 是否识别身份 |
|---|---|---|
| 人脸检测（MSR+MNP 两级） | **43.1 ms/帧** | ⚠️ 识别人脸 |
| 单级人脸 PICO_224 | 137.4 ms/帧 | ⚠️ 识别人脸 |
| 单级人脸 PICO_416 | 445.0 ms/帧 | ⚠️ 识别人脸 |
| ⭐ **行人检测 pico_s8_v1** | **125.0 ms/帧** | ✅ **不识别身份，只知道有人** |

⇒ **行人检测 125 ms/帧天然满足「不认人、只判断在不在」**，比人脸检测更快且更符合隐私定位。
**这让 05 号 R2 从「未验证的技术假设」降级为「有官方数字支撑，但仍需真机验证」**。

⚠️ 反向约束（同时记录）：mmWave（LD6002/B）**电流 ≥1A**，与 550–700 mAh 电池硬冲突 ⇒ 直接排除；Wi-Fi CSI 零 BOM 但受 AGC 干扰，`wisense` 作者**自述未在真机 ESP32 上验证**。

### 3.7 ⭐ 「设备是身体，App 是镜子」（第 6 条护城河的具体化）

53 号的通道边界 + 58 号的架构决策合起来，给出了第 6 条护城河一个**具体到组件**的实现形态：

| 轨道 | 载体 | 能表达什么 | 性质 |
|---|---|---|---|
| **设备轨 = 身体** | 设备 320×240 屏 + 双舵机 + 12 灯 | 官方 6 情绪 + 连续参数 + 0x14 关键帧时间轴 | **低保真但真实**：在物理空间里、会被摸到、**每 2 秒会被它自己的动画覆盖一次** |
| **App 轨 = 镜子** | iPhone 上我们自写的 SwiftUI/Canvas 表情渲染器 | **任意表情**（不受 6 情绪 / 5 参数限制） | **高保真但只是影子**：关系的连续投影 |

> ⭐ **关键推论：设备上的表情本身是「不可信的记录」** —— 它每 2 秒就被自己的 blink/idle/breath 抹掉一次。
> ⇒ **关系档案必须建在 App 端**（完整、连续、可回看、可导出、可审计），**设备端只负责「当下的身体」**。
> ⇒ 这就是「设备即档案」的极端形态：**档案本来就在用户自己的 iPhone 上，因此天然不入库、天然可带走、天然零锁定**。

**这一条同时解释了三件事**：
1. 为什么档案永不入库不是妥协 —— 而是**架构的必然结果**；
2. 为什么 App 端必须有自己的表情渲染器 —— 它不是 UI 装饰，是**档案的显示层**；
3. 为什么护城河第 6 条与护城河②（身体表达）**不冲突** —— 前者是「关系的记录」，后者是「当下的身体」，是**两条正交的轨**。

> ⭐ **2026-10-25 IA 修订带来的正面影响**：用户把主界面改成**控制台**
> （第二次拍板：「主要界面还是控制舵机那样操作」），
> 「设备是身体、App 是镜子」这条护城河**从口号变成了首屏** ——
> 主界面第一眼看到的是**能直接拨动的身体**，不是聊天框。
> ⇒ 设备轨（低保真但真实）与 App 轨（高保真但只是影子）**不再争同一个首屏**：
> App 首屏做**控制**（身体的操作台），脸做**镜像**（关系的投影）⇒ 两条正交的轨各归其位。

### 3.8 ⭐⭐ 对外表述的三条红线（2026-10-25 夜，来自 `docs/research/81` 补读）

> 这三条不是「保守」，是**证据逼出来的**：一旦写进作品集被追问，露馅的代价远大于少写一句漂亮话。
> 三条都**不占用用户拍板时间** —— 是事实约束，不是选择题。

| # | 红线 | 证据 | 正确写法 |
|---|---|---|---|
| 1 | ⭐ **不得承诺心理疗效，且不得暗示「可替代真人陪伴」** | 同行评议的社交机器人心理健康项目只报 `mixed results` ⇒「陪伴机器人能改善心理健康」**本身不确定**（[`81`](../research/81-补读证据-人格一致性与长期记忆边界.md) §十二.1）。⭐ **第四轮夜补上机制证据**（[`84`](../research/84-第四轮夜间纪要与新证据提取-20261025.md) §四，arXiv `2609.07243`：CharacterAI 用户两波纵向研究，基线 **1182** 人 → 随访 **439** 人（平均 **12 个月**）⇒ **持续的 AI 陪伴通过「降低人类互动」预测更低的幸福感**）⇒ 对外表述还须避免「**替代真人**」的暗示 | 写「陪伴体验与长期记忆的工程实现」；**不写**「改善心理健康」「缓解孤独」「治疗」，也**不写**「替代真人社交」 |
| 2 | ⭐ **不得写成「从零做陪伴产品」** | 市场已有 **489 个** AI 陪伴 App（`81` §十一.4）⇒ **不是空白市场** | 写「换掉账号体系与入口 + 接 MiniMax 做大脑 + 原生 iOS 重建」；差异化在**工程深度**，不在品类空白 |
| 3 | ⭐ **不得声称「感知用户情绪」** | 情绪识别基准测的是「**诱发**」不是「**感知**」（`81` §六）⇒ 模型输出的是**小灯自己的情绪**（Q20 读法 A，用户情绪只作诱因） | 写「情绪标签驱动表情参数」；**不写**「它能感知你的情绪」 |

> ⭐ 连带的产品设计后果（不是文案问题）：
> ① 第 1 条 ⇒ **里程碑不得把「心理健康效果」写进完成判据**（已同步 `docs/spec/00` M 里程碑）；
> ② 第 3 条 ⇒ **`emotion` 是我们输出的、不是我们读到的**（已同步 `docs/spec/06` §0.1 C-4）；
> ③ 第 2 条 ⇒ 护城河论证必须落在**可验证的工程深度**（三层护城河 + 三层可验收判据），不能落在「品类首创」。

### 3.2 第 6 条护城河 = 「设备即档案 + 可审计来源」

48 号给出 6 个候选（A 设备即档案 / B 可审计来源 / C 关系阶段 / D 身体先于语言 / E 设备即凭证 / F 低打扰主动性），裁决如下：

| 候选 | 裁决 | 定位 |
|---|---|---|
| **A 设备即档案** | ⭐⭐⭐⭐⭐ | **主护城河**。关系长在用户自己拥有的东西上，可带走 |
| **B 可审计来源** | ⭐⭐⭐⭐⭐ | **A 的刃**。每条记忆能翻出处、可当场纠正、它改不了自己的历史 |
| C 关系阶段 | ⭐⭐⭐⭐ | **长期主攻**。A 的时间维度延伸 |
| D 身体先于语言 | ⭐⭐⭐⭐ | **长线**。A 的物理维度延伸 |
| E 设备即凭证 | ⭐⭐ | 分发机制，非护城河 |
| F 低打扰主动性 | ⭐⭐⭐ | A 的日常表现 |

**合起来才成立：单独看 A 不足，单独看 B 太薄。A+B+C+D 合起来才是"别人抄了也追不上"的完整结构。**

#### A｜设备即档案

**它是什么**：StackChan 不是通往云服务的入口，**它自己就是关系的载体**。人格、记忆、关系进展全部存在用户自己拥有的设备/文件里，可读、可改、可导出。硬件坏了、云厂商倒闭、公司关门，关系都还在。

**为什么别人做不了**（不是技术问题）：
- **技术全部免费可抄**：`mem0`（Apache-2.0，LoCoMo 92.5）、`Zep/Graphiti`（token 降 90%）、`Letta`（Apache-2.0，25,239★，含 Git-based Memory）
- **商业模式互斥**：Vector $11.99–14.99/月、ElliQ $39–59/月、NICOBO ¥1,100/月、BOCCO ¥1,700/月、Miko $14.99/月 —— **订阅收入与"关系可带走"直接互斥**
- **巨头抄不了**：Character.AI 于 2026-10-13 被 Disney 以 **$20M 清算资产** + 非独占永久许可 —— 巨头买的是"技术"，不是"用户关系"，因为关系不可转让
- **我们抄得了**：单人 + AI 团队 + MiniMax API + fork 官方 server —— **恰好能承受"不锁定"的代价**（没有订阅收入要保护）。**因为小所以能**，这是一种独特的护城河

#### B｜可审计来源

**它是什么**：不是"它记得你"，而是"**它记得你，是因为那天你说了一句什么 —— 你可以当场检查、当场纠正，而且它改不了自己的历史**"。

**为什么别人做不了**：一旦承诺"可核对出处"，就必须保留逐字原文，就必须承认"它会记错"，就必须暴露"哪些数据真的被存了"。Replika / Nomi / Character.AI / Moflin 的记忆**全部是黑箱或不可解释的条**。

**⭐ 法律侧反而成了助力**：SB 243 要求"必须让用户清楚交互是 AI 生成"、"聊天机器人不得把自己表现为治愈者" —— **可审计是我们满足合规的最省力方式**。

**裁决建议**：保留 append-only 的原始层 + 允许用户标记"这条记错了"（用户标记改变**检索权重**，但不删除原文）。**这比"允许 AI 悄悄改历史"诚实得多。**

#### ⭐ 最硬的对照证据：Loona DeskMate（2026-01 CES 发布，与我们正面对位）

56 号把**唯一一个把「隐私」写得像我们、而且在同一个价位带同品类**的对手完整拆了一遍。
它的隐私叙事比任何人都漂亮 —— **5 条隐私红线 + 3 条行为边界**（Granular Tool Permissions / Pull-Mode Screen Awareness / Controllable Memory / Physical Sleep Mode / Face & attention on-device only；One Nudge Then Quiet / No Commentary / Nothing Without Permission）。

**但把它自己的官方页面放在一起看，它恰好证明了我们的第 6 条护城河不是自我安慰：**

| # | Loona 的官方事实（原文） | 它证明了什么 |
|---|---|---|
| 1 | 订阅分档把**屏幕感知深度**分级：Free `Basic Screen Awareness` / Plus `Advanced Screen Awareness` / Pro `Full Screen Awareness & Action`；credits `Free 200 / Plus 1,000 / Pro 3,000` | ⭐ **「能力深度 = 会费」的直接证据**。我们若做屏幕感知，就会被迫回答「免费给多少深度」⇒ 能力分级与订阅被绑死 |
| 2 | 给的是 `Clear memory with one tap`（一键清空），而**全站零处**出现 export / portable / 可携带承诺 | **删除权 ≠ 所有权**。它给的是删除权，我们要给的是所有权 |
| 3 | 官方 Privacy Policy `Last updated: February 05, 2023`，全文**零处**提记忆存放位置 / 可导出 / 训练数据边界 | ⭐ **「五条红线」没有法律兜底** ⇒ 红线写在文案里没用，必须写成**可验证的实现 + 可审计日志**（00 号 S-1..S-9，建议扩到 S-11） |
| 4 | 只承诺表情/注意力**派生量**留在 iPhone，**原始图像是否出机未承诺** | 我们承诺的是 **S-1：原始帧默认不出本机** ⇒ **我们比它硬**，可直接写进对外叙事 |
| 5 | 官方自相矛盾：产品页挂 Free/Plus/Pro 三档 plans，买家指南却称 `Zero-Subscription Model` / `Subscription Fee $0/mo` | 「不订阅」在订阅型商业里**只是宣传口径** ⇒ 我们的零锁定必须靠**架构**（本地档案 + 导出 + 出网默认关），不是靠承诺 |

> **⇒ 第 6 条护城河是唯一可长期独占的位置，而且对手的空档是结构性的**：
> 订阅 + 云端记忆**必然**导向锁定 —— 它不是没做，是做不了。
> ⭐ **对我们的反向要求**：正因为它证明了「不订阅可以只是话术」，我们更不能只承诺 —— 必须让「可导出 / 可审计 / 原始帧不出机」变成**能演示、能测试、能被用户当场查**的东西（00 号 S-1..S-11 + 58 号 §2 的模块边界）。

**不写的**（避免自造）：不写「我们更便宜」（我方价格未定）、不写「我们响应更快」（我方延迟未实测，无真机）、不写「我们的记忆更聪明」（无对比数据）。

### 3.3 必须诚实写下的四个弱点

1. **"越用越厚"是慢变量，前期不明显。** 冷启动期用户感受不到复利。
2. **它要求用户愿意被记住**，而有一部分人不想被记住 —— **这不是缺陷，是筛选**。产品要能诚实地接受"我不要它记住我"。
3. **"零锁定"是减法护城河**：让我们更难赚钱，也更难被抄成订阅 —— **护城河不能靠订阅续命，必须靠硬件销量 + 生态**。
4. **端侧存在性检测在 ESP32-S3 + 8MB PSRAM 上可行 —— 这是推断，未实测。** 必须先做原型验证再当承诺。

## 四、让用户持续上瘾：8 条机制与优先级

**硬红线（不可违反）**：不做金币 / 积分 / 亲密度等级 / 好感度进度条 / 连续天数 / 进度环 / 排行榜 / "今日完成 N 次"。

### 4.1 八条机制（每条已自检红线）

| 序 | 机制 | 为什么会上瘾 | 难度 | 护城河增益 |
|---|---|---|---|---|
| **M1** | **档案在长厚**（看得见的复利） | **唯一能被用户亲眼看到的增长**。用户不是被"积分"留住，是被"这是我们的东西"留住 | 中 | ★★★★★ 主护城河最小可见形态 |
| **M2** | **它先开口**（一天一次，稀缺所以重） | 稀缺 + 意外 + **私人**。它说的是"我"，不是天气待办 | 中 | ★★★★ |
| **M3** | **身体先说话**（抬头 → 转过来 → 看着你 → 才开口） | **零解释成本的"它知道我在"**。走开 10 分钟回来它正好转过来，这 1 秒比任何文案都强 | 中偏高 | ★★★★ App 复制不了 |
| **M4** | **它拒绝我** | **关系只有在有摩擦时才是关系。** 永远顺从会腻，会拒绝让人想留下来哄它 | 低 | ★★★★ 护城河①唯一未占据落点 |
| **M5** | **默契**（学会我的节奏） | "被理解"的生理级快感，且收益瞬时可感（"它今天没打断我"） | 中 | ★★★☆ |
| **M6** | **串门**（NFC 带人格给别人） | 把独处关系变成**可炫耀**的关系。**唯一天然带传播的机制** | 中 | ★★★ |
| **M7** | **它今天做了一件事** | "它在我不在的时候也活着" —— 孤独感的直接解药 | 低到中 | ★★★☆ |
| **M8** | **关系年鉴**（可导出的实体纪念品） | **"舍不得删"** 是最强留存动机 —— 用户舍不得的不是玩具，是那段关系 | 低 | ★★★★★ 主护城河的用户可见出口 |

### 4.2 优先级（一个人一个季度只能做 3 条）

1. **M1 档案在长厚** —— 主护城河的最小可见形态；没有它，A/B 两条都看不见
2. **M3 身体先说话** —— 唯一 App 复制不了、成本最低的差异
3. **M4 它拒绝我** —— 反向陪伴的最小形态，几乎零成本

> 顺序原则：**先让护城河"看得见"，再让护城河"摸得着"。**

### 4.3 每条机制的风险与对策（不能只写好处）

| 机制 | 真实风险 | 必须的约束 |
|---|---|---|
| M1 | 变成 KPI 面 | **只展示条目本身，不展示计数**。"本周新增 12 条"绝对不做 |
| M2 | 变成骚扰 | 勿扰时段 + 主动降频 + **"它今天没话说"是合法状态** |
| M3 | 变成神经质 | **宁可不转，也不要"每次路过都转头"**。冷却 + 节流 + 两段式（先转头→确认→决定是否继续） |
| M4 | 第一次就被识破 | **拒绝必须由它自己的状态驱动，不能是随机台词** |
| M5 | 过度模仿变讨人嫌 | 挑选学什么、不学什么（不学口头禅） |
| M6 | ① 安全 ② 尴尬 ③ **稀释独占感** | 卡片必须签名，**私人层绝不经 NFC**；**串门记忆独立成层，不进主档案** |
| M7 | 卖萌刷屏 | **每条必须与关系有关，否则删掉** |
| M8 | 分享泄露隐私 | **导出默认脱敏**，不自动带原文私密片段 |

## 五、⭐ 冷启动：主护城河最致命的问题

48 号 §6.8 诚实写下了六点难点。这里给出**对策**，因为这是唯一可能让整套护城河崩掉的地方。

### 5.1 致命问题：第一周几乎没有档案

新用户的档案是空的 → 它无法"关系化"，只能说通用的话。
**这是所有做"关系"的产品的原罪。**

**对策：种子档案**
首启 10 分钟内，引导它问出 **3–5 件有日期锚点的事**（"你上周在做什么？"），并**当场**把这几条写进档案。
**第一周结束时，用户已经拥有一份"不是空的"档案。**

### 5.2 档案薄的时候召回质量差

mem0 的 LoCoMo 92.5 是 benchmark，真实用户的第 3 天约等于 benchmark 的零数据状态。

**对策：阶段化召回**
- 档案薄 → 靠 **身体 + 好奇心 + 主动性**撑住体验
- 档案厚 → 才切到 **记忆驱动**

**这正好是候选 C「关系阶段」的工程形态** —— 不是额外工作量，是同一件事的两个阶段。

### 5.3 "它记得"必须同时"它记对"

错的记忆比没记忆更伤。**纠错 UX 是这条护城河的第一优先级，不是后期优化。**

**对策**：
- 每条记忆带**逐字出处 + 日期**（候选 B）
- 界面上一键可"这条记错了" → 立即改检索权重
- **当场纠正即时生效**（不是事后同步）

### 5.4 冷启动用户成本高

愿意填档案的用户本来就是高粘性用户 → **早期留存曲线会很好看，但样本极小。不要用早期数据外推。**

### 5.5 档案价值需要被"看见"

如果用户永远看不到自己的档案在长厚，飞轮就转不起来。
**iOS 端"关系年鉴"页不是锦上添花，是飞轮的第二半。**

### 5.6 合规反噬

SB 243 要求"必须让用户清楚交互是 AI 生成"。
**档案页必须清晰标注每条是"它记住的"还是"真的发生过的"，不得暗示后者。**

### 5.7 ⭐ 冷启动的外部证据与可执行方案（2026-10-24，来自 51 号）

§5.1–5.6 是我们的推演。51 号把冷启动**外部证据化**了，其中三条直接改写我们的做法：

#### 5.7.1 冷启动原罪有名字，且有可借的北极星指标

**IceBreaker**（arXiv 2604.18375，字节系产品上线 >1 月的 A/B）把这个现象命名为 **first-message barrier**（首条消息壁垒），并给出可直接借用的指标 **CSR = 发起对话率（Conversation Start Rate）**：

| 指标 | A/B 提升 |
|---|---|
| CTR | **+94.25‰** |
| Active | **+1.84‰** |
| **CSR（发起对话率）** | **+1.27‰** |

论文自己承认关键限制：**RID（首条消息）需要历史 session summary 才能更好处理冷启动**。
⇒ **种子档案 = 在没有历史的第一天，手工制造 trigger interests。** 这正是 §5.1 的做法，现在有了论文背书与指标口径。

#### 5.7.2 Character.AI 破产 = 「档案在用户设备、零锁定」的最硬论据

| 事实 | 数字 |
|---|---|
| 规模 | 20 亿条消息 / 2000 万 MAU / 运营 5 年 |
| 结局 | 仍资不抵债（资产 $50–100M），**2026-10-13 被 Disney 以 $20M 收购清算** |
| 错在哪 | 它让用户造了「对方」，**却没让用户被「认识」**；用户档案为 0，关系资产不归用户 |

arXiv 2507.15783 进一步证明：**平台单方面变更（哪怕只是改模型/功能）本身就会摧毁关系**。
⇒ 这直接支撑我们的**第 6 条护城河**（档案可带走 + 可审计 + 不入库），也是 P1「零锁定」商业模型的现实依据。

#### 5.7.3 关系阶段有双重外部佐证

| 来源 | 证据 |
|---|---|
| **Kindroid 官方**《the-7-stages-of-bonding-with-your-kindroid》 | 关系是**离散阶段**，不是分数 |
| **arXiv 2509.22505** | 明确建议 **surface relationship stages**：initiation → escalation → bonding |

⚠️ 但这两条**不构成护城河**（见 §3.6.3：`OttoClaw` 已实现 5 阶段）⇒ 我们的 P3 关系阶段是**必要工程**。
⇒ 且**阶段不得出现在 UI 上**（遵守「不做积分·等级·进度条」红线）——只作为服务端行为开关。

#### 5.7.4 四个「用户主动讲述 / 建档」案例（可抄的机制）

| 产品 | 机制 | 可借鉴点 |
|---|---|---|
| **Nomi** | 引导用户填关系类型 → 名字/性格/兴趣/外观 → Shared Notes  backstory；官方文档明写 **"Interests are really just initial icebreaker topics"** | ⭐ 把「兴趣」明确定义为**破冰话题**，而不是画像标签 |
| **Kindroid** | backstory 自由文本 | 与 Nomi 的结构化形成互补 |
| **IceBreaker** | 个性化首条消息生成 | 模板化但按档案填充 |
| **Autiverse** | AI 引导的多模态日记 | 降低「写档案」的门槛 |

#### 5.7.5 落地方案（51 号 §4，可直接编码）

| 项 | 内容 |
|---|---|
| 内部指标（4 个） | 含 **CSR**（发起对话率）定义 —— 第一周就盯它，不盯留存 |
| 首启脚本 | 6 段原文 + 10 条备选问句 |
| 日期锚点判定 | 5 条规则（R1–R5），把「有日期锚点的事」变成可判定项 |
| 时机规则 | 8 条 + 主动开口间隔规则（配合 M2 的稀缺性） |
| 「我不想说」 | **三段式**追问，且**禁止情绪施压**（不得说「你不说我会难过」） |
| ⭐ 切换阈值 | **双阈值：≥5 条锚点 且 跨 ≥3 天 ⇒ 切到记忆驱动**（⚠️ **A/B 可调的工程参数，不是研究结论**） |
| 关系阶段开关 | 4 个离散阶段，**不出现在 UI** |
| 档案页 | 可核对原文 + 锚点 + 来源（配合 P1-3 可审计） |

## 六、技术选型：护城河需要什么技术能力

### 6.1 一张能力 → 护城河映射表

| 能力 | 用在哪 | 技术选型 | 硬约束 | 状态 |
|---|---|---|---|---|
| **关系档案存储** | A / M1 / M8 | server 侧自研 schema（`source_turn_id / source_date / verbatim`）+ 向量索引 | 档案在用户账号空间，**可导出、不做训练数据** | 待建 |
| **可审计来源** | B | append-only 原始层 + 用户标记改权重 | 原始层不可删 | 待建 |
| **关系阶段状态机** | C | server 侧离散状态机（陌生→试探→习惯→依赖→疏远→重逢） | **不可见**：不改数字，改说话方式/主动性阈值/身体表达 | 待建 |
| **端侧存在性检测** | D / M3 | ESP32-S3 + BMI270 + 触摸区 + 图像亮度/运动统计 | **不做"识别这是谁"**，只做"有人/靠近/离开" | **未验证** |
| **两段式转头** | D / M3 | 舵机调度时序（先转头→确认→决定是否继续） | 冷却 + 节流 | 待建 |
| **韵律→身体映射** | ③ | 音频特征 → 动作参数映射表 | 需真实人机对话语料 + 逐次调参 | 待建 |
| **三通道同步反馈** | 全局 | 声音 + 表情(`controlAvatar`) + 运动(`controlMotion`) | 表情用官方引擎，不自研资产 | 协议已通 |
| **主动开口（它先开口）** | M2 | 挑话题器 + 判断器（基于档案） | 一天最多一条 | 待建 |
| **会拒绝** | M4 | 状态机 + 语气映射 | 拒绝必须状态驱动 | 待建 |
| **NFC 串门** | M6 | 卡片签名 + 人格导入导出 | **私人层绝不经 NFC** | 待建 |
| **本地大模型（可选）** | 隐私叙事 | iOS 27 `LanguageModelExecutor` + Apple `ChatCompletionsLanguageModel`（README 点名 `minimax-m2.5`） | **Foundation Models 中国大陆不可用** —— 不可作为唯一本地大脑 | 41 号已定 |

### 6.2 三条不能违反的技术红线

1. **不改固件、不改 PCB、不改结构。** 档案层完全在 server 侧；表达参数只能通过已有 `controlAvatar` / `controlMotion` 下发。
2. **不自研表情资产。** 官方表情引擎保留。
3. **个人数据永不入库。** 记忆存在用户自己的账号空间，**不做训练数据**，可导出。

### 6.3 三段链路的实现要点（详见 03 号）

```
[iOS App] ──远程WS 5字节帧──▶ [自研 server（fork 官方 MIT）] ──远程WS──▶ [设备 ESP32-S3]
     ▲                                                            │
     └────────── 局域网 20 字节帧（App 起 WS 服务，设备反向连入）◀───┘
```

| 要点 | 结论 |
|---|---|
| 帧格式 | 远程 = `[type:1][len:4 BE][payload]`；LAN = `[0x53 0x43][ver:1][type:1][flags:2][session:8][seq:4][len:2]` |
| payload | 控制类 = **MAC(12 字节 ASCII) + JSON**；server 转发前**剥掉 12 字节**只把 JSON 给设备 |
| 舵机单位 | **0.1 度**。yaw ±1280（±128°）、pitch 30~870（3°~87°） |
| LAN 方向 | **App 起 WS 服务，设备反向连入**（不是设备连 App）→ 手机不需公网 |
| iOS 后台 | NWListener 后台不可用 → **后台降级为服务器中转**，状态机 6 态 |
| 姿态真值 | ⚠️ **官方固件未实现 `getAvatarPosture`（0x15）** —— 官方 App 的 3D 预览是"发出即乐观显示"，不是回读。**我们要真值必须自己实现（加固件分支或走 BLE 读舵机角）** |

> ⚠️ 最后一条是本轮新查实的事实，直接影响"姿态真值"这条设计决策 —— 详见 03 号文档 §修正记录。

## 七、落地顺序（12 周单人可执行的最小闭环）

| 阶段 | 周 | 交付 | 对应护城河 |
|---|---|---|---|
| **P0 打通** | 1–2 | 真机连通（USB + Wi-Fi + 绑定自研 server）+ 协议跑通 + iOS 最小壳（连接状态 + 姿态下发 + 表情下发） | 入场券 |
| **P1 档案** | 3–5 | server 侧档案存储 + 记忆提取 + **可审计来源**（带日期与逐字出处）+ iOS 档案浏览页 | A + B |
| **P2 身体** | 6–8 | 端侧存在性检测原型 + 两段式转头 + 表情/运动时序对齐 | D + M3 |
| **P3 阶段** | 9–10 | 关系阶段状态机 + 每阶段的语气/主动性/身体参数映射 | C |
| **P4 主动性** | 11–12 | 种子档案（首启 10 分钟）+ 它先开口 + 它会拒绝 | M1/M2/M4 |

**顺序理由**：P1 先做，因为**它同时交付主护城河和第一可见的留存机制**；P2 放第二因为它是唯一 App 复制不了的部分；P3/P4 是放大器。

**如果时间被砍到一半**：砍 P3，**绝不砍 P1**。

## 八、必须由用户拍板的 5 件事

按影响大小排序。**这是战略级取舍，不是我能替用户决定的。**

### P1 · 是否彻底放弃订阅？
- **放弃** → 护城河 A/B 成立（"关系可带走"与订阅互斥）
- **保留订阅** → 护城河 A/B 不成立，只能靠 D（身体）+ C（时间）
- **我的建议**：**放弃**。但这等于放弃"被动收入"这条路，必须接受"靠硬件销量 + 生态变现"。

### P2 · "个人数据永不入库"与"服务端有记忆"如何切分？
- 建议：**记忆存在用户自己的账号空间**（我们提供存储），**不做训练数据**，**可导出**。
- 这不是技术难点，是**承诺的可验证性** —— 要不要给"可审计日志"？

### P3 · 官方社交玩法（post / friend / dance / pano / appstore）做不做？
- **全做** → 工作量巨大且与"减法"原则冲突
- **全不做** → 浪费了官方已有的服务端能力
- **我的建议**：**只做"小栈的一天"**（自动生成生活流 + 朋友圈），其余不做。

### P4 · 固件基线同步到哪一版？ ✅ **已核实（2026-10-24）**
- 官方 `origin/main` = **`eff0d6b`（2026-10-22，commit "feat(app): prepare 1.2.8 release for open source"）**
- **固件版本 = `1.6.0`**（`firmware/CMakeLists.txt`：`set(PROJECT_VER "1.6.0")`）
- **官方 App 版本 = `1.2.8+32`**（`app/pubspec.yaml`）
- 本地 clone HEAD = `1b57655`（2026-08-19，`firmware-dev` 合并点）—— **落后 origin/main**
- ⇒ **建议**：**直接以 `origin/main` = `eff0d6b`（固件 1.6.0 / App 1.2.8）为基线**，不需要"先同步到 v1.6.0"这一步（它已经是当前 main）。
  ⚠️ 但**我们只读官方仓库做协议取证，不 fork 固件**（红线：不改固件）⇒ "同步"只影响我们的**取证基准**，不影响交付物。

### P5 · 规格冲突以谁为准？ ✅ **已核正（§3.4）**
- 任务书写 `yaw ±128° / pitch 3~87° / BMI270`
- 官方 README 写 `360° / 90° / 9 轴 IMU`
- **实读源码结论**：`hal_servo.cpp` 的 `angleLimit` 确实是 **yaw ±1280（±128°）/ pitch 30~870（3°~87°）** → **以源码为准，任务书的 yaw/pitch 对，README 的 360° 是营销口径**；IMU 确实是 BMI270 6 轴；**固件零 NFC 驱动**。
- ⇒ **待办**：检查我们自己的文档与 UI 里有没有从 README 抄来的「360°」表述，全部改成 ±128°。
