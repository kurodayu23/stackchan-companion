## 一、三句话结论

1. **AI 层用 MiniMax API，不接 Realtime**；**本地模型是可选增强，不是必需**（中国大陆 Foundation Models 不可用）。
2. **固件零改动，协议零发明** —— 官方 **25** 个 MsgType（⚠️ 原写 24，已回源官方 `msg_type.dart` 订正，见 `docs/spec/03` §2.2；`0x08`/`0x0F` 官方空缺）+ 两套帧格式直接用；我们只替换 server 的 AI 层与认证层。
3. **iOS App 是身体的一部分，不是遥控器** —— 它承载"档案"这个主护城河，而不只是控制舵机。

### 2.1 三条不能违反的选型红线

1. **不改固件、不改 PCB、不改结构。** 表达参数只能通过官方已有的 `controlAvatar` / `controlMotion` 下发。
2. **不自研表情资产。** 官方表情引擎保留。
3. **个人数据永不入库。** 记忆存在用户自己的账号空间，**不做训练数据**，**可导出**。⚠️ **2026-10-25 订正：本条落实的是「② 不进运营方自有存储 / 不进训练集 / 可导出」**，**不是**「① 不外发给任何第三方」—— 走云端 LLM 时对话原文必然发给 MiniMax（见 P1-2 记忆提取）。⇒ **两种读法的取舍是 Q5**（`docs/spec/07` §3.5）；对外文案在拍板前只承诺本条这一种。
4. ⭐ **本条按「敏感值的生命周期」逐段定规则，不按字段切**（2026-10-25 补读，`docs/research/81`）：
   SP-Mem 明写 `simply removing sensitive values can undermine system utility`、
   `privacy protection … should govern the full life cycle of sensitive values rather than only sanitizing individual records`。
   ⇒ 五段各定规则：**存**（能不能落盘）· **取**（能不能检索出来）· **用**（能不能进生成上下文）·
   **展示**（能不能出现在回复里）· **导出**（能不能带走）。
   ⚠️ 其中「**取**」「**用**」两段最危险，也是我们此前完全没写的两段。
   ⇒ **可测口径**：HUSH-Bench 的 `Unsolicited History Integration Score (UIS; 0--100, higher is worse)`
   —— 保守策略是「**当前轮给出使用理由时，敏感历史才影响回复**」⇒ 私人层要有一道闸门，
   当前轮无理由时敏感历史**不得**进入生成上下文。
5. ⭐ **记忆分两层，且要区分「过时」与「活跃」**（`docs/research/81` §十一.3–11.4）：
   - 分层依据：HiMem 的 **Episode Memory（事件型）** + **Note Memory（稳定知识型）**（切分维度 = 事件 / 意外），
     与我们的「会话记忆 vs 档案」结构一致；另 `.22` 证明**单粒度切分不够**（`partial retrieval of useful information or substantial noise`）。
   - 老化依据：MINDSET 要求 `preserve both current and historical states, distinguish stale information from active knowledge`，
     且 `avoid repeatedly invoking a large language model to rewrite prior interactions`
     ⇒ 我们的 **append-only 原始层**同时解决「保留历史」与「省 token」两件事。

## 三

> ⭐ **2026-10-25 第四轮夜续（`docs/research/85`）**：本节数据分级表的**「取 / 用」两段要加运行时一致性检查** —— 声明的目的必须与运行时行为对齐（arXiv `2607.20190`：实践中目的常被当成与系统行为脱钩的非正式声明）⇒ 校验点 = 每次取/用敏感值时校验其所属目的。另：分级表的**字段骨架**建议改用 *Privacy Engineering* 系统综述（arXiv `2606.23696`）的**13 维 / 2 核心**（`PETs + PM + VT` / `GA + TC + OM`，`MS` 居中），每条敏感值挂「用什么技术处理 / 怎么量化风险 / 怎么自动验证没被破坏」。⚠️ **本节本轮未改写** —— 改写需先定 Q5 的读法（哪种承诺口径），属**拍板后动作**。

、⭐ "姿态真值"的技术裁决（新增，因协议实读而改变）

### 3.1 事实

官方固件**没有实现 `getAvatarPosture`(0x15)**（详见 `03` 号 §2.4）。
官方 App 的 3D 预览是「**发出即乐观显示**」，不是设备真值回读。

### 3.2 三个选项

| 方案 | 做法 | 成本 | 违反红线？ | 裁决 |
|---|---|---|---|---|
| **A 加固件** | 加 0x15 分支，读 `motion.yawServo().getCurrentAngle()` 回传 | 固件 fork + 刷机 + 维护 | ❌ 违反"不改固件" | **否决** |
| **B 走 BLE 读舵机** | 设备 BLE 通道读真实角度 | 中；BLE 协议是私有扩展，风险高 | ⚠️ 部分 | 备选（若 A/B 都不做） |
| **C 接受乐观值** | App 记住"我命令它转到哪"，并在 UI 上**明确标注这是目标值不是实测值** | 零 | ✅ 不违反 | ⭐ **推荐** |

### 3.3 裁决理由与代价

- **护城河不在姿态读数**，在"身体表达"本身（04 号 §二 第一层）。
- **C 的代价**：物理阻滞时 App 显示与实际不符 —— 但 StackChan 的舵机是 SCSCL 总线且有 stall protection，**实际阻滞概率低**。
- **C 的补偿**：设备端**表情**是真实回传的（`controlAvatar` → 屏幕立即变化），所以用户有至少一路真实反馈。
- ⚠️ **必须在 UI 文案上诚实**：不要把乐观值标成"实时姿态"。用「**目标朝向**」或「**已转到**」。

### 3.4 若将来要升级到 A

改固件只需加一个 `case DataType::GetAvatarPosture` 分支（约 15 行），但会带来**刷机与版本管理成本**。
建议：**等 P4 阶段（12 周后）再评估**，不阻塞主线。

#### P2 的技术细节（来自 55 号，可直接进开发）

**插值器选型**（保形不过冲 ⇒ 不可能把 ±128.0° 顶出限位）：

| 用途 | 选型 | 理由 |
|---|---|---|
| **舵机主插值** | **PCHIP（单调三次 Hermite / Fritsch–Carlson）** | 保形单调 ⇒ 绝不过冲；官方物理限位之外的软限位再留裕量 |
| 脸部参数 | Catmull-Rom（**必须钳位**） | 脸部要平滑可略微过冲，但不得越界 |
| 落定 / 停顿 | cubic-bezier | 只用于「到位」与「停住」 |
| 微动作（眨眼等） | smoothstep | 幅度极小，不值得上样条 |

- **已发表的帧率/滤波参数**（引用 arXiv:2403.12670，非我们自定）：**25 Hz 帧率 / Δt=40 ms**、**320 ms 滑窗**、**8 Hz 5 阶 Butterworth** 平滑。
- **软限位与落点**（自研设定）：软限位裕量 **yaw 5.0° / pitch 2.0°**，落点 **≤ ±115.0°**（不贴物理限位）。

**韵律 → 动作的 7 个维度**（55 号）：

| 韵律维度 | 映射到 | 说明 |
|---|---|---|
| F0 均值 | 头部俯仰基线 | |
| F0 重音峰 | 点头幅度 / 强调 | |
| 能量 | 眼睛 weight、灯亮度 | |
| 语速 | ⭐ **只映射到时间轴缩放**，**不映射角度** | 说话快不应变成动得多 |
| 停顿 | ⭐ 映射成「落定」，**不是「不动」** | 停顿是表达，不是没内容 |
| HNR | 眉/眼睑的柔和度 | |
| 谱质心 | 灯色冷暖 | 颜色在 **Oklab** 空间插值（H 通道必须显式指定 `shortest` / `longer` 策略，CSS Color 4 §13.5） |

**参数量化**（55 号）：**情绪基线 22 + 韵律调制 9 + 个性化 7 + 设备常量 4 ≈ 42 个标量**。

**四步标定法**（55 号）：
1. **motor babbling**：200 点 / 20 Hz / 5 分钟，采出设备的真实响应
2. **岭回归**拟合 8 个韵律增益（需 ≥60 句语料）
3. **情绪基线手工锚定**（90 次配对比较）
4. **只动个性化组（C 组）的 5 轮偏好微调**

⭐ **离线标定已先行一步**（87 号）：合成韵律语料跑真实管线，把「情绪会不会被音频淹没 / 6 情绪可辨识度 / 增益单调性 / 越界 / 带宽」变成机器判据（门禁 `tools/check_prosody.py`）。实测 **淹没比 0.41 ⇒ 情绪没被音频淹没**；**跨韵律变体可辨识度 83.3%**（`Neutral`/`Sad`/`Sleepy` 4/4 全对，`Happy` 3/6、`Doubt` 2/4 最弱 ⇒ 这两对是第 3 步「情绪基线手工锚定」的重点）。⚠️ 测的是**输出空间可分性**，**不等于**「人能认出」。

⭐ **真实 TTS 口径已跑（88 号，18 条真实语料入库 `assets/prosody-corpus/`）**，并**推翻了 87 号的乐观结论**：合成语料上的可辨识度 83.3% ⇒ **真实语料上只有 61.1%**（跨文本留一）。根因实测清楚：

| 口径 | 跨文本留一可辨识度 |
|---|---|
| 纯标签基线（静音 + 各自情绪基线） | **6 / 6 完美可分**（两两距离 0.000） |
| **标签基线 + 真实韵律调制（我们系统的用法）** | **61.1%** |
| 纯音频韵律（统一 Neutral 基线） | **33.3%** |

⇒ ⭐ **当前「韵律调制」是净负贡献**：把本来 6/6 完美的区分度拉到 61.1%。
⇒ 根因：**能量通道和情绪基线在争夺同一个通道（嘴）** —— 情绪基线最小间隔 **2.0** 个 weight 单位，而同一情绪内的韵律扰动最大 **10.37** ⇒ **SNR = 0.19**。
⇒ ⇒ **第 3 步「情绪基线手工锚定」现在有了可判目标**：标定到「跨文本留一可辨识度 ≥ X%」且 **SNR ≥ 0.5**，而不是凭主观感觉调。
⚠️ **已实测出两处互相冲突**（88 号 §3.3–3.4）：`e_min` 取全轨 p20 ⇒ 能量动态被压到 **0.242** 窄带（表情呆板）；但单独修它会让 SNR 从 0.19 掉到约 0.06 ⇒ **必须与增益一起调**，已登记为待拍板 **Q21**，**未擅自改**。

⚠️ **韵律信号源已裁决在服务端**（54 号）：服务端同时握有用户上行 PCM 与 **TTS 下行 PCM** —— **我们合成的语音，其韵律就是设备该表达的身体语言** ⇒ 零固件 / 零 App / 零协议改动。⚠️ esp-sr **零 F0 提取**、Apple **无内置音高 API** ⇒ 不要指望端侧有现成方案（05 号 R15）。

⭐ **原型已落地**（59 号）：`tools/prosody_to_motion.py`（44 KB）+ `tools/protocol_sim.py` 新增 `0x14` 设备侧处理。
端到端跑通：`TTS PCM → YIN 韵律 → 7 维 → 42 参数 → 语义锚点 → PCHIP → 0x14 关键帧 → 云 → 设备`。
自检 **42 项全绿**（含 verifier 复核后重写的断言）；设备侧实测打印「59 个关键帧 / 总时长 2360 ms / speed 档位 [500] → 弹簧刚度 170.0」。

⭐ **独立复核判定 FAIL 后已全部修正**（59 号 §11）：4 阻断（眼睛 weight 极性反了 / 模拟器给 0x14 加 MAC 前缀 / 语速偷改角度 / 消息类型写成 0x13）+ 3 重要 + 3 建议，**自检重写为独立算帧数、静音对照、像素换算**等真断言。

⭐ **真机通道已打通到协议层**（62 号）：`tools/stackchan_ble.py`（scan / connect / demo / play / wifi / selftest，离线自检 22/22）把 0x14 关键帧切成 BLE 三路载荷。

⚠️ **实现期抓到的 5 个 bug，其中 3 个是「不报错但静默给错结果」**（59 号 §5，必须写进团队规范）：

| # | 坑 | 通用形式（可复用判据） |
|---|---|---|
| 1 | YIN 差函数的「窗口切片和」用错后缀和表 ⇒ F0 全错 | 自相关/差函数的切片和**必须用后缀和表**，前缀和表错一格就全错 |
| 2 | 平滑时把未浊音帧的 `0` 一起平均 ⇒ 信号塌成常数 | **稀疏信号 → 平滑必须先补齐再滤，最后按原掩码还原** |
| 3 | **Butterworth 归一化截止频率误用音频采样率（16 kHz）而非帧率（100 Hz）** ⇒ 截止 0.08 Hz ⇒ 滤波器退化成均值滤波器 | **施加在派生序列上的滤波器，截止频率必须用该序列的采样率**；输出出现「异常整齐的常数」先查这个比值 |
| 4 | 情绪基线 `pitch` 超过舵机物理上限 87° ⇒ 情绪差异被钳平 | **情绪基线必须先过一遍设备限位再定值** |
| 5 | `rateTimeScale` 未接线 ⇒ 「改它不影响结果」的断言恒真（假通过） | **断言「参数 X 不影响 Y」前，必须先断言 X 确实改变了某项可观测量** |

## 五、功能减法：官方有、我们不做

| 官方能力 | 我们的处理 | 理由 |
|---|---|---|
| `device_post` / `device_post_comment` 动态+评论 | **只做「小栈的一天」自动生成生活流** | 全做工作量巨大且与减法原则冲突 |
| `device_friend` 好友 | **不做** | 陪伴是私人的，社交会稀释独占感（04 号 §4.3 M6 风险③） |
| `device_dance` 舞蹈 | **不做**（保留协议通路） | 舞蹈是"表演"，不是"关系" |
| `device_pano` 全景 | **不做** | 与陪伴无关 |
| `app_store` 应用商店 | **不做** | 我们的分发靠人格包 + NFC |
| 设备端 `callAppClient` 主动呼叫 | **做（但降级）** | 有价值但实现成本高，放 P4 之后 |
| BLE 通道 | **不做** | 官方协议已够；BLE 是私有扩展，风险高 |
| **NFC 人格卡** | **不做（降级为可选增强）** | 官方固件无 NFC 驱动 ⇒ 要做需外挂模块；不进 P0–P2 主线（04 号 §3.4.2）。⭐ 且 52 号裁决：**只做「分享」，不做「迁移」** —— 私人层永不过卡 |
| 官方 xiaozhi AI 转发 | **替换成 MiniMax** | 这是我们的替换靶点 |
