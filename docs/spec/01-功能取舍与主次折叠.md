## §0 一句话

> **38 项功能不是 38 个按钮。**
> **App 上一级可见的元素只有 12 个；其余 26 项全部下沉到二级、三级、后台、系统表面或设备端。**
> **能让人一眼看出"这东西不一般"的，只有 5 个护城河功能；剩下 6 个是技术实力的证明；其余是必须做但不构成卖点的运维项。**
> **主界面是控制台，不是聊天框。** 对话降级为二级页；设置里必须有 **更新 / 连接 / 网络**。

## §1 极简要有量化标准

「简约」不能靠感觉。每一条规则都要能判定：

| # | 规则 | 阈值 | 判定方法 |
|---|---|---|---|
| **S-1** | 单个 Tab 内**一级可见元素**上限 | **≤ 6** | 打开该 Tab，闭眼能数清的控件数 |
| **S-2** | 一个 App 全部表面（Tab + Scene + 系统表面）**一级可见元素**总数 | **≤ 12** | 把所有表面的可见控件加起来 |
| **S-3** | 信息层级深度 | **≤ 2** | 任意功能从入口到完成 ≤ 2 次点击 |
| **S-4** | 同一屏内的**强调色块**数量 | **= 1** | 截图取色，暖色/高饱和色块只有一处 |
| **S-5** | 同一屏内的**字号级数** | **≤ 3** | 屏标题 / 正文 / 辅助 |
| **S-6** | 同一屏内的**分隔手法** | **只用 1 种**（描边/背景/阴影 三选一） | 目视检查 |
| **S-7** | 一次交互产生的**触感** | **0 或 1 次** | 不叠加 haptic |
| **S-8** | 首屏的**未接线元素** | **= 0** | 每个可见元素都有实现 |

> ⚠️ **S-1 上限修订（2026-10-25，第二次 IA 拍板）**：原为 **≤ 5**（源自 `40` 号的通用启发式）。
> 新 IA 的 Tab 1「控制」要同时承载「它是谁」（设备卡 / 状态 chip）与「我能动它」（摇杆 / 表情 / 动作），
> 压到 5 会逼着把「状态 + 交互」塞进同一张卡、必然过载 ⇒ 上限放宽到 **6**。
> ⇒ **真正的守门指标不是这个数字，是 §7 C1「同屏不得有两个视觉权重相当的焦点」** —— 放宽 S-1 不放宽 C1。
> **S-2 是硬线。** 超过 12 个，说明这个 App 是"功能清单"而不是"产品"。

## §2 四个表面的分工：谁才是主角

一个 App 之所以显得杂乱，通常不是功能多，而是**每个功能都想当主角**。必须明确只有一个主角。

> ⭐ **2026-10-25 用户第二次 IA 拍板**：主界面 = **控制台（舵机操作）**，
> 聊天**降级为小功能**，设置里必须有 **更新 / 连接 / 网络**。
> 溯源：`docs/spec/07` §3.4b。

| 表面 | 角色 | 注意力占比 | 出现时机 | 绝对不做的事 |
|---|---|---|---|---|
| **① 控制（主界面，Tab 1）** | ⭐ **唯一主角**：舵机控制台 | **~60%** | 打开就在 | 不放设置、不放功能网格、不做聊天气泡流 |
| **② 对话（二级页）** | 配角：从「和它说话」进入 | ~25% | 想找它说话时 | 不占 Tab、不做成主区 |
| **③ 设置（Tab 2）** | 配角：调参 | ~15% | 主动进入 | 不堆开关；每组 ≤ 5 行 |
| **④ 系统表面**（Live Activity / 通知 / Shortcuts / 控制中心） | **主角的第二现场** | 常驻余光 | 离开 App 时 | 不做第二套功能，只做"状态 + 一个动作" |

### 关键洞察

> **控制台是产品，`对话` 和 `设置` 都是它的附属品。**
> 大多数人做陪伴 App 会把"聊天"做成主界面 —— 那是把**聊天框**当主角。
> 我们的主角是**那台能被你直接拨动的身体**。
>
> 所以：主界面里最显眼的元素是**一个可以直接拖的舵机摇杆**，不是一排功能按钮，也不是一列气泡。

### ✅ 2026-10-25 用户拍板：App 定位 = **两个都要，控制为主**

**用户原话（第一次拍板）**：「陪伴聊天为主，设备是它的身体」/「都要有」。
**用户原话（第二次拍板，本节依据）**：「聊天界面你就分到一个小功能里面去，主要界面还是控制舵机那样操作，然后设置里面就要有更新连接网络这些的。」

⇒ **两次拍板的关系**：第一次定「都要有」；第二次**只调主次、不推翻** ⇒
**设备遥控从「Tab 2 的配角」升为「Tab 1 的主角」，对话从「Tab 1 的主角」降为「二级页的小功能」**。
⇒ 两次拍板**共同成立**：两边都不删，但**主角换成控制台**。

| 拍板项 | 结论 | 落地位置 |
|---|---|---|
| 设备遥控 | **主体** | Tab 1「控制」：设备卡 + 摇杆 + 表情 + 动作 |
| 陪伴聊天 | **降级为小功能**，但**必须存在** | Tab 1 的「和它说话」→ 二级页 |
| 设置 | **必须有**，且含 **更新 / 连接 / 网络** | Tab 2「设置」 |
| 两者关系 | **设备是 App 的身体** | ⇒ App 里的脸 = 设备脸的**镜像** ⇒ 渲染器必须支持镜像模式 |

⇒ 脸渲染器的双模式规格见 `docs/spec/06` §9.2b（8 条约束）。
⇒ 溯源：`docs/spec/07` §3.2（第一次拍板）与 §3.4b（第二次拍板）。

⚠️ **公开订正（2026-10-25）**：本节上一版写「80 / 15 / 5 的注意力占比就是「陪伴为主」的落地口径」——
那是**第一次拍板**时的口径。第二次拍板后**注意力占比改为 60 / 25 / 15**。
⇒ **80/15/5 作废**，不得再被引用。

## §5 折叠规则：什么收进哪里

| 收纳位 | 放什么 | 规则 |
|---|---|---|
| **状态条** | 情绪、在场、电量 | **一个元素承载 3 个信息**，不拆成 3 个胶囊 |
| **长按 / 滑动** | 次要动作（点头、看别处、前倾、让它安静、查看记忆） | 每个手势位最多 4 项，超过就再往下一层 |
| **横向滑动组** | 同类动作的集合（8 个动作） | **禁止网格**（网格 = 杂乱） |
| **折叠区（默认收起）** | 感知读数、详细数值、调试信息 | 默认收起，只在需要时展开 |
| **设置 > 分组** | 偏好与配置 | 每组 ≤ 5 行；每行 = 一个动词 + 一个当前值 |
| **设置 > 高级** | 校准、存储、固件、恢复出厂 | 全部收进一个「高级」二级页 |
| **搜索 / 命令面板** | 低频但存在的功能 | iOS 不适用 → 用设置里的「高级」代替 |
| **通知** | 需要打断用户的事 | **只有 4 类**，其余一律走 Live Activity 或状态条 |
| **设备端 320×240** | 一屏一件事 | 表情 + 一行状态 + 必要的系统状态 |

### 反面清单（做了就杂乱）

- ❌ Tab 里放"功能宫格"（九宫格 = 2010 年的 Launcher 味）
- ❌ 同一屏出现两处以上强调色
- ❌ 把"设置项"直接铺在主页
- ❌ 每个功能配一个图标按钮
- ❌ 状态用文字标签堆（改成图形 + 一个词）
- ❌ 用 Push 通知承载常驻状态（那是 Live Activity 的活）
- ❌ 设备控制做成一排滑杆

## §6 ⭐ 护城河 / 技术实力 / 运维项 —— 三分层

> 「哪些功能是护城河，哪些很体现技术」——这是两个不同的问题，答案也不一样。
> **护城河 = 别人抄了也做不出**（产品哲学 + 物理 + 长期积累）
> **技术实力 = 别人有钱就能抄，但能证明我们的工程水平**

### 6.1 护城河（6 个，**这是产品的全部说服力**）

| # | 护城河 | 为什么抄不走 |
|---|---|---|
| **★1** | **反向陪伴：它也需要你** | 这不是功能，是**产品哲学**。要放弃"永远秒回、永远温柔、永远免费"。抄的人不会愿意付这个代价。**这一条立住，其余都是锦上添花。** |
| **★2** | **在场感知 +「别过头再转回来」** | 需要**物理身体**才能感知你走了、在你回来时先别过头。一行代码都抄不动。 |
| **★3** | **韵律驱动的身体表达** | 需要官方 HAL + 自研轨迹算法（临界阻尼弹簧 + 8 条去机械感硬规则 + 总线时序控制）。**最贵、最难、最能证明"这是硬工程"。** |
| **★4** | **物理化情绪**（侧身 / 前倾 / 压低） | 纯软件产品没有身体。360°→±128° 的真实限幅我们用源码核实过，**这份核实本身就是壁垒**。 |
| **★5** | **NFC 人格卡** | 需要硬件 + 人格包体系 + "社交但专属"的产品设计。**它让产品从"私人陪伴"变成"可传播"**。 |
| **★6** | **三通道同步反馈**（声音 + 表情 + 运动） | 同一个事件同时走三条通道，**只有"有身体 + 有对话"的设备做得到**。纯 App 只有声音，纯硬件只有运动。⭐ 取证：Antigravity IDE 把状态做成**听觉事件**（`contrib/antigravitySounds/media/*.mp3` 钢琴采样库），说明多模态是 AI 工具"质感"的第一来源；而**三通道同步**是我们的加强版，纯软件抄不动。 |

> ⭐ **★6 的证据链**（`39` 号 §一.3 / §二.1(e) / §8.4）：
> Antigravity IDE 的 `resources/app/out/vs/workbench/contrib/` 下**只有 1 个自研模块**（`antigravitySounds`），
> 其余全部继承 VS Code —— **它的"质感"来自听觉事件与折叠结构，不是配色**。
> ⇒ 我们的对应物：`设备音效事件 ≤ 4 个` + `不新增一级导航` + `表情/姿态/声音同一时刻发生`。

### 6.2 体现技术实力（6 个，**进 README / 简历 / 演示视频**）

| # | 技术点 | 证明什么 |
|---|---|---|
| T-1 | **双 WS 架构 + 自研 MiniMax 语音协议层** | 读懂了官方「控制面 vs 语音面」分离，并替换掉唯一没被官方实现的一层 |
| T-2 | **Opus 容器选型 + 帧格式对齐**（控制面裸包 vs 语音面 OGG、24 kHz vs 16 kHz） | 在协议层做到了毫秒级正确，**这是普通教程里看不到的东西** |
| T-3 | **情绪协议零固件改动复用 + 语义映射表** | 不是"重写"，是"读懂源码后精准复用" —— 更高级的能力 |
| T-4 | **舵机轨迹算法**（临界阻尼、8 条硬规则、总线时序、基线跟踪） | 算法 + 硬件时序的结合，**最能体现工程深度** |
| T-5 | **表情 morph 插值器**（15 维参数 + 最短弧 + 跨五官归一化） | 在官方"离散"之上做出"连续"，且不破坏原有结构 |
| T-6 | **本地推理 provider + 隐私架构** | 让"个人数据永不入库"从口号变成可切换的架构事实 |

### 6.3 运维项（必须做，但**不构成卖点**，别在 UI 上强调）

配网 · OTA · 舵机校准 · 存储健康 · 设备自检 · 设置项 · 通知 · 图标 · 许可与署名

> **判断法则**：一项功能如果**关掉它，产品的说服力不变**，它就是运维项。
> 校准、OTA、存储清理关掉之后，小栈照样是那个"不一般的小栈" → 它们必须在后台安静地工作，**不要占据一级界面**。

### 6.4 反向检验：护城河在 UI 上的样子

护城河不需要按钮，但**需要一个"看得见的证据"**：

| 护城河 | 用户在哪里"看见"它 |
|---|---|
| 反向陪伴 | 它低落时的一句短话 + 状态条图标 + 你哄好时它真的转回来 |
| 在场感知 | 你离开时屏幕自己暗下去；你回来时它别过头再转过来 |
| 韵律身体表达 | 设备端身体跟着说话动（**App 里看不到，必须在设备上看到**） |
| 物理化情绪 | 它真的侧过身不理你 |
| NFC 人格卡 | 你贴一张卡，它整个性格变了 |
| 三通道同步反馈 | 它说完话的那一刻，**声音停了、表情收了、头沉了一下、手机轻震了一下** |

⇒ **这五条都发生在"设备"和"对话"里，不发生在"设置"里。**
⇒ **所以 App 的职责不是展示功能，是让用户看见这些瞬间。**

## §7 "看起来杂乱"的 6 个可检测成因（自查用）

> 每个成因都有**可机械执行的检测方法** —— 设计/实现可自测，验收方可复核。
> 源自 `40-交付感判据与高完成度UI规范` §5.4。

| # | 成因 | 可检测特征 | 检测方法 | 判定阈值 | 本项目状态 |
|---|---|---|---|---|---|
| **C1** | **同层级竞争** | 一屏内 ≥2 个视觉权重相当的焦点 | 逐屏截图，统计"强调色着色控件数"与"最大字号元素数" | 同屏强调色控件 **>1** 或 最大字号元素 **>1** → 不过 | 陪伴页只有状态条 1 处 ✅ |
| **C2** | **一致性破缺** | 同屏混用 ≥2 套间距/圆角/字重/描边体系 | 导出该屏全部间距值/圆角值/字重值，统计**不同取值数** | 任一维度取值种数 **>2** → 不过 | 交由 `DESIGN.md` 令牌保证 |
| **C3** | **分隔手段过多** | 混用分隔线 + 阴影 + 背景色块 + 留白 | 逐屏标注分隔手法种类 | 手法种数 **>1** → 不过 | 已定：三选一（`02` 号 Q-8） |
| **C4** | **强调色滥用** | 强调色出现在多个不相关区域 | 统计强调色像素面积占比 + 出现区域数 | 面积占比 **>10%** 或 出现区域 **>2** → 不过 | 每屏 1 处 ✅ |
| **C5** | **密度不均 / 节奏断裂** | 同屏间距分布无规律，分组间距 = 组内间距 | 计算同屏相邻间距值的标准差/最大值比 | 组内间距 ≥ 组间间距，或 组内间距种类 **>2** → 不过 | 需在设计稿阶段检查 |
| **C6** | **兜底缺失** | 元素"看起来能点但不知道是什么 / 点了没反应" | Accessibility Inspector 扫空 `accessibilityLabel`；人工遍历「空/错/离/拒」4 条路径 | 空 label 可点元素 **>0**，或 4 条路径任一无解释 → 不过 | 见 `02` 号 §6 状态矩阵 |
| **C7** | ⭐ **同一状态被两条通道重复表达** | 同一语义状态既有图案又有文字（或两处文字） | 逐屏列出每个状态的**表达通道**（图案 / 文字 / 动画） | 同一状态 **>1 条** 表达通道 → 不过 | Tab 1：**情绪只由灯带图案表达**，文字只给**设备事实**（连接 / 电量 / 版本）⇒ 不重复（依据见 `86` 号） |

> ⭐ **整体观感的补充检测（最狠的一条）**：
> 把任意两个页面并排放大到同一尺寸，**能在 3 秒内说出哪个是主页面** —— 说不出即触发 C1。
>
> ⭐⭐ **折叠优先的实物证据（`39` 号 §二.1(d)）**：
> Antigravity IDE 的 `resources/app/out/vs/workbench/contrib/` 下**只有 1 个自研模块**（`antigravitySounds`），
> 其余 8 个（debug / extensions / externalTerminal / notebook / output / terminal / webview / welcomeGettingStarted）
> **全部继承 VS Code**。
> ⇒ **它没有为 AI 功能新造一级导航**，而是把 AI 能力挂进既有工作台 → 视觉层级与信息层级天然一致。
> ⇒ **我们的对应硬线**：新增任何能力，**先问"它能不能挂在已有的一级元素下面"**；不能，就先问"这个一级元素是不是可以合并掉"。
> ⇒ 这条是 C1–C6 的**根因对策** —— 杂乱不是排版没排好，是**一级结构膨胀**。

## §7.1 ⭐ 5 问决策表（给任意一个功能，问 5 个问题决定它放哪）

> **用法**：拿到一个待安置的功能，依次问 Q1→Q5；**第一个答"否"的问题就决定它去哪**。
> 源自 `40` 号 §5.5。

| 问 | 问题 | 判据 | 答"是"→ 去哪 |
|---|---|---|---|
| **Q1** | **它是不是"使用这个 App 的主要目的"？** | 删掉它，App 就没有存在意义了吗？ | → **Primary**：Tab / 首屏主区 / 主按钮 |
| **Q2** | **它日频/周频被使用吗？** | 日均 ≥1 次 或 周 ≥3 次 | → **Secondary**：一级可见，但降权 |
| **Q3** | **它需要"不进入就能看到当前状态"吗？** | 用户必须一眼看到它的状态/数值/进度 | → **常驻状态位**（状态条 / 常驻小部件）；否则不必常驻 |
| **Q4** | **折叠后还能被找到吗？** | 有没有至少一条兜底路径（More / 长按 / 搜索 / 设置）？ | 有 → **Tertiary**：折叠<br>没有 → **不折叠**，强制升为 Secondary |
| **Q5** | **放进一级会稀释主操作吗？** | 同层是否会出现第二个同等权重的视觉焦点？ | 会 → **折叠**（或与主操作合并）；不会 → 可放一级 |

**决策速查**
```
Q1 是                              → Primary
Q1 否 & Q2 是                      → Secondary（一级可见，降权）
Q1 否 & Q2 否 & Q4 有兜底路径      → Tertiary（折叠）
Q1 否 & Q2 否 & Q4 无兜底路径      → 强制升为 Secondary（可发现性优先）
Q3 是                              → 追加"常驻状态位"（不占功能入口）
Q5 是                              → 再降一级 / 合并 / 移出屏幕
```

**三条硬性兜底规则**（无论五问结果如何）
1. 危险 / 不可逆 / 会丢数据 → **Alert 二次确认**（不论层级）
2. ⭐ **机器人硬件的直接控制（音量、灯光、动作、姿态）→ 常驻可折叠控制面板** —— 桌面机器人的核心动作**不能藏在三级**（这正是 Tab 2「小栈」存在的理由）
3. 任何"可见即可用"要求：折叠项在被折叠前**必须**在父级有可见入口（More / 长按 / 角标）

## §9 交付感：这份文档不解决的部分

**极简 ≠ 交付感。** 一个极简但粗糙的 App 依然不叫"有质感"。

质感来自另外四件事（`40-交付感判据与高完成度UI规范` 正在取证，结论会回填）：

1. **动效只有一个家族**（一套 spring 参数、一套时长阶梯）—— 不是每处各写一个曲线
2. **每个状态都被设计过**（加载 / 空 / 错 / 离线 / 权限拒绝 / 设备不在线）
3. **每个动作都有触感**，且一次交互只叠一次
4. **没有未接线的元素** —— 看得见的就一定能用

> 我们的「12 个一级元素」是**减法**的答案；上面四条是**工艺**的答案。
> **减法让它不杂乱，工艺让它有质感。缺一不可。**
