## 一、问题陈述

夜间自主工作会同时碰到三类东西，处理方式完全不同：

| 类别 | 定义 | 处理方式 | 返工风险 |
|---|---|---|---|
| **事实层** | 从源码 / 实测 / 官方文档取来的客观结论，**带 file:line 出处** | 放心做，做完就定 | 无 |
| **契约层** | 跨端必须一致的**数据形状与语义**（协议字段、JSON Schema、参数含义） | 可以做，但**只定形状不定长相** | 低 |
| **决策层** | 视觉风格、配色、布局、语气、优先级取舍 —— **只有用户能定** | ⛔ **只留占位，不许实现** | 高 |

早期把三者混在一起做，就会出现「代码写完了，用户说不是这个风格 ⇒ 全部重写」。

⇒ **本文档是一份「谁还没定」的账本**，任何一条没销账，相关代码就不许进入「已实现」状态。

## 三、决策层（⬜ 待用户拍板，未销账）

### 3.0 ⭐ 平台原生度 —— ✅ **已定，是硬约束不是风格选配**

> 用户 2026-10-25 原话：「绝对不能做成安卓版，你要做成 iOS。」
> 上一轮的教训：`prototype/variants/` 里 20 个原型**全部作废** —— 它们是 Web/Android 味的静态稿，
> 官方 App（Flutter 但用原生 `UITabBar` + `CupertinoIcons`）都比它们更有 iOS 感。

**这不是"选哪个视觉风格"，而是"必须遵守哪个平台语言"。** 判定标准：

| 维度 | 要求 | 依据 |
|---|---|---|
| 导航 | 原生 Tab Bar + **导航栈**（push/pop + **边缘右滑返回手势**），不是页面切换 | Apple HIG Navigation |
| 导航栏 | 大标题（34pt Bold）滚动收起为小标题（17pt Semibold）+ 材质 | HIG Navigation Bars |
| 列表 | **Inset Grouped**（16pt 边距 / 10–12pt 圆角 / 0.5pt 分割线左缩进 16pt / 44–52pt 行高），不是 Material 卡片 | HIG Lists |
| 底部 | 浮动毛玻璃 Tab Bar，**二级页隐藏**（官方 App 同做法） | `app/lib/view/home/home.dart:135` |
| 图标 | **SF Symbols 风格内联 SVG**，不用 Material 图标、不用 emoji 当图标 | HIG Icons |
| 控件 | 开关 51×31pt 胶囊、chevron 7–8×13–14pt、原生 Slider / Segmented | HIG Controls |
| 反馈 | `sensory feedback`（selection / impact / notification）语义化 | `ios-fetch/sensoryfeedback.md` |
| 材质 | Liquid Glass / Materials 只用于 Tab Bar、导航栏、Sheet | `docs/spec/02` |
| 外壳 | 真 iPhone 外框 + 灵动岛 + 状态栏 + Home Indicator | — |

**⛔ Android 味禁止项**（出现在任何交付物里即判不合格）：
Material ripple / FAB / 药丸式底导航 / Toast / Snackbar / 实色顶栏 /
厚阴影饱和卡片堆叠 / 通栏分割线 / 底部一排彩色大按钮 / Material 图标 / 居中大标题卡片头。

**验收方式**：机器可检（`prototype/ios/check_ios.py` 逐条判定 iOS 特征齐全 + 安卓味零命中），
不靠"看起来像"。

**产出物**：`prototype/ios/`（浅色 / 深色 2 个可交互原型）+ `docs/spec/08-iOS官方规范事实层.md`（官方出处）。

### 3.6 ⭐ 音频承载方式（3 选 1，新增）

> 背景与取证：`docs/research/64-固件音频通道取证与谁出声架构裁决.md`
> （固件源码证明：**设备没有服务器→设备音频通道**，官方也是**手机出声**）
> ⇒ 这个选择**只影响 App↔云**，**不影响设备**，设备侧永远不发音频。

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. WS 二进制分片** | 沿用现有 WS 帧 `[Type(1)][Length(4)][Payload]`，新增**自研扩展类型**承载 PCM 分片 | 一条连接、实时、与现有协议同构、可边收边播 | 要新增消息类型；PCM 16 kHz/16-bit = 32 KB/s ⇒ **必须分片**（**分片大小取 160 ms = 4 帧 = 5120 B**，对齐关键帧分组边界 ⇒ 完整规格见 §3.6.1） |
| **B. HTTP 拉取整段** | 云端给临时 URL，App `URLSession.download` 取回再播 | 实现最简；不受 WS 帧上限约束 | 多一次往返；起播延迟大；弱网体验差 |
| **C. App 直接调 TTS** | App 直接请求 MiniMax | —— | ⛔ **不可行**：API Key 不能进客户端 |

⭐ **推荐 A**，并建议新增扩展类型 **`0x1C`**：
设备侧 `isKnownType` 不认 0x1C ⇒ **永远不会误发给设备**；
同时在 `docs/spec/03` §2.2 明确标注「0x1C = App↔云私有扩展，设备侧不使用」。

⚠️ **拍板前不动**：`docs/spec/03` §2.2 的消息类型表（25 项）与
`server/stackchan_ai/protocol.py` / `ios/.../CoreProtocol` 的常量**都先不加 0x1C**。

#### 3.6.1 方案 A 的具体规格（拍板后可直接实现）

| 项 | 规格 | 依据 |
|---|---|---|
| 帧格式 | 沿用 `[Type(1)][Length(4 BE)][Payload]`，`Type=0x1C` | 与全部现有帧同构，无需新解析器 |
| 载荷结构 | `[streamId:2 BE][seq:4 BE][totalChunks:4 BE][pcmBytes: 变长]` | 4 字节序 = uint32 BE，与 `Length` 字段风格一致 |
| 分片大小 | **160 ms = 4 帧 = 5120 B**（= `tools/audio_chunk.py` 的 `framesPerChunk=4`） | 片边界正好落在关键帧分组边界 ⇒ App 侧能直接知道「这 160 ms 音频对应哪 4 帧动作」 |
| 分片总数 | 2350 ms ⇒ 15 片；1358 ms ⇒ 9 片 | 实测值 |
| 结束标志 | `totalChunks` 已给出 ⇒ 收满即结束，**不需要额外结束帧** | 省一个类型 |
| 带宽 | 16 kHz × 16-bit = **32 KB/s** ≈ 256 kbps | PCM 未压缩；这是「不用 Opus」的代价 |
| 背压 | App 侧 `scheduleBuffer` 回调驱动补料；缓冲上限 4 片（640 ms） | 超出则丢弃最旧片并**记录告警**（不静默） |
| 时钟 | 播放起点 = **首片到达时刻**；动作调度起点 = 同一时刻 + 音频首字节 | 见 `docs/spec/03` §2.7.4 |

⚠️ **方案 A 的两个已知代价**（拍板时一并知晓）：
① **首字延迟**取决于 WS 往返（RTT/2 + 服务端合成时间），比 HTTP 拉整段**低**；
② PCM 未压缩 ⇒ 流量比 Opus 大 **~8~11 倍**（本文件 §3.6.1 给的 PCM = 32 KB/s ≈ **256 kbps**；Opus 语音典型 24~32 kbps ⇒ 256÷32=8.0×、256÷24≈10.7×），⭐ 2026-10-25 订正：原文写「~5~8 倍」与同文件给出的码率**算不出来**；
   在**弱网**下表现为音频先卡后播；对策是「先下发关键帧让设备动起来，音频追上」。

## 五、防返工工程机制（这才是关键）

光列清单不够，得让「未定」在代码里**看得见、换起来便宜**。

### 5.1 视觉 token 集中 + 多方案可切换

⭐ **2026-10-25 拍板后机制升级**：原先是「全部占位，等销账一次性填」。
现在 4 套方案**都要做**，所以机制变成：

```swift
// iOS/StackChanCompanion/DesignSystem/Tokens.swift
public protocol ThemePalette: Sendable {
    var identifier: String { get }
    var displayName: String { get }
    var isDarkBased: Bool { get }          // 深浅是方案属性，不是正交维度
    func color(for token: ThemeToken) -> Color
}
```

- 所有颜色 / 字号 / 圆角 / 间距 / 动效曲线 **集中在 DesignSystem**（6 个文件）。
- 换方案 = 改 `ThemeChoice` 的 case + `ThemePalette` 实现，**不动任何 Screen 逻辑**。
- **新增方案的成本 = 1 个 `ThemePalette` 实现 + 1 个 `ThemeChoice` case**（不碰别的）。
- ⚠️ 视觉字面量**只允许出现在 DesignSystem** ——
  由 `ios/tools/validate_project.py` 强制（DesignSystem 之外出现即 FAIL）。
  这是「改一处、Screen 不动」能长期成立的前提。
- 剩下的 `TODO_PENDING_DESIGN_DECISION` 只应出现在**尚未拍板**的部分
  （如 App↔云音频承载、Tab Bar 行为），`grep` 一下就知道还剩多少没定。

### 5.2 渲染器只吃参数，不长设计

- 渲染器输入 = 协议里的 avatar 参数，输出 = 几何。
- **渲染器里不许出现色值、阴影、字体、动效曲线**；要上色就由外部注入 token。
- ⇒ 「App 是镜子」还是「App 自己设计」这个决定，只影响**渲染器外部**的一层，渲染器本体不动。
  （本轮拍板「两种都要」⇒ 这层变成 `FaceRenderMode` 枚举，渲染器本体仍不动。）

### 5.3 视觉无关的测试

- 协议编解码、限位、参数语义、帧结构 —— 这些**不依赖任何视觉决策**，可以先写、先跑、先绿。
- 视觉断言（截图比对、对比度、字号层级）⇒ 全部**推迟到销账之后**再写。

### 5.4 事实与判断在文档里分栏

每份 spec 结尾的「文末自查」表都区分「**事实**（有出处）」与「**我的判断**（可被用户推翻）」。
本项目的历史教训：**文档与实现不符**比设计不好看更致命。
