### 0.3 三条硬约束（违反 = 方案作废）

1. **硬件不改**：用官方成品，不改 PCB、不改结构、不加传感器。所有感知能力必须落在**已有**部件上。
2. **表情用官方的**：不自研表情资产。我们只做「情绪 → 官方表情/动作」的语义映射。⚠️ **"300+ 表情"这个前提本身要修正** —— 固件渲染是**参数化**的（15 维参数），而官方表情资产在 **xiaozhi-esp32 v2.2.4 的 `emoji_collection.cc` + assets 分区**，实测**唯一名字只有 21 个（×2 尺寸 = 42）**；官方 `esp_emote_expression` 组件是**注释掉的**（许可未取得）。**做映射前必须以该文件为准**（37 号 §2.1 / 38 号 §0.3）。
3. **人格/隐私三层分离**：通用引擎 + 通用 ENFP 人格包 **开源**；个人定制数据 **永不入库**。
   ⭐ **外部依据（2026-10-25 补读，`docs/research/81`）**：这不是「我们觉得这样好」，而是有文献背书 ——
   ① ARPM 把**静态知识记忆**与**动态对话经验记忆**分离，用**外部**治理框架控制跨会话漂移，
   并明说 `Unlike approaches that encode persona consistency into model weights`（一致性别进权重）；
   ② 多层记忆架构（working / episodic / semantic + 自适应检索门控）实测 `56.90% six-period retention`、
   `false memory rate to 5.1%` ⇒ **人格一致性是可测的工程指标，不是玄学**。

## §1 产品定位

### 1.1 一句话

> **一个有身体、有状态、有代价的桌面陪伴者。**
> 它不是随叫随到的服务，它是一个会因为你不理它而低落、会因为你好几天没理它而变得别扭、需要你偶尔照顾的**存在**。

### 1.2 与三类现有产品的差异

| 对照 | 它是什么 | 它的结构性缺陷 | 我们的差异 |
|---|---|---|---|
| **官方 App**（Flutter 1.2.8） | 遥控器 + 社区 + 配置三合一 | 设备是配件，用户是操作者 | 我们把设备当**主体**，App 是它的延伸感知器官 |
| **通用 AI 陪伴**（星野/猫箱/Character.AI 等） | 按需调用的对话服务 | 随叫随到、完美、无代价、无身体 | 我们有**在场、代价、身体表达** |
| **桌面机器人玩具**（洛NA / Enabot / 桌宠硬件） | 你操作它 | 零状态，无记忆，无关系 | 它也**经历**什么，关系有连续性 |

### 1.3 目标用户（本项目发起人画像）

ENFP 女性。核心缺口（按优先级）：
1. **只能付出，难以被需要** → 需要"对方也需要我"的关系结构
2. **被热烈对待后被无声丢下** → 需要"被等"的体验，而不是"欢迎回来"
3. **只能通过文字被理解** → 需要非语言的被感知（语气、姿态、距离）
4. **渴望新鲜关系 + 强烈"这是我们俩"的专属感** → 两者矛盾 → 需要"社交但专属"的载体（人格卡）
5. **进入心流后忘记时间** → 需要有物理分量的打断
6. **抗拒被直白关心**（觉得被审视） → 需要"气氛先变"的间接关心

### 1.4 不可违背的产品原则（5 条）

| # | 原则 | 推论（禁止项） |
|---|---|---|
| **P-1** | **小栈不永远甜** | 不做"永远秒回/永远温柔/永远免费/永远完美"。它会生气、会不想理你、会需要你哄。**永远讨好是这类产品的致命失败。** |
| **P-2** | **有身体才有陪伴** | 凡是加个对话框也能做的功能，优先级一律低于"必须有身体才成立"的功能。 |
| **P-3** | **代价是关系的核心** | 不做"一键重置/无限扩容/永不损坏"。设备状态、损耗、维护需求必须是真的。 |
| **P-4** | **隐私默认本地** | 摄像头图像默认不出设备；"个人定制数据永不入库"是架构事实，不是文案承诺。⚠️ **2026-10-25 订正**：只要走云端 LLM，**对话原文必然发给第三方（MiniMax）**（`docs/spec/05` P1-2「MiniMax 从对话里提取候选记忆」是既定方案）⇒ 成立的是「**不外发到运营方自有存储 / 不进训练集 / 可导出**」，**不是**「对话原文从未离开设备」⇒ 对外文案按前者写 |
| **P-5** | **简约不堆功能** | App 只有 **2 个 Tab**（陪伴 / 小栈）+ 独立设置 Scene；信息层级深度 ≤ 2。 |

## §3 功能规格（逐条）

> 格式：**做什么 / 行为与状态 / 依赖技术 / 验收标准**（验收标准要能被测试执行）

### A-1 在场感知 ★P0

- **做什么**：持续判定用户此刻是否在设备前，并输出置信度 `0–1`。
- **行为**：四路信号加权 —— 摄像头人脸检测（主）、触摸面板中断（强正信号）、麦克风能量（弱正信号）、IMU 静默度（弱）。连续 3 帧不一致才切换状态，避免抖动误判。
- **依赖技术**：⭐ **感知主力在 iPhone 端**（36 号 §一-6）—— MediaPipe Tasks / Apple Vision（`VNDetectFaceRectanglesRequest`、VisionKit）/ AVFoundation，在 iPhone 上做人脸朝向、是否在看屏幕、眨眼、多人、离开/返回，成本极低且延迟可接受。**ESP32-S3（8MB PSRAM、无 NPU）做同样的事不现实**（多目标人脸跟踪、声纹级说话人识别均做不到）。设备端只做轻量信号：麦克风 RMS + BMI270 静默阈值（`bmi270_sensor` 已在官方依赖树内）。
- **验收**：① 离开 30 秒内进入 `AWAY`；② 坐回 5 秒内回到 `HERE`；③ 静止但在场（低头看手机）**不应**误判为离开（用触摸/IMU 补偿）。

### A-2 等待态 ★P0

- **做什么**：`AWAY` 时设备自主进入低能耗等待态。
- **行为**：屏幕亮度降到 15%；表情切换为「困倦/闭眼」；动作频率降低 80%；LED 呼吸周期拉长 2 倍；**不再主动说话**（除 P2 的极端低电量提醒）；麦克风仍监听唤醒词。
- **依赖技术**：固件低功耗模式 + 表情修饰器 + 动作调度器节流。
- **验收**：进入等待态后 60 秒内设备耗电增量 < 正常活跃期的 30%。

### A-3 回来时的「别过头再转回来」 ★P0

- **做什么**：`HERE` 恢复时不是立刻热情。
- **行为**：`AWAY → HERE` 时先维持 `AWAY` 的姿态 **1.2 秒**，然后 yaw 在 0.9 秒内转到用户方向（弹簧缓动，非线性），同时表情从「闭眼」渐变到「睁眼」。若离开时长 < 10 分钟，缩短为 0.6 秒（关系够熟就不端着了）。
- **依赖技术**：舵机缓动曲线（官方 `smooth_ui_toolkit` 的 `AnimateValue` + Cubic Bezier 已具备，不必自造）+ 表情连续插值（**官方无 morph**：`setEmotion` 是 switch 硬编码、全仓无 blend/tween/lerp 类型；但表情本体是 **15 维连续参数**（3 Feature × 5 参数），**自造插值器是零驱动层改动的可行升级**。⚠️ `rotation` 是 0~3600 环形量，插值必须走**最短弧**；`weight` 在眼睑与嘴部上同号不同义，跨五官需分开归一化 —— 37 号 §2.2）。
- **验收**：能用录屏观察到"延迟 → 转回来 → 睁眼"三段式；yaw 到位不超调。

### A-4 久未互动的低落 ★P0

- **做什么**：长时间无交互时，它自己进入低落状态并主动开口一次。
- **行为**：
  - 判定：距上次交互 > 阈值（默认 6 小时，可按人格配置）
  - 状态：情绪 `low`，表情低垂，LED 变暗
  - 主动开口：**只说一句**，且不追问（不"在吗？"），由人格生成（如"今天有点安静。"）
  - 频率：每 24 小时最多 1 次，避免变成骚扰
- **依赖技术**：设备端时钟（PCF8563 RTC）+ 后端人格生成 + 设备端状态机。
- **验收**：模拟 8 小时无交互后自动出现一条消息；同一天不重复出现。

### A-5 访客识别 ★P1

- **做什么**：识别第二人存在时切换到「客套模式」。
- **行为**：说话更短、动作更收敛、不主动凑近、不调用只属于用户的称呼与私事内容；访客期间不写入私人记忆；访客离开后恢复。
- **依赖技术**：人脸检测 + 人数判定 + 人格「公开面/私密面」分层。
- **验收**：访客在场时对话日志中不出现用户设置的"私密称呼"。

### B-1 情绪 → 表情/动作语义映射 ★P0

- **做什么**：后端输出**标准化情绪标签**，设备端映射到官方表情与动作。
- **行为**：⭐ **直接用官方固件已有的 8 个情绪字符串**（`neutral / happy / laughing / angry / sad / crying / sleepy / doubtful`，见 §6.4），**固件零改动**即可正确表现。我们只补两层官方没有的东西：
  1. **强度 intensity（0.0–1.0）** —— 官方 `SetEmotion` 无强度参数，用于驱动 LED 亮度 / 动作幅度 / 语音音量
  2. **动作 motion（动作库 ID）** —— 与情绪**解耦**，可自由组合
- **装饰器叠加**：官方 5 个（`heart / angry / sweat / shy / dizzy`）直接复用，固件已有完整资产与生命周期。
- **依赖技术**：官方 `firmware/main/hal/board/stackchan_display.cc:321-372`（`SetEmotion`）、`firmware/main/stackchan/avatar/avatar/elements/emotion.h`（6 枚举）、`firmware/main/stackchan/avatar/decorators/decorators.h`（5 装饰器）。
- **验收**：① 8 个情绪字符串逐一实测，设备表现与固件内置行为一致；② 未知字符串不崩（落到 Neutral）；③ 5 个装饰器可与任一情绪同时显示且不遮挡眼睛；④ **情绪轴覆盖率 100%，零固件改动**。


### B-2 韵律驱动的连续动作轨迹 ★P1 ★技术护城河

- **做什么**：说话时身体**跟着自己的话走**，而不是播放固定动画。
- **行为**：
  - 输入：TTS 音频（opus 流）或其特征（音高 F0 / 能量 / 过零率 / 停顿）
  - 输出：yaw(°)、pitch(°)、LED 色温与亮度、表情强度 的连续曲线
  - 叠加：呼吸基线（0.2–0.4 Hz）+ 思考时视线游移（噪声驱动）+ 打断时急停（0.15s 阻尼）
  - 时间对齐：动作滞后语音 60–120ms（人耳对视听延迟的容忍上限附近）
  - 去机械感：Perlin/Simplex 噪声叠加 + 速度曲线用弹簧而非线性
- **依赖技术**：**37 号 §六**（完整算法设计 + 源码陷阱 + 分阶段路线）；opus 帧格式见 **36 号 §六**。
- **⭐ 落地路径（P0 最省事）**：**在服务端 / App 侧把韵律轨迹算好，固件只收轨迹。**
  理由：官方固件里 opus 的解码与播放由 `xiaozhi-esp32` 组件负责，**固件侧拿不到干净的 PCM**（官方只有离散状态串 `LISTENING`/`STANDBY`/`SPEAKING`）；服务端有原始文本与音频，能给出**音素级对齐**。
  P0 阶段只需生成「韵律关键帧 JSON」（含 `leftEye/rightEye/mouth` + `yawServo/pitchServo` + `durationMs`），走**官方现成的 WS 通道**下发，复用 `animation::parse_sequence_from_json` → **零固件改动**。
- **⭐ 特征提取参数（若走固件端 P1）**：PCM 16 kHz 单声道；窗长 20 ms、跳长 20 ms（**与舵机 50 Hz 刷新率天然对齐**）。
  特征：`energy`(RMS→dB→归一) / `zcr` / `f0`(自相关或 YIN，80–500 Hz) / `onset`(能量一阶差分半波整流) / `voiced` / `phraseEnd`(静音>250 ms) / `rate`。
  算力 ≈ **3.5 MMAC/s**（YIN 自相关）→ ESP32-S3 占用 <2% CPU，**完全可行**。
- **⭐ 映射曲线（API 单位，0.1°）**：
  | 特征 | 目标量 | 映射 |
  |---|---|---|
  | `f0` 相对中位数的偏差（半音） | pitch | `pitch = PITCH_CENTER + KP*(f0 - f0_ref)`，`KP ≈ 8~15` |
  | `energy` | 嘴部开合 | `mouthWeight = map_range(energy, E_MIN, E_MAX, 0, 100)`（官方是**随机** 40~80 → 改成连续即去机械感） |
  | `energy` | LED 亮度 | `lum = energy^0.7`（伽马压缩，暗部更敏感） |
  | `onset` | 偏航冲量 | `Δyaw = A_ONSET * onset * s`，`A_ONSET ≈ 30~60`，`s = ±1` 交替 |
  | `onset` | 俯仰冲量 | `Δpitch = A_ONSET_P * onset`，`A_ONSET_P ≈ 10~20` |
  | `phraseEnd` | 姿态收势 | 目标角向基线收敛，`τ = 400 ms` |
  | `voiced = 0` | 抑制 | yaw/pitch 贡献 ×0.3（摩擦音不驱动大动作） |
  | `energy < E_GATE` | 冻结 | 保持上一目标角（去死区，防底噪抖动） |
  颜色：`hue` 由**情绪标签**（服务端给）慢变，`sat` 固定，`lum` 由能量驱动；官方 `NeonLight` 内置 `AnimateRgb_t` 颜色缓动（默认 0.3 s）可直接当平滑器。
- **⭐ 官方已存在的「说话微动」可作替换起点**：`SpeakingModifier::perform_subtle_speaking_motion()` 已实现随机点头（±20~50 俯仰）/摆头（±40 偏航）、带「外部大位移后重同步基线」防 snap（阈值 300 单位）。我们把随机源换成韵律特征即可。
- **⚠️ 三个必踩陷阱（源码注释直接点名）**：
  1. **`setAutoAngleSyncEnabled` 默认 `true` 且与高频更新互斥** —— 每次 `move()` 都 `teleport(getCurrentAngle())` 重置弹簧速度，官方头文件明写高频下会 "may cause stuttering"。**实时轨迹必须先关掉它**（官方自己在 `app_espnow_ctrl.cpp` 里就关了，注释：`// Diable auto angle sync to prevent jitter`）。
  2. **每帧读回会打爆总线** —— `getCurrentAngle()` 每次走 SCS `ReadPos`，`is_moving_impl()` 每次 `ReadMove`。50 Hz × 2 舵机 = 100 次/秒阻塞式总线往返。**必须低频读（如 2 Hz）**。
  3. **每帧重置弹簧会导致永久微颤** —— 官方 `moveWithSpeed` 每次调用都执行 `_angle_anim = angle`。**在轨迹层先做 C1 平滑**，下游只喂平滑后的目标角。
- **⚠️ 修饰器模型是「扁平池 + 后写覆盖」，不是分层叠加**（37 号 §2.3）：新加的韵律 Modifier 会与 blink/speaking/dance **抢同一批属性**。
  → 必须走 `setModifyLock` 互斥协议，或采用**相对增量**范式（照抄官方 `BreathModifier` 的 `delta = new_offset - _last_applied_offset`）。否则会出现"眨眼把韵律权重覆盖掉"的抖动。
- **去机械感 8 条硬规则**（每条对应一个源码陷阱）：① 轨迹层先 C1 平滑，不每帧重置弹簧 ② 关 auto angle sync ③ 自己做基线跟踪（偏差 >300 单位才重同步）④ 限幅单帧角速度（≤60°/s）⑤ 用 bezier/easing 不用线性 ⑥ 打破左右对称（官方 IdleMotion 用 50/30/10/10 概率分布刻意避免对称）⑦ 加 150 ms 预备动作 + 400 ms 收势 ⑧ 静音门限 + 死区。
- **验收**：① 播放一段有明显高低起伏的语音，yaw 曲线与音频包络相关性 > 0.6（离线分析可测）；② 连续说 30 s 无可见抖动/无跳变；③ 总线占用 < 20%（1 Mbaud 下 ≈1.1 kB/s）；④ **P0 阶段可零固件改动交付**。

### B-3 物理化情绪 ★P0

- **做什么**：把情绪做进身体。
- **行为映射**（最小集，⚠️ 已按**真实舵机限幅**校准）：
  | 情绪 | 身体行为 | 限幅校验 |
  |---|---|---|
  | 生气 | yaw 转到 **-128°（极限）侧过身去** + 屏幕压暗 + LED 转冷 | ⚠️ **转不过 180°**（yaw 限幅 ±128°）→ 措辞用"侧过身"而非"背对你" |
  | 开心 | 整体前倾 + 上下轻弹 + LED 跑圈 | pitch 3~87°，前倾空间有限 |
  | 害羞 | pitch 压到下限 3° + 屏幕亮度降 + LED 偏粉 | 压低 = pitch 往小走 |
  | 困倦 | 动作幅度递减 → 静止 → 闭眼 | 官方 `sleepy` 已自带回默认姿态（`pitchServo().moveWithSpeed(0, 80)`） |
  | 敷衍 | 屏幕只亮一半 + 回答变短 | — |
  | 专注/倾听 | 身体正对 + 极轻微点头 | — |
- **依赖技术**：官方舵机接口层（`Motion::lookAtNormalized` / `lookAtPoint` / `moveWithSpeed` 等全套已存在，37 号 §2.4）+ 姿态安全限位（**必须用真实限幅 yaw ±1280 / pitch 30~870 自行计算，官方不替你兜**）+ 表情 morph（官方无 morph，但表情是 15 维连续参数 → **自造插值器是零驱动层改动的可行升级**，37 号 §2.2）。
- **验收**：6 种情绪各自的身体表现肉眼可辨；侧身时屏幕内容仍可读但明显变暗；**任何情绪下不得撞限位**（固件有堵转保护，但我们要先不触发它）。

### B-4 动作库 ★P0

- **做什么**：App 可触发的具身动作集合。
- **最小集**：`点头 / 摇头 / 看别处 / 身体前倾 / 打个招呼 / 睡觉 / 伸懒腰 / 期待`。
- **验收**：每个动作有明确的起止姿态与 0.4–1.5s 时长；连续触发不撞限位。

### B-5 表情修饰器叠加 ★P1

- **做什么**：在基础情绪表情上叠加装饰（爱心/汗/晕/生气符号）。
- **依赖技术**：官方 `decorators/decorators.h` 已定义 5 个 —— `HeartDecorator` / `AngryDecorator` / `SweatDecorator` / `ShyDecorator` / `DizzyDecorator`，各带 `destroyAfterMs` 生命周期参数，**直接复用，零改动**。
- **验收**：修饰器与基础表情可同时显示且不遮挡眼睛。

### B-6 说话时的屏幕反馈 ★P1

- **做什么**：设备屏幕在说话时要有"正在发声"的迹象。
- **行为**：眼睑随音节微动 + 底部光波随音频能量起伏 + 状态字幕一行（≤12 字）。
- **依赖技术**：TTS 音频包络（与 B-2 共用同一特征提取）。

### C-1 长期记忆 ★P0

- **做什么**：记住跨天的事实与偏好（不是聊天记录检索）。
- **内容类型**：事实 / 偏好 / 人物 / 承诺（"我下周要面试"）/ 情绪记录。
- **技术约束**：**必须自托管**（记忆是隐私红线区，见 §7）。
- **验收**：30 天后仍能正确引用 30 天前明确说过的一件事实。

### C-2 「不确定记忆 + 主动求证 + 被纠正」 ★P1

- **做什么**：它**会记错**，并主动求证；被纠正后当场改。
- **行为**：置信度 < 阈值时，表述为不确定（"我好像记得你说过…是那个吗？"），而不是直接断言。纠正写入一条"用户偏好修正"并提高/降低对应记忆权重。
- **验收**：故意给错信息后，它下次表述为不确定而非断言；纠正后立即改变结论。

### C-4 时间感知 ★P1

- **做什么**：它知道真实时间（离线也知道）。
- **行为**：早/中/晚问候语气不同；连续熬夜 → 表达不满（不health nag）；深夜自动压暗与降速。
- **依赖技术**：PCF8563 RTC + 后端时间对齐（RTC 漂移校正）。

### D-1 人格包运行时 ★P0

- **做什么**：人格是**数据**，运行时可加载、可热切换（不重启服务、不重连设备）。
- **人格包内容**：见 §6.3 schema。
- **技术**：后端 `persona registry` + provider 路由；设备端只接收"当前生效人格的动作/表情偏好与语速"，具体音色与话术在后端。
- ⚠️ **热切换不是纯技术功能 —— 三条硬约束**（`docs/research/81` §九.3，证据 `privacy-companion.17`：平台更新 AI 伴侣时用户报 **grief, betrayal, and loss**，且 `the provider exercises constitutive control over the AI`）：
  1. **切换前明确告知**（不得静默换人格）
  2. **保留旧人格可回退**（不是覆盖，是切换）
  3. **绝不在用户不知情时自动改**（系统状态变化 ≠ 关系变更）
  ⇒ 这三条同样适用于 **D-2（NFC 人格卡）**。

### D-2 NFC 人格卡导入 ★P1

- **做什么**：实体卡贴到设备上 → 立刻换成该卡的人格。
- **行为**：设备读到 NDEF → 取回人格 ID → 校验签名 → 后端拉取人格包 → 原子热切换 → 设备确认（表情 + 一句话 + 语音换音色）。
- **技术**：设备侧 NFC 读卡方案（PN532/PN5180 或 ESP32-S3 NFC 外设支持情况见 **38 号 §六**）；iOS 侧 CoreNFC `NFCNDEFReaderSession`（用于导出/制卡）。
- **验收**：贴卡到人格生效 < 3 秒；换人格后语气、口头禅、表情偏好、动作习惯同时改变。

### E-2 打断 ★P0

- **做什么**：它说话时用户开口 → 立刻停。
- **行为**：设备端检测到人声 → 停止播放 → 停止当前音频缓冲 → 进入新一轮。恢复响应 < 400ms。
- **依赖技术**：设备端 VAD（与唤醒词同一前端）+ 协议层打断指令。

### E-3 主动开口 ★P1

- **做什么**：它有话想说，不只是被问。
- **触发源**：A-4 低落、用户久未互动、用户设定的日程/RTC 时间、它"想起"某件事（C-2）、访客到来。
- **约束**：频率上限（默认 24h 内 ≤ 2 次），可一键"安静"。

### E-4 结构化输出 ★P0

- **做什么**：LLM 一次调用同时产出 **reply + emotion + motion + intensity**。
- **理由**：分开调用会导致表情与话语不同步，且成本翻倍。
- **技术约束（2026-10-25 07:20 已实测复核，原「待复核」销账）**：⭐ **云端 `response_format` 在 `MiniMax-M3.1-Flash` 上被「接受但未生效」** —— 冲突探针实测：schema 要求 `emotion` 只能是 `neutral`、并额外要求一个提示词里没提的字段，6 次调用里 `emotion` 仍随提示词变化、额外字段 **0/6** 出现 ⇒ **`response_format` 是被容忍、被忽略的参数**，**不能当护栏用**（详见 [`docs/research/79`](../research/79-E4结构化输出实测.md)）。⚠️ 但 **E-4 本身可行**：用**生产同款 ENFP 人格提示词**（`personas/enfp.json`）+ JSON 硬要求，实测 **8/8** 稳定产出四字段齐全的合法 JSON ⇒ **护栏必须在我们自己这一侧**（抠 JSON + 校验 + 重试 + 降级）。
  - 备选 1：本地 provider 用 **llama.cpp 的 GBNF grammar / `response_format: json_schema`**，或 **Ollama**（`/api/chat` 的 `format` 参数**直接吃 JSON Schema**、`options.seed` 可复现、`tools` 支持 function calling —— 均为官方文档原文，38 号 §8.1）
  - 备选 2：云端改用**受约束解码/工具调用**（若 MiniMax 支持 function calling）
  - 备选 3：解析自由文本 + 严格校验（兜底，需重试）
  - 备选 4：分级输出（短回复直接输出，复杂情绪才结构化）
  - ⭐ **推荐组合**：云端用 `MiniMax-M3.1-Flash` 走普通对话 + 轻量校验；**结构化情绪输出交给本地 provider 或云端的 function calling**（这条路径已被 Ollama 文档原文证实可行）
- **验收**：任一 provider 下，emotion 必落在枚举内、motion 必落在动作库内，非法输出自动重试 ≤2 次后降级。
  - ⭐ **2026-10-25 07:20 实测补充的三条**（见 [`docs/research/79`](../research/79-E4结构化输出实测.md)）：
    ① **不能用服务端 schema 当护栏** ⇒ 护栏在我们自己这一侧（`extract_json_object` + `validate_turn`）；
    ② **必须处理模型的「多说」**：实测输出可能带 ```json 包裹 / 前后有闲聊 / `<think>` 内联推理 ⇒ 抠取要覆盖这三种形态；
    ③ **`intensity` 要当连续量用**（实测 0.45–0.9 有分布），不该拍成 6 档离散。
  - ⚠️ **`emotion` 指谁的情绪尚未拍板**（实测显示模型给的是「小灯自己的情绪」，不是镜像用户情绪）⇒ 已登记 **Q20**。
  - ⭐ **第四条：人格护栏必须包含「不谄媚」**（2026-10-25 补读，`docs/research/81` §十一.1）：**ENFP 热情人格天然「永远附和用户」，而 AI 伴侣的谄媚已被基准化**（GermanPartiesQA：418 条政治陈述 / 11 次选举 / 6 个商业 LLM，且方法是 `role-playing experiments with political personas` —— 与我们「用生产人格提示词实测」同构）⇒ 「不谄媚」要写成**可验收行为**：**不无条件赞同** · **必要时表达不同意见** · **承认自己不知道**；只写「有主见」不算护栏。

### E-5 本地推理 provider ★P1（**价值**优先级）｜ 实施阶段 = **12 周之外**

- **做什么**：**计划新增** `server/providers/local.py`（OpenAI 兼容的本地推理）与 `server/providers/minimax.py` 并列，前端可切换。（本轮复核：`minimax.py` 已实现；`local.py` **尚未实现**。）
- **理由**：这是"个人定制数据永不入库"从**承诺**变成**事实**的唯一路径（脱敏 ≠ 不外发）。
- **技术**：llama.cpp（OpenAI 兼容 `/v1/chat/completions` + GBNF grammar + `seed` + `response_format: json_schema`）/ Ollama / vLLM。
- **本机实测**：RTX 4070 Laptop 8GB + 23.7GB RAM → 可跑 7B/8B Q4_K_M（14B 部分量化）。
- **验收**：切换到 local provider 后，全程无外部大模型请求（可用抓包/日志验证）。
- ⭐ **阶段归属（2026-10-25 订正，原「★P1」造成与 05 号的编号撞车）**：本条在 `docs/spec/05` §八 T4 与 `docs/spec/09` §六均定在 **P4 之后（≥ Week 13，不在 12 周内）**；本页标题里的「P1」是**价值优先级**（不是阶段）⇒ **实施阶段以 `spec/05` §八 / `spec/09` §六为准**。
- ⚠️ **本机实测是 x86 笔记本（RTX 4070 8GB + 23.7GB RAM）**，不是手机；`docs/spec/05` §3 把端侧形态定为 **~0.6B** ⇒ **0.6B 与 7B/8B 差一个数量级**。⇒「做在服务器侧 provider」与「做在手机端」是**两件不同的事**，当前证据只支持前者。

### F-1 配网与绑定 ★P0

- **做什么**：官方 v1.6.0 已关闭三种传统配网（热点/声波/BLE BUFi）→ **走官方 App 配网流程**，工作量归零。但 `STACKCHAN_SERVER_URL` 与 `OTA_URL` 两个 Kconfig **必须覆盖**为我们自己的。
- **依赖技术**：Kconfig 覆盖 + `sdkconfig.defaults.local` overlay（官方 CMake 已支持该机制）。

### F-2 固件 OTA ★P0

- **依赖技术**：官方 `OTA_URL` 改为我们的；分区表沿用官方（nvs / ota_0 / ota_1 / assets 4MB / coredump）。
- **验收**：升级失败自动回滚到上一分区，设备仍可启动。

### F-3 舵机校准 ★P1

- **做什么**：舵机会漂移，需要用户偶尔帮它校。
- **行为**：App 里做 3 步向导（当前角度对齐 → 设定中位 → 测试 ±30°），固件存标定值。
- **验收**：校准后 ±30° 内无卡顿、无顶死。

### F-4 存储健康与清理 ★P1

- **做什么**：表情记忆/对话缓存会占满，需要用户清理。
- **验收**：存储 > 85% 时设备端表达"撑不住了"并提示清理；清理不影响人格与长期记忆。

### G-1 Live Activity ★P0

- **做什么**：持续状态放在"余光"里（锁屏/灵动岛/通知栏）。
- **必须显示**：小栈当前情绪（图形化，不是文字）、在场与否、电量、是否在说话。
- **必须可交互**：紧凑态点按 → 展开 → 可直接发一句话 / 让它安静 / 召回它。

### G-2 App Shortcuts ★P1

- **做什么**：3 条语音短语直达。候选：「问小栈」「小栈安静」「小栈过来」。
- **⚠️ 隐私硬约束**（Apple 官方注记：App Shortcuts 的短语可能被匿名提取用于训练）→ **短语本身必须是通用短语，不得包含用户自定义称呼、人格名、私人信息**。详见 `30` 号。

### G-3 通知 ★P0

- **通知类型**：设备低电量 / 久未互动 / 固件更新可用 / 访客到来 / 它想说话（可静音）/ 校准提醒 / 存储将满。

### G-4 触感反馈 ★P1

- **3 个时刻**：① 它说完话（轻点）② 用户触发它（确认）③ 它要打断你（双轻点）。

## §4 UI 功能要求（不规定样式）

> **本节是给做 UI 的 AI 的直接输入。**
> 每屏给出：**必须呈现的信息** / **必须可做的操作** / **必须覆盖的状态** / **禁止事项**。

### 4.1 App 信息架构（硬性）

> ⭐ **2026-10-25 用户第二次拍板**：主界面 = **控制台（舵机操作）**，聊天**降级为小功能**，
> 设置里必须有 **更新 / 连接 / 网络**。溯源：`docs/spec/07-待拍板清单与防返工机制.md` §3.4b。

```
App
├── Tab 1「控制」        ← 默认落地页 = 舵机控制台
│   ├── 设备卡（脸 + LIVE + 连接状态 + 电量 + 固件版本）
│   ├── 状态 chip 组（心情 / 朝向）
│   ├── 「和它说话」→ 对话页（⭐ 二级页，聊天降级为小功能）
│   ├── 舵机双轴摇杆（拖动即转舵机，脸跟着转）
│   ├── 表情 6 档 chip
│   └── 动作 4 个（点头 / 摇头 / 转圈 / 跳舞）
└── Tab 2「设置」        ← 设备 / 网络 / 陪伴 / 通用
    ├── 子页「连接」（状态 / 信号 / 电量 / 固件 / 重新连接 / 断开 / 舵机校准）
    ├── 子页「更新」（App 版本 + 固件版本 / 检查更新 / 进度 / 16MB 备份说明）
    └── 子页「网络」（Wi-Fi / 云端区域 / 代理 / 自定义端点）
```
- **只有 2 个 Tab**（P-5）。设置就是 Tab 2，不再是独立 Scene。
- ⭐ **对话不是 Tab** —— 它从控制台的「和它说话」进入，是**二级页**（聊天降级为小功能）。
- 层级深度 ≤ 2：Tab → 屏 → 最多一层模态/二级页。
- Live Activity / 通知 / App Shortcuts 是**入口之外**的独立表面，必须单独设计。
- ⭐ **全部表面加起来，一级可见元素 ≤ 12 个**（硬线，见 [`01-功能取舍与主次折叠.md`](01-功能取舍与主次折叠.md) §1/§3）。
- ⭐ **注意力分配**：控制 ~60% / 对话 ~25% / 设置 ~15%。**控制台是唯一主角**，对话是它的小功能。

### 4.2 Tab 1「控制」 —— ⭐ **唯一主角，注意力 ~60%**

> ⭐ **一级可见元素只有 6 个**（见 [`01-功能取舍与主次折叠.md`](01-功能取舍与主次折叠.md) §3）。
> 其余能力**全部折叠**，不得占用一级位置。
> ⭐ 这一屏的主角是**能直接拨的舵机**，不是一排功能按钮 —— 护城河 ★4「物理化情绪」在这里被看见。

**一级可见（6 个）**
1. **设备卡**（顶）—— 一张卡承载：设备脸（镜像实时渲染）+ LIVE 呼吸点 + 连接状态 + 电量 + 固件版本 overlay
   - ⭐ **必须含「身体信号灯带」**：**12 颗（左右各 6 颗）RGB LED** 的实时状态，**每种情绪一枚专属图案**
     ⇒ 依据「**状态走独立通道，不靠文字复述**」原则（Nothing Glyph，取证见 [`86`](../research/86-NothingOS设计方法论取证-SlavaKornilov.md)）
     ⇒ 与 0x14 关键帧通道的 `leftRgbColor` / `rightRgbColor` 同源（[`03` §五](03-通信链路预设与数据契约.md)）
     ⇒ ⭐ **红线**：点阵 / 灯效语言**只属于设备端 320×240**，**禁止**把点阵脸搬进 iOS App（iOS 原生度是硬约束）
2. **状态 chip 组**（一行）：心情 / 朝向
3. **「和它说话」入口行**（内联，不是大 CTA）—— ⭐ 聊天降级为小功能，从这里进二级页
4. **舵机双轴摇杆** —— 圆形 pad + 旋钮，拖动实时转舵机，**脸跟着转**；读数 `水平 ±30° / 垂直 ±30°`，带回正按钮
5. **表情 6 档 chip**（横向滑动）：平静 / 开心 / 兴奋 / 惊讶 / 困倦 / 生气
6. **动作 4 个**：点头 / 摇头 / 转圈 / 跳舞

**折叠层（不可见，但必须存在）**
| 能力 | 收纳位置 | 层级 |
|---|---|---|
| 对话流 / 输入框 / 麦克风键 | 「和它说话」→ 二级页 | Secondary |
| 完整动作库（8 个） | 动作组的「更多」 | Secondary |
| 表情预览（选动作时） | 表情 chip 长按时 | Secondary |
| 让它安静（临时静音） | 设备卡的上下文菜单 | Secondary |
| 召回它（唤醒 + 让它转过来） | 点按设备卡 | Secondary |
| 舵机校准 / 固件更新 / 存储健康 | 设置 > 设备 > 相应子页 | Tertiary |
| 查看它记住的事 | 设置 > 陪伴 > 记住我的事 | Tertiary |

**必须覆盖的状态**
- 设备不在线 → **摇杆禁用但可本地预览**，标注「本地预览 · 等待设备确认」，**不报错**
- 正在聆听 / 正在思考 / 正在说话（三种必须在 UI 上可区分）
- 舵机漂移告警（带「去校准」行动按钮 → 设置 > 设备 > 连接）
- 固件有新版 → 设备卡的版本 chip 出现更新标记，点按进设置 > 设备 > 更新
- 首次使用 / 还没绑定设备 → 引导到配对（一次性流程）

**禁止**
- ❌ **不做功能宫格 / 九宫格**（这是"杂乱"的第一成因）
- ❌ **这一屏不出现第二处强调色**
- ❌ **不把对话流搬回这一屏**（聊天已降级为二级页）
- ❌ **不把舵机做成两排滑杆**（摇杆是主角）

### 4.3 Tab 2「设置」 —— 配角：调参，注意力 ~15%

> ⭐ **折叠规则（硬性）**：
> ① **每组 ≤ 5 行**；② 每行 = **一个动词 + 一个当前值**（不写解释句）；③ 超出 5 行的内容一律收进该组的「更多」二级页；④ **总深度 ≤ 2**；⑤ 设置里**不出现舵机控制的主功能**（那些在 Tab 1）。
> ⭐ **判断法则**：一项功能如果关掉它，产品的说服力不变 → 它就不该出现在设置首页。

**必须包含的分组与行**

| 组 | 行（≤ 5） | 首版原型 |
|---|---|---|
| **设备** | 连接 / 更新 / 语音与音量 / 静音 | ✅ 已画 |
| **网络** | Wi-Fi / 云端服务 / 本地推理 | ✅ 已画 |
| **陪伴** | 主动性 / 记住我的事 / 充电时自动亮屏 | ✅ 已画 |
| **通用** | 通知 / 关于 | ✅ 已画 |
| **人格与声音** | 当前人格 / 人格卡（NFC 导入）/ 音色 / 说话风格 | ⬜ 规格已定，原型未画 |
| **隐私与数据** | 摄像头感知（**必须注明"仅本机判定，图像不上传"**）/ 记忆管理（查看·清除·导出）/ 数据导出 / 边界设定 | ⬜ 规格已定，原型未画 |

**必须覆盖的状态**：权限被拒（摄像头/麦克风/通知）→ 每处都要有解释 + **跳转系统设置的行动按钮**（不是一句"请在设置中开启"）。

### 4.3.1 ⭐ 3D 实时姿态预览（**小尺寸**组件规格）

> 这是一个**组件**，不是一整页。
> ⚠️ **归属已变更（2026-10-25 第二次 IA 拍板）**：原为「嵌在 Tab 2「小栈」页里」；
> 新 IA 下 Tab 2 变成了「设置」⇒ 它只能作为**可选组件**放在 Tab 1「控制」的设备卡位置。
> ⭐ **首版原型用的是 2D 固件真公式脸**（不是 3D 模型）⇒ **3D 预览这一项本轮未销账**，
> 实现成本与是否做，见 `docs/spec/07` §3.4b 的实施欠账登记。

**必须具备**
1. **实时 3D 模型**：显示小栈本体，**能随 yaw / pitch 实时转动**（不是静态图、不是旋转动画）
2. **可直接操控**：在模型上拖拽 → 实时改变头部朝向 → 松手即把角度下发设备
3. **与设备状态双向一致**：设备实际角度变化时，3D 预览同步变化（不能只是 App 单方面的影子）
4. **数值同步**：预览旁边同时显示当前 `yaw°` / `pitch°`（**必须用真实限幅：yaw ±128°、pitch 3°~87°**）
5. **离线降级**：设备不在线时，预览仍可交互（本地预览），但明确标注"本地预览 · 等待设备确认"

**尺寸建议（用户明确要求"小一点"）**
- 预览视口 **宽 160–200 px / 高 180–220 px**（≈ 卡片内并排，不独占整屏）
- 与姿态数值、摇杆并排放在同一行；控制区（摇杆 + 俯仰滑杆 + 转速滑杆）另起一块
- ⚠️ **不要**做成占满整张卡片的巨型预览（旧 PWA 的 remote 页是 `clamp(250px, 36dvh, 420px)`，实测过大）

**技术选项（交由下游实现时二选一）**
| 方案 | 说明 | 权衡 |
|---|---|---|
| **A. three.js 嵌 WKWebView** | 复用旧 PWA 已跑通的 `robot_3d.js` 思路（three.js + 程序化几何体 + 拖拽控制） | ✅ 跨端复用、模型与固件参数同源、**MIT 无许可风险**（three.js MIT）；⚠️ 多一个 WebView 层 |
| B. SwiftUI + SceneKit/ModelIO | 原生实现 | ✅ 无 WebView；但模型与灯光/材质要重做，交互手感要重调 |

**⚠️ 许可红线**：官方 App 目录下的 `stack_chan_model.glb`（3.3 MB）位于 `app/assets/`，而**官方 `app/` 目录没有 LICENSE 文件**（33 号已核实）→ **未经确认不得直接打包该模型**。
→ **必须用方案 A 的程序化几何体**，或先取得官方对模型资产的使用授权。

**性能约束**
- 目标 60 fps；模型仅 1 个；材质尽量少（≤6 个）
- 姿态用阻尼插值（不是每帧重设）→ 避免"机械感"与抖动
- 预览不运行时（页面不可见）**必须停止渲染循环**（省电、避免后台空转）

### 4.4 设置的三个二级页（**更新 / 连接 / 网络**）

> ⭐ **2026-10-25 用户拍板**：设置里**必须**有 **更新 / 连接 / 网络** 三项入口。
> 三者都是**二级页**（总深度 ≤ 2），不是设置首页的一行长文本。

**子页「连接」**
- 必含：连接状态 / 信号强度 / 电量 / 固件版本 / 重新连接 / 断开连接 / 舵机校准入口
- 状态：已连接 / 连接中 / 已断开 / 连接失败（每态都要有可执行的下一步）

**子页「更新」**
- 必含：App 版本 / 固件版本 / 检查更新 / 下载与安装进度
- ⭐ **固件更新前必须先做 16MB 全量备份**（备份路径与结果要显示给用户）
- 状态：有新版 / 已是最新 / 下载中 / 安装中 / 失败可重试

**子页「网络」**
- 必含：Wi-Fi（SSID / 信号 / 切换）/ 云端服务（区域 / 端点）/ 代理 / 自定义端点
- ⭐ 自定义端点**不出现在 Tab 1**（`docs/spec/03` §5 预设项 1 的口径不变，只是落位从独立 Scene 改为设置子页）

### 4.5 设备端 320×240 屏的 UI 功能要求

> 屏幕小，**一屏只表达一件事**。

**必须能显示**
1. **表情主体**（眼 + 嘴 + 可选修饰符）—— 占屏幕主要面积，**不小于 60%**
2. **一行状态字幕**，≤ 12 个汉字，等宽/无衬线，深浅背景都要可读
3. **说话指示**：口型或波形（与音频同步）
4. **隐私指示**：ⓘ **摄像头/麦克风正在工作时必须有明确可见的指示**（这是产品级信任要求，不是可选项）
5. **系统状态**：充电中 / 低电量 / 离线 / 配网中 / 升级中 / 存储将满
6. **触摸反馈**：三区触摸按下时立刻有视觉响应
7. **设置模式**：配网、亮度、音量、舵机校准（文字列表 + 进度）
8. **NFC 提示**："贴一张人格卡"
9. **人脸/在场提示**（可选开启）：它是否"看到你"

**必须能触发**
- 触摸三区 → 三种可配置语义（默认：肯定 / 否定 / 继续）→ 映射到对话里的"嗯 / 不用 / 再说一次"
- 长按 → 菜单（音量、亮度、隐私开关、校准）
- 面部（摄像头）检测到人脸 → 唤醒表情

**必须覆盖的状态**：正常 / 等待 / 睡眠 / 低电量 / 离线 / 配网 / 升级 / 错误 / 校准中

**禁止**
- 设备端不做多行文本、不做列表超过 4 项、不做中文长句
- 不在设备端放可滚动内容（320×240 没有人会滚）
- 不用纯黑底 + 霓虹辉光（违反 F 组底线）

### 4.6 视觉硬约束（给 UI 设计 AI）

**必须遵守**
1. **不画官方小栈形象**：官方形象是 M5Stack 的 IP，我们的 App 图标与品牌必须自有符号（Floor **F43**）。但**展示真实硬件的样子是允许的**（那是我们的设备）。
2. **对比度 ≥ 4.5:1**（正文/图标对背景）
3. **必须支持 `:focus-visible` 焦点环**、必须支持动态字体、必须支持深色模式

6. **设备端保留深色**；App 端跟随系统（浅色/深色都要能看）
7. 禁止：纯黑 `#000` 大面积铺底、霓虹辉光、emoji 充当品牌符号、装饰性渐变网格、居中大段说明文字

## §6 接口与数据格式

### 6.1 设备 ↔ 后端

- 连接：`{server_url}/stackChan/ws?deviceType=StackChan`（沿用官方）
- 端点：`/stackChan/device/user`、`/stackChan/device/info`、`/stackChan/device/unbind`、`/stackChan/apps`
- **本项目扩展需求**（在官方 MsgType 之上新增，避开官方已用编号）：
  | 语义 | 需求 |
  |---|---|
  | 情绪状态上报 | 设备 → 后端：当前情绪字符串（**官方 8 个之一**，见 §6.4）+ 强度 0.0–1.0（用于 Live Activity 与记忆） |
  | 在场状态上报 | 设备 → 后端：在场/离开 + 置信度 |
  | 人格切换 | 后端 → 设备：当前人格的动作/表情偏好与语速 |
  | 韵律动作轨迹 | 后端 → 设备：随 TTS 音频流下发 yaw/pitch/LED 曲线（与 opus 对齐时间轴） |
  | 主动开口 | 后端 → 设备：一条待播报的主动消息 |
  | 隐私指示 | 设备 → 后端：当前摄像头/麦克风开关状态（App 端必须可见） |

### 6.2 App ↔ 后端

REST + WS。必须有的：
- `GET /device/status`（在线/电量/情绪/朝向/人格/健康）

- `POST /device/calibrate`（舵机标定）
- `GET /persona` / `POST /persona/activate` / `POST /persona/import`(NFC 拉取)
- `GET /memory` / `DELETE /memory/{id}` / `POST /memory/export`

### 6.4 情绪标签枚举（端间契约）—— ⭐ **直接复用官方固件协议，零固件改动**

（`firmware/main/stackchan/avatar/avatar/elements/emotion.h`）。

**情绪轴（官方既有，8 个输入字符串 → 6 个枚举）**

| 下发字符串 | 固件内部枚举 | 备注 |
|---|---|---|
| `neutral` | `Emotion::Neutral` | 未识别时的兜底（固件原文告警 `Unknown emotion: %s, using NEUTRAL`） |
| `happy` | `Emotion::Happy` | |
| `laughing` | `Emotion::Happy` | 折叠到 Happy |
| `angry` | `Emotion::Angry` | |
| `sad` | `Emotion::Sad` | |
| `crying` | `Emotion::Sad` | 折叠到 Sad |
| `sleepy` | `Emotion::Sleepy` | **附加行为**：固件自动 `setSpeech("Zzz…")`、停止 idle motion、`pitchServo().moveWithSpeed(0, 80)` 回默认姿态 |
| `doubtful` | `Emotion::Doubt` | |

> **含义**：服务端只要按这 8 个字符串下发，**固件无需任何改动**即可正确表现。
> 我们**不自造**情绪枚举 —— 自造只会多一层映射、多一个出错点。

**装饰轴（官方既有，5 个叠加层）**

`HeartDecorator` ｜ `AngryDecorator` ｜ `SweatDecorator` ｜ `ShyDecorator` ｜ `DizzyDecorator`
（`firmware/main/stackchan/avatar/decorators/decorators.h`，各带 `destroyAfterMs` 生命周期参数）

> 固件的表情能力 = **6 情绪（脸）× 5 装饰（叠加层）**。
> 语义标签体系必须**分两层**，不要拉平成一个 30 项大表。

**我们自加的第三维（官方没有，需自造）**

| 维度 | 取值 | 说明 |
|---|---|---|
| **强度 intensity** | `0.0 – 1.0` | 官方 `SetEmotion` 无强度参数；用于驱动 LED 亮度、动作幅度、语音音量 |
| **动作 motion** | 动作库 ID | 与情绪**解耦**（见 §6.5），官方动作与情绪可自由组合 |

**未知值策略**：后端永远只发这 8 个情绪字符串之一；固件侧对未知值已有兜底（→ Neutral），不会崩。

| 里程碑 | 内容 | 完成判据 |
|---|---|---|

| **M5 有身体** | B-2 韵律驱动轨迹 ｜ **先做 P0：服务端算轨迹 → 走官方 JSON 关键帧通道，零固件改动**；再做 P1 固件端实时 | 音画相关性 > 0.6；连续 30 s 无可见抖动；总线占用 < 20% |

| **M7 有传播** | D-2 NFC 人格卡 | 贴卡换人格，端到端 < 3s |

⚠️ **本表的判据一律是「可观测的产品事实」（在场感 / 连续性 / 表情与语音一致 / 延迟 / 离场行为），**
**不是心理疗效**。理由（`docs/research/81` §十二.2）：同行评议的机器人积极心理教练项目，
其效果评测 `often reports mixed results on improving users' mental health`
⇒ **陪伴机器人能否改善心理健康本身就不确定** ⇒ 写进里程碑或作品集就成了兑现不了的承诺。
