## §0 一句话结论

> **官方已经把「App ↔ 设备 ↔ 云」的三段链路全部实现了，协议是公开的二进制格式。**

## §1 三段链路全景

```
        ┌──────────────────────────┐
        │  我们的后端（fork 官方）  │  :12800
        │  ├─ 替换 AI 层（xiaozhi → MiniMax）
        │  └─ 替换账号层（自建）
        └──────┬────────────┬──────┘
               │            │
   ① WS       │            │  ② WS（长期）
  /stackChan/ws            │  /stackChan/ws
  ?deviceType=StackChan    │  ?deviceType=App&deviceId=<id>
               │            │
        ┌──────┴──────┐  ┌──┴────────────┐
        │  小栈设备     │  │  我们的 iOS App │
        │ (ESP32-S3)   │  │  (SwiftUI)      │
        └─────────────┘  └───────┬─────────┘
                                  │
                    ③ LAN 直连（App 起 WS 服务，设备反向连入）
                       路径 /ws · 20 字节头 · payload = MAC + JSON
```

| 链路 | 承载 | 官方实现位置 | 我们要做什么 |
|---|---|---|---|
| **① 设备 ↔ 云** | WebSocket，音频 + 状态 + 控制 | `firmware/main/hal/hal_ws_avatar.cc:88` | **只换 AI 层**，设备侧零改动 |
| **② App ↔ 云** | WebSocket，`deviceType=App` | `app/lib/app_state.dart:332` | 重写为 SwiftUI，协议照抄 |
| **③ App ↔ 设备（LAN）** | App 起 WebSocket 服务，**设备反向连接** | `app/lib/network/local_area_network_service.dart` | iOS 侧实现 `NWListener` + WS 握手 |

> ⭐ **③ 是关键设计**：**不是设备连 App，而是 App 在局域网开一个 WebSocket 服务，设备主动连进来。**
> ⇒ 手机不需要公网地址、不需要端口映射、不需要在路由器上做设置。
> ⇒ 但 **iOS 后台限制**：`NWListener` 只在 App 前台有效 → 见 §5 的降级策略。

### 1.5.2 三条通路的可行性裁决

| 通路 | 要我们的服务器 | 要改固件 | 要 Wi-Fi | 现状裁决 |
|---|---|---|---|---|
| **BLE 直连** | 不需要 | 不需要 | 不需要 | ⭐ **首选**：UUID 与 JSON 契约两版一致，62 号已交付驱动 `tools/stackchan_ble.py`（离线自检 22/22） |
| **云 WS** | 需要 | 不需要 | 需要 | 设备只认 `47.113.125.164:12800` ⇒ 需**网络层接管**同网段该地址（`http://` 明文，可劫持），或重编译固件（**违反「固件零改动」**） |
| **LAN 直连** | 不需要 | 需要（刷 1.6.0） | 需要 | ⛔ 真机 1.5.1 **不具备** ⇒ 第一版不纳入 |

> ⚠️ **BLE 没有时间轴**：BLE 三路写入是「设定一次姿态」（固件 `updateMotionFromJson` / `updateAvatarFromJson` / `updateNeonLightFromJson`），
> **不是 0x14 关键帧序列**。⇒ 韵律→身体在 BLE 上必须由**主机侧以 25 Hz 连续写**来播放时间轴；
> 设备端是**单槽标志**（`update_flag` 已置位就丢弃后来的写入）⇒ **可能丢帧**，实测前不要当成精确时间轴。
>
> ⭐ **本节结论**：第一版真机验收走 **BLE**（62 号驱动已就绪）；云通道（网络层接管）作为第二阶段；LAN 通道推到刷 1.6.0 之后。

### 2.2 消息类型表（**25 个**，官方 Dart 枚举全量）

`app/lib/model/msg_type.dart` —— 注释明写 *"Matches the raw values used on iOS"*（**官方有 iOS 版，这就是 iOS 实现的直接参考**）。

> ⭐ **订正（2026-10-25 回源核对）**：本节标题原写「24 个」，是**错的**。
> 回源官方 `app/lib/model/msg_type.dart` 逐个数，枚举**正好 25 个成员**
> （`opus` 0x01 → `appLanAddress` 0x1B）⇒ 标题改为 **25**；
> §7 的「24 个 MsgType 及其数值」同步订正。
> **表内容本身是对的**（17 行里合并了同值的多个类型）—— 错的只是标题里的数字。
> 附带查清的一件事：官方枚举**不是 0x00–0x1C 连续** —— **`0x08` 与 `0x0F` 官方空缺**
> （没有对应成员）⇒ 协议表不能按「连续号段」推。

| 值 | 名称 | 方向 | 我们的用途 |
|---|---|---|---|
| `0x01` | `opus` | 双向 | 音频（**控制面裸包**） |
| `0x02` | `jpeg` | 设备→App | 摄像头帧 |
| `0x03` | `controlAvatar` | App→设备 | ⭐ **控制表情** |
| `0x04` | `controlMotion` | App→设备 | ⭐ **控制动作（双舵机）** |
| `0x05` / `0x06` | `onCamera` / `offCamera` | App→设备 | 摄像头开关 |
| `0x07` | `textMessage` | 双向 | ⭐ **文本消息（我们的对话主通道）** |
| `0x09` | `requestCall` | 设备→App | ⭐⭐ **设备主动呼叫 App**（"它要找你"） |
| `0x0A`/`0x0B`/`0x0C` | `refuseCall`/`agreeCall`/`hangupCall` | 双向 | 通话应答 |
| `0x0D` / `0x0E` | `updateDeviceName` / `getDeviceName` | 双向 | 设备名 |
| `0x10` / `0x11` | `ping` / `pong` | 双向 | 保活 + LAN 探测 |
| `0x12` / `0x13` | `onPhoneScreen` / `offPhoneScreen` | 双向 | ⭐ **手机投屏（设备画面推到手机）** |
| `0x14` | `dance` | 双向 | 舞蹈 |

| `0x16` / `0x17` | `deviceOffline` / `deviceOnline` | 云→App | 在线状态 |
| `0x18` / `0x19` | `onAudio` / `offAudio` | 双向 | 音频开关 |
| `0x1A` | `aimedTakePhoto` | App→设备 | 拍照 |
| `0x1B` | `appLanAddress` | App→设备 | ⭐⭐ **告诉设备"我的局域网地址是 X"** → 开启 LAN 直连 |

> ⭐ **`0x1B` 是 LAN 链路的握手**：App 连上服务器后，把自己的局域网 IP + 端口通过 `appLanAddress` 告诉设备，
> 设备随后**直接连 App 的 `LanServerEndpoint`**，此后走 LAN，不再经服务器。

### 2.3 两套帧格式（**不能混用**）

| 通道 | 帧头 | 说明 |
|---|---|---|
| **远程 WS**（经服务器） | **5 字节** `[type:1][length:4 BE][payload]` | `app_state.dart:275-279` |
| **LAN 直连** | **20 字节** `[0x53 0x43][ver:1][type:1][…][session:8 BE][seq:4 BE][len:2 BE][payload]` | `hal/utils/local_network/local_network_protocol.h` |

- LAN 帧头 magic = **`0x53 0x43`（"SC"）**，`HeaderSize = 20`。
- 源码注释：*"LAN frames use a separate 20-byte header and cannot go through the remote WebSocket's 5-byte decoder."*
- 设备侧 `decodeToRemoteFrame()` 会校验包络与目标 MAC，然后**复用同一个 HAL handler**（剥掉 MAC 前缀，返回 `[type:1][length:4][payload]`）。
  ⇒ **对上层是同一套语义**，只是传输层不同。

### 2.4 Payload 数据契约（已实读，2026-10-24 二次核正）

> **payload = `MAC(12 字节 ASCII) + JSON 字符串`**（不是 JSON 对象，也不是 protobuf）

⚠️ **二次核正（第 1 稿把 MAC 写成 12 字节二进制，是错的）**：

| 项 | 正确值 | 证据 |
|---|---|---|
| MAC 前缀 | **12 字节 ASCII**（12 个十六进制字符，无冒号），**不是 6 字节二进制** | 官方 App `avatar.dart`：`final motionJsonString = widget.deviceMac + motionData.toString();` —— 字符串拼接；官方 server `web_socket.go`：`macAddr := string(payload[:12])` —— `string()` 转字符串 |
| 云的行为 | **转发给设备前剥掉 12 字节**，设备收到的是**纯 JSON** | server `readAppClientMessage`：`data := payload[12:]; newMsg := createMessage(msgType, data)` |
| 例外 | `appLanAddress`(0x1B) **没有 MAC 前缀**，是纯 JSON `{port, path, ip[]}` | `local_area_network_service.dart` `LanServerEndpoint.encode()`：`Uint8List.fromList(utf8.encode(jsonEncode(toJson())))` |

| 指令 | JSON 结构（**真实嵌套对象，不是标量**） | 出处 |
|---|---|---|
| 控制动作 | `{"type":"bleMotion","pitchServo":{"angle":N,"speed":500},"yawServo":{"angle":N,"speed":500}}` | `app/lib/model/expression_data.dart` `MotionData.toJson()` |
| 控制表情 | `{"type":"bleAvatar","leftEye":{"x":0,"y":0,"rotation":0,"weight":0,"size":0},"rightEye":{…},"mouth":{…}}` | 同上 `ExpressionData.toJson()` |
| 固件解析 | `update_servo()` 读 `angle` / `speed` / `rotate` / `spring`；`update_feature()` 读 `rotation` / `weight` / `size` | `firmware/main/stackchan/json/json_helper.cpp:41,117` |

⭐ **舵机单位 = 0.1 度**（不是度）：
- 固件限幅 `yaw: Vector2i(-1280, 1280)`、`pitch: Vector2i(30, 870)` → **`yaw ∈ [-128.0°, +128.0°]`、`pitch ∈ [3.0°, 87.0°]`**
  —— 出处 `firmware/main/hal/hal_servo.cpp` `servo_init()`
- App 的 3D 预览同样除以 10：`double clampedYaw = data.yawServo.angle / 10.0;` —— 出处 `app/lib/view/util/stackchan_robot_box.dart`
- 官方 App 的 `MotionDataItem.toJson()`：`if (angle != 0) return {'angle': angle, 'speed': speed};`

⭐ **`ExpressionData` 的 3 个字段与官方 15 维参数结构一致**（leftEye / rightEye / mouth 三个 feature，每个 5 个参数）。

⚠️ **`getAvatarPosture`(0x15) 官方固件没有实现** —— 这推翻了"姿态真值来自设备回读"的原假设：

| 事实 | 证据 |
|---|---|
| 固件 `DataType` 枚举里**没有 0x15** | `firmware/main/hal/hal_ws_avatar.cpp` 枚举：`Opus 0x01 … AppLanAddress 0x1B`，**跳过 0x15** |
| 固件收到 0x15 会落到 `default: break` | 同一文件的 `switch (type)` 末尾 |
| 固件只主动发 6 种消息 | `sendPacket()` 调用点：`AcceptCall` / `DeclineCall` / `EndCall` / `GetDeviceName` / `HeartbeatPong` / `Jpeg` |
| 官方 App 收到 0x15 也只是 `break` | `app/lib/view/popup/motion.dart:72` |
| ⇒ **官方 App 的 3D 预览是「发出即乐观显示」，不是设备真值回读** | |

**影响与对策**：
- 我们若要"设备真实姿态"，必须**自己实现**：① 加固件分支（读 `motion.yawServo().getCurrentAngle()` 回传）—— 但这违反"不改固件"约束；或 ② 走 BLE 读舵机角；或 ③ **接受乐观值**，把"姿态真值"降级为"我命令它转到哪"（并明确标注）。
- **推荐 ③**：不改固件 + 明确文档化。护城河不在姿态读数，而在"身体表达"本身。
- **协议模拟器 `tools/protocol_sim.py` 已按此事实实现**（设备侧遇到 0x15 打印"官方固件未实现，仅本地快照"）。

### 2.5 ⭐ 表情与动作通道契约（2026-10-24 实读固件表情引擎，全文见 53 号）

官方固件的表情引擎只认 **3 个元素 × 5 个字段**，且**远程表情撑不过 2 秒**；而动作通道是一条**完整的关键帧时间轴**。这两条直接决定后端怎么做。

#### 2.5.1 ControlAvatar(0x13) —— 只认 3 个 key

`firmware/main/stackchan/json/json_helper.cpp:41-78` 实际解析的字段**只有**：

```json
{ "leftEye":  { "x": int, "y": int, "rotation": int, "weight": int, "size": int },
  "rightEye": { "x": int, "y": int, "rotation": int, "weight": int, "size": int },
  "mouth":    { "x": int, "y": int, "rotation": int, "weight": int, "size": int } }
```

| 项 | 结论 |
|---|---|
| 量纲 | `x`/`y` ∈ [-100,100]；`rotation` ∈ [0,3600]（0.1 度）；`weight` ∈ [0,100]；`size` ∈ [-100,100] |
| `speechBubble` | ❌ **不被解析** ⇒ 气泡不能走 0x13 |
| `visible` / `emotion` / `ignoreEmotion` | ❌ **不被解析** ⇒ 眼睛显隐与情绪**不能远程控制** |
| 未知 key | ⚠️ ArduinoJson 逐字段判断，**静默忽略，不报错** ⇒ 后端必须有本地 schema 校验 |

#### 2.5.2 ⭐ 远程表情的寿命 ≤ 2 秒（必须保活重发）

| Modifier | 周期 | 覆盖字段 |
|---|---|---|
| `BlinkModifier` | 睁 5200 ms / 闭 200 ms | eye `weight` |
| `IdleExpressionModifier` | 2000 ~ 6000 ms | eye / mouth `position` |
| `BreathModifier` | cycle 6600 ms | `position` |

三者都先检查 `avatar.isModifyLocked()`，但**远程下发路径从不加锁**（`stackchan.h:151` `updateAvatarFromJson` 直接调 `update_from_json`）⇒ 远程表情最长 **2 秒**后被设备自身动画覆盖。

**⇒ 后端硬性要求**：表情必须**保活重发**，周期 < 2000 ms（建议 800 ~ 1200 ms），且保活流量要计入带宽成本模型。

#### 2.5.3 ⭐ DanceSequence(0x14) —— 程序化动作合成的官方通道

`app_avatar.cpp:206` → `parse_sequence_from_json`（`json_helper.cpp:178`）→ `DanceModifier`。

顶层是**数组**，每个元素一个关键帧：

```json
[ { "leftEye":     { "x": -10, "y": 0, "rotation": 0, "weight": 50, "size": 0 },
    "rightEye":    { "x": -10, "y": 0, "rotation": 0, "weight": 50, "size": 0 },
    "mouth":       { "x": 0,   "y": 0, "rotation": 0, "weight": 50, "size": 0 },
    "yawServo":    { "angle": 300,  "speed": 200 },
    "pitchServo":  { "angle": -100, "speed": 200 },
    "leftRgbColor":  "#FF6D60",
    "rightRgbColor": "#8FD3F4",
    "durationMs": 800 } ]
```

| 特性 | 结论 |
|---|---|
| 覆盖范围 | 脸（3 元素）+ 脖子（2 舵机）+ **左右两侧 RGB 灯**（12 颗 LED） |
| modify lock | ✅ **绕过**（`Keyframe::apply()` 直接 set，不查锁）⇒ 不被空闲动画覆盖 |
| 舵机方式 | ⚠️ **已更正**：`moveWithSpeed(angle, speed)` 实际走 **`moveWithSpringParams`**，`speed` 是**弹簧刚度**（`10 + (speed/1000)²×640`），物理写入恒为 `WritePos(id,pos,Time=20,Speed=0)` ⇒ **speed 到不了舵机速度寄存器**（57 号） |
| 插值 | ❌ **无插值**，到 `durationMs` 边界硬切 ⇒ 自制动作必须自己插值加密集关键帧 |
| 打断 | 屏幕点击 → 移除 dance modifier |
| 内置序列 | `Happy`(6 帧) / `Robot`(6) / `Panic`(8) / `LookAround`(5) |

#### 2.5.4 TextMessage(0x07) —— 气泡 + 说话动作 + 情绪

`app_avatar.cpp:186-204`：

| 效果 | 参数 |
|---|---|
| 气泡显示 `"{name} says: {content}"` | 6000 ms（`TimedSpeechModifier`） |
| 嘴开合 | 2000 ms，开合间隔 180 ms（`SpeakingModifier`） |
| 情绪 Happy | 2000 ms —— **仅当内容含 `hello` / `hi` / `love`** |

⚠️ 气泡文案格式**不可定制**。

⚠️ **中文基本渲染不出来**（57 号实测字库 `font_puhui_basic_20_4`：**801 字形 / 184 个汉字**，常用字「你好中文说猫」全部缺字形）⇒ **后端只向 0x07 发 ASCII / emoji**，中文只走 App 端与 TTS 音频。

#### 2.5.5 情绪只有 6 种，且不能远程设置

`emotion.h:11-18`：`Neutral / Happy / Angry / Sad / Doubt / Sleepy`（无惊讶、无兴奋、无失望）。

## §2.6 ⭐ 0x14 载荷上限与分段下发裁决（2026-10-25 固件源码取证）

> 触发：真实 MiniMax TTS（11.68 s）编译出 **292 帧 / 94 042 B**，
> 超过局域网单帧上限 **65 535 B**（`local_network_protocol.h:18` `UINT16_MAX`）⇒ **必须解决，否则设备收不到完整动作**。

### 2.6.1 三条候选解法与裁决

| 候选 | 裁决 | 依据 |
|---|---|---|
| **A. 稀疏/差分编码**（只写变化的字段） | ❌ **不可行** | 固件解析是 `if (kfObj["leftEye"].is<JsonObject>())` —— 缺字段**不是保持上一帧**，而是保留 `Keyframe` **默认值**：`ServoKeyframe(angle=0,speed=0)`、`FeatureKeyframe(weight=0)`、`durationMs=0`，且 `FeatureKeyframe::size` **构造函数里根本没初始化**（未定义值）。⇒ 差分会让舵机归零、眼睛闭死、并引入未初始化内存。 |
| **B. 降帧率 / 缩短时长** | ⚠️ 可用但有代价 | 每帧必须带全 8 键（`tools/stackchan_server.py` 的 `validate_dance_sequence` 已强制），所以**压缩只能压帧数**，压不了单帧大小。25 fps × 11.68 s = 292 帧 ⇒ 降到 15 fps 可落进 65 535 B，但动作会变"跳"。 |
| **C. 切成多段 0x14 按时序下发** | ✅ **采纳为主方案** | 见 2.6.2 |

### 2.6.2 ⭐ 固件对「连续 0x14」的真实行为（**替换，不是排队**）

`firmware/main/apps/app_avatar/app_avatar.cpp:205-214`：

```cpp
GetHAL().onWsDanceData.connect([&](std::string_view data) {
    LvglLockGuard lvgl_lock;
    auto sequence = stackchan::animation::parse_sequence_from_json(data.data());
    if (!sequence.empty()) {
        if (_dance_modifier_id >= 0) {
            GetStackChan().removeModifier(_dance_modifier_id);   // ← 先移除上一段
        }
        _dance_modifier_id = GetStackChan().addModifier(
            std::make_unique<DanceModifier>(sequence));           // ← 再新建
    }
});
```

配套语义：

- `DanceModifier` 构造即 `_timeline.start()`（`modifiers/dance.h:96-99`）
  ⇒ **新段到达的那一瞬间，第 0 帧立刻 apply**，姿态硬切。
- `Timeline::update()` 按每帧 `durationMs` 推进，播完 `requestDestroy()`（`dance.h:103-106`）。
- `Keyframe::apply()` **无条件**应用全部字段（`animation.cpp:17-37`）。

⇒ **裁决**：

1. 段与段之间**没有队列**，后到的段会**顶掉**前一段。
2. 因此服务端必须**按段的总时长精确调度**：第 k 段发完后，等 `Σ durationMs(第k段) − 一帧周期` 再发第 k+1 段。
   早到会硬切，晚到会出现"停顿"。
3. 每段**帧数**不能太大：ArduinoJson 要在 WS 收包线程里反序列化整段 JSON（`LvglLockGuard` 内），
   段过大 ⇒ 解析耗时长 ⇒ 掉帧。**建议单段 ≤ 64 帧 / ≤ 16 KB**（自研设定，非官方值）。
4. **BLE 通道天然分段**（单次写 ≤ 2048 B），不适用本节。

### 2.6.3 对实现的硬性要求

- 服务端 0x14 发送器**必须**是「分段 + 定时调度」，不是「一次发一坨」。
- 段大小 = **实测字节数**，不是估算 ⇒ 分段器必须用**真实序列化后的长度**切。
- 切分后**总时长不变**（各段 `durationMs` 之和 == 原始总时长），否则音画不同步。

## §2.7 ⭐ 音频通道裁决：手机出声，设备做身体（2026-10-25 固件源码取证）

> 完整取证见 [`docs/research/64-固件音频通道取证与谁出声架构裁决.md`](../research/64-固件音频通道取证与谁出声架构裁决.md)。
> 本节只写**结论与对实现的硬性要求**。

### 2.7.1 事实（固件源码，只读）

| 事实 | 出处 |
|---|---|
| `DataType::Opus = 0x01`，但 `case DataType::Opus` **整段被注释** | `hal_ws_avatar.cpp:50` / `:211-220`（1.6.0） |
| 注释引用的 `AudioStreamPacket` / `_audio_service` **在整个固件树里无定义** | `git grep` 全树仅命中那两行注释 |
| `0x18 StartAudioStream` / `0x19 StopAudioStream` 是**空 case**（只 `break`） | `hal_ws_avatar.cpp:383-388` |
| 1.5.1（`94856a7^`）**完全一样**（同样注释、同样空 case） | 1.5.1 的 `hal_ws_avatar.cpp:59/77-78/221-224/392/395` |
| 局域网帧**复用同一个 HAL handler** ⇒ LAN 的 0x01 同样落进注释分支 | `local_network_protocol.h` 的 `decodeToRemoteFrame()` |
| 官方 iOS App **自己在手机上播**：`AVAudioEngine` + `AVAudioPlayerNode`，16 kHz 单声道 | `app/ios/Runner/Utils/NativeBridge.swift:22-30/193-245` |
| 官方 App 的 `0x18/0x19` 是**通话开关**（`_sendAudioControl(.onAudio/.offAudio)`），不是 TTS 音频流 | `app/lib/view/home/avatar.dart:236-258/287` |

### 2.7.2 裁决

| 项 | 结论 |
|---|---|
| **谁出声** | ⭐ **手机**（iOS App 用 `AVAudioEngine` 播 TTS 音频）；**设备不出声** |
| **设备做什么** | 只做**身体**：0x14 关键帧（表情 + 动作 + 嘴型） |
| **是否要 Opus** | ⛔ **不要**。官方用 Opus 是为传**麦克风实时流**；我们的 TTS 是**一次性非实时**音频 ⇒ 直接用 PCM，**零编码器、零第三方库** |
| **音画同步怎么保证** | 关键帧与音频**来自同一段 PCM** ⇒ 时间轴同源；关键帧量化到 25 fps 栅格（`durationMs=40`）⇒ 误差 **≤ 一帧 = 40 ms**（已进 `tools/demo_offline.py` 自检，31 项全绿） |
| **「设备出声」这条需求** | 🚫 **在「官方固件零改动」前提下不可实现**（刷自定义固件已被 `docs/spec/07` §3 排除）⇒ 原任务项作废 |

### 2.7.3 对实现的硬性要求

1. **音频通道不发给设备**：任何情况下都不要试图给设备发 0x01 / 0x18 / 0x19 —— 固件会**静默丢弃**。
2. **App 侧必须能播 PCM16LE / 16 kHz / 单声道**（云端 TTS 的原生输出格式）。
3. **必须有一个共享时间轴**：音频播放时钟与 0x14 动作调度共用同一个起点，
   否则嘴和声音会错位（这是本架构唯一的技术风险点）。
4. **App↔云的音频承载方式尚未拍板**（WS 二进制分片 / HTTP 拉取 / 自研扩展消息类型三选一）
   ⇒ 见 `docs/spec/07` §3 与 64 号 §4.1；**推荐 WS 分片 + 新增扩展类型（设备侧永不使用）**。

### 2.7.4 音画对齐的落地细则（**实测得出，不是设计出来的**）

⚠️ **关键事实**：真实 TTS 的 PCM 长度**不是** 40 ms 栅格的整数倍。
**两次真实 MiniMax TTS 实测**：

| 文本 | 真实音频时长 | 关键帧 | 栅格余数 |
|---|---|---|---|
| 「今天真开心啊！」 | **2350 ms** | 59 帧 = 2360 ms | −10 ms |
| 「今天真开心啊！」（server 链路实时合成） | **1358 ms** | 34 帧 = 1360 ms | −2 ms |

⇒ 量化到 25 fps 必然产生 ≤1 帧（40 ms）的尾部差，**不是偶然，是必然**。

⇒ 由此得到**两条不可省**的实现约束：

| # | 约束 | 理由（实测证据） |
|---|---|---|
| 1 | **音频切片必须「关键帧驱动」**，不能只按固定时间栅格切 | 纯时间栅格切出的末片 `endMs=1358`，**落在关键帧栅格之外** ⇒ 对账必然失败（实测 `tools/audio_chunk.py --plan grid` 报「1 个片段边界不落在关键帧栅格上」，两次真实 TTS 均复现） |
| 2 | **App 侧播放时必须容忍「末片比末帧短」**（1358 ms 音频 vs 1360 ms 动作） | 量化到 25 fps 必然产生 ≤1 帧（40 ms）的尾部差；末帧动作会把嘴多闭 2 ms，**视觉上不可察** |

**机器可判的保证**：`tools/audio_chunk.py`（自检 49 项全绿）已把这件事变成可执行断言：

| 断言 | 含义 |
|---|---|
| `--plan keyframes` 对账误差 **0 ms** | 音画严格同栅格 |
| `--plan grid` 在非栅格音频上**判失败** | 反向证明对账器不是摆设 |
| 每片带 `keyframeStart` / `keyframeEnd` | App 侧可精确知道「这一片音频对应哪几帧动作」 |
| 片段音频字节拼回 == 原始 PCM | 切片不丢帧、不重复 |

**真实闭环实测（2026-10-25 夜间）**：MiniMax TTS → 韵律 → 关键帧 → 切片 → 对账，
音频 43468 B / 1358 ms / 34 帧 → 关键帧驱动切法 **误差 +0 ms**、
**切片字节拼回 == 原始 PCM** ⇒ 端到端通过。

⇒ **生产路径固定用 `--plan keyframes`**（`--plan auto` 在给了 `--keyframes` 时即走它）。

⇒ **5 字节远程帧 / 20 字节 LAN 帧 / 24 MsgType / MAC 前缀剥离 / 舵机 0.1 度限幅 / appLanAddress 格式，全部按官方实现验证通过。**

**本轮修掉的 3 个模拟器 bug（都是真实协议认知错误，值得记住）**：
1. **websockets 15 新 API**：handler 不再传 `path` 参数，路径在 `ws.request.path` —— 旧写法导致 `deviceType` 解析失败，虚拟设备被当成 App。
2. **MAC 前缀是 ASCII 字符串不是二进制** —— 用 `bytes.fromhex()` 导致云剥 12 字节后 JSON 解析失败。
3. **舵机限幅单位** —— 应在 0.1 度线上单位做（±1280 / 30~870），不是在度上做（否则 -60° 会被算成 -12.8°）。

### 7.1 ⭐ 让设备连上来的正确动作（**用户侧**）

设备要能被我们的 App 找到，必须满足：

1. **设备已联网**（连到与电脑/手机**同一个 Wi-Fi**）。
2. 设备已绑定到**我们的服务器**（默认是官方 xiaozhi 服务器 ⇒ 必须改配置指向我们的 `192.168.2.100:12800`）。
3. 若要走 **USB 调试**：插数据线后应出现 **COM3**（`USB JTAG/serial debug unit`）；当前未出现 ⇒ **线没插、插的是充电线、或驱动未装**。
