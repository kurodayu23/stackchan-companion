## 0. 方法论总纲：「好看」不是感觉，是三个可判定的层

### 0.1 本文的立场

「好看」在工程上必须被翻译成**可机械判定的规则**，否则：
1. 评审变成个人偏好之争（用户审美由她把控，但工程需要可复现的尺子）；
2. 好看与「能用」混为一谈——能用的稿子不一定好看，好看的稿子不一定能用；
3. 改稿时无据可依，只能靠感觉返工。

本文不讨论「什么风格更美」，只回答两个问题：**哪些设计特征让人一眼觉得好看（正向判据）**，以及**哪些特征一眼让人觉得丑（负向清单，第 5 节）**。

### 0.2 三层模型

把「好看」拆成三层，每层是一道 **Gate（不通过即退回）**，而不是一个分数。理由：层级错了，色板再对也没用；秩序乱了，材质再好也救不回来。

| 层 | 名称 | 回答的问题 | 判定方式 | 权重 |
| --- | --- | --- | --- | --- |
| **L1** | 结构层 | 能不能一眼看懂？看哪？ | 主动作数、主/次/三级是否量化可分 | **最高（权重 ~50%）** |
| **L2** | 秩序层 | 乱不乱？ | 令牌是否全部落在既定阶梯上（间距/字号/圆角/色） | **中（~30%）** |
| **L3** | 质感层 | 舒不舒服？ | 对比度、动效时长、材质、留白、图形质量 | **低（~20%）** |

> 出处：分层依据 Apple HIG 把「层级」列为排版的首要目的——「Your typographic choices can help you display legible text, **convey an information hierarchy**, communicate important content, and express your brand or style.」（https://developer.apple.com/design/human-interface-guidelines/typography.md ）。L1 权重最高这一分配为本项目的判断，非标准。

### 0.3 一条总公式

> **好看 = 层级可辨（能被一眼排序）× 秩序可预期（能被预判）× 质感统一（不被单点破坏）**

「×」不是加法：任何一项为 0，整体就是 0。实践含义：
- 一张图很美但用户找不到按钮 → L1 失败 → 整体失败，**不要去调色板**；
- 一张图信息清楚但每张卡片圆角都不一样 → L2 失败 → **不要去加阴影**。

### 0.4 评审动作顺序（避免「先挑色再挑结构」）

1. **遮住颜色**（转灰度）：如果层级读不出来 → L1 问题，回到第 1 节改尺寸/字重/间距。
2. **缩到 25%**：如果元素挤成一团 → L2 问题，回到第 2 节改间距/字号。
3. **对比度检测**：如果读着费劲 → L3 问题，回到第 3 节改色板。
4. **动态预览（0.5× 速度）**：如果看着吵 → L3 问题，回到第 4 节改动效。

> 出处：步骤 1、2 是经典的「灰度测试 / squint test」，用「去色—去细节—降速」逐层剥离干扰项。本步骤序列为本项目自定流程，非引用标准。

### 0.5 与上游文档的关系

`02-设计契约与交互规范.md` 给的是**「我们这款产品定了什么」**（令牌值、禁止项、迁移判据）。
本文给的是**「怎么判断好看」**（判据、阈值、反模式、评审清单）。
两者关系：本文的 L2/L3 规则若被采纳，会**回写**为 `02` 第 8 节令牌表的补充判据；本文不替代 `02`，`02` 仍是本项目的唯一设计契约。

## 1. 视觉层级（权重最高）

> 本节回答：一屏之内，怎么让「主要 / 次要 / 三级」一眼可分。

### 1.1 层级的定义：不是「大小」，是「排序」

层级 = 用户在 **0.5 秒内**能给出的元素重要性排序。
Apple HIG 的表述是：「Adjust font weight, size, and color as needed to emphasize important information and **help people visualize hierarchy**」，并要求「maintain the relative hierarchy and visual distinction of text elements **when people adjust text sizes**」。
出处：https://developer.apple.com/design/human-interface-guidelines/typography.md

关键推论：**层级是一个「序」，不是「差」**。设计稿常见错误是把所有元素都放大一点点，结果谁也不突出。正确做法是让第 1 名和第 2 名之间**拉开明确的量级差**，第 3 名和第 2 名之间可以只差一点。

### 1.2 量化判据表（相邻两级必须可辨）

对同屏相邻的两个层级（如「主标题 vs 描述」），下列 9 个维度中**第 1 项必满足，且总共至少满足 2 项**才算层级成立：

| # | 维度 | 主要 vs 次要 | 次要 vs 三级 | 备注 / 依据 |
| --- | --- | --- | --- | --- |
| 1 | **字号比** | **≥ 1.30×** | ≥ 1.15× | 1.30 是「一眼分开」的最小经验值；本项目取值 |
| 2 | 字重比 | ≥ 2 档（600 vs 400） | ≥ 1 档（500 vs 400） | Apple：系统字体从 Ultralight 到 Black 全档位可用，但「avoid light font weights」（typography.md） |
| 3 | 文字对比度 | vs 底 **≥ 7:1** | vs 底 ≥ 4.5:1 | WCAG 2.2 SC 1.4.3，正文 4.5:1、大字 3:1（https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html） |
| 4 | **表面明度差** | **ΔL\* ≥ 6** | ΔL\* ≥ 3 | 只用明度区分层级，见 1.3 |
| 5 | 色相 / 饱和度差 | ΔH ≥ 30° **或** ΔS ≥ 15 | 不作为主要手段 | 色相是「加分项」不是「主手段」，见 1.3 |
| 6 | **留白比**（间距） | 主元素上下留白 ≥ 次元素的 1.5× | ≥ 1.25× | 「免费的层级」，见 1.5 |
| 7 | 位置 | 主在阅读起点（上/左），次偏离 ≤ 1 个栅格单位 | — | Apple：「place the most important items near the top and leading side」（layout.md） |
| 8 | 容器 | 主元素独占一个容器；次元素**不套容器**（或反之） | — | 层级差用「有无容器」表达比用阴影便宜 |
| 9 | 描边 vs 阴影 | 主：无阴影（或极轻）；次：1px 描边 | 描边 1px，透明度 ≥ 12% | 见 4.2「边框优先于重阴影」 |

> **「灰度测试」是最便宜、最有效的层级判据**：把稿子转成灰度，如果主次仍可分 → 层级成立（说明它不依赖颜色）。如果转灰度后主次糊在一起 → 层级是靠颜色硬撑的，色弱用户和打印稿都会失效，改字号/字重/留白。
> Apple 的无障碍要求印证此点：「Avoid relying solely on color to differentiate between objects, indicate interactivity, or communicate essential information」（https://developer.apple.com/design/human-interface-guidelines/color.md ）。

### 1.3 只用明度、不用颜色区分层级：苹果与 Google 的同一套解法

**苹果（iOS / iPadOS）**——背景层级是三档**同色相**、仅明度递进：

| 语义 | API | 层级用途（Apple 原文） |
| --- | --- | --- |
| Primary background | `systemBackground` | Primary for the overall view |
| Secondary background | `secondarySystemBackground` | Secondary for grouping content or elements within the overall view |
| Tertiary background | `tertiarySystemBackground` | Tertiary for grouping content or elements within secondary elements |

出处：https://developer.apple.com/design/human-interface-guidelines/color.md （iOS, iPadOS 章节）

文字层级同理，四档同色相明度递进：`label`（primary content）→ `secondaryLabel` → `tertiaryLabel` → `quaternaryLabel`（"A text label that contains tertiary/quaternary content"）。
出处：同上。

**Google（M3）**——把同一思路做成了**显式的 surface container 阶梯**（以下为 m3.material.io 页面内 CSS 变量 `mio-theme-color-surface-*` 的实测值，Light 主题）：

| 令牌 | 值 | 说明 |
| --- | --- | --- |
| `surface-0` | `#FFFFFF` | 最高层表面 |
| `surface-1` | `#F8F1F6` | |
| `surface-2` | `#F2ECEE` | |
| `surface-3` | `#ECE7E9` | |
| `surface-4` | `#E6E1E3` | |
| `surface-5` | `#E6E1E3` | |
| `surface-variant` | `#E8E0E8` | 弱化表面 |
| `background` | `#FEFBFF` | 画布 |
| `on-surface` | `#1C1B1D` | 主文字 |
| `on-surface-variant` | `#4D4256` | 次文字 |

出处：https://m3.material.io/styles/typography/overview （抓取时页面内联 CSS 变量 `mio-theme-color-*`）

**共同点（这是可以直接抄进本项目的原则）**：
1. 层级**默认用明度**（surface 阶梯）表达，色相留到最后；
2. 文字层级**同色相不同明度**（`on-surface` / `on-surface-variant`），而不是「标题黑 + 描述蓝」；
3. 品牌色**只在一个地方**出现（主按钮 / 状态点 / 焦点环），不铺在每一层表面。

M3 的阴影同样有明确阶梯（同页 CSS 变量 `mio-theme-elevation-*`）：
- `elevation-1`: `0 1px 2px 0 rgb(0 0 0/30%), 0 1px 3px 1px rgb(0 0 0/15%)`
- `elevation-2`: `0 1px 2px 0 rgb(0 0 0/30%), 0 2px 6px 2px rgb(0 0 0/15%)`
- `elevation-3`: `0 1px 3px 0 rgb(0 0 0/30%), 0 4px 8px 3px rgb(0 0 0/15%)`

> 注意：M3 的 elevation 是**双层影**（一层贴地短影 + 一层扩散长影），不是一笔重投影。这是「阴影堆叠看起来廉价」和「阴影看起来干净」的分水岭，见 4.2。

### 1.4 苹果的「Bring to the foreground / De-emphasize」两段式

Apple 的层级方法论可以拆成两个方向相反的动作，**同一屏里必须同时用**：

| 动作 | 含义 | 苹果的具体做法 | 出处 |
| --- | --- | --- | --- |
| **Bring to the foreground**（前景化） | 把**功能层**抬到内容层之上，让它明确是「可操作的界面」而不是「内容」 | iOS 26 起用 **Liquid Glass** 作为「a distinct functional layer for controls and navigation elements — like tab bars and sidebars — **that floats above the content layer**」；材质承担层级，内容层保持安静 | materials.md |
| **De-emphasize**（后退） | 把**内容层**的干扰降到最低：不用玻璃、不用重阴影、不用品牌色 | 「**Don't use Liquid Glass in the content layer**」；内容层用 standard materials（ultra-thin / thin / regular / thick） | materials.md |
| **Sparingly**（克制） | 玻璃只给「真正重要」的功能元素 | 「Use Liquid Glass effects **sparingly**… Limit these effects to the **most important functional elements** in your app」 | materials.md |
| **色彩即强调** | 品牌色只用在需要被看见的地方 | 「Apply color **sparingly**… reserve it for elements that truly benefit from emphasis, such as **status indicators or primary actions**」；「To emphasize primary actions, apply color to the **background rather than to symbols or text**」 | color.md |
| **内容层不与控件撞色** | 内容层的颜色不能和控制层撞色 | 「Make sure your interface maintains sufficient contrast by avoiding **overlap of similar colors in the content layer and controls**」 | color.md |

**对本项目的直接含义**：
- 设备端 320×240 上，**表情层 = 内容层，控件层 = 功能层**。控件用 1px 描边 + 明度更高的表面，**不要**给控件加玻璃/高光。
- iOS 端主按钮是唯一允许「品牌色铺底」的地方；其他按钮一律描边/次级表面。
- 「不用系统默认蓝作为强调色」这条禁止项（`02` 文档 #17）在 Apple 的规则里也能找到依据：Apple 自己说彩色背景下控件应改用单色外观，否则标签难读（color.md）。

### 1.5 负空间（negative space）为什么比「留白」更影响高级感

| 概念 | 定义 | 作用 |
| --- | --- | --- |
| **留白（whitespace）** | 元素**之间**的空白 | 纯粹的分隔，是「减法」 |
| **负空间（negative space）** | 被内容**围出来**的、有形状的空白 | 本身是构图元素，是「加法」 |

Apple HIG 明确把负空间当作**分组手段**，与容器形状、分隔线并列：
「**Group related items** to clearly express related information or functions. For example, you might use **negative space, container shapes, or separator lines** to show which elements are related and which are unrelated.」
出处：https://developer.apple.com/design/human-interface-guidelines/layout.md

**为什么负空间更影响「高级感」**：
1. 负空间形成**形状**，人眼先读形状再读内容；一个被留白切出的干净轮廓，比一堆加边框的盒子更「贵」；
2. 加边框/加阴影是在**元素上**加信息，负空间是在**版面里**做减法——前者越加越吵，后者越减越贵；
3. 负空间天然承载层级（「Apple HIG：indented items are perceived as subordinate」，layout.md），不需要额外加粗或加色。

**量化建议（本项目取值）**

| 指标 | 设备端 320×240 | iOS 端 | 依据 |
| --- | --- | --- | --- |
| 页面边距 | 10–18 px（现有原型 10–18） | 20 pt | `02` 文档版式规则；iOS 页面边距取 20 |
| 卡片与卡片间距 | 8–12 px | 16 pt | 4/8/12 节奏 |
| **空白面积占比（空/整屏）** | **≥ 40%** | **≥ 35%**（首页 40–55%） | 本项目设定 |
| 元素之间的「呼吸缝」 | ≥ 字号 × 1.0 | ≥ 字号 × 1.25 | 本项目设定 |
| 主元素上方留白 | ≥ 下方留白的 1.5× | 同 | 视觉重心上移，符合阅读顺序 |

设备端现有实算：`.app-card` 284×156 于 320×240 画布上 → 占用 44304 px² / 76800 px² = **57.7%**，空白 **42.3%**，刚好落在 ≥40% 线上。
出处：`02` 文档 1.3 节（`v2/prototype.html` 的 `.app-card` 尺寸）。

**负空间的反模式**：用「负空间 = 元素之间的缝」来做层级是最常见的偷懒——缝一样宽就等于没有层级。层级要靠**不等宽的缝**（主元素周围的缝更大）来表达。

### 1.6 「一个画面只保留一个主要动作」的可执行判据

原始表述来自本项目设计哲学：「**每个画面只保留一个主要动作。**」（`02` 文档 6.1 节，引 `v2/DESIGN.md:5`）
把它变成**能机械判定**的四条：

| # | 判据 | 阈值 | 怎么查 |
| --- | --- | --- | --- |
| **P1** | 同屏 **filled（填充品牌色）按钮**数量 | **≤ 1** | 数「背景色 = accent」的控件 |
| **P2** | 同屏「视觉重量最高的可点击元素」 | **唯一**，且 ≥ 次高者的 **1.8×** | 视觉重量 ≈ 元素面积 × 对比度增量；操作上可用「把该元素填成黑、其余填成白，看是否一眼锁定」 |
| **P3** | 主按钮与次要按钮的**面积比** | ≥ 1.5×（高 ≥ 1.25×） | 主按钮至少高 44 pt / 设备端 44 px |
| **P4** | 同屏**强调色填充区域**占内容区面积 | ≤ 5%（iOS）/ ≤ 8%（设备端） | 见 3.5「大面积中性 + 极小面积强调」 |

**P1 的依据**：Apple color.md —— 品牌色「reserve it for elements that truly benefit from emphasis, such as status indicators or primary actions」，且「Refrain from adding color to the background of **multiple controls**」。
**P4 的依据**：本项目 `02` 文档设计哲学「粉色只用于选中态、主按钮和少量强调，**不再铺满每一层表面**」（引 `v2/DESIGN.md:36`）。

**反例自查**：一屏出现「开始聊天（filled）+ 上传照片（filled）+ 换表情（filled）」→ 违反 P1，必须把后两个降级为描边图标按钮或文字按钮。

### 1.7 渐进披露：本项目「一次只显示一个」的技术出处

Apple：「**Use progressive disclosure to make layouts cleaner and easier to interact with.** An interface with too much content and too many choices makes it harder to find information quickly, and harder to understand the choices that are available.」
出处：https://developer.apple.com/design/human-interface-guidelines/layout.md

这正是本项目否决六宫格、改为「一次只显示一张功能卡」的**通用设计依据**，而不仅仅是审美偏好：
- 设备端 320×240：横向放不下两张 → 轮播；
- iOS 端：不用 8 个 Tab（`02` 禁止项 #16），改成「吉祥物 + 单一主行动 + 下方功能条/分区」。

> **注意**：渐进披露≠藏功能。Apple 的另一条约束是「All key actions have visible entry points」（`02` 文档 S10，引 `v1/DESIGN.md:6`）。渐进披露收纳的是**次级内容**，不是**主行动**。

## 2. 排版与栅格

### 2.1 iOS 端字号阶梯（SF Pro / Dynamic Type）

Apple HIG 的系统文本样式是「字体粗细 + 字号 + 行高」的固定组合，且随 Dynamic Type 等比缩放。下列为 **Large（默认档）** 的完整阶梯：

| Style | Weight | Size (pt) | Leading (pt) | 行高比 | Emphasized | 本项目用途 |
| --- | --- | --- | --- | --- | --- | --- |
| Large Title | Regular | **34** | 41 | 1.21 | Bold | 全屏页大标题（设置/关于/个人主页） |
| Title 1 | Regular | 28 | 34 | 1.21 | Bold | 页面主标题 / 模态标题 |
| Title 2 | Regular | 22 | 28 | 1.27 | Bold | 区块主标题、卡片标题 |
| Title 3 | Regular | 20 | 25 | 1.25 | Semibold | 列表分组标题、小卡标题 |
| Headline | Semibold | 17 | 22 | 1.29 | Semibold | 列表行主文本、按钮文字 |
| Body | Regular | **17** | 22 | 1.29 | Semibold | 正文（**默认字号 = 17 pt**） |

1. **能用系统 text style 就不要自定义字号**——自动获得 Dynamic Type 与「放大时优先放大重要内容」的行为（Apple：「Prioritize important content when responding to text-size changes」）。
2. **层级在放大后必须保持**：「maintain the relative hierarchy and visual distinction of text elements when people adjust text sizes」。
3. **自绘稿必须手动补 tracking**：Apple 明确「In a running app, the system font **dynamically adjusts tracking at every point size**」，所以做视觉稿时必须自己加，否则稿子和真机不一致。

### 2.3 设备端 320×240 的最小可读字号

#### 已知事实
- 屏幕分辨率 **320×240**，驱动 ILI9342C / ILI9342E（2026.8.7 起改为 ILI9342E）。
  出处：https://docs.m5stack.com/en/core/CoreS3 （PinMap → LCD Screen：「LCD Pixels: 320x240」）
- Apple iOS 最小字号 11 pt（typography.md，见 2.1）。

#### 推导（**含未验证假设**）
**未验证假设 A**：屏幕物理对角线 **2.0 英寸** → 对角像素 = √(320²+240²) = 400 → **PPI ≈ 200**。
> 本轮抓取 m5stack 官方页时中段被截断，**未能取到官方标注的屏幕尺寸**，此假设需实测：量屏对角线（cm）→ PPI = 40 / 对角线(cm)。

**视觉角度法**（字高 → 张角 → 视距）：

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| 视距 D | 500 mm | 桌面机器人的典型视距 40–60 cm，取中值 |
| 舒适阅读所需字高张角 | 16 弧分 (0.267°) | 「可读」的下限；5 弧分为「勉强可辨」 |
| 字高 h = D × θ(rad) | 2.32 mm（舒适）/ 0.73 mm（极限） | |
| 换算到 px @200 PPI | **18.3 px（舒适）/ 5.7 px（极限）** | 1 mm = 7.87 px |
| 中文修正 | ×1.0（汉字比拉丁字母笔画更密，需更大字高） | clreq：汉字字面率较小，小字号需补偿线幅 |

**结论（设备端字号下限）**：

| 角色 | 建议字号 (px @320×240) | 行高 | 依据 |
| --- | --- | --- | --- |
| 计时数字 / 超大展示 | 28–32 | 1.2 | 唯一允许的「大字」，1–2 处/屏 |
| 页面标题 | 21–24 | 1.3 | |
| 卡片标题 | 18 | 1.33 | |
| 引语 / 重点正文 | 15–16 | 1.45 | |
| **正文** | **13–14** | **1.5** | 中文行高下限，见 2.5 |
| 描述 / 次要 | 12 | 1.45 | |
| **元数据（时间戳等）** | **11** | 1.4 | 绝对下限 |
| < 11 px | **禁止** | — | 低于 Apple iOS 最小 11pt 的等效线幅 |

**交叉验证**：Apple 的 11pt（= 3.88 mm）在 500 mm 视距下约 25.6 弧分；设备端 14 px @200 PPI = 1.78 mm ≈ 11.7 弧分 ≈ iPhone 最小字号的 **46%**。
> **这个比值本身就是一条设计结论**：320×240 的设备屏在物理上**承载不了长文案**，只能承载「一个标题 + 一行短句 + 一个动作」。
> 这就是「一次只显示一个功能」在**排版层面**的必然性，而不只是审美偏好。

**对现有原型（`v2/prototype.html`）的体检结论（建议修订项，待回写 `02` 文档）**：
现状 9 px（落款/设置值）、10 px（状态/次要文案）、10.5 px（`card-desc`）**低于 11 px 绝对下限**。

| 现状 | 建议 | 处理 |
| --- | --- | --- |
| 9 px 落款/设置值 | 11 px | 提上来（11 px 仍在 320 宽内排得下） |
| 10 px 状态/次要文案 | 11–12 px | 提上来 |
| 10.5 px `card-desc` | 12 px | 提上来 |
| 13/14 px 正文 | 13–14 px | 保持 |
| 16 px 导航标题 | 18 px | 提到卡片标题档 |
| 21 px `card-title` | 21 px | 保持 |
| 24 px 计时数字 | 24–28 px | 保持 |

> ⚠️ 上述提字号会挤压现有 284×156 卡片的信息量，需连带减少每屏信息项（这与「渐进披露」方向一致，不是倒退）。

### 2.4 中英混排的差异（中文排版硬规则）

出处：W3C《中文排版需求》（Chinese Text Layout Requirements, clreq）中文版 https://github.com/w3c/clreq （`zh/index.html`，下同）

| 规则 | clreq 原文要点 | 本项目落地 |
| --- | --- | --- |
| **中西之间的空隙** | 「漢字與西文字母、數字間使用**四分之一個漢字寬**的字距或空白」 | iOS/SwiftUI 由系统排版自动处理；设备端若手写排版需自行留 1/4 em |

### 2.5 中文行高为什么必须比英文大

**clreq 的硬数据**：
> 「版心之行距多半介於**文字尺寸之 50%–100%** 之間，當行長較短、或文字尺寸較小時，行距設定也會相對較小。反之，行距一般不會超過文字尺寸。」
> 「**行高＝文字尺寸÷2＋行距＋文字尺寸÷2＝文字尺寸＋行距**」，「**行距＝行高－文字尺寸**」
> 出处：`zh/index.html:281, :286, :287`

推导：行高 = 字号 + 行距 = 字号 × (1 + 50%) ～ 字号 × (1 + 100%) = **1.5× ～ 2.0× 字号**。

**对比 Apple SF Pro 的行高比**（见 2.1 表）：正文 17/22 = **1.29**、说明 13/18 = 1.38、脚注 12/16 = 1.33、最小 11/13 = 1.18。

> **结论：中文行高下限 = 英文的 1.5 / 1.29 ≈ 1.16 倍，即中文行高要比英文大 15%–25%；中文长文建议 1.7–1.8×。**
> **本项目取值：中文正文行高 = 字号 × 1.5（下限），长段引语 = 字号 × 1.65；标题 = 字号 × 1.25–1.35（标题短，不需要大行高）。**

### 2.6 间距系统 4/8/12/16/20/24/32 与字号的配合

**统一间距档位**：`4 / 8 / 12 / 16 / 20 / 24 / 32`（本项目已沿用，`02` 文档 S3）

**节奏规则 R1：相邻间距比 ≤ 2:1**。`4 → 8 → 16 → 32` 构成一条等比链；`12 → 20` 是补充档，插入时不得打断链条（12 的下一个必须是 24，不允许 16 和 20 混着当同一级用）。

**节奏规则 R2：间距与字号绑定**（决定「呼吸感」）：

| 文本角色 | 字号 | 中文行高 | 该段落**之后**的间距 | 该元素**内部**内边距 |
| --- | --- | --- | --- | --- |
| Large Title 34 | 34 | 45 | 24 | — |
| Title 28 | 28 | 38 | 16 | — |
| Title 2 22 | 22 | 30 | 16 | 16 |
| Title 3 20 | 20 | 26 | 12 | 12 |
| Headline / Body 17 | 17 | 26 | 16 | 16 |
| Subhead 15 | 15 | 23 | 12 | 12 |
| Footnote 13 | 13 | 20 | 8 | 8 |
| Caption 11–12 | 11–12 | 17 | 8 | 8 |

**节奏规则 R3：段间距 > 字间距**。段后间距至少是行高的 0.5 倍，否则段落会糊成一片。

**节奏规则 R4：容器内边距 ≥ 该容器内最大字号的 0.75 倍**。32 pt 标题的卡片，内边距不能只有 8 pt。

### 2.7 栅格

#### 设备端 320×240（8 栏）
```
边距 12 | 30 | 8 | 30 | 8 | 30 | 8 | 30 | 8 | 30 | 8 | 30 | 8 | 30 | 边距 12
```
验算：12 + 8×30 + 7×8 + 12 = 12 + 240 + 56 + 12 = **320** ✓
- 列宽 30 px，gutter 8 px，边距 12 px
- **不设多列网格 UI**（一次只显示一张功能卡），栅格只用于内部对齐：图标容器 92 px ≈ 3 栏 + gutter；文本区 168 px ≈ 5 栏 + gutter
- 现有 `.app-card` 284×156 的内边距 24/22 → **内边距 ≈ 2 栏**，符合 R4（标题 21 px × 0.75 ≈ 16 px，取 24 更宽松）

#### iOS 端
- 页面左右边距 **20 pt**；卡片间距 16 pt；卡片内边距 20 pt（沿用 `02` 文档 L4）
- 内容最大宽度 **480 pt**，超出居中（iPad）
- 不做固定列数栅格（iOS 用 `LayoutGuide` / `safeArea` 自适应），但**间距必须落在 4/8/12/16/20/24/32 之内**——Apple：「**Use consistent spacing.** When content isn’t consistently spaced, it no longer looks like a grid and it’s harder for people to scan.」（layout.md）
- 列表行高 ≥ 56 pt，图标行 ≥ 60 pt（`02` 文档 L7）

## 3. 色彩系统

### 3.1 一个完整色板必须有的 12 层

| # | 语义层 | 作用 | 缺了会怎样 |
| --- | --- | --- | --- |
| 1 | `canvas` | 页面底色（最外层） | 内容没有「舞台」，页面像贴纸 |
| 2 | `surface` | 卡片/内容块表面 | 层级塌陷 |
| 3 | `surface.secondary` | 次级分组表面（列表分组、设置分区） | 分组只能靠描边 |
| 4 | `surface.elevated` | 浮层（弹窗、抽屉、下拉） | 浮层和卡片同色，弹窗「浮不起来」 |
| 5 | `border` | 1px 描边（分隔与轮廓） | 只能靠阴影，轻薄感丢失 |
| 6 | `ink.primary` | 主文字 | — |
| 7 | `ink.secondary` | 次要文字 | — |
| 8 | `ink.tertiary` | 三级文字（时间戳、落款、禁用说明） | — |
| 9 | `accent` | 品牌强调（主按钮、焦点环、选中态、图标） | 产品没有品牌记忆点 |
| 10 | `accent.tint` / `accent.container` | 强调色容器（选中底、图标底） | 强调色只能大面积铺，反而廉价 |
| 11 | `success / warning / danger` | 语义状态色 | 状态只能靠文字描述 |
| 12 | `on-*`（压色文字） | 铺在强调色/状态色**上面**的文字色 | 白字压不住浅粉，对比度崩 |

> **第 12 项是最常被漏掉的一层。** 「主色 = 品牌粉 + 白字」是最容易犯的错：浅粉上白字对比度必然不足（见 3.6 实测）。
> M3 的做法值得抄：每个主色都配一个 `on-primary`（压在其上的文字色）。出处：https://m3.material.io/styles/typography/overview （页面内 `mio-theme-color-primary` / `--mio-theme-color-on-primary` 变量，Light 主题 `#6442d6` / `#FFFFFF`）。

### 3.2 WCAG 数值，以及「陪伴型 App 能不能放宽」

**WCAG 2.2 的硬数值**（SC 1.4.3 Contrast (Minimum)，Level AA）：

| 场景 | 要求 | 原文依据 |
| --- | --- | --- |
| 正文文本 | **≥ 4.5:1** | 「The visual presentation of text and images of text has a contrast ratio of at least 4.5:1」 |
| 大字 | **≥ 3:1** | 「Large-scale text and images of large-scale text have a contrast ratio of at least 3:1」 |
| 大字定义 | ≥ 18 pt，或 ≥ 14 pt 粗体 | 「18 point text or 14 point bold text is judged to be large enough」 |
| 装饰 / 失效控件 / Logo | 无要求 | 「pure decoration, that are not visible to anyone… have no contrast requirement」 |

出处：https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html （更新日期 2026-09-06）
**UI 组件（非文字）** 另见 SC 1.4.11 Non-text Contrast，阈值同为 **3:1**（本轮未逐条抓取该页，标记为**未验证**，但数值与业界通行一致）。

**判断：陪伴型 App 不能放宽。**

理由（按权重排序）：
1. **物理约束比审美偏好硬**：设备端 320×240 只有 400 px 对角线，任何「柔和低对比」在小屏上直接变成「看不清」。见 2.3 的角度推导。
2. **使用场景是「瞥一眼」**：桌面陪伴机器人的交互是余光接收，不是专注阅读。0.5 秒读不懂 = 装饰。
3. **这是开源求职作品**：会被无障碍工具、被面试官、被其他开发者用 APCA / axe / Lighthouse 扫。AA 不合格的色板是硬伤。
4. **「陪伴感」不等于「低对比」**：陪伴感来自**暖色温 + 柔和形状 + 动效节奏**，不来自「字看不清」。想要更柔，正确手段是**降饱和度**（S 64.5% → 45%）而不是降明度差。

**唯一允许的放宽**：三级文字在**大字**（≥18 pt / ≥14 pt bold）下可用 3:1 —— 这是 WCAG 自身的大字豁免，不是额外让步。

**建议的「陪伴感而不牺牲对比度」配方**：
| 想要的效果 | 正确手段 | 错误手段 |
| --- | --- | --- |
| 更柔和 | 降饱和度（S ↓）、加一点同色相 | 降文字与底色的明度差 |
| 更亲近 | 暖色温的 canvas、圆角、表情 | 降低文字对比度 |
| 更轻盈 | 1px 描边 + 大留白 | 去掉描边用重阴影 |
| 更「高级」 | 减少颜色数量 | 加渐变、加材质 |

### 3.3 浅色 / 深色双主题：一一对应，但不是「加黑」

**角色对应原则**（本项目采用）：
> **每个语义角色在两个主题下各有一个值，角色关系不变；颜色关系可变。**

即 `canvas↔canvas`、`surface↔surface`、`ink.primary↔ink.primary`……但**具体色值不要求同色相**。

**本项目的实测结果**：浅色 canvas `#F1DFE5`（H=340，暖粉）→ 深色 canvas `#0E1117`（H=220，冷灰蓝）。**色相变了 120°。**
这正说明：**深色主题不是浅色主题的负片或「加黑」**，而是重新挑了一组同角色、不同气候的色板。

**「浮起来的层」的明度方向**（关键规则）：
- 浅色主题：越浮起 → 越亮（surface L\* 98.8 → elevated L\* 100），底色 canvas 最"重"（L\* 90.4）。
- 深色主题：越浮起 → 越亮（surface L\* 12.7 → elevated L\* 20.3）。
- （L\* 为 CIE L\*，由 WCAG 相对亮度 Y 换算：L\* = 116·Y^(1/3) − 16；实测值见第 7 节色板表。）
- **统一规则：`surface` 是基准层，`elevated` 永远比 `surface` 更「远离主题底色」**；canvas 永远是离底色最近的一层。

| `on-surface-variant` | `#4D4256` | — |

出处：https://m3.material.io/styles/typography/overview （`mio-theme-color-surface-*`）
> ⚠️ **未验证**：M3 深色主题下同一组 surface 编号的明度方向是否反转（本轮只抓到 Light 主题变量）。已知 M3 的设计意图是「编号 = 离主题底色的距离」，因此深色下编号越大应越亮——**本轮未取到深色值，落地前请核对**。

**深色主题的两条硬规则**：
1. **不用纯黑 `#000000`**。纯黑 + 高亮白字会造成光晕（halation），长时间看刺眼。本项目用 `#0E1117`（L\* 5.0）。
   例外：设备端 OLED 省电场景下可单独用 `#000000` 作为**画布**（此时文字相应降到 `#F5F7FA` 而非纯白，避免光晕）。
2. **深色下的品牌色要提亮**。浅色的 `#D94F78`（L\* 53.7）在深底上偏暗；深色主题改用 `#F2A0B8`（L\* 74.5），实测在 `#1C212B` 上 8.06:1。

### 3.4 强调色数量上限，以及「颜色 / 形状 / 图标 / 文字」怎么分工

**数量上限**：

| 范围 | 上限 | 理由 |
| --- | --- | --- |
| 全局品牌强调色 | **1** 个（`accent`） | Apple：「reserve it for elements that truly benefit from emphasis, such as status indicators or **primary actions**」 |
| 同屏「有色」元素总数 | **≤ 3**（accent + 1 功能色 + 1 状态色） | 超过 3 个，眼睛无法建立优先级 |
| 同屏「功能强调色」 | **≤ 1** | 上游禁止项 #25（`02` 文档） |
| 同屏 filled（品牌色填充）控件 | **≤ 1** | 见 1.6 的 P1 |

**四类信息的分工表**（这是避免「什么都用颜色表达」的关键）：

| 要表达的信息 | 用什么 | 不要用什么 |
| --- | --- | --- |
| **状态**（在线 / 离线 / 成功 / 失败） | 颜色 + **形状或图标**（双通道） | 只用颜色 |
| **选中 / 当前项** | 颜色 + 位置/形状 | 只用颜色 |
| **动作**（可点击） | 图标 + 文字 | 只用颜色 |
| **类别 / 分区** | 容器形状 + 标题文字 | 彩虹配色 |
| **信息本身** | 文字 | 任何装饰 |

> **Apple 的无障碍条款是这条表的出处**：「**Avoid relying solely on color** to differentiate between objects, indicate interactivity, or communicate essential information… you can use text labels or glyph shapes to identify objects or states.」（https://developer.apple.com/design/human-interface-guidelines/color.md ）
> 同时也解释了为什么 WCAG 刻意规定：**颜色在计算对比度时「is not a key factor」**——判定可读性只看明暗，不看色相（contrast-minimum.html 的 Intent 段：「the contrast is calculated in such a way that color (hue) is not a key factor」）。这正是 1.3 节「只用明度做层级」的规范依据。

### 3.5 浅粉 / 暖色系当主色的风险与化解

**三个真实风险（附量化）**：

| 风险 | 机制 | 量化判据 |
| --- | --- | --- |
| **甜腻 / 糖果感** | 大面积**高明度 + 高饱和**粉 = 儿童玩具 / 美妆包装 | 大面积底色必须 **L\* ≥ 90 且 S ≤ 40%** |
| **廉价感** | 高饱和粉 + 渐变 + 圆角 + emoji，四件套一齐出现 | 见第 5 节反模式清单 |
| **对比度不足** | 粉的明度高，白字压不住；反过来粉字压在浅底上也不够 | 实测必须 ≥ 4.5:1，见 3.6 |

**量化对照（实测）**：

| 颜色 | H | S | L (HSL) | **L\* (CIE)** | 判断 |
| --- | --- | --- | --- | --- | --- |
| 本项目 canvas `#F1DFE5` | 340 | **39.1%** | 91% | **90.4** | ✅ 大面积底色合格（S ≤ 40%，L\* ≥ 90） |
| 上游禁止的 `#FF6699`（「草莓牛奶」式整屏底） | 330 | **100%** | 70% | 64.2 | ❌ 饱和度是本项目的 2.6 倍 → 必甜腻 |
| 本项目 accent `#D94F78` | 342 | 64.5% | 58% | 53.7 | ⚠️ 饱和度偏高，**必须限面积** |
| 本项目 accent.fill `#C23A64` | 341 | 54.0% | 49.4% | 46.2 | ✅ 压白字用（L\* 更低，实测 5.14:1） |

> 上游禁止项 #1「不使用高饱和 `#FF6699` 作为整屏底色」，量化后就是这条：**大面积底色 S ≤ 40%，L\* ≥ 90**。`#FF6699` 的 S = 100%，是本项目 canvas 的 2.6 倍——这就是「草莓牛奶」被否的真正原因（`02` 文档 6.2 节：「仍容易回到糖果玩具感」）。

**化解公式：大面积中性 + 极小面积强调**

| 场景 | 底色 | 强调 | 强调占比上限 |
| --- | --- | --- | --- |
| iOS 首页 | `canvas` #F1DFE5 + `surface` #FFFBF8（占大面积的 85%+） | accent 只在主按钮 + 焦点环 | **≤ 5%** 内容区面积 |
| iOS 功能详情 | `surface` 近白 | accent 只在图标容器 tint + 状态点 | ≤ 5% |
| 设备端 Launcher | `#0E1117` 画布 | 每个功能卡的 icon-wrap tint | 单卡 ≤ 8% |
| 设备端游戏/相册 | 深色舞台 | accent 只在分数/计时数字 | ≤ 5% |

**执行方式**：
1. 底色永远是**中性或极低饱和**的暖色（canvas S=39.1% 已是上限）；
2. 强调色**永远不铺满表面**，只做「点」（按钮、图标底、状态点）；
3. 需要一块品牌色区域时，用 `accent.container`（S 74.2%、L 93.9% 的浅粉）而不是 `accent` 本色；
4. 品牌粉**只出现在 3 个地方**：主按钮填充、焦点环、当前状态点。

## 4. 形状、材质、动效

### 4.1 圆角档位体系

**外部锚点：M3 的 shape scale**（实测自 material-web v0.192 令牌文件）：

| 令牌 | 值 | 用途 |
| --- | --- | --- |
| `corner-none` | 0 | 直线元素、分隔线 |
| `corner-extra-small` | 4 px | 极小元素（标签 chip、小图标底） |
| `corner-small` | 8 px | 小控件（图标容器、小按钮） |
| `corner-medium` | 12 px | 按钮 / 输入框 |
| `corner-large` | 16 px | 卡片 / tile |
| `corner-extra-large` | 28 px | 大容器（对话框、底部抽屉、图标底） |
| `corner-full` | 9999 px | 胶囊 / 圆形 / 头像 |

出处：https://raw.githubusercontent.com/material-components/material-web/main/tokens/versions/v0_192/_md-sys-shape.scss （Apache-2.0，Google Material 3 v0.192）

**本项目的圆角阶梯（建议）**：

| 令牌 | 设备端 (px) | iOS 端 (pt) | 对应元素 |
| --- | --- | --- | --- |
| `radius.xs` | 4 | 4 | 小图标底、页点 |
| `radius.sm` | 8 | 8 | 图标容器（92 px 的用 24，见下）、小按钮 |
| `radius.control` | 12 | **12** | 按钮、输入框、胶囊标签 |
| `radius.tile` | 16 | **16** | 功能 tile、列表分组块 |
| `radius.card` | 20 | **20** | 卡片、主卡 |
| `radius.sheet` | 24 | 24 | 底部抽屉、对话框 |
| `radius.full` | 999 | 999 | 胶囊、头像、圆形状态点 |

**为什么 iOS 上 12–16 pt 比 24 pt 更「原生」**（三条理由）：
1. **圆角不承载层级，只承载形状**。层级由字号/字重/明度差/留白承担（见第 1 节）。当圆角被放大到 24 pt，它就变成一种「强调」信号，于是页面里每个 24 pt 圆角都在抢注意力——结果是**没有强调**。
2. **圆角半径应与容器尺寸成比例，而不是绝对值递增**。经验公式：`radius ≈ min(容器短边 × 0.10, 20 pt)`。
   - 56 pt 的列表行 → 5.6 → 取 8–10
   - 160 pt 的卡片 → 16 → 取 16
   - 300 pt 的大面板 → 30 → **但上限 20–24**，再大就变成「玩具」
   - **推论：圆角有天花板（20–24 pt），尺寸小的时候反而应该更小。**上游原型把 `.app-card` 放大到 24 px，在 284×156 的卡上比例偏高（24/156 = 15%），这是「显得软、显得玩具」的主要来源之一（另见 `02` 文档 1.4 节三代对比中「圆角 14–27」一栏）。
3. **与 iOS 系统形状语言一致**。iOS 的分组列表单元格、按钮、动作面板使用的是**中等圆角**，大圆角是 Apple 自己保留给「贴纸式」大卡片的。⚠️ **未验证**：Apple 未在公开文档中逐项列出各系统组件的圆角数值；此处为基于「M3 shape scale + 上游 `02` 文档已采用值」的设计判断，落地前建议用 Apple Design Resources 的 iOS 模板实测校准。

**嵌套圆角的「父子同心」规则**：
> **外层圆角 = 内层圆角 + 内边距**（同心圆弧）

| 外层 | 内边距 | 内层圆角 |
| --- | --- | --- |
| 20（卡片） | 12 | 8 |
| 20（卡片） | 16 | 4 |
| 24（sheet） | 16 | 8 |
| 24（sheet） | 12 | 12 |

验算：外圆角中心在外边缘内 20 px 处；内元素边缘在外边缘内 12 px 处。要让两段圆弧同心，内圆角必须 = 20 − 12 = 8 ✓

**不遵守会怎样**：内元素露出「四个尖角戳破外圆角」的效果，视觉上就是「贴歪了」——这是「廉价感」最常见的来源之一，且大多数人说不出来为什么。

### 4.2 边框优先于重阴影

**本项目的原则**（上游 `02` 文档已定，引 `v2/DESIGN.md:34`）：「边框优先于重阴影」。
**Apple 的同向依据**：Apple 的 iOS 背景层级用的是**同色相的明度阶梯**（`systemBackground` / `secondarySystemBackground` / `tertiarySystemBackground`），**没有用阴影**建立层级；Material 则用 elevation 阴影，但用的是**双层影**。

**M3 elevation 的双层影结构**（实测自 m3.material.io 页面内 CSS 变量 `mio-theme-elevation-*`）：

| 级别 | 阴影值 |
| --- | --- |
| `elevation-1` | `0 1px 2px 0 rgb(0 0 0/30%), 0 1px 3px 1px rgb(0 0 0/15%)` |
| `elevation-2` | `0 1px 2px 0 rgb(0 0 0/30%), 0 2px 6px 2px rgb(0 0 0/15%)` |
| `elevation-3` | `0 1px 3px 0 rgb(0 0 0/30%), 0 4px 8px 3px rgb(0 0 0/15%)` |

出处：https://m3.material.io/styles/typography/overview （页面内联 CSS 变量）
（M3 的 elevation 级别与模糊半径映射：`level0=0, level1=1, level2=3, level3=6, level4=8, level5=12`，实测自 https://raw.githubusercontent.com/material-components/material-web/main/tokens/versions/v0_192/_md-sys-elevation.scss ）

**结构拆解（这是「阴影看起来干净 vs 廉价」的真正分水岭）**：

| 层 | 作用 | 参数规律 | 不透明度 |
| --- | --- | --- | --- |
| 第 1 层 | **贴地影**：把元素和背景「粘」在一起 | blur ≈ offset + 1，spread = 0 | 高（30%） |
| 第 2 层 | **扩散影**：表达元素「浮起」的高度 | blur ≈ offset × 2.5，spread ≈ offset − 1 | 低（15%） |

> **廉价阴影 = 单层 + 大 blur + 大 spread + 低不透明度**（例如 `0 12px 34px rgba(0,0,0,.12)`）。它看起来像「一块脏渍」，因为缺少贴地影，元素没有「坐在」表面上。
> **干净阴影 = 双层**，或干脆**不用阴影，只用 1px 描边 + 明度差**。

**本项目的「边框优先」参数替代表**：

| 层级 | 替代方案 | 参数 |
| --- | --- | --- |
| 卡片（iOS） | **1pt 描边 + 明度差**，不投影 | 描边 `color.border` 1pt；`surface` 与 `canvas` 明度差 ≥ 6 L\* |
| 卡片（设备端 320×240） | **1px 描边**，零阴影 | 描边 `#2A303B`（深色主题） |
| 浮层（弹窗 / sheet） | 描边 + **一层**极轻投影 | `0 8px 24px rgba(0,0,0,.24)` + 1pt 描边（沿用 `02` 文档 8.1） |
| 按钮按下态 | **改变表面明度**，不投影 | 明度 +6%（`surface` → `surface.pressed`） |
| 卡片悬浮（桌面平台） | 双层影 | `0 1px 2px 0 rgba(0,0,0,.30), 0 4px 8px 3px rgba(0,0,0,.15)` |

**设备端为什么零阴影**：320×240 的 IPS 屏 + 嵌入式渲染，阴影既费性能又抢注意力；且小屏上阴影的模糊半径在视觉上等于「一圈灰边」，不如 1px 描边干净。

**描边颜色的取法**（不要用纯黑描边）：
`border = canvas 明度 −10% L\*`，或直接给「同色相的低饱和深色」。
例：canvas `#F1DFE5` → border `#D6BCC6`（实测 1.38:1 明度差，H 340→337 同色相）。
出处：本文 3.6 与 7.1 的实测。

### 4.3 玻璃材质（Liquid Glass）：正确用法与滥用后果

**Apple 的原文规则**（https://developer.apple.com/design/human-interface-guidelines/materials.md ）：

| # | 规则 | 原文要点 |
| --- | --- | --- |
| G1 | **玻璃是「功能层」** | Liquid Glass「forms a distinct functional layer for controls and navigation elements — like tab bars and sidebars — **that floats above the content layer**」 |
| G2 | **不要在内容层用玻璃** | 「**Don't use Liquid Glass in the content layer.** …including it in the content layer can result in unnecessary complexity and a confusing visual hierarchy」 |
| G3 | **克制使用** | 「Use Liquid Glass effects **sparingly**… overusing this material in multiple custom controls can provide a subpar user experience **by distracting from that content**」 |
| G4 | **只给最重要的功能元素** | 「Limit these effects to the **most important functional elements** in your app」 |
| G5 | **clear 变体只用于「视觉丰富」的背景**（照片/视频）；内容多、文字多的组件用 regular 变体 | 「Only use clear Liquid Glass for components that appear over visually rich backgrounds」；regular 用于「components with a significant amount of text, such as alerts, sidebars, or popovers」 |
| G6 | **clear 变体在亮背景上要压一层 35% 暗色遮罩** | 「If the underlying content is bright, consider adding a dark dimming layer of **35% opacity**」 |
| G7 | **玻璃上要放 vibrant 颜色** | 「use **vibrant colors** on top of materials」，否则细笔画符号会糊 |

**滥用后果（逐条）**：
| 滥用方式 | 后果 | 违反 |
| --- | --- | --- |
| 每个卡片都玻璃 | 内容层与功能层混淆，层级反转 | G1/G2 |
| 一屏 5 个玻璃按钮 | 注意力被玻璃折射抢走，内容反而看不见 | G3/G4 |
| 文字多的弹窗用 clear 玻璃 | 文字与背景花纹打架，可读性崩 | G5 |
| 玻璃上放非 vibrant 的灰图标 | 符号与背景同明度，图标「消失」 | G7 |
| 用玻璃做「内容卡」 | 卡片失去实体感，界面像一堆漂浮的碎片 | G2 |

**本项目的结论（很干脆）**：
1. **设备端 320×240 IPS：无玻璃。** 没有 GPU 合成、没有足够像素、且上游禁止项 #12「不使用 `backdrop-filter` 毛玻璃」已定。
2. **iOS 端：玻璃几乎无处可用。** 因为本项目**没有 Tab Bar**（上游禁止项 #16：不用 iOS 标准 Tab Bar 承载 8 个功能）。Liquid Glass 在 iOS 26 的主要载体就是 Tab Bar / Toolbar / Sidebar / 浮层按钮。
   → **唯一可能的落点**：底部弹出抽屉（sheet）的顶部控件区，或一个浮在内容上的「小栈形象」悬浮按钮。
   → **默认落点：不用玻璃。** 用 `surface.elevated` + 1pt 描边（见 4.2）即可达到「浮起来」的效果，成本更低、更可控、对比度更稳。
3. 若未来真要用玻璃，必须同时满足：只用在**一个**功能层元素上 + 背景是**内容**而非照片 → 用 regular 变体。

| `motion.toggle` | 200 ms | `standard` | 开关、选中态切换 | 两端 |
| `motion.enter` | **250–300 ms** | `emphasized` | 元素进场（透明度 + 位移 ≤ 12 px） | 两端 |
| `motion.screen` | **300–400 ms** | `emphasized` | 页面转场 / sheet 弹出 | iOS 为主 |
| `motion.layer` | 400–450 ms | `emphasized` | 浮层出现（弹窗） | iOS |
| `motion.character` | 400–700 ms | spring | 角色表情变化（听到声音、思考） | 设备端 |
| `motion.blink.close` | 120 ms | `standard-decelerate` | 眨眼（闭） | 设备端 |
| `motion.blink.open` | 90 ms | `standard-accelerate` | 眨眼（睁） | 设备端 |
| `motion.idle` | **3.5–5 s** | ease-in-out 循环 | 待机呼吸 | 设备端 |
| `motion.sway` | 4–6 s | ease-in-out 循环 | 待机摆动 | 设备端 |

**依据**：
- Apple：「Aim for **brevity and precision** in feedback animations」「In apps, generally **avoid adding motion to UI interactions that occur frequently**」（https://developer.apple.com/design/human-interface-guidelines/motion.md ）
- 上游 `02` 文档已有 `motion.press 0.16s`、`motion.enter 0.28s`、`motion.layer 0.5s`、`motion.sheet 0.45s`、`motion.ambient 1.45s`。

> ⚠️ **发现一处需要修订**：`motion.ambient 1.45 s` 循环 = **0.69 Hz**。这在「呼吸感」上偏快，读起来是「有点躁」而不是「在呼吸」。
> **建议改为 4–5 s 周期（0.2–0.25 Hz）**，理由见 4.4.4。

#### 4.4.2 缓动曲线

**M3 官方缓动令牌**（实测自 material-web v0.192）：

| 令牌 | cubic-bezier | 用途 |
| --- | --- | --- |
| `easing-linear` | `(0, 0, 1, 1)` | 进度条、计时器 |
| `easing-standard` | `(0.2, 0, 0, 1)` | 通用（元素移动） |
| `easing-standard-accelerate` | `(0.3, 0, 1, 1)` | 元素离场 |
| `easing-standard-decelerate` | `(0, 0, 0, 1)` | 元素进场 |
| `easing-emphasized` | `(0.2, 0, 0, 1)` | 强调转场 |
| `easing-emphasized-accelerate` | `(0.3, 0, 0.8, 0.15)` | 强调离场 |
| `easing-emphasized-decelerate` | `(0.05, 0.7, 0.1, 1)` | **强调进场** |
| `easing-legacy` | `(0.4, 0, 0.2, 1)` | 旧版通用 |

**iOS 的 spring**（SwiftUI `.spring(response:dampingFraction:blendDuration:)`）：

| 场景 | 参数 | 说明 |
| --- | --- | --- |
| 小元素状态变化 | `response: 0.25, dampingFraction: 0.8` | 快、几乎不过冲 |
| 卡片/页面转场 | `response: 0.35, dampingFraction: 0.86` | 略有回弹但不弹过头 |
| 拖拽跟手 | `interactiveSpring(response: 0.15, dampingFraction: 0.85)` | 手势直接驱动 |

> **Spring vs cubic-bezier 的选择规则**：
> - **可被手势打断/跟手的动效** → spring（SwiftUI 里用 `.interactiveSpring()`）
> - **固定时长的状态切换** → cubic-bezier（可预测、可计时、易于在设备端用 LVGL 复刻）
> - **设备端（LVGL / M5GFX）没有 spring 原语** → 用 cubic-bezier 近似；上游曲线 `cubic-bezier(0.2, 0.8, 0.2, 1)` 恰好与 M3 `easing-emphasized-decelerate (0.05, 0.7, 0.1, 1)` 属同一族（快出慢收），**可以正式命名为 `emphasized-decelerate`**，两端共用。

**曲线选择的物理直觉**：
| 曲线 | 感觉 | 用在哪 |
| --- | --- | --- |
| `linear` | 机械 | 只用于进度/计时 |
| `standard` | 中性 | 元素在屏内移动 |
| `standard-decelerate` | 从快到慢「落定」 | 元素进场 |
| `standard-accelerate` | 从慢到快「离开」 | 元素退场 |
| `emphasized-decelerate` | 快出 + 长收尾 | **主转场、进场** |
| `emphasized-accelerate` | 起步慢 + 加速离场 | 退场 |
| spring (damping 0.86) | 一点点回弹，「有生命」 | 角色动画、手势跟手 |

#### 4.4.3 弹簧与曲线在两端的落地

| 端 | 手段 | 具体 |
| --- | --- | --- |
| iOS | SwiftUI | `.animation(.spring(response: 0.35, dampingFraction: 0.86), value:)`；转场用 `.timingCurve(0.05, 0.7, 0.1, 1)` |
| iOS | 计时数字 | `.monospacedDigit()` + `linear` 逐秒跳变，避免宽度抖动 |
| 设备端 | LVGL 动画路径 | `lv_anim_path_ease_out` ≈ `emphasized-decelerate`；定时器逐帧推进 |
| 设备端 | 待机呼吸 | 硬件定时器 + 正弦插值（不用 CSS 动画） |

> ⚠️ **未验证**：本项目固件是否实际使用 LVGL（`02` 文档第 9 节已标注「现有固件是否用 LVGL 待确认」），故设备端动效 API 以「若用 LVGL」为条件表述。

#### 4.4.4 「陪伴型产品」的呼吸感微动效

**核心原则**：陪伴型产品的动效不是「展示」，是「**在不在**」。判据三条：
1. 用户不看它时，它不该抢注意力（低幅度、低频率、低对比）；
2. 用户看它时，它应该在「回应」（有明确的触发-反馈对应）；
3. 它必须能**被关掉**（Apple：「**Make motion optional**」；且「avoid using it as the only way to communicate important information」）。

**参数表（设备端 320×240）**：

| 动效 | 幅度 | 周期 / 时长 | 缓动 | 随机化 |
| --- | --- | --- | --- | --- |
| **眨眼** | 眼皮全闭 | 闭 120 ms + 开 90 ms | `standard` | 间隔 **2.5–6 s 随机**（固定间隔 = 机械感 / 恐怖谷） |
| **待机呼吸** | 整体缩放 ±1.5%，或上下 ±1 px | **3.5–5 s** | ease-in-out | 不需要 |
| **待机摆动** | 左右 ±2 px（或 ±1°） | **4–6 s** | ease-in-out | 相位随机，避免多台设备同步 |
| **被注视反应** | 眼睛上移 2 px | 200 ms 进 / 400 ms 回 | `emphasized` | — |
| **听到声音反应** | 眼睛放大 8% + 头部微抬 2 px | 250 ms | spring(0.3, 0.82) | — |
| **说话口型** | 开合 2 档 | 每帧 80–120 ms 随机 | 阶跃（不插值） | 必须随机，否则像在「念经」 |
| **思考** | 眼睛左右微移 | 每次 400 ms，间隔 1.2–2 s | `standard` | — |

**关于 0.2 Hz**：Apple 在 visionOS 章节明确提示「**Avoid showing objects that oscillate in a sustained way.** In particular, you want to avoid showing an oscillation with a frequency of **around 0.2 Hz** because people can be very sensitive to this frequency. If you need to show objects oscillating, aim to keep the **amplitude low** and consider making the content translucent.」
出处：https://developer.apple.com/design/human-interface-guidelines/motion.md （visionOS 段）
> ⚠️ 该建议原文针对 visionOS（周边视觉更敏感），**不是**移动端/桌面端的直接规范。但它揭示了底层原理：**低频持续振荡（约 0.2 Hz）最容易被察觉为「晃动」，也最容易被感知为不适**。
> 本项目据此把待机周期定在 **4–5 s（0.2–0.25 Hz）**，并把幅度压到 ±2 px。这是对 Apple 建议的**保守化应用**（恰好在 0.2 Hz 附近，故同时强调「幅度要低」）。
> **同时修正上游 `motion.ambient 1.45 s`（0.69 Hz）** —— 它偏快，读感是「躁」而不是「呼吸」。

**「不打扰」的三条红线**：
| 红线 | 判据 |
| --- | --- |
| 待机时不得有任何**颜色变化** | 只有几何位移（±2 px）和眼皮开合 |
| 动效不得**遮挡**用户的照片/内容 | 内容层永远压在动效层之上 |
| 退出/离开时必须**全部停止** | 上游 S11「退出即清理」——循环动画也必须停，否则设备在桌面上永远耗电（且 `02` 文档 4.6 已列「退出即清理」） |

### 6.1 Design Review Checklist（25 条 · 通过/不通过制）

| 结果 | 处理 |
| --- | --- |
| 1–7 有任一不通过 | **退回**（结构问题，改色板无用） |
| 8–15 有任一不通过 | **退回**（秩序问题，先修令牌再谈稿子） |

### 6.2 设计令牌的组织方式

#### 6.2.1 命名原则

| 原则 | 说明 | ✅ 正确 | ❌ 错误 |
| --- | --- | --- | --- |
| **语义命名，不外观命名** | 名字回答「它是什么角色」，不是「它长什么样」 | `surface.elevated` | `white.2` |
| **层级用嵌套 group 表达，不用点号** | DTCG 规定名字里**不能出现 `.`、`{`、`}`**，也不能以 `$` 开头 | `{"color": {"surface": {"elevated": {...}}}}` | `color.surface.elevated` 作为**名字** |
| **角色词表固定** | 只允许固定的 role 词 | `canvas / surface / surface.secondary / surface.elevated / border / ink.primary / ink.secondary / ink.tertiary / accent / accent.text / accent.container / accent.onContainer / success / warning / danger` | 临时造词 `pinkish` |
| **一套名，两套值** | light/dark 是**同一批 group 下的不同 theme**，不是两套命名 | `{"theme": {"light": {...}, "dark": {...}}}` | `colorLightSurface` / `colorDarkSurface` |

> DTCG 名称约束原文：「token and group names **MUST NOT** begin with the `$` character」且「the following characters **MUST NOT** be used anywhere in a token or group name: `{` `}` `.`」
> 出处：https://www.designtokens.org/tr/drafts/format/ （§5.1 Name and value / §5.1.1 Character restrictions）

#### 6.2.2 单一真源与多端输出

**单一真源**：`design/tokens/*.tokens.json`（DTCG 格式）。**代码里不允许出现裸色值/裸字号/裸圆角**——这是唯一能防住「文档与实现脱节」的机制（`02` 文档已记录过 v2 `DESIGN.md` 描述浅色而 `prototype.html` 实际是深色的历史事故）。


#### 6.2.3 防漂移的三条 CI 规则（自造，极低成本）

| # | 规则 | 实现 |
| --- | --- | --- |
| **CI-1** | 代码里不得出现裸 hex | `grep -rInE '#[0-9a-fA-F]{6}' src/ ios/ firmware/` 必须零命中（生成产物目录排除） |

### 6.3 DTCG 令牌文件结构示例

> 下列结构严格遵守 DTCG：`$value` 必填；`$type` 可从**最近的带 `$type` 的父 group 继承**；`$description` / `$extensions` / `$deprecated` 可选；group 可用保留名 `$root` 定义根令牌；别名用 `{group.token}` 的 JSON-Pointer 风格。
> 出处：https://www.designtokens.org/tr/drafts/format/ （§5.1–§5.3、§6.2–§6.3）

**目录结构**：
```
design/tokens/
  core.json          # 原始调色板 + 基础尺度（主题无关）
  theme.light.json   # 语义层 → light 值
  theme.dark.json    # 语义层 → dark 值
  motion.json        # 时长 / 缓动
  typography.json    # 字号 + 行高 + 字重
```

**`core.json`（节选）**：

### 7.6 每个数值的取舍理由（速查）

| 数值 | 理由 |
| --- | --- |
| canvas `#F1DFE5`（S 39.1%，L\* 90.4） | 满足「大面积底色 S ≤ 40%、L\* ≥ 90」；比被否的 `#FF6699`（S 100%）低 2.6 倍饱和度，避开糖果感 |
| surface `#FFFBF8` 而非纯白 | 纯白卡片在暖粉底上会「发冷、脱离」；带一丝暖的米白让卡片像纸 |
| surface vs canvas 1.24:1 | 表面层级靠**明度差 + 1pt 描边**，不靠阴影；1.24 加上 1.72:1 的描边对比足够分层 |
| ink.primary 14.41:1 | 远高于 4.5:1 底线，给长时间阅读留余量 |
| ink.tertiary 定在 **4.50:1**（恰好达标） | 三级文字是最容易被牺牲的一档；宁可在 canvas 上也守住 4.5:1，也不用「反正不重要」放宽 |
| accent 三拆（base / fill / text） | 解决「浅粉压不住白字」：`base` 只做图标（3.82:1 ≥ 3:1），`fill` 配白字（5.14:1），`text` 单独加深（5.93:1）。**一份品牌色，三种用法各自达标** |
| 深色 accent 提亮到 `#F2A0B8` | 浅色 `#D94F78`（L\* 53.7）在深底上偏闷；提亮后 8.06:1 |
| 深色不用纯黑 | `#0E1117`（L\* 5.0）避免眩光；且与 `#1C212B` 表面有 1.17:1 的可辨层次 |
| success `#28694B`（而非 `#2F7D57`） | 后者在 canvas 上只有 3.92:1（不达标）；加深后 5.11:1 |
| warning 拆 `.text` / `.fill` | 黄色 `#F5C542` 在浅底上只有 1.39:1，**只能当填充**；当文字必须换成 `#805900`（4.91:1） |
| danger `#B62A43` | `#D6455E` 在 canvas 上 4.16:1 不达标；加深后 4.83:1 |
| 字号 11–34（iOS） | 直接采用 Apple 系统阶梯 → 自动获得 Dynamic Type 与「放大时优先放大重要内容」 |
| 设备端下限 11 px | 14 px ≈ 11.7 弧分 @500 mm 视距（由 200 PPI 假设推导，见 2.3）；**PPI 需实测复核** |
| 设备端正文 13 px | 比 14 px 更省空间，且仍高于下限；给 320×240 留出「一句完整中文」的空间 |
| 间距 4–32 | 4 的倍数可被 8 栏栅格整除（12 + 8×30 + 7×8 + 12 = 320）；相邻比 ≤ 2:1 保证节奏不塌 |
| 圆角上限 20–24 | 圆角是强调信号，处处放大 = 没有强调；`radius ≈ min(短边×0.10, 20)` |
| press 120–150 ms | Apple「brevity and precision」；高频交互的动效越短越好（motion.md） |
| idle 3.5–5 s | 避开 Apple 提示的高敏感低频区（约 0.2 Hz）；且 1.45 s（0.69 Hz）读感是「躁」不是「呼吸」 |
| 禁止 > 500 ms 装饰动画 | 陪伴型产品的动效是「在不在」，不是「展示」 |

**采用决策：混合**

**理由**：
1. **标准化「令牌文件与编译链路」** —— 这是跨端、跨人、跨时真正会失控的部分。本项目已经吃过「成文契约与实现脱节」的亏（v2 `DESIGN.md` 描述「柔雾樱花」浅色，`prototype.html` 实际是深色 StackChan OS）。把真源收敛到一个**可编译**的 DTCG JSON 是最低成本的根治手段。
2. **组件层自造薄壳** —— 不引入通用 SwiftUI 组件库（`isamercan/ThemeKit` 之类），因为本设计语言（线性图标、玫瑰强调色、吉祥物主体）气质高度定制，套用通用组件的成本高于自写；`theme-kit` 的「令牌 → codegen → Environment 注入」**结构**值得直接照搬。
3. **规则与数值全部复用第三方，不自造** —— 字号阶梯用 Apple 系统阶梯（顺带白拿 Dynamic Type），圆角/阴影/动效用 M3 官方令牌（Apache-2.0），中文排版用 clreq（W3C），对比度用 WCAG 2.2。这些是「有据可查的共识」，比任何个人偏好都更经得起作品集的评审。
4. **设备端令牌机制条件采用 LVGL** —— 先核实固件技术栈，再决定是否引入；不把它当作 iOS 契约的前置依赖。

### 8.1 速览

- **DTCG 格式规范** 用途：跨端令牌的唯一真源格式 许可：W3C CG 规范（非 W3C 标准） 接入成本：低 替代自造的：自定令牌格式与命名约定
- **Style Dictionary** 用途：DTCG → Swift / C 头文件 / CSS / JSON / Android 产物 许可：Apache-2.0 接入成本：中 替代自造的：手写脚本同步两端常量
- **Tokens Studio for Figma** 用途：设计侧维护并导出 DTCG 许可：MIT 接入成本：低 替代自造的：手写 JSON 与手工同步
- **theme-kit** 用途：SwiftUI 主题注入结构参考 许可：MIT 接入成本：低–中 替代自造的：自写 Environment 注入与 codegen
- **Apple SF Pro / SF Symbols / Dynamic Type** 用途：iOS 字体、图标与字号缩放 许可：系统限定 接入成本：零 替代自造的：自绘字体与缩放库
- **Material 3 令牌（material-web）** 用途：圆角/阴影/动效数值参考 许可：Apache-2.0 接入成本：零 替代自造的：自造数值阶梯
- **W3C clreq** 用途：中文排版硬规则 许可：W3C 文档许可 接入成本：零 替代自造的：凭感觉定中文行高
- **WCAG 2.2** 用途：对比度阈值与公式 许可：W3C Recommendation 接入成本：零 替代自造的：凭眼睛判断可读性
- **LVGL `lv_theme_t`** 用途：设备端主题映射（条件采用） 许可：MIT 接入成本：中 替代自造的：固件裸常量

**采用决策：混合** 理由：标准化「令牌文件与编译链路」，组件层自造薄壳；规则与数值全部引第三方共识（Apple HIG / M3 令牌 / clreq / WCAG），不自造审美标准。

### D. CI 验证脚本（PowerShell，可直接跑）

> 用法：把本文 7.1 的色板填进 `$L` / `$D`，脚本会断言所有关键配对的阈值；任何一条不达标则 `exit 1`（构建失败）。

```powershell
$ErrorActionPreference = 'Stop'

function Convert-Ch($c) { if ($c -le 0.04045) { $c / 12.92 } else { [Math]::Pow(($c + 0.055) / 1.055, 2.4) } }
function Get-Lum([string]$hex) {
  $h = $hex.TrimStart('#')
  $r = Convert-Ch ([Convert]::ToInt32($h.Substring(0,2),16) / 255.0)
  $g = Convert-Ch ([Convert]::ToInt32($h.Substring(2,2),16) / 255.0)
  $b = Convert-Ch ([Convert]::ToInt32($h.Substring(4,2),16) / 255.0)
  0.2126*$r + 0.7152*$g + 0.0722*$b
}
function Get-Ratio($a, $b) {
  $l1 = Get-Lum $a; $l2 = Get-Lum $b
  if ($l1 -lt $l2) { $t = $l1; $l1 = $l2; $l2 = $t }
  [Math]::Round((($l1 + 0.05) / ($l2 + 0.05)), 2)
}

$L = @{
  canvas='#F1DFE5'; surface='#FFFBF8'; surfaceSecondary='#F5E9EC'; elevated='#FFFFFF'
  border='#D6BCC6'; inkPrimary='#33232B'; inkSecondary='#6F5761'; inkTertiary='#766069'
  accentBase='#D94F78'; accentFill='#C23A64'; accentText='#B32E56'
  accentContainer='#FBE4EB'; accentOnContainer='#8E2442'
  success='#28694B'; warningText='#805900'; warningFill='#F5C542'; danger='#B62A43'
}
$D = @{
  canvas='#0E1117'; surface='#1C212B'; surfaceSecondary='#232935'; elevated='#2A3140'
  border='#38404E'; inkPrimary='#F5F7FA'; inkSecondary='#A9B2C0'; inkTertiary='#939CA9'
  accentBase='#F2A0B8'; accentFill='#E888A6'; accentText='#F4A9BE'
  accentContainer='#3A2430'; accentOnContainer='#F7C6D5'
  success='#5BD39B'; warningText='#F0C674'; warningFill='#F0C674'; danger='#FF7A85'
}

$fail = 0
function Assert-Ratio($name, $a, $b, $need) {
  $v = Get-Ratio $a $b
  $ok = $v -ge $need
  if (-not $ok) { $script:fail++ }
  '{0,-42} {1,6}:1  need {2,4}:1  {3}' -f $name, $v, $need, $(if ($ok) { 'PASS' } else { '**FAIL**' })
}

# --- Light ---
Assert-Ratio 'L ink.primary on surface'      $L.inkPrimary $L.surface 4.5
Assert-Ratio 'L ink.secondary on surface'    $L.inkSecondary $L.surface 4.5
Assert-Ratio 'L ink.tertiary on surface'     $L.inkTertiary $L.surface 4.5
Assert-Ratio 'L ink.tertiary on canvas'      $L.inkTertiary $L.canvas 4.5
Assert-Ratio 'L accent.text on surface'      $L.accentText $L.surface 4.5
Assert-Ratio 'L accent.base icon on surface' $L.accentBase $L.surface 3.0
Assert-Ratio 'L white on accent.fill'        '#FFFFFF' $L.accentFill 4.5
Assert-Ratio 'L onContainer on container'    $L.accentOnContainer $L.accentContainer 4.5
Assert-Ratio 'L success on canvas'           $L.success $L.canvas 4.5
Assert-Ratio 'L warning.text on canvas'      $L.warningText $L.canvas 4.5
Assert-Ratio 'L danger on canvas'            $L.danger $L.canvas 4.5
Assert-Ratio 'L border vs canvas'            $L.border $L.canvas 1.3
Assert-Ratio 'L surface vs canvas'           $L.surface $L.canvas 1.15

# --- Dark ---
Assert-Ratio 'D ink.primary on surface'      $D.inkPrimary $D.surface 4.5
Assert-Ratio 'D ink.secondary on surface'    $D.inkSecondary $D.surface 4.5
Assert-Ratio 'D ink.tertiary on surface'     $D.inkTertiary $D.surface 4.5
Assert-Ratio 'D ink.tertiary on canvas'      $D.inkTertiary $D.canvas 4.5
Assert-Ratio 'D ink.tertiary on elevated'    $D.inkTertiary $D.elevated 4.5
Assert-Ratio 'D accent.text on surface'      $D.accentText $D.surface 4.5
Assert-Ratio 'D accent.base icon on surface' $D.accentBase $D.surface 3.0
Assert-Ratio 'D dark on accent.fill'         '#1A0F14' $D.accentFill 4.5
Assert-Ratio 'D onContainer on container'    $D.accentOnContainer $D.accentContainer 4.5
Assert-Ratio 'D success on canvas'           $D.success $D.canvas 4.5
Assert-Ratio 'D warning on canvas'           $D.warningText $D.canvas 4.5
Assert-Ratio 'D danger on canvas'            $D.danger $D.canvas 4.5
Assert-Ratio 'D border vs canvas'            $D.border $D.canvas 1.3
Assert-Ratio 'D surface vs canvas'           $D.surface $D.canvas 1.15

if ($fail -gt 0) { Write-Error "$fail 项不达标"; exit 1 }
Write-Output "ALL PASS"
```
