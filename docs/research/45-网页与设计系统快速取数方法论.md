# 45 · 网页与设计系统的快速取数方法论

> **这份文档回答："有没有快速读取提取页面的方式？一切以效率为先。"**
>
> 结论：**有，而且不需要 LLM 参与判断。** 三条通道 + 一个专用工具，批量化的关键是「一次调用抽整页」而不是「逐条点」。
>
> 实战日期：2026-10-24 ｜ 全部命令在本机 Windows + pwsh 7 实测通过

---

## §0 三条通道速查

| 通道 | 适用 | 单次成本 | 限额 | 关键手法 |
|---|---|---|---|---|
| **A. 浏览器 + 结构化 JS** | 需要 JS 渲染 / 有登录态（抖音、小红书、App Store） | 1 次调用抽整页 | 无 | `evaluate_script` 一次返回 20–40 条结构化 JSON |
| **B. 纯 HTTP 批量** | 静态站、GitHub raw、jsdelivr | **可并发 20+** | 无 | `curl.exe` + 循环 + `--max-time` |
| **C. GitHub REST API** | 找仓库、查元数据 | 0.3s/次 | core 60/h、search 10/min | 搜索用 `search/repositories` 一次拿 8 条 |
| **D. 专用工具 `designlang`** | **提取任意网站的设计系统** | ~30s/站 | 无 | `npx designlang <url>` → 8 个产物文件 |

> ⭐ **效率的关键**：别用「读页面 → 理解 → 写下来」的循环，改成「**一次调用 → 结构化 JSON → 落盘**」。

## §1 通道 A：浏览器 + 一次性结构化 JS

### 1.1 为什么这是最快的

抖音搜索页有 20+ 结果卡，**逐条点击是 20 次调用**；一次 `evaluate_script` 直接把整页抽成 JSON，**1 次调用搞定**。

### 1.2 实测脚本（抖音搜索页通用）

```js
() => {
  const cards = Array.from(document.querySelectorAll('[data-e2e="scroll-list-item"], .search-result-card'));
  const rows = [];
  for (const c of cards) {
    const lines = (c.innerText || '').split('\n').map(s => s.trim()).filter(Boolean);
    if (!lines.length) continue;
    if (lines[0].startsWith('相关搜索')) continue;   // 过滤"相关搜索"伪卡片
    rows.push({ info: lines.slice(0,3).join(' '), desc: lines.slice(3).join(' ').slice(0,420) });
  }
  return { n: rows.length, rows };
}
```

### 1.3 三个要点

| 要点 | 做法 | 为什么 |
|---|---|---|
| **选择器冗余** | `'[data-e2e="scroll-list-item"], .search-result-card'` | 抖音改版时两个 class 会换着用，冗余选择器抗改版 |
| **按换行切字段** | `innerText.split('\n')` | 抖音卡片是「时长\|点赞\|描述\|@作者\|日期」的纯文本流，切行即得字段，不用猜 DOM 结构 |
| **过滤伪卡片** | `lines[0].startsWith('相关搜索')` | "相关搜索"也是 `.search-result-card`，不过滤会混进结果 |

### 1.4 坑：浏览器 profile 冲突

```
The browser is already running for ...\chrome-devtools-mcp\chrome-profile
```
→ MCP 侧有残留实例。**解法**：
- 换 `new_page` 而不是 `navigate_page`（后者在实例重启后会报 `No page found`）
- 或用 `mcp_browser`（`browser-use` skill）走独立 profile
- ⚠️ **子代理没有 chrome-devtools MCP 工具** → 抖音这类取证**必须主会话自己做**，不能外包。

## §2 通道 B：纯 HTTP 批量（`curl.exe`）

### 2.1 为什么用 `curl.exe` 而不是 `Invoke-WebRequest`

实测 `Invoke-WebRequest` 在本机会抛 TLS 上下文错误（`The underlying connection was closed`），而 `curl.exe` 稳定。

```powershell
curl.exe -s -m 25 -L -H "User-Agent: StackChan-Research" "<url>" -o "<outfile>"
```

### 2.2 免配额的 GitHub 内容通道

| 用途 | URL | 限额 |
|---|---|---|
| 读仓库文件原文 | `https://raw.githubusercontent.com/<u>/<r>/<branch>/<path>` | 无 |
| 读任意 tag 版本 | `https://cdn.jsdelivr.net/gh/<u>/<r>@<tag>/<path>` | 无 |
| 查包版本列表 | `https://data.jsdelivr.com/v1/packages/gh/<u>/<r>` | 无 |
| 读仓库目录 | `https://api.github.com/repos/<u>/<r>/contents/<path>` | **core 配额** |

> ⭐ **`raw.githubusercontent.com` 与 `cdn.jsdelivr.net` 完全免配额**，在 API 配额耗尽时是唯一可靠通道。

### 2.3 批量抓取模板（本次实战用了 3 次）

```powershell
$targets = @(@('messaging','imessage'), @('messaging','wechat'), @('misc','claude'))
foreach($t in $targets){
  $cat=$t[0]; $app=$t[1]
  $u = "https://raw.githubusercontent.com/Meliwat/awesome-ios-design-md/main/design-md/$cat/$app/DESIGN.md"
  curl.exe -s -m 25 -L -H "User-Agent: $UA" $u -o "$ws\$app.md"
}
```

一次循环 12 个仓库，**总耗时 < 20 秒**。

## §3 通道 C：GitHub REST API（配额会重置）

### 3.1 配额实测

```powershell
curl.exe -s -H "User-Agent: X" -H "Accept: application/vnd.github+json" https://api.github.com/rate_limit
```

实测输出：
```
core   : 60 / 60   (reset 01:05:02)
search : 10 / 10
```

> ⚠️ **重要**：core 配额是 **60/小时**，按 IP 计。**昨晚耗尽，今天凌晨自动重置**。
> ⇒ **不要因为一次配额耗尽就放弃 GitHub 调研，等一小时即可恢复。**

### 3.2 搜索用法（一次拿 8 个仓库）

```
https://api.github.com/search/repositories?q=<urlencoded>&sort=stars&order=desc&per_page=8
```

**search 限流是 10 次/分钟** ⇒ 循环里 `Start-Sleep -Seconds 7` 即可安全连续跑。

### 3.3 本次实战：21 个关键词 → 89+ 个仓库，用时约 100 秒

## §4 ⭐ 通道 D：`designlang` —— 直接提取任意网站的设计系统

> **这是本轮找到的效率杠杆最大的工具。**

### 4.1 安装（本机已装好，v13.3.2）

```powershell
npm.cmd install -g designlang
designlang --version    # => 13.3.2
```

### 4.2 用法

```powershell
npx designlang <url> --screenshots                    # 单站
npx designlang <url> --depth 3 --screenshots          # 爬多页
npx designlang <url> --dark --screenshots              # 同时抽深色模式
designlang diff <urlA> <urlB>                          # 两站对比
designlang history <url>                               # 历史版本
```

### 4.3 输出 8 个文件（最值钱的是第 1 和第 6 个）

| 文件 | 用途 |
|---|---|
| `*-design-language.md` | ⭐ **给 LLM 用的完整设计系统说明**（最直接可喂给 AI） |
| `*-preview.html` | 可视化速查报告（色板 / 字阶 / 阴影 / a11y） |
| `*-design-tokens.json` | **W3C Design Tokens 标准格式** |
| `*-tailwind.config.js` | Tailwind 主题 |
| `*-variables.css` | CSS 自定义属性（**可直接套进我们的原型 token**） |
| `*-figma-variables.json` | Figma Variables 导入格式 |
| `*-theme.js` | React / CSS-in-JS 主题对象 |
| `*-shadcn-theme.css` | shadcn/ui 主题变量 |

### 4.4 它还做 **WCAG 可访问性评分**（省掉自己算对比度）

`design-extract`（MIT）的 README 明确写了 *"Also runs WCAG accessibility scoring"*。
⇒ 我们不用再手写对比度脚本，**直接读它的评分**。

### 4.5 它自带 6 个适配面（说明它不是一个玩具）

`design-extract` 仓库结构实测：
```
.claude-plugin/  commands/  skills/extract-design/SKILL.md
chrome-extension/  figma-plugin/  raycast-extension/  github-action/  vscode-extension/  smithery.yaml
```
⇒ ⭐ **它自带一个 Claude skill**（`skills/extract-design/SKILL.md`，3,344 B，已读原文），
可以直接装进我们的 skill 体系，让任何 AI「一键提取目标网站的设计系统」。

### 7.2 ⚠️ 抖音取数的边界（不可破）

> **抖音是「灵感 + 反例」源，不是设计规范源。**
> 已验证：被奉为"高级"的做法里，**"柔焦渐变基底""深色流光渐变""霓虹光感"恰好命中我们的禁止项 C1/C2**。
> ⇒ 引用时**只取"低饱和""留白""信息层级""单一强调色"这类结构原则，不取具体色值与特效**。
> ⇒ 所有取来的做法**必须回到 `19` 号 Floor 文档 + `docs/spec/02` 的判据上过一遍**。

## §9 一句话总结

> **别逐条读页面。用「一次结构化 JS」抽整页、用 `curl.exe` 并发抓、用 `designlang` 直接吐设计系统 token、用 GitHub API 批量搜。**
> 本轮实测：21 个 GitHub 关键词 + 11 份顶级设计系统文档 + 30 条抖音情报，**总耗时 < 15 分钟**，
> 而逐条手动读取需要数小时。
