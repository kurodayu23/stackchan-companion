## 二、⭐ 候选强调色对比度实测（完整数据）

### 2.1 为什么测这个

用户的原话反馈是旧 `DESIGN.md` 里的品牌色「丑」，同时**旧 PWA 里有一版已验证的强调色**。
但「好看」不能拍脑袋 —— `DESIGN.md` §2.4 写死「**未实测的数值一律不写**」，对比度是**硬指标**（正文 ≥4.5:1 / 大字与非文字组件 ≥3:1，陪伴型产品不放宽）。

⇒ 在用户拍板前，把**所有候选色在所有候选底色上的真实比值**先测出来，让拍板有数据而不是审美。

> ⭐ **订正我自己在 2026-10-24 23:32 给用户的推荐**：
> 我当时建议「浅色端保留 `#ff6d60`、深色端换成 `#8fd3f4`」。

## 三、⭐ 视觉方向冲突登记（待用户拍板）

### 3.1 冲突事实

| 来源 | 主张 |
|---|---|
| `DESIGN.md` §2.1（产品真相层，2026-10-23） | **iOS 画布 = `systemBackground`（浅）**；「iOS 端不用系统默认蓝已被推翻：系统语义色是骨架，暖色只作品牌 `.tint`」 |
| `docs/spec/00` §2.2 / §3.3 | 同上；品牌暖色 `#B33A55` / `#E8638C` |
| 我的 2026-10-24 推荐（原型 18 深色 tuck） | **iOS 走深色**（`#111113` 底 + 琥珀强调） |
| 原型 20 方案 | 浅色 12 个 / 深色 8 个，两边都有 |

⇒ **这不是「谁对」的问题，是产品真相层与探索层没对齐。** `DESIGN.md` 是已定裁决，18 是探索中的候选。

### 3.2 我为什么没有直接改 `DESIGN.md`

`DESIGN.md` 是**产品真相层**（用户拍板过的层），不是探索层。夜间自主推进的约束是
「**需求未定不许动手改产品逻辑**」。⇒ 改它属于越权。

### 3.3 我做了什么让两个方向都不返工

- **iOS 侧**：DesignSystem 做成 **token 化双主题** —— `SystemLightTheme`（= `DESIGN.md` 现行裁决）与 `TuckDarkTheme`（= 18）**两套都实现**，切换点收敛到一个 enum。⇒ 无论最终选哪个，SwiftUI 代码不用重写。
- **强调色**：本文第二节把两个方向各自的合法色集用实测数据圈定了。⇒ 拍板后只需改 token 值。

### 3.4 需要用户拍板的一句话

> **iOS 端用浅色（`DESIGN.md` 现行，暖色 `#B33A55` / `#9E3B26`）还是深色（原型 18，琥珀 `#E3A857`）？**
>
> 补充事实：设备端**已经**是深色（`#080A0F` / `#0E1117`，`DESIGN.md` §2.2）。
> 选深色 iOS 会让 **App 与设备同调**（更连贯）；选浅色 iOS 会让 **App 与设备对调**（更分离、更「镜子」）。
