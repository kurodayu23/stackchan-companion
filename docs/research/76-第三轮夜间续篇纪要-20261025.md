## 三、第 4 个门禁 `tools/check_decisions.py`

### 3.1 为什么需要

`spec/07` §3.5 管「**有哪些**待拍板项」，`spec/09` §四 管「每个项**解锁什么**」。
两份都靠人维护 ⇒ 会漂。漂了的后果不是「文档不好看」，而是**真的漏工**：
新增一个决策却没登记依赖 ⇒ 没人知道它卡住了哪条任务。

### 3.2 十一个检查码

| 码 | 判什么 |
|---|---|
| DEC-01 | 07 §3.5 的每个 Q 在 09 依赖表里都有登记 → FAIL |
| DEC-02 | 09 依赖表出现的每个 Q 在 07 §3.5 存在 → FAIL（防凭空造决策） |
| DEC-03 | D 系列编号从 D1 连续到 Dn → FAIL |
| DEC-04 | 依赖表每行的「建议 / 阻塞 / 降级路径」三列不得为空 → FAIL |
| DEC-05 | 09 必须有「未验证」小节且 ≥3 条 → FAIL（防边界声明被删） |
| DEC-06 | 09 声称由本工具守门 ⇒ 正文必须出现本工具名 → FAIL（防文档说谎） |
| DEC-07 | 09 号写的「07 号 §3.5（N 项）」必须等于实际条目数 → FAIL |
| DEC-08 | 72 号写的「N 个真缺陷」必须等于其清单实际条目数 → FAIL |

| DEC-11 | 05 号 §八 的每个技术侧待拍板项（T-）必须与 07/00 跨表登记 → FAIL |
### 3.3 它当场抓到的 1 个真 bug（在我自己的脚本里）

第一版自检 **DEC-05 报 FAIL**：真仓库的「未验证」小节明明有 12 行，却只数出 0 行。
根因：`_section()` 的终止条件写成「下一个标题」，而它从**第一个标题（H1）**开始取
⇒ 取到的只是引言段 ⇒ 表头表体一个都没进去。
⇒ 修法：另写一个「从含『未验证』的标题开始、到下一个标题为止」的取段函数。
**教训**：自检 FAIL 要先分流「脚本错 / 被测物错」—— 这次是脚本错。

### 3.4 还有一处真 bug：Q 号只在「编号」列找不到

第一版实现只从依赖表的**编号列**抽 Q 号 ⇒ D2–D6 这几行（Q 号写在**事项**列里，
如「视觉终选（Q15）」）被判成「未登记」，同时 `Q4/Q5/Q6` 被当成一个编号 ⇒ 报「凭空造决策」。
⇒ 修法：扫**整行**，并把 `/` 分隔的多编号拆开。
**教训**：登记表类解析一定要按**文档实际写法**写，不能按自己想当然的列位置。

## 五、⭐ 真实 MiniMax 全链路实测（`docs/research/75`）

### 5.1 跑通了什么

`server/run.py --demo --provider minimax`：**真实 Chat（ENFP 人格）→ 真实 TTS → 韵律 → 42 参数 → PCHIP → `0x14` 关键帧 → WebSocket → 设备模拟器收到帧**，退出码 0。
原始日志留在 `docs/research/runs/20261025-0640-e2e-minimax.log`（**已加 `.gitignore` 例外让它能进库**）。

### 5.2 逐条手算复算（不信任工具自己的输出）

| 量 | 手算 | 结论 |
|---|---|---|
| 关键帧数 | `ceil(6.095×25)=153` / `ceil(4.598×25)=115` / `ceil(5.759×25)=144` | ✅ 全对 |
| 时间轴 | `153×0.04=6.120 s` / `115×0.04=4.600 s` / `144×0.04=5.760 s` | ✅ 全对 |
| 帧长 | `frame − payload = 5 B` = 帧头 `[Type(1)][Length(4)]` | ✅ |
| 载荷/帧 | 5 次都是 **321–323 B** ⇒ 单帧结构固定 | ✅ |
| 限位 | yaw 观测 `[-45, 48]` vs 限位 `±1280`（0.1°）⇒ 余量 26 倍 | ✅ 未撞限位 |

### 5.3 ⭐ 关键发现：MiniMax 的输出**不可复现**

| 次 | 音频时长 | 帧数 | f0 | 语速 | 重音 | 停顿 | LLM 回复 |
|---|---|---|---|---|---|---|---|
| A1 | 6.095 s | 153 | 246.6 Hz | 5.03 Hz | 15 | 6 | 三次**文本都不一样** |
| A2 | **4.598 s** | 115 | 254.3 Hz | 5.88 Hz | 9 | 6 | |
| A3 | 5.759 s | 144 | 256.6 Hz | 6.52 Hz | 10 | 8 | |

⇒ 时长极差 **+32.6%**；另有 4 次无留痕的探索性调用观测到 8.139 s（**只算旁证**）。

### 5.4 三条硬约束

| # | 约束 |
|---|---|
| 1 | **关键帧必须由「本次合成的实际 PCM」实时编译**（不能预烘焙） |
| 2 | **不能把「预计时长」写进任何缓存键、对外承诺或 UI 文案** |
| 3 | **「音画对齐」只能在同一份 PCM 的相对时间轴上成立** |

### 5.5 顺带解释了为什么坚持「关键帧驱动切法」

`tools/audio_chunk.py` 按关键帧栅格切 PCM ⇒ 关键帧随每次合成的音频变 ⇒ **切片片数也会变**。
⇒ 规格 `spec/07` §3.6.1 里「2350 ms ⇒ 15 片」只能当**示例**，不能当契约。

## 七、DeepSeek 派单（第 3 次）：**两个机械坑 + 一次空转**

| 坑 | 现象 | 根因 | 修法 |
|---|---|---|---|
| ① **任务书不在 worktree 的提交里** | worker 报「`dsh-tasks/task-A-*.md` 不存在（已用 git 核实）」，然后**自己即兴发挥** | 我在**第一次 commit 之后**才建的任务书，而 worktree 是从 HEAD 建的 | 任务书**全文内联进 Prompt**（DSH 会把 Prompt 落到 `dsh-outbox\<id>\task.md`），不再依赖仓库文件 |
| ② `-WorktreeName` 语义搞反 | 池直接抛错退出 | 它是「**复用**已有 worktree」，不是「按名字新建」 | 不传该参数，让池自建 |

**附带**：`schtasks /end` **不会**杀掉池脚本的 pwsh 子进程 ⇒ 池继续跑下一轮，
而此时 `schtasks /run` 因任务仍标记 Running 而**静默不启动新实例**（日志里看不到新的 start 标记）。
⇒ 必须先按 PID 杀 pwsh 与该轮 node worker，再 `/run`，并**在日志里确认出现了新的 start 标记**。

**验收方式**：不看 token 数，看 `dsh-outbox\<id>\report.md` 的**字节数与结论密度**
（`dsh-outbox\<id>\task.md` 是派单器自动写的，**不能**当产出证据）。

### 14.3 ⚠️ 我自己在这个新门禁上踩的两个坑（都已写进自检）
