## 0. 一句话结论

**7 项全部拿到了实质进展，其中 4 项被源码直接定案（✅），3 项推进到间接确认（🟡），0 项卡在完全无证据（⬜ 但仍有残余待真机）。**

三个最反直觉、也最影响我们后端设计的发现：

1. **官方 App 从不做表情保活重发。** App→Server→Device 全链路对 `0x03 ControlAvatar` 都是**一次性转发**，服务端是纯 relay（`server/internal/web_socket/web_socket.go:553-565`）。整个 App 里唯一的周期性重发是蓝牙摇杆姿态流，节流到 **≥200 ms**（`app/lib/view/home/record_dance.dart:571-586`）。
   ⇒ **我们的「表情保活调度器」不是补官方 App 的漏，而是官方栈根本没有的能力 = 我们的差异化点。**
2. **`speed` 不是舵机速度单位，而是 UI 工具包的弹簧刚度。** 物理舵机写入恒为 `WritePos(id, pos, Time=20, Speed=0)`（`firmware/main/hal/hal_servo.cpp:86`），JSON 里的 `speed` **根本到不了舵机速度寄存器**。它只映射成 `stiffness = 10 + (speed/1000)² × 640`（`firmware/main/stackchan/motion/servo.cpp:126-161`）。
   ⇒ **53 号文档 §5.4「关键帧通道无弹簧」的说法需要更正为「用弹簧，但速度语义是 UI 刚度」。**
3. **气泡的中文基本渲染不出来。** StackChan 板卡的内置文本字体是 `font_puhui_basic_20_4`，实测只有 **801 个字形、其中 CJK 汉字仅 184 个**，且 `你 好 中 国 文 说 猫` **全部缺失**，全角逗号 `U+FF0C`、省略号 `U+2026` 也没有。英文/ASCII 正常。

### 1.1 远程表情被覆盖的实际观感 —— ✅ 机制已定案

**机制链（全部源码实证）**

1. 远程路径**不取 modify lock**：`firmware/main/stackchan/stackchan.h:152` `updateAvatarFromJson()` → `avatar::update_from_json()`，全程不查 `isModifyLocked()`。
2. `BlinkModifier`（`firmware/main/stackchan/modifiers/blink.h:25`，默认睁 5200 ms / 闭 200 ms）：
   - 眨眼瞬间写死 `apply_eye_weights(stackchan, 25, 25)`（`blink.h:83`）→ **直接盖掉远程下发的 eye `weight`**。
   - 睁眼时恢复 `_left_eye_weight` / `_right_eye_weight`（`blink.h:91`），而这两个值是**每次闭眼瞬间重新备份**的（`blink.h:80-81`）。
   - 睁眼间隔带 0–500 ms 随机抖动（`blink.h:88-89`）⇒ 远程表情的实际寿命是 **随机**的，不是一个固定值。
3. `IdleExpressionModifier` / `BreathModifier` 写 `position`（`firmware/main/stackchan/modifiers/idle_expression.h`、`breath.h`），同样与远程 JSON 写同一批字段 ⇒ 后写者胜。
4. ⇒ **远程表情的实际寿命 = 最早被覆盖的时刻 = idle 首次触发的 2000 ms（blink 要到 5200 ms 才首次闭眼），之后每次 blink 闭眼（5200 + 0~500 ms 抖动）再盖一次**。

**⭐ 最硬的旁证：官方 App 自己不做保活**

| 位置 | 行为 | 是否保活 |
|---|---|---|
| `app/lib/view/home/avatar.dart:713-730` `sendDanceData()` | 一次性发 `controlAvatar` + `controlMotion` | ❌ |
| `app/lib/view/popup/motion.dart:95-107` `_saveAvatarData()` / `_saveMotionData()` | 摇杆每次改动各发一次 | ❌ |
| `app/lib/view/home/dance.dart:191-197`（网络模式） | **整条舞蹈序列打成一条 `0x14` 发完**，之后 50 ms 定时器只更新 UI 高亮（`dance.dart:203-252`） | ❌（也不需要，0x14 绕锁） |
| `app/lib/view/home/dance.dart:137-150`（单帧） | 发一帧，等 `durationMs`（蓝牙 +70 ms） | ❌ |
| `app/lib/view/home/record_dance.dart:571-586`（蓝牙姿态流） | **节流到 ≥200 ms 重发同一帧** | ✅（唯一一处周期重发） |
| `server/internal/web_socket/web_socket.go:553-568` | 服务端对 `ControlAvatar` / `ControlMotion` **纯转发**，无重发、无状态机 | ❌ |

> **结论（✅）**：官方 App + 官方 Server 从不做表情保活重发。官方唯一「想让姿态粘住」的做法是蓝牙通道下 **200 ms 节流重发**（`record_dance.dart:575`）。
> **推论（不是确认）**：官方产品接受「表情会在 2 s 内被设备自己改回去」的观感，或官方从未注意到该问题。二者都指向同一个工程结论 —— **保活调度器是我们的净增量功能**。

**外部旁证（🟡）**

- 官方 issue #95「Feature Request: Option to disable idle motion in AI Agent mode」原文：*"In AI Agent mode, StackChan continuously performs random head movements every 4-8 seconds while idle."* — <https://github.com/m5stack/StackChan/issues/95>
  → **官方 issue 独立佐证了空闲动画的 4–8 s 节奏**（与源码 `idle_expression` 2000–6000 ms 同量级），说明「设备会自己动」是用户可感知的。
- 官方 issue #47（已合入 v1.3.1）：把空闲头动做成可配置（Enable / Frequency / Intensity）— <https://github.com/m5stack/StackChan/issues/47>；#51 是其重复单 — <https://github.com/m5stack/StackChan/issues/51>
  → 用户主动要求「让它别动」= 设备自主动作确实会打扰人。
- 第三方实现 `xuruiray/stackchan-local` 的 `react` 命令：`durationMs` 默认 **2000**、clamp 到 `100..10000`，**一次性发送、不重发** — <https://github.com/xuruiray/stackchan-local/blob/main/docs/robot-command-protocol.md>
  → 另一个独立开发者同样选择了「一次性 + 有限时长」而不是保活流。**其 `durationMs` 默认值 2000 恰好等于 idle 最短间隔**，可作为我们取保活周期的反向参考。

**仍缺什么**：真机录像。需要在真机上发一条 `0x03`，观察第 2 秒 eye weight 被 `25` 顶掉时肉眼是否「跳变」（观感层面无法从源码推断）。

### 1.2 保活重发周期 800–1200 ms 是否够（有无抽搐） —— 🟡 间接确认

**已知锚点（源码/第三方实证）**

| 来源 | 数值 | 含义 |
|---|---|---|
| `app/lib/view/home/record_dance.dart:575` | **200 ms** | 官方 App 蓝牙姿态流的重发节流下限（连续姿态，不闪） |
| `app/lib/model/expression_data.dart`（`MotionDataItem`） | speed 默认 **500** | 官方 App 的默认运动档 |
| `firmware/main/stackchan/motion/motion.h:103,129,149` | `goHome` / `lookAtNormalized` / `lookAtPoint` 默认 speed **500** | 固件默认档 |
| `stackchan-local/desktop/src/robot/controller.ts:20-23` | `MANUAL_MOTION_HOLD_MS=2500`、`ANIMATION_MOTION_HOLD_MS=10000`、`FACE_TRACKING_HOLD_MS=900` | 第三方 daemon 的运动仲裁 hold 时长 |
| `stackchan-local/desktop/src/robot/motion-arbitrator.ts:35-44` | `reserve(owner, holdMs, reason)` / `release(owner)` | 第三方用**独占仲裁 + 过期释放**替代保活 |
| `server/README.MD:972` | 服务端心跳 **每 5 秒**一次 | 只是 WS ping，**不是**表情保活 |

**判读**

- 官方 App 敢用 **200 ms** 连续重发姿态 ⇒ 200 ms 级别的重发在官方产品上是可接受的，不会被视为「抽搐」。
- 第三方 daemon 用 **900 ms** 作为人脸跟踪目标的 hold 时长（比我们的 800–1200 ms 下限略低但同量级）⇒ **800–1200 ms 落在「已被别人用过」的区间内**。
- 官方 App **一次表情都不重发** ⇒ 「表情保活」这条路径**没有前人踩过坑的公开数据**。

**仍缺什么**
- **无任何公开的「表情抽搐」实测报告**（社区/issue/视频均未找到）。判定只能到「官方与第三方都用过 200–900 ms 量级」。
- 建议真机一次性验证：同一表情分别以 200 / 500 / 800 / 1200 / 2000 ms 重发，肉眼找「抽搐」临界点。

### 1.4 `leftRgbColor` / `rightRgbColor` 是否作用到 12 颗灯的左右两侧 —— ✅ 已确认

**源码链**

| 环节 | 证据 |
|---|---|
| JSON 解析 | `firmware/main/stackchan/json/json_helper.cpp:216-221`：关键帧里的 `leftRgbColor` / `rightRgbColor` 解析为字符串 |
| 应用到硬件 | `firmware/main/stackchan/animation/animation.cpp:32-33`：`stackchan.leftNeonLight().setColor(leftRgbColor); stackchan.rightNeonLight().setColor(rightRgbColor);` |
| 左右实例 | `firmware/main/stackchan/stackchan.h:184-185`：`_left_neon_light` / `_right_neon_light` 是 `StackChan` 的直接成员 |
| 灯珠数 | `firmware/main/stackchan/addons/neon_light/neon_light.h:56` `LeftNeonLight() : NeonLight(6)`；`:71` `RightNeonLight() : NeonLight(6)` ⇒ **左 6 + 右 6 = 12** |
| 索引映射 | `firmware/main/stackchan/addons/neon_light/neon_light.cpp:81-84` 左灯 `setRgbColor(index, …)`（index 0–5）；`:91-94` 右灯 `setRgbColor(index + 6, …)`（index 6–11） |
| 硬件侧 | `firmware/main/hal/hal_io_expander.cpp:51` `_io_expander->setLedCount(12)`；`:87-90` `showRgbColor` 循环 `i = 0..11` ⇒ **硬件确实是 12 颗 RGB LED**（PY32 IO 扩展芯片驱动，通道 13） |
| 另一条独立通道 | `firmware/main/stackchan/json/json_helper.cpp:236-261` `update_neon_light_from_json()` 单独支持 `leftRgbColor`/`rightRgbColor` + `leftRgbDuration`/`rightRgbDuration`，入口 `firmware/main/stackchan/stackchan.h:176-179` |

**⚠️ 两条源码级「坑」（对我们设计关键帧很重要）**

1. **颜色是渐变的，不是瞬变的**：`firmware/main/stackchan/addons/neon_light/neon_light.cpp:14` `_color_anim.duration = 0.3f` ⇒ 每次 `setColor` 都要 **300 ms 渐变**到目标色。
   ⇒ **关键帧 `durationMs < 300` 时，灯根本来不及变成该帧的颜色。** 想让颜色「卡」住，关键帧时长必须 ≥ 300 ms（且下一帧颜色不同才能看出渐变）。
2. **刷新上限 50 Hz**：`neon_light.cpp:24-27` 每 20 ms 才刷新一次（`update()` 早退）。
3. **颜色有「时长」语义**：`json_helper.cpp:249-257` 支持 `leftRgbDuration`/`rightRgbDuration`（单位秒，`neon_light.cpp:77` `setDuration`）—— 这是 0x03/其它通道才有的能力，**0x14 关键帧里没有**。

**仍缺什么**：**物理左右排布**（哪 6 颗在机身左侧、哪 6 颗在右侧、是否绕到背面）源码里只有索引语义，**必须真机看**。另外「12 颗灯是否就是官方宣传的 12 颗」也需真机数。

### 1.5 `moveWithSpeed(angle, speed)` 的 `speed` 档位实际映射 —— ✅ 已确认（**不是舵机速度单位**）

**源码链（⭐ 本轮最重要的更正）**

| 环节 | 证据 |
|---|---|
| 入口 | `firmware/main/stackchan/motion/servo.cpp:84-88`：`Servo::moveWithSpeed(angle, speed)` → `map_speed_to_spring_options(speed)` → `moveWithSpringParams(angle, stiffness, damping)` |
| **映射公式** | `firmware/main/stackchan/motion/servo.cpp:126-161`：<br>`speed = clamp(speed, 0, 1000)`<br>`stiffness = 10 + (speed/1000)² × (650 − 10)`<br>`damping = 2 × √(1 × stiffness)`（临界阻尼）<br>`speed > 800` → `restDelta = restSpeed = 0.5`，否则 `0.1` |
| 语义注释 | `firmware/main/stackchan/motion/motion.h:62,77,96,103,124,145`：「speed (0-1000)」「0 (slowest) to 1000 (fastest)」 |
| **物理舵机写入** | `firmware/main/hal/hal_servo.cpp:86`：`_scs_bus.WritePos(_config.id, mapped_angle, 20, 0);`<br>驱动签名 `firmware/main/hal/drivers/FTServo_Arduino/src/SCSCL.h:57`：`int WritePos(u8 ID, u16 Position, u16 Time, u16 Speed = 0);`<br>⇒ **第 3 参是 Time=20，第 4 参 Speed=0，永远是这两个常量** |
| 结论 | **`speed` 只改「上位机弹簧动画的刚度/阻尼」，物理舵机的速度寄存器恒为 0（SCSCL 协议里 Speed=0 表示不限速/最快档），每次动画步进都用 `Time=20 ms` 追一个中间目标位。** |

**⚠️ 对 53 号文档的更正**：53 号 §5.4 写「舵机运动方式 `moveWithSpeed`（**无弹簧**）」。**这是错的** —— `moveWithSpeed` 明确走 `moveWithSpringParams`，就是弹簧插值。真实情况是：**有弹簧，但速度语义是 UI 刚度，不是舵机 RPM**。

**官方内置 4 条序列用到的 speed 值**（`firmware/main/stackchan/modifiers/dance.h`）

| 序列 | 用到的 speed | 换算 stiffness | 语义 |
|---|---|---|---|
| `Happy`（`:20-33`） | 200 | 35.6 | 慢摆 |
| `Robot`（`:41-54`） | 500 / 800 | 170 / 419.6 | 中速、机械 |
| `Panic`（`:62-77`） | 1000 / 200 | 650 / 35.6 | 高频抖动（帧长仅 100 ms） |
| `LookAround`（`:83-94`） | 150 / 200 | 24.4 / 35.6 | **最慢**，帧长 1000–2000 ms |

**官方 App 侧**：`app/lib/model/expression_data.dart` 的 `MotionDataItem({this.angle = 0, this.speed = 500, this.rotate = 0})` ⇒ **默认 speed = 500**；`MotionDataItem.toJson()` 只输出 `{angle,speed}` 或 `{rotate,speed}`，**从不输出 `spring`**。

### 1.7 `BlinkModifier::resyncEyeWeights()` 在远程 weight 冲突时的行为 —— ✅ 已确认（含一个隐藏 bug）

**源码链**

| 环节 | 证据 |
|---|---|
| 接口定义 | `firmware/main/stackchan/modifiers/blink.h:41-44`：`void resyncEyeWeights() { _needs_resync = true; }` |
| 消费点 | `firmware/main/stackchan/modifiers/blink.h:66-71`：`_needs_resync` 为真时，**抓取当前 left/right eye weight 作为新的备份值**，然后清标志 |
| 前置条件 | `blink.h:48-50`：`_update()` 开头 `if (!stackchan.hasAvatar() \|\| stackchan.avatar().isModifyLocked()) return;` ⇒ **modify lock 期间 resync 请求会被丢弃**（标志仍为 true，等解锁后才生效） |
| **唯一调用点** | `firmware/main/hal/board/stackchan_display.cc:374-378`：在 `SetEmotion(...)` 末尾 —— 「Resync blink modifier base eye weights」。**远程 `0x03` JSON 更新不会调用它** |
| 冗余性 | `blink.h:79-83`：每次闭眼瞬间都会**重新备份** `_left_eye_weight`/`_right_eye_weight` ⇒ 正常情况下 `resyncEyeWeights()` 是冗余的 |
| 注释与实现不一致 | `blink.h:64-65` 注释写「如果眼睛正闭着，我们只记录权重，等睁眼时再应用」，但 `blink.h:66-70` 的代码**没有任何状态判断**，无论睁闭都会立刻抓取当前 weight 作为新基准。若在闭眼期间（weight=25）处理该请求，基准会被刷成 25 |

**⇒ 结论（✅）**

1. `resyncEyeWeights()` 的语义 = 「**把当前眼睛 weight 设为眨眼恢复时的基准值**」，只在**设置情绪**时被调用，**远程表情下发不会触发**。
2. 远程 weight 与 blink 冲突时：**闭眼期间下发的新 weight 会被静默丢弃**（见下）。

**⚠️ 本轮发现的隐藏 bug（源码实证）**

```
blink.h:79-83   闭眼瞬间：_left_eye_weight = 当前 weight ; 然后 apply_eye_weights(25,25)
blink.h:91      睁眼瞬间：apply_eye_weights(_left_eye_weight, _right_eye_weight)   ← 恢复的是「闭眼前」的旧值
```

⇒ **如果在「闭眼的 200 ms 窗口」内下发远程 eye weight，睁眼时会被旧值覆盖 —— 这次远程更新直接丢失，且设备不报错。**
⇒ 对我们的直接含义：**保活重发的间隔若与 200 ms 闭眼窗口对齐，会出现「每隔 N 个周期丢一次表情」的随机丢帧**。保活周期**不要**取 200 ms 的整数倍附近，或干脆取 ~500 ms 这类与 200 ms 非整除的值。

**仍缺什么**：真机上「闭眼窗口内下发被吞」的**实际观感**（表现为「表情偶尔不生效一次」）。

### 2.5 给我们后端 API 的 5 条直接结论

1. **帧格式**：1 字节类型 + 4 字节大端长度 + payload；**payload 前 12 字节是 MAC**（`server/README.MD:931-936`、`web_socket.go:553-565`）。
2. **优先级**：**动作走 `0x14`，表情走 `0x03`**。`0x14` 绕 modify lock、自带 RGB 与舵机 ⇒ 自研动作合成的唯一正路（与 53 号结论 4 一致）。
3. **必须自己做保活**：官方栈零保活。**保活周期建议 500 ms 左右**（非 200 ms 整数倍，避开闭眼窗口；显著快于 idle 最短间隔 2000 ms）。
4. **关键帧 `durationMs ≥ 300`**：否则 RGB 渐变来不及到位（`neon_light.cpp:14`）。
5. **关键帧最后一条必须是「收尾帧」**（回到中性表情 + `yaw/pitch = 0` + `#000000`），因为**播完不自动复位**（§1.6）。
