## 0. 一句话结论

官方固件的**表情通道比想象中窄、动作通道比想象中宽**：

- **表情通道（ControlAvatar 0x13）只认 3 个元素 × 5 个字段，且撑不过 2 秒**就被设备自己的空闲动画覆盖。
- **动作通道（DanceSequence 0x14）是一条完整的关键帧时间轴**，一次串起「脸 + 脖子 + 双 RGB 灯」，而且**绕过 modify lock**——这才是我们做「程序化动作合成」应该走的路。

⇒ **护城河②（韵律表达）从「造表情」重新定义为「造时间轴 + 持续保活调度器」。**

## 2. 情绪 → 渲染的映射表（关键取证）

`firmware/main/stackchan/avatar/skins/default/eyes.cpp:87-120` `DefaultEyes::setEmotion`

| Emotion | eye weight（眼睑下沉） | eye rotation（左眼，0.1°） | 右眼 rotation | 视觉含义 |
|---|---|---|---|---|
| Neutral | 100 | 0 | 0 | 全睁、平视 |
| Happy | 72 | 1550 | -1550 | 眯眼上斜（笑眼） |
| Angry | 70 | 450 | -450 | 眼角下压（凶） |
| Sad | 70 | -400 | 400 | 眼角上挑（哭） |
| Doubt | 75 | 0 | 0 | 半眯、眉不动（狐疑） |
| Sleepy | 35 | -50 | 50 | 几乎闭（困） |

映射实现是 `apply_style(weight, rotation)`：**直接调用 `setWeight()` + `setRotation()`**。

### 2.1 ⭐ 由此推出的三条硬事实

**事实 A：情绪会覆盖远程表情。**
`setEmotion` 写的就是 `weight`/`rotation` 这两个字段，和 ControlAvatar JSON 写的是同一批字段 ⇒ **后写者胜**。设备端任何一次情绪变更都会抹掉我们刚下发的眼睛参数。

**事实 B：「忽略情绪」开关是死代码。**
`Element::setIgnoreEmotion()`（`element.h:68`）本意是让远程表情豁免情绪覆盖，但**全仓 grep 只有声明，没有任何调用点**：

```
origin/main:firmware/main/stackchan/avatar/avatar/elements/element.h:68:    virtual void setIgnoreEmotion(bool ignore)
```

⇒ 官方固件没有给我们这个豁免能力。

**事实 C：情绪只能由设备自己触发。**
`setEmotion` 的真实调用点只有两处：

| 位置 | 触发 | 持续 |
|---|---|---|
| `firmware/main/apps/app_setup/workers/connectivity.cpp:239` | 配网完成后 | 永久 |
| `firmware/main/apps/app_avatar/app_avatar.cpp:198,201` | 文本内容含 `hello`/`hi`/`love` | 2000 ms |

⇒ **远程无法直接设置情绪**，只能通过「发一条含 hello/hi/love 的文本消息」间接触发 Happy。

## 3. ControlAvatar（0x13）JSON 契约

`firmware/main/stackchan/json/json_helper.cpp:41-78` `update_from_json(Avatar*, const char*)`

实际被解析的字段**只有**：

```
{
  "leftEye":  { "x": int, "y": int, "rotation": int, "weight": int, "size": int },
  "rightEye": { "x": int, "y": int, "rotation": int, "weight": int, "size": int },
  "mouth":    { "x": int, "y": int, "rotation": int, "weight": int, "size": int }
}
```

### 3.1 不被解析的（重要）

| 字段 | 是否解析 | 后果 |
|---|---|---|
| `speechBubble` | ❌ | 气泡**不能**通过 ControlAvatar 下发 |
| `visible` | ❌ | 眼睛/嘴的显隐**不能**远程控制 |
| `emotion` | ❌ | 情绪**不能**远程设置（见 §2.1 事实 C） |
| `ignoreEmotion` | ❌ | 同上 |
| 任何其它 key | ❌ | ArduinoJson 逐字段 `is<int>()` 判断，未知字段**静默忽略** |

> ⚠️ 未知字段静默忽略 ⇒ **我们下发拼错的 key 不会报错，只会「什么都没发生」**。后端必须有本地 schema 校验，不能指望设备报错。

### 3.2 语义与量纲

| 字段 | 范围 | 含义 |
|---|---|---|
| `x`, `y` | -100 ~ 100 | 归一化位置（`Element::setPosition` 内 clamp） |
| `rotation` | 0 ~ 3600 | 0.1 度单位（3600 = 360°） |
| `weight` | 0 ~ 100 | 归一化强度；眼睛=眼睑下沉，嘴=开合 |
| `size` | -100 ~ 100 | 眼睛大小（0 = 正常） |

眼睛的渲染映射（`eyes.cpp:14-18`）：眼位基准 `(-70, -16)`，位置偏移限幅 `±16`，容器尺寸限幅 `(8, 32)`。

## 4. ⭐⭐ 远程表情撑不过 2 秒（本轮最重要的工程约束）

### 4.1 事实链

1. `firmware/main/stackchan/stackchan.h:151-156` `updateAvatarFromJson()` 直接调 `avatar::update_from_json()`，**全程不碰 modify lock**。
2. 固件里有三个 modifier 会持续改写**同一批字段**，且它们都先检查 `avatar.isModifyLocked()`：

| Modifier | 文件:行 | 周期 | 改写的字段 |
|---|---|---|---|
| `BlinkModifier` | `modifiers/blink.h:23,48` | 睁 5200 ms / 闭 200 ms | eye `weight` |
| `IdleExpressionModifier` | `modifiers/idle_expression.h:20,29,43-50` | 2000 ~ 6000 ms 随机 | eye `position`（70% 概率「眼神游离」）、mouth `position` |
| `BreathModifier` | `modifiers/breath.h` | cycle 6600 ms，amplitude 16 | `position` |

3. 远程路径**从不加锁** ⇒ `isModifyLocked()` 恒为 false ⇒ 三个 modifier 照常运行。

### 4.2 结论

> **远程下发的表情，实际寿命 ≤ 2 秒**（最短的 idle 间隔），此后会被设备自身的眨眼 / 眼神游离 / 呼吸覆盖。

### 4.3 对后端的三条硬性要求

1. **不能「发一次表情然后放着」**。表情必须是**保活流**：像心跳一样周期性重发，直到状态转移。
2. **保活周期必须 < 2000 ms**（留裕量建议 800 ~ 1200 ms），否则会出现肉眼可见的「表情抽搐」。
3. **保活流量必须计入成本**。每个表情帧是一帧 WebSocket 二进制包；我们必须评估「同时在线 N 台设备 × 1.2 次/秒」的带宽与云端开销。

> 💡 **这条路也可能是护城河**：保活调度器需要在「设备空闲动画」和「远程表情」之间做**时间片仲裁**——这是纯工程细节，但直接决定「它的表情听起来像活的」还是「像被人在遥控」。

### 4.4 备选：走 DanceSequence 通道（§5 展开）

关键帧通道**绕过 modify lock**（`animation.cpp` `Keyframe::apply()` 直接 set），所以不存在被覆盖问题。

## 5. ⭐ DanceSequence（0x14）= 程序化动作合成的官方通道

### 5.1 接线

`firmware/main/apps/app_avatar/app_avatar.cpp:206-214`

```
onWsDanceData(data)
  → stackchan::animation::parse_sequence_from_json(data)   // json_helper.cpp:178
  → DanceModifier(sequence)                                  // modifiers/dance.h
```

### 5.2 JSON schema（实测自 `json_helper.cpp:178-233`）

顶层是**数组**，每个元素是一个关键帧：

```json
[
  {
    "leftEye":     { "x": -10, "y": 0, "rotation": 0, "weight": 50, "size": 0 },
    "rightEye":    { "x": -10, "y": 0, "rotation": 0, "weight": 50, "size": 0 },
    "mouth":       { "x": 0,   "y": 0, "rotation": 0, "weight": 50, "size": 0 },
    "yawServo":    { "angle": 300,  "speed": 200 },
    "pitchServo":  { "angle": -100, "speed": 200 },
    "leftRgbColor":  "#FF6D60",
    "rightRgbColor": "#8FD3F4",
    "durationMs": 800
  }
]
```

### 5.3 字段语义

| 字段 | 类型 | 单位/范围 | 作用 |
|---|---|---|---|
| `leftEye`/`rightEye`/`mouth` | object | 同 §3.2 | 脸 |
| `yawServo`/`pitchServo`.`angle` | int | **0.1 度**（同 ControlMotion） | 水平/垂直舵机目标角 |
| `yawServo`/`pitchServo`.`speed` | int | 舵机速度档位 | 运动快慢 |
| `leftRgbColor`/`rightRgbColor` | string | `#RRGGBB` | 左右两侧 RGB 灯颜色 |
| `durationMs` | int | 毫秒 | 本关键帧停留时长 |

### 5.4 播放语义（`firmware/main/stackchan/animation/animation.cpp`）

`Keyframe::apply()`：

```cpp
feat.setPosition(kf.position);  feat.setRotation(kf.rotation);
feat.setWeight(kf.weight);      feat.setSize(kf.size);
servo.moveWithSpeed(kf.angle, kf.speed);          // ⚠️ 见 §5.4 更正：speed 实为弹簧刚度
stackchan.leftNeonLight().setColor(leftRgbColor);
stackchan.rightNeonLight().setColor(rightRgbColor);
```

| 特性 | 结论 |
|---|---|
| 是否绕过 modify lock | ✅ **绕过**（直接 set，不查锁） |
| 舵机运动方式 | ⚠️ **已更正（2026-10-24 第 2 轮，57 号实测）**：`moveWithSpeed(angle, speed)` 实际走的是 **`moveWithSpringParams`**，且 `speed` 不是舵机速度单位，而是**弹簧刚度**：`stiffness = 10 + (speed/1000)² × 640`；物理写入恒为 `WritePos(id, pos, Time=20, Speed=0)` ⇒ **JSON 的 speed 到不了舵机速度寄存器** |
| 插值 | ❌ **无插值**。`Timeline::update()` 到 `durationMs` 边界**硬切**到下一关键帧 |
| 循环 | 默认 `loop=false`，播完 `isFinished()` → `requestDestroy()` |
| 打断 | 屏幕点击 → `removeModifier(_dance_modifier_id)`（`app_avatar.cpp:246-252`） |

> ⚠️ **「硬切无插值」是我们自研动作的硬约束**：想做出顺滑的转头，必须自己插值生成密集关键帧（例如把 800 ms 的转头拆成 8 个 100 ms 帧）。这也是我们动作合成器的主要工作量所在。

### 5.5 内置的 4 条现成序列（`modifiers/dance.h`）

| 序列 | 关键帧数 | 语义 |
|---|---|---|
| `Happy` | 6 | 左右摇摆 + 眯眼 + 张嘴 |
| `Robot` | 6 | 生硬、机械的折线动作 + 瞪眼 |
| `Panic` | 8 | 高频左右抖 + 瞪眼大张嘴 |
| `LookAround` | 5 | 缓慢扫视四周 + 嘴微张 |

⇒ **官方已经给了「动作=关键帧时间轴」的心智模型和 4 个样例**，我们要做的不是发明格式，而是**把「情绪 → 时间轴」的映射做成可积累的资产**。

## 6. TextMessage（0x07）→ 对话气泡 + 说话动作 + 情绪

`firmware/main/apps/app_avatar/app_avatar.cpp:186-204`

```cpp
GetHAL().onWsTextMessage.connect([&](const WsTextMessage_t& message) {
    stackchan.addModifier(std::make_unique<TimedSpeechModifier>(
        fmt::format("{} says: {}", message.name, message.content), 6000));
    stackchan.addModifier(std::make_unique<SpeakingModifier>(2000));
    if (contains_word(message.content, {"hello", "hi"})) {
        stackchan.addModifier(std::make_unique<TimedEmotionModifier>(avatar::Emotion::Happy, 2000));
    } else if (contains_word(message.content, {"love"})) {
        stackchan.addModifier(std::make_unique<TimedEmotionModifier>(avatar::Emotion::Happy, 2000));
    }
});
```

| 效果 | 参数 | 来源 |
|---|---|---|
| 气泡显示 `"{name} says: {content}"` | 6000 ms | `TimedSpeechModifier` |
| 嘴开合 | 2000 ms，开合间隔 180 ms，权重随机 | `SpeakingModifier`（`modifiers/speaking.h`） |
| 情绪 Happy | 2000 ms | 内容含 `hello`/`hi`/`love` 时 |

### 6.1 限制

- **气泡文案格式不可定制**（固定 `"{name} says: {content}"`），不能做多行排版、不能加前缀标签。
- ⚠️⚠️ **中文基本渲染不出来（2026-10-24 第 2 轮，57 号实测字库）**：StackChan 板卡字体为 `font_puhui_basic_20_4`（`firmware/main/CMakeLists.txt:118`），实测**仅 801 字形 / 184 个汉字**；常用字「你好中文说猫」**全部缺字形**，全角逗号与省略号亦无。
  ⇒ **对策：后端只向 0x07 下发 ASCII / emoji**，中文一律不进设备气泡（中文只走 App 端与 TTS 音频）。
- **中文气泡能否正常渲染：未验证**（需真机 + 字体 `setSpeechTextFont` 确认）。
- 气泡 API 在 `firmware/main/stackchan/avatar/avatar/avatar.h:79-97`（`setSpeech` / `clearSpeech` / `setSpeechTextFont`），另有 `stackchan_display.cc:397/399` 的内部调用路径。

### 7.1 ⭐ 官方身体感知的真实底座

**是 BMI270 的加速度事件 + 触摸手势，不是摄像头人脸检测。**

- `imu.h:22-27`：订阅 `GetHAL().onImuMotionEvent`，只关心 `ImuMotionEvent::Shake`。
- `imu.h:41-49`：摇晃时每 600 ms 交替 `mouth().setRotation(±25)` + `setWeight(65)` ⇒ **嘴在抖 = 害怕/惊讶**。
- `head_pet.h:24-31`：订阅 `GetHAL().onHeadPetGesture`，区分 `SwipeForward` / `SwipeBackward` / `Release` ⇒ **能区分摸头方向和松手时刻**。

⇒ 对我们「在场感知」护城河的直接影响：**官方已经占住了「物理接触」和「晃动」两种身体信号**，而且做得比我们能想到的更细。我们若要在这条线上建立壁垒，**必须走「端侧更高级的感知」（人体存在/朝向/距离）而不是重复 IMU 抖动**。

### 7.2 装饰器（情绪之外的额外表达）

`firmware/main/stackchan/avatar/decorators/`：`angry` / `dizzy` / `shy` / `sweat` / `heart`（含 `assets/decorator_*.c` 位图）。

⇒ 设备有「害羞」「冒汗」「爱心」这类**超出 6 种情绪的叠加表达**，但它们由固件内部逻辑驱动，**不走远程 JSON 通道**。

## 9. 对我们的 9 条结论

| # | 结论 | 影响 |
|---|---|---|
| 1 | 远程表情**撑不过 2 秒**，必须保活重发（周期 < 2000 ms） | 后端架构：新增「表情保活调度器」；成本模型要含带宽 |
| 2 | 未知 JSON key **静默忽略**，设备不报错 | 后端必须有本地 schema 校验 + 单测 |
| 3 | 情绪**不可远程设置**，只有 hello/hi/love 能触发 Happy | 「情绪引擎」只能建在 6 种情绪 + 参数连续空间上，不能指望设备有丰富情绪态 |
| 4 | 关键帧通道（0x14）**绕过 modify lock**、含**双 RGB 灯**、含**颈部** | 程序化动作合成的**主战场是 0x14，不是 0x13** |
| 5 | 关键帧**硬切无插值**（时间维） | 自研动作必须自己插值（时间维）。⚠️ **原「舵机无弹簧」已作废** —— 舵机其实走弹簧刚度模型（§5.4），但**刚度由 speed 间接决定**，我们不能直接指定弹簧参数 |
| 6 | 气泡文案格式固定 `"{name} says: {content}"`，6000 ms | 气泡是**副产品**，不能当主表达界面；主界面仍在手机 |
| 7 | 官方身体感知 = **IMU 摇晃 + 触摸手势** | 「在场感知」壁垒必须走**端侧人体存在/朝向**，不能重复 IMU |
| 8 | 装饰器（shy/sweat/heart/dizzy/angry）**不走远程通道** | 想用这些效果 ⇒ 需要固件改动 ⇒ **与我们「固件零改动」的决策冲突**，已排除 |
| 9 | 设备侧枚举**跳过 0x15/0x16/0x17** | 云端下发前过滤；与 05 号 §3「接受乐观值」裁决一致 |
