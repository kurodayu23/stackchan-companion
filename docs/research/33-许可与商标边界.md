# 33 · 许可与商标边界：我们的仓库能不能合法公开

> 核实日期：2026-10-23
> 核实者：我本人（主会话，许可原文用本地 git clone 实读）
> 触发原因：用户的目标是**把项目发布到 GitHub 当求职作品**。
> 发布前必须先搞清楚：**哪些代码能拿走、必须保留什么署名、哪些东西碰了会让整个仓库变成别人的许可证。**

---

## 一、一句话结论

> **可以公开，MIT 允许。但有 4 条硬纪律必须写进仓库，其中 1 条是红线（AGPL）。**
> 另外有一件事必须做：**我们的仓库要明确声明"非官方第三方项目"** ——
> 因为我们用的是官方硬件、官方表情引擎、官方协议，这是**最容易让用户误认**的组合。

## 二、官方仓库的许可实况（`git show origin/main:<path>` 实读）

### 2.1 各目录 LICENSE 文件

| 路径 | 有 LICENSE？ | 内容 |
|---|---|---|
| **仓库根** | ❌ **没有** | — |

### 2.2 但每个源文件都带 SPDX 头（实读样例）

```c
/* SPDX-FileCopyrightText: 2026 M5Stack Technology CO LTD
 * SPDX-License-Identifier: MIT
```

在 `firmware/main/hal/hal_ws_avatar.cpp`、`app/lib/main.dart`、`server/main.go` 上都实测到同一格式。

**⇒ 事实上的许可**：**全仓库 MIT**（`app/` 缺 LICENSE 文件属于上游疏漏，SPDX 声明已覆盖）。
**⚠️ 但法理上 `app/` 无明确许可文件** → **我们不碰 `app/`**（我们要用原生 SwiftUI 从零重写 iOS 端），问题自动消失。

### 2.3 第三方子许可（固件内嵌）

| 路径 | 许可 | 版权 |
|---|---|---|
| `firmware/main/hal/drivers/FTServo_Arduino/LICENSE` | **MIT** | Copyright (c) 2024 ftservo |
| `firmware/main/hal/drivers/bmi270/BMI270_SensorAPI/LICENSE` | **BSD-3-Clause** | Copyright (c) 2023 Bosch Sensortec GmbH |

### 2.4 根 README 里**没有任何**许可 / 商标 / 署名条款
实读 `origin/main:README.md`，`licen|trademark|copyright|CC-BY|attribution` **零命中**。
→ 上游没有在 README 里写许可条款，许可只体现在 LICENSE 文件与 SPDX 头里。**我们的 fork 必须自己补上明确声明。**

## 三、⭐ 四条硬纪律（写进我们仓库的 README 与 LICENSE）

### 纪律 1 —— MIT 的义务：保留原始声明
MIT 只要求两件事：**保留版权声明** + **保留许可文本**。
**做法**：
- 我们的仓库根放 `LICENSE`，正文用 MIT，**版权行写清楚两段**：
  ```
  Copyright (c) 2026 StackChan Contributors (our original work)
  Portions Copyright (c) 2026 M5Stack Technology CO LTD (derived from m5stack/StackChan, MIT)
  ```
- fork 下来的**每一个文件保留原 SPDX 头**（不要"整理"掉）。
- 在 README 的 Credits 段落列出：`m5stack/StackChan`（MIT）· `Bosch BMI270`（BSD-3-Clause）· `ftservo`（MIT）· Twemoji（CC-BY 4.0）· 以及我们实际引入的其他开源项目。

### 纪律 2 —— ⭐⭐ 红线：AGPL 项目只能借鉴，不能复制代码
`23` 号文档实测：**`SillyTavern` 的许可是 AGPL-3.0**（另有 `openai/swarm` 等已废弃项）。

**AGPL 的传染性**：一旦我们**复制**了 AGPL 项目的代码（哪怕只是一段角色卡解析逻辑），
**我们整个仓库就必须以 AGPL 发布** —— 这与"求职作品想用什么许可自己定"的意图直接冲突，
而且会把我们所有自研代码变成强 copyleft。

**⇒ 纪律**：
- AGPL / GPL 项目（`SillyTavern` 等）：**只读设计思路与公开的格式规范，不复制任何代码**。
- 采纳其思路时**独立实现**，并在文档里写"参考了 X 的公开设计"。
- 每次引入外部代码前，先确认它不是 AGPL/GPL 且与我们要选的许可兼容。
- ⚠️ **例外要特别小心**：`18` 号 §6.1 的人格包格式参考了 SillyTavern 的 **Card V2 格式** ——
  **格式规范本身通常不受版权保护**（思想/接口），但**其实现代码受保护**。
  ⇒ 我们**只对齐字段名与语义，自己写解析器**，不复制其 JSON schema 文件本体。

### 纪律 3 —— 商标与形象：我们的 App 不能长得像官方的
官方 StackChan 的**机身、脸、官方 App 图标**是 M5Stack 的商标与角色形象资产。

**⇒ 纪律**（与 `29` 号 L4 一致）：
- **我们的 App 图标不画官方小栈**（29 号已定：单符号、填充重叠、无文字、无光效、矢量分层、6 种外观一致）。
- 我们的产品**不使用 "StackChan" 作为自己的 App 名或商标**（那是 M5Stack 的商标）。
  → 用我们自己的项目名，并在 README 显著位置写：
  > *"This is an unofficial, community-driven project. StackChan is a trademark of M5Stack Technology CO LTD. This project is not affiliated with or endorsed by M5Stack."*
- 官方表情引擎的资产**保留原来源标注**，不包装成我们的原创美术。

### 纪律 4 —— 引用不存在的资产 = 公开的谎言
`23` 号文档实测（我们 worker 读 git 树得到）：
- 官方 server README **三处声称**含 "Prebuilt Flutter Web admin assets" / `web/management`，
  但 `git ls-tree -- server/web` = **0 行**，`git grep "web/management"` 只命中 README 与 `cmd.go`。
  → **fork 后访问 `/` 会直接 404，管理后台必须 100% 自建。**
- 官方固件里 `espressif2022/esp_emote_expression` 是**被注释掉的**依赖
  （该组件 2025-11-30 才建仓、仅 8★、**许可未取得**）。

**⇒ 纪律**：我们的文档里**不引用上游并不存在的东西**。凡是说"官方提供了 X"，必须用
`git ls-tree` / `git show` 实测过存在。**这条正是我们情报库一直在执行的取数纪律，现在扩展到对外发布。**

## 六、未核实范围（如实登记）

1. **`app/` 在法理上到底算什么许可** —— 上游缺 LICENSE 文件，只有 SPDX 头。**我们不碰它，所以对我们无影响**，但若有人问"官方 App 到底什么许可"，答案是"未明确"。
2. **根目录无 LICENSE 对整个仓库的影响** —— 上游根目录缺 LICENSE，严格法理下仓库整体许可不明；但各子目录有。**我们按各子目录的许可来用。**
3. **M5Stack 是否另有商标注册** —— 未查商标数据库。**我们的做法（不用其商标、不复制其形象）已经规避了风险**，不需要精确知道注册范围。
4. **表情引擎内含的美术资产（除 Twemoji 外）的许可** —— 官方表情是**程序化绘制**（17 号 §4 实测：6 情绪 + 5 装饰器位图 130.9 KB），**位图装饰器的原始出处与许可未逐个核实**。→ 发布前需查 `assets` 目录内每个位图的来源。
5. **`78/xiaozhi-assets-generator` 生成的资产许可** —— 未核实。
6. **`espressif2022/esp_emote_expression` 的许可** —— 未取得（且官方固件里是注释状态）。
7. **各 worker 实测的第三方许可是否与上游当前版本一致** —— 需发布前复核。
