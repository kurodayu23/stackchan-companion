## 二、⭐ 事故 1：首提交差点把官方 3D 模型带上去（许可红线）

|---|---|
| `docs/spec/00` **O-12** | 「✅ **已定：不用**」官方 `stack_chan_model.glb`（官方 `app/` 目录**无 LICENSE** ⇒ 许可未取得） |

⇒ 这正是「门禁只查已登记的类别」的真实边界：**规则之外的东西不会自己变成问题**。

1. **移出版本控制**：`git rm --cached`（文件**留在本机**，本地仍能看 3D），

2. **补判据**（这是重点）：`tools/repo_release_check.py` 新增 **`OFFICIAL_ASSET_IN_REPO`**，
   判据覆盖三件事：
   - 官方资产**文件名**（`stack_chan_model.glb`）；
   - **任何 3D 模型扩展名**（`.glb` / `.gltf` / `.fbx` / `.obj`）
     —— 本仓的 3D 预览一律是**程序化几何体**（three.js MIT），仓内出现模型文件就是误入；
   - 官方目录名 `app/assets/` 出现在仓内任意路径。

   自检夹具同步加了一个假 GLB ⇒ `repo_release_check.py --self-test` 由 16 个检查码增至 **17 个**，
   级别符合预期（FAIL）。

> 顺带处理：**全仓零引用的孤儿图** `ui-prototype/assets/photo.jpg`（751 KB，出处未核实）

### 3.1 事故 3：iOS 那条线（本机根本没编过）

| 问题 | 细节 | 修法 |

### 3.2 判据补强：把「读者可见的 404」和「合法的本地生成物」分开

事故 3 暴露了一个**门禁盲区**：`check_links.py` 查的是**本机文件系统**，
所以「本机有、但被 `.gitignore` 排除」的路径**本机永远查不出来**，只有 CI 才炸。

修法（`tools/check_links.py`）：

| 场景 | 处置 | 理由 |
|---|---|---|
| **行内代码**里提到本地生成物（如 `` `prototype/output/` ``） | **INFO** | 这是在**说明**「产物落在哪」，读者不会去点 |
| **markdown 链接**指向本地生成物 | **FAIL** | 读者点开就是 404 |
| 路径本身**不存在**且不是本地生成物 | **FAIL**（原有行为） | 真坏链 |

配套加了 `_resolve_repo_rel()`：链接**先按所在 `.md` 的目录解析、再按仓库根解析**，
然后**只对解析出来的那个路径**判忽略规则。
（不解析就判会误伤：`docs/research/75-真实MiniMax端到端闭环实测与TTS不可复现性.md` 里的 `runs/xxx.log` 其实是
`docs/research/runs/xxx.log`，它被 `.gitignore` 的 `!docs/research/runs/*.log` **反选**回库了。）

自检同步加了两个用例 ⇒ `check_links.py --self-test` **29 → 30 项**。

## 四、⭐ 绕开 github.com：本机到 GitHub 的网络现实

发布时才发现：**本机 `github.com:443` 不通**，`api.github.com` 通。

| 通道 | 状态 | 说明 |
|---|---|---|
| `api.github.com` | ✅ 通 | GitHub REST / GraphQL |
| `github.com:443` | ❌ 不通 | `git push` 的 smart-HTTP 握手走这里 |
| `ssh.github.com:443` | ✅ 通 | 但**账号没登记公钥** ⇒ `Permission denied (publickey)` |
| `codeload.github.com` | ❌ 不通 | |
| 系统代理 | 关闭（`ProxyEnable=0`，但 `ProxyServer` 仍留着 `127.0.0.1:7897`） | Clash 内核**没在跑**（只有 `clash-verge-service` 控制口在监听 33211） |

⇒ **不能开代理**（用户明令「别开代理了影响我工作」），于是走 **GitHub REST 的 Git Data API** 上传：

1. `POST /git/blobs` 逐个上传（**GitHub 的 blob SHA 就是 git 的 blob SHA-1**
   ⇒ 本地先算 SHA、GET 一下，已存在就跳过，**省限流额度**）；
2. `POST /git/trees` → `POST /git/commits` → `PATCH /git/refs/heads/main`（force）。
3. ⚠️ **Git Data API 在完全空仓上会 409 `Git Repository is empty`**
   ⇒ 先用 Contents API 建一个占位提交把仓变成非空，最后**强制**把 `main` 指到真根提交，
   占位提交遂成为不可达对象、**不出现在历史里**。
4. ⚠️ **次级限流**：写类请求 900 点/分，创建 blob 每个 5 点
   ⇒ 全局限速 ~2 次/秒，并对 403 次级限流自动退避 65 秒重试。
5. ⚠️ **API 造的 commit 与本地 commit 是两个对象**（时区 / 消息尾行不同）
   ⇒ 本地把远端 commit 对象**逐字节重建**出来（`git hash-object -w -t commit`）
   再 `update-ref`，**本地 main 与远端指向同一个 sha** ⇒ 以后 push 不会撞「非快进」。

**校验**：远端 `tree` SHA 与本地 `HEAD^{tree}` **完全一致**（`2762ece1…`）⇒ 内容字节相同。

## 五之二、第二轮 CI：iOS 线**第一次真的编译**

第一轮把 3 类红项修掉后重新推送、复跑 ⇒ **CI 的 5 个 job 里 4 个转绿，但 `Docs & release gates` 与 iOS 的 2 个 job 仍红**。
这一轮才是真正暴露问题的一轮。

### 5.2.1 `check_links.py --self-test` 在 Linux 上挂（29/30）

失败用例：**「大小写不敏感命中」**。

| 环节 | Windows（本机） | Linux（CI） |
|---|---|---|
| `os.path.exists("TOOLS/REAL.PY")` | ✅ **真**（NTFS 大小写不敏感） | ❌ **假**（ext4 大小写敏感） |
| 旧实现结论 | PASS | **FAIL** |

⇒ **同一个用例，本机永远绿、CI 永远红** —— 这就是「只在 Windows 上验过」的典型盲区。
根因：旧 `_exists()` 只用 `os.path.exists`，把「大小写不敏感」**外包给了操作系统**。
修法：改成**逐段 `listdir` 做不区分大小写的真实名解析**（命中后把路径换成真实名再往下走），
⇒ 两端结论一致，且**不依赖文件系统的大小写语义**。

### 5.2.2 iOS 单测：9 条断言不符（不是环境问题，是**真 bug**）

`swift test` 真跑起来后，**9 条断言红了**。逐条定性：

| `testJSONSerializationPreservesIntegerTypes` | `XCTAssertFalse` 失败 | **旧实现的「未验证假设」被证伪** | 见 5.2.3 |
| `testIntegerJSONNumberRejectsFractionalValue` | 抛 NSCocoaError 3840 | 同上 | 同上 |
| `testTopLevelNumberIsRejected` | 抛 NSCocoaError 3840 | 同上 | 同上 |

### 5.2.3 ⭐ 最值钱的一条：**「运行时未验证的假设」被 CI 证伪**

`JSONSchema.isIntegerJSONNumber` 的旧实现依赖一条**写在注释里的假设**：

> 「`JSONSerialization` 对 `10` 返回**整数型** NSNumber、对 `10.0` 返回**浮点型** NSNumber」

并声明「**【运行时未验证】** —— 本机（Windows）没有 Swift 编译器」，由单测在 macOS CI 守门。

**2026-10-30 第一次真跑 ⇒ 这条假设直接被推翻**，而且比预想的更糟：
`JSONSerialization.jsonObject(with:options:)` **连顶层片段都解析不了** ——
`"10"` / `"10.0"` / `"10.5"` 全部抛 `NSCocoaError 3840`
（"JSON text did not start with array or object and option to allow fragments not set"），
⇒ 顶层是数字的 payload **根本走不到我们的 `SchemaError`**，直接抛 Foundation 的错。

⇒ **处置：不再依赖 Foundation 的数字类型**。新增 `CoreProtocol/JSONValue.swift`
（**自研 JSON 解析器**）：int / double **按字面量判定**（出现 `.` / `e` / `E` ⇒ double），
与固件 ArduinoJson 的 `is<int>()` 语义一一对应，**与平台、Foundation 版本完全无关**；
顺带顶层片段能被正常解析成值，再由 schema 层用**我们自己的错误类型**拒收。
`JSONSchema` / `DanceSequence` 全部改用它，`encode` 也改用自研序列化器
（`JSONSerialization` 可能把整数重写成 `10.0` ⇒ **我们自己编的帧会被固件静默忽略**）。

### 5.2.5 第三轮 CI：又是 2 处红，一处是**同一类 Windows 假阴性**

前两轮修完后复跑 ⇒ **iOS 单测转绿 ✅**（9 条断言 + 自研 JSON 解析器全过），
但还剩两处红：

#### (a) `repo_release_check.py` 在 Linux 上误报「坏链」

`[MD_LINK_BROKEN] docs/research/18-开源AI陪伴记忆人格语音栈.md:220 — 相对链接指向不存在的路径：...`

那行是**引用上游 README 原文的片段**：

```text
`... [Kokoro](...), [MiniMax](https://docs.pipecat.ai/…), [Mistral](...) ...`
```

`...` 是**省略号占位**，根本不是链接。⇒ 但判定器把它当成了相对链接。

⚠️ **为什么本机永远绿、CI 永远红**：
`os.path.exists("docs\\research\\...")` 在 **Windows 上返回 True** ——
Win32 会**剥掉路径分量末尾的点**，`...` 被当成空分量 ⇒ 实际解析成 `docs\research`（存在）；
Linux 上 `...` 就是个不存在的文件名 ⇒ False。
⇒ **又一处 Windows 独占的假阴性**（与 5.2.1 同类）。

修法（三条一起）：
1. **行内代码跨度里的方括号不是链接** —— markdown 把 `` `[x](y)` `` 渲染成代码，
   原来只跳过「引号跨度」，漏了「代码跨度」；
2. **省略号占位不是链接** —— 目标里出现**整段都是点**的分量（`...`）就跳过；
3. **末尾带点的分量不采信 `os.path.exists`** —— 这类路径在两端的结论相反，
   不能让平台差异掩盖真坏链。

⇒ 自检夹具的「干净夹具」里补了**同样的行** ⇒ 扫描器一回归就变红（有回归护栏）。

#### (b) iOS Build 还差 2 处编译错

`StackChanLiveActivityWidget.swift:21 — cannot find 'StackChanAttributes' in scope`
⇒ widget extension 链接了共享框架 `StackChanShared`（`project.yml` 里依赖是对的），
但**源文件没有 `import StackChanShared`** ⇒ 补 import。

### 5.2.6 这一轮的通用教训

1. **「本机绿」≠「CI 绿」**：大小写敏感、`os.path` 语义、Foundation 行为差异都只在某一端成立。
2. **「写了单测」≠「单测跑过」**：那 9 条断言**一次都没被运行过** —— 写完就当过了。
3. **注释里写「未验证」的假设 ⇒ 必须有一端能真跑它**，否则它就是个定时炸弹。
   本次把它换成**自研解析器**，假设直接消失（不再依赖任何 Foundation 行为）。
4. **静态检查器（`validate_project.py`）只能查结构**，查不出「类型不存在」「缺 import」这类
   **语义级**错误 ⇒ 只有真编译器能抓。
5. ⭐ **判定器自己也会骗人**：本轮两条红里有两条是**判定器在 Windows 上给假阴性**
   （大小写、尾点剥除）⇒ **判定器必须自己也有跨平台自检**，
   否则「门禁全绿」只是「在 Windows 上全绿」。
