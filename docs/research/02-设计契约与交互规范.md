# 02 · 设计契约与交互规范（设备屏 320×240 → iOS App 迁移研究）

> 来源：`output/design/stackchan-screen-redesign-20260720-v1/`（DESIGN.md、screen-redesign.html）与 `-v2/`（DESIGN.md、INTERACTION.md、prototype.html），辅以 `YYC.html` / `birthday-letter.html`（2026-08-02，移动端尺寸的同源产物）。

## 0. 结论速览

1. **项目里存在三代视觉，不是两代。** v1 深色 OLED（`#080A0D` + 珊瑚粉）→ v2 文档「柔雾樱花」浅色（`#F1DFE5` + 莓红 `#D94F78`）→ v2 原型 7/22 起改回深色「StackChan OS」（`#080A0F` + 青 `#00D2FF`）。**最终落地的是第三代深色系统**，`prototype.html`（最后修改 2026-07-31 16:40）是唯一活代码。
2. **成文契约与实现已漂移。** v2 `DESIGN.md` / `INTERACTION.md` 描述的是浅色「柔雾樱花」，而 `prototype.html` 的实际 CSS 里**没有任何一个柔雾樱花色值**。iOS 端若照抄文档会与设备屏脱节。
3. **可迁移到 iOS 的核心资产不是数值，而是结构**：单焦点层级、4/8/12/16/24 间距节奏、44pt 触摸区、`cubic-bezier(0.2,0.8,0.2,1)` 主曲线、每功能一个主符号、克制的强调色、明确的禁止项。
4. **不可迁移**：字号上限（27px）、300×166 卡片、320×240 画布、单卡轮播的物理约束、44px 触摸区在 iOS 上的"分辨率无关"含义已变（iOS 是 pt 且 HIG 同为 44pt）。
5. **令牌管理建议：混合**——DTCG 格式作单一真源 + Style Dictionary 编译 + SwiftUI/LVGL 侧薄壳自造，不引入现成 SwiftUI 组件库（审美主导，气质不匹配）。

### 1.4 三代对比与演进原因

| 维度 | v1 深色 OLED | v2 文档 柔雾樱花 | v2 原型 最终态 StackChan OS | 谁是最终 |
| --- | --- | --- | --- | --- |
| 画布 | `#080A0D` 纯黑 | `#F1DFE5` 灰樱花粉 | `#080A0F` 近黑蓝 | 深色 |
| 强调 | 珊瑚粉 `#FF7C82` | 莓红 `#D94F78` | 青 `#00D2FF` + 8 组功能色 | 功能色 |
| 表面层级 | 3 层灰阶 | 2 层暖白 | 4–5 层冷灰 | 深色 |
| 圆角 | 10–12 | 10–16 | 14–27 | 深色（更大） |
| 阴影 | 有重投影（`0 12px 34px`） | 边框优先于重阴影 | 只保留一层轻投影 + 1px 边 | 深色（更克制） |
| 图案 | 单色字形图标 | 3D「小栈软质物件」插画 | 线性 SVG 图标（stroke 1.7） | 深色 |
| 表情 | 位图 gummy | 位图 gummy | CSS 矢量脸（眼/嘴/腮红/眉） | 深色 |
| 主曲线 | 无 | 无 | `cubic-bezier(0.2,0.8,0.2,1)` | 深色 |

演进原因（据 DESIGN.md「探索方向/采用」段 + 时间线推断）：

- v1 → v2 文档：v1 把小栈当「设备控制台」（2×3 应用网格、联网/电量、控制中心）。v2 判定「小栈是陪伴型桌面机器人，不是手机启动器」，因此否决了网格化陈列，改成「一次只显示一张功能卡」。
- v2 文档选「柔雾樱花」而非「草莓牛奶」「夜间莓果」：官方理由是「轻柔、清楚，照片和 gummy 表情都容易融入」；否决草莓牛奶是因为「仍容易回到糖果玩具感」，否决夜间莓果是因为「游戏感强，但陪伴与相册会显得沉重」。
- v2 文档 → 最终原型：**设计文档未回写**。`prototype.pre-ui-index-replacement-20260722-141211.html` 仍是 `--canvas:#f1dfe5`，下一份快照（15:32）起变回 `--bg-color:#080a0f`，此后 25 份快照全部为深色。CSS 注释 `/* ===== Product UI refresh: face layer intentionally untouched ===== */` 标记了这次换肤。**推断原因**：浅色奶油系统在深色 OLED 屏上功耗高、发灰；同时「每功能一个强调色」的深色系统更好承载 8 个功能分区与游戏舞台。最终态里「柔雾樱花的暖白/粉/莓红」并没有完全消失——它活到了 `YYC.html`（2026-08-02）里作为**面向人（生日信）的移动端产物**。
- **风险**：`v2/DESIGN.md` 与 `v2/INTERACTION.md` 仍是仓库里唯一的成文契约，内容已与实现脱节。写 iOS 契约前必须先定：iOS 端跟「文档」还是跟「实现」。

### 3.3 迁移到 iOS 的规则

| 规则 | iOS 落地方式 | 继承/新增 |
| --- | --- | --- |
| 同一套底座，不拼图标库 | 全部功能图标自绘一套线性图标集；统一 viewBox 64×64、stroke 1.7、圆端圆角 | 继承 |
| 每功能只加一个主符号 | App 图标 = 主符号 + 极小辅助符号（如 AI Chat 的三个眼珠点），不超过 2 个元素 | 继承 |

| 图标容器 = tint 底 + accent 前景 | 用 `color-mix`/双层 Shape；深浅主题各一套 tint | 继承 |
| 图标不含文字 | App 图标禁止带中文；功能名一律系统文字 + 本地化 | 继承 |

## 6. 设计哲学

### 6.1 逐条摘出与解释

| 原句 | 出处 | 拆解 |
| --- | --- | --- |
| 「小栈是陪伴型桌面机器人，不是手机启动器。」 | v2 DESIGN.md:5 | **陪伴 vs 工具的第一性区分**。否掉的是「把功能排成网格让你挑」的启动器心智，改成「它一直在，你走过去它才回应」。落到版式就是：一次只显示一个功能，不做 6 宫格。 |
| 「320×240 屏幕首先要让人感到安静、亲近、可信，其次才是可爱。」 | v2 DESIGN.md:5 | **优先级排序被写成了句子**。安静（不吵）> 亲近（暖）> 可信（稳）> 可爱（甜）。可爱排最后一位，意味着：大眼、腮红、闪粉这些手法可用，但必须排在「不吵、不糊、可依赖」之后。设计评审时用这句当裁判尺。 |
| 「每个画面只保留一个主要动作。」 | v2 DESIGN.md:5 | **单焦点**。不是「一个页面」，是「一个动作」。一个页面可以有很多信息，但只有一个动作是主按钮；其余降级为次级。 |
| 「一眼知道当前页面、设备状态和下一步操作。」 | v1 DESIGN.md:5 | 三问自检：我在哪 / 设备怎样 / 下一步按哪里。 |
| 「所有关键操作都有可见入口，边缘手势只作为快捷方式。」 | v1 DESIGN.md:6 | **手势是加速器不是入口**。iOS 直接继承：左边缘返回可做，但不能只有手势没有按钮。 |
| 「保留全屏 gummy 表情的陪伴感，同时不让控制面板遮住嘴和脸颊。」 | v1 DESIGN.md:7 | 角色感优先于控件感，但控件不能破坏角色。落到实现：表情层常驻、控制层可分层。 |
| 「游戏画面保留深莓色舞台，但导航、按钮和信息层级继续使用同一套浅色系统。」 | v2 DESIGN.md:13 | **局部换肤不换系统**。沉浸内容（游戏/相册）可以有自己的舞台色，但导航与信息层级不换。这条对 iOS 极重要：深色模式下游戏/相册页也不能另起一套蓝色系统。 |
| 「粉色只用于选中态、主按钮和少量强调，不再铺满每一层表面。」 | v2 DESIGN.md:36 | **强调色是信号不是涂料**。任何「大面积铺强调色」都视为跑偏。 |
| 「边框优先于重阴影。」 | v2 DESIGN.md:34 | 层级靠 1px 边和表面明度差建立，不靠投影。 |
| 「8 个图案全部重做为同一套『小栈软质物件』，不是从不同图标库拼接。」 | v2 DESIGN.md:40 | **一致性能被一眼识别**，混用来源会立刻破坏「可信」。 |
| 「图案在 512×512 透明画布中的主体占比保持 45%–76%，放到 154px 卡片区域仍能一眼识别。」 | v2 DESIGN.md:43 | 给了可测的数值区间——**规范要能被验收**，不是「差不多」。 |

### 6.2 探索方向与取舍（v2 DESIGN.md:9–13）

| 方向 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 柔雾樱花（奶油白表面、灰调樱花粉画布、莓红强调、炭灰文字） | 轻柔、清楚，照片和 gummy 表情都容易融入 | — | **文档层采用** |
| 草莓牛奶（更鲜亮的粉红底 + 白卡） | 活泼 | 仍容易回到糖果玩具感 | 否 |
| 夜间莓果（深色背景 + 粉色高光） | 游戏感强 | 陪伴与相册会显得沉重 | 否（文档层） |

> 注：**最终原型实际走向了深色**，与当时「夜间莓果：陪伴与相册会显得沉重」的判断相反，且设计文档未回写。写 iOS 契约时必须显式裁决这一条：iOS 端走浅色（柔雾樱花）还是深色（StackChan OS）。本报告在第 8 节给出建议（双主题，浅色为主）。

### 7.1 屏幕无关（直接继承）

| S11 | 退出即清理（计时/动画/循环全部停） | `onDisappear` 停任务 |

补充说明（对任务中点名项的实测结论）：

- **SwiftUI 侧「`MetricScale` 类库」：GitHub 检索 `MetricScale` + `language:swift` 返回 0 条结果，该名称下没有可用的 Swift 包。** 最接近的替代是：① 上述 SwiftUI 主题/令牌包；② Apple 原生 `Dynamic Type`（`@ScaledMetric` / `UIFontMetrics` / `.relativeTo`）——这才是 iOS 端排版缩放的正解，且零依赖。
- **深浅色双主题**没有专门的「库」需求，用 DTCG 的 group + Style Dictionary 的多 theme 即可表达，SwiftUI 侧用 `EnvironmentValues` 承载（方案 #4）。
- LVGL 官方文档站点 https://docs.lvgl.io/master/index.html 可访问（主题 API 章节路径随版本变动，引用时以仓库 `docs/` 目录为准）。

### 采用决策

**混合。**

- **采用 DTCG（第 1 项）作为唯一令牌真源格式** —— 它的 `color` / `dimension` / `duration` / `cubicBezier` / `typography` / `shadow` 类型与我们的令牌一一对应，且是跨端（设备屏 + iOS）唯一被广泛接受的事实标准；同时它只是格式约定，不引入运行时依赖，零风险。
- **采用 Style Dictionary（第 2 项）作编译层** —— 一份 JSON 编译出 iOS 的 `DesignTokens.swift`、设备端的 JSON / C 头文件、文档站表格。避免两套手写常量漂移（当前仓库已经出现过「文档与实现脱节」）。
- **参考 theme-kit（第 4 项）的 Environment 注入模式，但只自造薄壳** —— 不引入整套第三方 SwiftUI 组件库（第 5 项），因为我们这套设计语言（线性图标、玫瑰强调色、吉祥物主体）气质高度定制，套用通用组件库的成本高于自写；`theme-kit` 的「令牌 → 代码生成 → Environment 注入」这套结构值得直接照搬。
- **LVGL（第 6 项）只取其 theme 组织方式** —— 是否实际使用 LVGL 需先核实固件技术栈，故列为「对设备屏的补充建议」而非本次 iOS 契约的前置依赖。

**理由**：真正需要标准化的是**令牌文件与编译链路**（跨端、跨人、跨时），而不是 UI 组件（单端、审美主导、可控范围小）。本项目已经吃过「文档与实现脱节」的亏（v2 DESIGN.md 与 prototype.html 完全不同），把真源收敛到一个可编译的 JSON 是最低成本的根治手段。

### 速览

- **Design Tokens Community Group（DTCG）格式规范** 用途：定义跨端设计令牌的唯一 JSON 真源格式与类型体系（color / dimension / duration / cubicBezier / typography / shadow / border / transition / gradient） 许可：W3C Community Group 规范（非 W3C 标准，仓库 `design-tokens/community-group`） 接入成本：低（纯格式约定，零运行时依赖） 替代自造的：自定令牌文件格式与命名约定
- **Style Dictionary** 用途：把令牌 JSON 编译成 iOS Swift 常量 / 设备端 JSON 与 C 头文件 / CSS / 文档表格 许可：Apache-2.0 接入成本：中（Node 构建脚本 + 一份配置，4.x 需 Node 20+） 替代自造的：手写脚本同步两端令牌常量
- **Tokens Studio for Figma** 用途：设计师侧维护令牌并导出 DTCG JSON，接入 Style Dictionary 链路 许可：MIT 接入成本：低（Figma 插件，导出即用，引入 Figma 依赖） 替代自造的：手写 JSON、手工同步 Figma 样式
- **rozd/theme-kit** 用途：SwiftUI 侧「令牌 → 主题代码生成 → Environment 注入」与深浅色切换 许可：MIT 接入成本：低–中（SPM 依赖 + 配置 token 源） 替代自造的：自写主题注入与 codegen
- **isamercan/ThemeKit** 用途：SwiftUI 组件库 + 令牌绑定 + 深浅色 + Figma 同步 许可：MIT 接入成本：中（组件气质与本项目不符，需大改，收益有限） 替代自造的：自写卡片 / 按钮 / 输入框组件
- **LVGL（`lv_theme_t` 主题机制）** 用途：设备屏侧令牌组织，把 DTCG 令牌映射为 LVGL style 与 theme 许可：MIT 接入成本：中（需转 `lv_style`，且固件是否用 LVGL 待核实） 替代自造的：固件里散落的颜色 / 尺寸常量

采用决策：**混合**  理由：标准化「令牌文件与编译链路」（跨端、跨人、跨时），组件层自造薄壳不套用通用组件库——本设计语言气质高度定制，且仓库已出现过「成文契约与实现脱节」（v2 DESIGN.md 描述柔雾樱花浅色，prototype.html 实际是深色 StackChan OS），把真源收敛到一个可编译的 DTCG JSON 是最低成本的根治手段。
