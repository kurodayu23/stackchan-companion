### 3.2 `mem0ai/mem0`

- **实测依据（README 原话）**：
  - 副标题："Mem0 - The Memory Layer for Personalized AI"
  - **"Single-pass ADD-only extraction** -- one LLM call, no UPDATE/DELETE. Memories accumulate; nothing is overwritten."
  - "**Agent-generated facts are first-class** -- when an agent confirms an action, that information is now stored with equal weight."
  - "**Entity linking** -- entities are extracted, embedded, and linked across memories for retrieval boosting."
  - "**Multi-signal retrieval** -- semantic, BM25 keyword, and entity matching scored in parallel and fused."
  - "**Temporal Reasoning** -- time-aware retrieval that ranks the right dated instance for queries about current state, past events, and upcoming plans."
  - "**Multi-Level Memory**: Seamlessly retains User, Session, and Agent state with adaptive personalization"
  - 安装：自托管 "`cd server && make bootstrap`"；库模式 "`pip install mem0ai`"；混合检索需 "`pip install mem0ai[nlp]`" + "`python -m spacy download en_core_web_sm`"

  - ⚠️ README 自陈的诚实声明（值得抄）："Scores reflect Mem0's managed platform, which includes proprietary optimizations not available in the open-source SDK; open-source users should expect directionally similar gains but not identical numbers."
- **许可 / 依赖 / 商业限制**：**Apache-2.0**（README 明确）。依赖：默认 LLM 是 `gpt-5-mini`、默认 embedding 是 `text-embedding-3-small`（OpenAI）；混合检索要额外装 spaCy 模型。**注意：它的"混合检索"路径对中文不友好**（`en_core_web_sm` 是英文模型）。
- ⭐ **可复用方案**：**mem0 用途**：记忆抽取与检索范式 许可：**Apache-2.0**（可抄思路，代码可复用） 接入成本：**中**（要向量库 + LLM 抽取调用） 替代自造的：**替代 `memory_store.py` 的抽取层**——但只抄"ADD-only 不覆盖"这一条铁律。

### 4.2 Chat：真实路径与请求格式（原文要点）

官方 OpenAPI（`/docs/api-reference/text-post.md` 内嵌）原文：

```
servers:
  - url: https://api.minimax.io
paths:
  /v1/text/chatcompletion_v2:
    post:
      summary: Text Generation V2
      operationId: chatCompletionV2
```

- **鉴权**：`security: bearerAuth` → `HTTP: Bearer Auth`，`Bearer API_key`，Key 在 `Account Management>API Keys`。
- **必填**：`model` + `messages`。
- **model 枚举**（原文）：`MiniMax-M3.1-Flash`、`MiniMax-M3`。两者都是 reasoning 模型，**官方建议 streaming**。
- **messages[].role** 枚举：`system` / `user` / `assistant` / `tool`。
- **messages[].content**：支持 `string` 或多模态数组 `[{type: text|image_url}]`。
- **关键参数**：
  - `stream` (bool, 默认 false) —— 开启后 `Content-Type: text/event-stream`
  - `max_completion_tokens`（`max_tokens` 已标 deprecated）
  - `temperature` 范围 `(0, 1]`
  - `top_p` 默认 0.95
  - `stream_options.include_usage`（默认 false，开则最后一帧带完整 usage）
  - `tools` / `tool_choice`（`tool_choice` 仅 `auto`）
  - `response_format`：`json_schema` —— **原文明确"only supported by `MiniMax-Text-01`"**
  - `mask_sensitive_info`（默认 false）：把输出里邮箱/域名/链接/证件号/住址等私密信息替换成 `***` —— **对我们的"不编造/隐私"是现成开关**
- **响应体关键字段**：`choices[0].message.content`、`choices[0].message.reasoning_content`、`usage.total_tokens`、`usage.completion_tokens_details.reasoning_tokens`、`base_resp.status_code`、`input_sensitive` / `output_sensitive` / `*_sensitive_type`。
- **流式 chunk**：`choices[0].delta.content`、`object: chat.completion.chunk`、`finish_reason ∈ {stop, length, tool_calls}`。

**`base_resp.status_code` 错误码原文摘录**：`1000` 未知错误 / `1001` 请求超时 / `1002` 限流 / `1004` 鉴权失败 / `1008` 余额不足 / `1013` 内部错误 / `1027` 输出内容非法 / `1039` 超 token 限制 / `2013` 参数非法。

**流式协议（SSE）**：响应 `Content-Type: text/event-stream`，每个 chunk 是一个 `chat.completion.chunk` 对象，最后一个 chunk 带 `finish_reason`；开启 `stream_options.include_usage` 时最后一帧补齐 `usage`。

### 4.3 TTS WebSocket：真实路径、事件协议、情绪参数（原文要点）

来源：`/docs/api-reference/speech-t2a-websocket.md` 内嵌 AsyncAPI（`id: t2a_v2_websocket`）。

**地址**（AsyncAPI 原文）：
```
servers:
  - id: production
    protocol: wss
    host: api.minimax.io
address: /ws/v1/t2a_v2
```
→ **`wss://api.minimax.io/ws/v1/t2a_v2`**

**鉴权**：`Authorization: Bearer <API_KEY>`（官方 Python 示例用的 `os.getenv("MINIMAX_API_KEY")`）。

**事件时序（客户端 → 服务端 → 服务端回帧）**：

| 方向 | event | 说明 |
|---|---|---|
| 收 | `connected_success` | 连接建立，带 `session_id` / `trace_id` / `base_resp` |
| 发 | `task_start` | 开始合成；**必须先收到 `task_started` 才能继续** |
| 收 | `task_started` | 任务已启动 |
| 发 | `task_continue` | 送入文本（可多次，逐句） |
| 收 | `task_continued` | 返回 `data.audio`（**hex 编码**）+ `extra_info` + `is_final` |
| 发 | `task_finish` | 结束 |
| 收 | `task_finished` / `task_failed` | 完成 / 失败（失败必须关连接） |

**`task_start` 请求体关键字段**（原文）：

```json
{
  "event": "task_start",
  "model": "speech-2.8-hd",
  "voice_setting": {
    "voice_id": "male-qn-qingse",
    "speed": 1, "vol": 1, "pitch": 0,
    "emotion": "happy"
  },
  "audio_setting": {
    "sample_rate": 32000, "bitrate": 128000,
    "format": "mp3", "channel": 1
  }
}
```

- **model 枚举**：`speech-2.8-hd`、`speech-2.8-turbo`、`speech-2.6-hd`、`speech-2.6-turbo`、`speech-02-hd`、`speech-02-turbo`、`speech-01-hd`、`speech-01-turbo`。
- **`voice_setting.emotion` 枚举（情绪化 TTS 的关键）**：`happy` / `sad` / `angry` / `fearful` / `disgusted` / `surprised` / `calm` / `fluent` / `whisper`。
  - 原文："By default, the model automatically selects the most natural emotion based on text. Manual specification is only recommended when explicitly needed."
  - 原文：`fluent` / `whisper` 仅 `speech-2.6-turbo`、`speech-2.6-hd` 支持；`speech-2.8-hd` / `speech-2.8-turbo` **不支持 `whisper`**。
  - **`fluent` = 流利，`whisper` = 耳语** —— 这两个直接可用于"陪伴时的轻声/停顿"。
- **`audio_setting.format` 枚举**：`mp3` / `wav` / `flac` / `pcm` / `pcmu_raw` / `pcmu_wav` / `opus`。
  - 原文："`opus` is Ogg/Opus encoded; in streaming mode, audio chunks must be reassembled in arrival order before decoding."
  - **`opus` 对我们极其重要**：设备端是 Opus 传输，直接让 TTS 出 Opus 可省掉后端转码。
- **`audio_setting.sample_rate`** 支持 `[8000, 16000, 22050, 24000, 32000, 44100]`，默认 32000。
  - **`pcmu_raw` / `pcmu_wav` 是 G.711 μ-law（8kHz）** —— 可作为"低码率直推设备"的备选。
- **`voice_setting.voice_id`** 支持系统音色 / 克隆音色 / AI 生成音色；另有 **`timbre_weights`** 最多混 4 个音色（权重 1–100）。
- **`voice_setting.speed`** `[0.5, 2]` 默认 1；**`vol`** `(0, 10]` 默认 1；**`pitch`** `[-12, 12]` 默认 0。
- **`voice_modify`**：`pitch` / `intensity` / `timbre` 三档 `[-100,100]` + `sound_effects ∈ {spacious_echo, auditorium_echo, lofi_telephone, robotic}`。
- **`language_boost`**：`Chinese` / `Chinese,Yue` / `auto` 等 40 种；**`Chinese` 可显式指定**。
- **`subtitle_enable` + `subtitle_type ∈ {sentence, word, word_streaming}`** —— 字幕时间戳随音频一起回传。**这条对"设备端字幕/日志对齐"直接可用。**
- **`continuous_sound`**（仅 2.8 系列）：`true` = 不切句、连续推理（韵律更好）；`false` = 切句并发（延迟更低）。**默认 false。**

**`task_continued` 响应体**：`data.audio`（hex）、`data.subtitle`（含 `text` / `text_begin` / `text_end` / `time_begin` / `time_end` / `timestamped_words[]`）、`extra_info`（`audio_length` ms / `audio_size` / `usage_characters` 计费字符数 / `word_count` / `invisible_character_ratio`）、`is_final`。

**TTS 专有错误码**：`2201` 超时断连 / `2202` 非法事件 / `2203` 空文本跳过 / `2204` 超字符上限跳过 / `2205` 超请求数上限 / `1042` 非法字符 > 10%。

## 五、⭐ 记忆分层参考方案（可直接落到 `memory_store.py`）

> **现状基线（实读代码）**：`memory_store.py` 现在是**单层 JSON 文件**：`profile / likes / dislikes / goals / important / relationship / giver / temporary / conversation_notes / insights` 十个桶（`memory_store.py:110 summary()`），`context_text()`（`:76`）把全部桶拼成一段中文喂给模型。**当前是"每次全量注入"**——桶多了会撑爆上下文，且没有遗忘机制。
> **约束**：小型 VPS（已有 cloudflared）；**不引入向量数据库集群**；私人层永不入库。

### 5.1 三种分层设计（推荐 A，A' 是 A 的变体）

#### 方案 A ⭐⭐⭐⭐⭐：**三层 + TTL（SQLite FTS，纯标准库）** —— 推荐

| 层 | 名字 | 存储形态 | 检索时机 | 遗忘策略 |
|---|---|---|---|---|
| **L0 工作层** | `session` | 内存 dict + WS 连接生命周期 | 每轮对话，**只放当轮上下文** | 连接断开即销毁（**永不落盘**） |
| **L1 情节层** | `episode` | SQLite 表 `episodes(id, ts, user_id, kind, text, ttl_days)` + FTS5 虚表 | **对话结束前**、以及用户问"我们之前聊过什么"时 | **TTL 到期自动删**（默认 30 天）+ 容量上限（滚动删最旧） |
| **L2 语义层** | `fact` | SQLite 表 `facts(id, key, value, confidence, source_episode_id, updated_at)` | **每轮对话前**，按当前话题关键词做 FTS + 字面匹配，取 top-k | **不自动删**，但走 `forget` 显式删除 + 冲突覆盖 |

- **实现要点**：
  - SQLite 是 Python **标准库自带**，零外部依赖，**VPS 上一个文件**——这是"不要向量数据库集群"约束下的正解。
  - `facts` 表的 `key` 沿用现有桶名（`likes` / `goals` / `relationship`…），**直接复用 `memory_store.py` 现有 `DEFAULT_PROFILE`/`DEFAULT_LIKES` 结构**，迁移成本最低。
  - 检索用 **FTS5 + 字面匹配 + 关键词打分**，**不用 embedding**。理由：我们的记忆量级是"一个用户几个月内的几十到几百条"，embedding 收益极低而成本（模型 + 向量库 + 中文分词）极高。
- **隐私边界**（绝不入库）：
  1. **完整聊天原文**（只存提炼后的 episode 摘要，不存逐字对话）；
  2. **密码 / 令牌 / 证件号 / 住址 / 手机号** —— MiniMax Chat 的 `mask_sensitive_info: true`（§4.2 原文）可作为**第一道闸**，但**不能只靠它**；
  3. **摄像头画面与照片**；
  4. **私人层的原始文件**（`private/` 目录内容）—— 私人层**只在小栈本地**，后端永不接收（§6.4）。
- **⭐ 落地到 `memory_store.py` 的具体改法**：
  - `learn_from_message()`（`:49`）：从"直接写进长期桶"改成 **先写 `episodes`（带 TTL），再由后台任务抽取 `facts`** —— 这就是 mem0 的 **ADD-only**（§3.2）与 cognee 的 **session distillation**（§3.5）的合并。
  - `context_text()`（`:76`）：从"全量拼接"改成 **按当前话题 top-k 注入** —— 这就是 redis 的 **"Keeping full conversation history in the prompt does not scale"**（§3.6 原话）。
  - 新增 `forget(key)` / `improve(key, value)` 两个显式动作（§3.5）—— 让用户能删、能纠正。

#### 方案 B：**Redis 双层（session TTL + long-term）**

- **存储形态**：Redis 两个 keyspace：`session:{user_id}`（`EXPIRE` 设为连接 TTL）+ `facts:{user_id}`（持久）。
- **检索时机**：每轮读 session + 按需查 facts。
- **遗忘策略**：session 靠 TTL；facts 靠显式删除 + 定期归档。
- **优点**：直接抄 redis 官方的两层模型（§3.6），后台"晋升"（promote）用 Redis 的 pipeline 就能做。
- **缺点 / 不推荐理由**：ⓘ **我们的 VPS 上再养一个 Redis 只是为了两个 keyspace，不划算**；ⓘ **Redis 里的数据默认是"已存储"**，与"私人层不入库"的隐私叙事冲突（虽然可以配 `maxmemory-policy` + 定期 FLUSH，但那是运维负担）；ⓘ **一旦用了 Redis，运维复杂度从"一个 Python 文件"跳到"两个有状态服务"**。
- **采用**：**❌ 不采用**。但**它的两层命名与"后台晋升"机制被方案 A 吸收**。

#### 方案 C：**全量向量 + 图谱（mem0 / cognee / graphiti 全家桶）**

- **存储形态**：向量库（Qdrant / Milvus）+ 图数据库（Neo4j / FalkorDB）+ embedding 模型。
- **遗忘策略**：图谱合并 + 冲突消解。
- **❌ 不采用的硬理由**：
  1. **三套有状态服务**（向量 + 图 + 关系库）**在小 VPS 上跑不动**，且我们的 cloudflared 穿透只解决入口，不解决资源；
  2. **embedding 默认模型对中文不友好**（mem0 README 推荐 `gte-Qwen2-1.5B-instruct`，那是要跑 600M 模型的量级，§3.2）；
  3. **每次检索一次远程 embedding 调用** = 每轮对话多一次网络往返和一次 API 成本，而我们的场景是**单用户、单设备**；
  4. **与"私人层永不入库"正面冲突** —— 把用户的私密内容 embedding 进远程向量库，等于**多复制了一份离开本机的数据**。
- **采用**：**❌ 明确不采用**。其**思想**（ADD-only、实体链接、多信号检索、session distillation）被方案 A 以纯 Python 实现吸收。

### 5.2 ⭐ 记忆分层的**命名**（对齐 letta 的 core/recall/archival 概念，但按我们的规模重命名）

| 我们的层 | 对应 letta 概念 | 存在哪 | 谁写 | 谁读 |
|---|---|---|---|---|
| `session`（L0） | core memory（临时部分） | 内存 | 每轮对话 | 每轮对话 |
| `episode`（L1） | recall memory | SQLite + TTL | 对话结束 | 低频检索 |
| `fact`（L2） | archival memory | SQLite | 抽取任务 | 每轮 top-k |

### 5.3 ⭐ "World Info 式"的检索注入（抄 SillyTavern 的思路，§3.4）

SillyTavern 的 World Info 是"关键词命中 → 把条目注入 prompt"。**我们不需要独立的 World Info 功能**，因为**记忆检索本身就是 World Info**：

```
用户消息 → ① 抽取关键词（分词 + 停用词）
        → ② FTS5 查 episodes / facts，取 top-k
        → ③ 命中的 fact 拼进 system prompt 的"长期记忆"段
        → ④ 未命中的 fact **不注入**（省 token，也避免"AI 什么都记得"的假感）
```

⭐ **这一条直接解决"不编造数据"约束**：模型只看到**检索到的真实条目**，不会被塞一堆无关记忆后自己编。

### 5.4 ⭐ 遗忘策略的具体规则

| 规则 | 说明 | 依据 |
|---|---|---|
| **TTL 删** | `episodes` 默认 30 天到期删除；`facts` 不自动删 | 陪伴产品不该有"永久监控感" |
| **容量滚动删** | 每桶上限沿用现有 `MAX_ITEMS_PER_BUCKET = 80`（`memory_store.py:42`）、条目长度 `MAX_ITEM_LENGTH = 48`（`:41`）——**现有代码已经有这两个护栏，直接保留** | 现有实现 |
| **冲突覆盖** | 同一 `fact.key` 新值覆盖旧值，但**旧值进 `episodes` 留痕**（可追溯"我们之前以为你叫 X"） | mem0 ADD-only 的反面：facts 层覆盖、episodes 层只追加 |
| **显式遗忘** | 用户说"别记这个了" → 立刻 `forget`，**且不删除该 episode 的其他无关内容** | cognee `forget`（§3.5）+ 用户删除权 |
| **⭐ 不做** | **不做"连续天数 / 消息条数 / 亲密度"这类指标** | 我们自己的硬约束（§1.3）——Gentler Streak 的"非暴力设计"范式（`00-总纲` §0.9） |

### 6.1 人格包格式：**YAML**（不是 JSON）

**为什么 YAML 而不是 JSON**：
1. **我们要写注释** —— 人格包是给人读的（"这句为什么这么写"、"哪些是版权友好的表述"），JSON 不支持注释；
2. **多行文本**（`system_prompt` / `example_dialogues`）在 YAML 里可读得多；
3. **Persona Card V2 是 JSON**（SillyTavern 事实标准，§3.4）→ **我们在 YAML 里存，但导出时转 JSON**（§6.5 的 `card_v2_export`），两边通吃。

### 6.2 ⭐ 运行时加载：热更新 + 版本 + 回滚

| 机制 | 做法 | 为什么 |
|---|---|---|
| **加载时机** | 后端启动时读 `personas/index.yaml` → 按 `entrypoint` 加载 `enfp.yaml` → 与 `private/persona.local.yaml` **深合并**（private 覆盖 personas） | 与 `experience_store._merge()`（`:366`）的现有递归合并语义一致 |
| **热更新** | 每 60 秒比对 `personas/*.yaml` 的 `mtime + hash`；变了就重新加载并 `reload` 运行时 | 人格包是"产品配置"，改完不该重启服务 |
| **版本** | `version: 1.0.0`（语义化版本）+ `schema_version: 1`（字段结构版本）；**`schema_version` 变了才需要迁移代码** | 人格包会持续演进，字段结构与内容要分开版本化 |
| **回滚** | 保留上一份 `enfp.yaml` 的内容快照（内存），热更新加载失败（YAML 语法错 / schema 不符）时**回滚到上一份并记日志**，绝不半加载 | ⭐ 人格包是"机器人的人格"，加载坏了不能让机器人变哑巴 |
| **⭐ 生效边界** | 人格包**只影响 system prompt 组装与表现参数**，**不影响已存的 `facts`** —— 换人格不该改写记忆 | mem0 的 ADD-only 原则（§3.2） |

### 6.3 ⭐ 合并优先级（唯一真相来源）

```
private/persona.local.yaml   ← 最高（个人定制，永不入库）
        ↓ 覆盖
personas/enfp.yaml            ← 通用人格包（开源）
        ↓ 覆盖
代码里的 DEFAULT_* 常量       ← 兜底默认值（memory_store.py:6 / experience_store.py:8）
```

⭐ **关键**：`DEFAULT_*` 常量是**兜底**，不是真相来源。当前代码里 `DEFAULT_LIKES` / `DEFAULT_IMPORTANT` / `DEFAULT_INSIGHTS`（`memory_store.py:16-36`）是**硬编码的"依婵"个人数据** —— ⚠️ **这必须搬家**：它们属于第 3 层，应移到 `private/`，**不能留在开源代码里**。

### 6.4 ⭐ 私人层隔离（三条硬规则）

1. **不入库**：`private/` 目录**不接后端、不接 Git、不进任何日志**。我们的 VPS 上，私人层只存在于**小栈本机**。
2. **不外发**：私人层内容**只在本地拼接进 prompt**，**不作为独立字段发给 MiniMax 之外的任何服务**。我们只用 MiniMax（§4 已核实端点），且开 `mask_sensitive_info: true`（§4.2 原文）。
3. **不可被引擎写回**：通用引擎（开源部分）**只读**私人层，**永不写**。写入只能由用户显式操作（`add_manual_item` / `remove_item`，`memory_store.py:125/133`）。

> **这条与 §3.5 的 cognee `forget` 呼应**：`forget` 是用户行使删除权的入口，必须真实可用、能验证。

### 6.5 三层契约（抄 elizaOS 的 `AgentRuntime` 三段划分，§3.7）

| 层 | 对应 elizaOS | 我们对应物 | 谁定义 |
|---|---|---|---|
| **引擎层**（通用，开源） | `AgentRuntime` / "canonical types" | `stackchan_ai/` 全部通用代码 | 我们 |
| **人格层**（通用，开源） | plugin contracts | `personas/enfp.yaml` | 我们（可被社区 fork） |
| **状态层**（个人，永不入库） | "memory and state primitives" | `private/` + `facts`/`episodes` | 用户本人 |

⭐ **导出兼容**：人格包可一键导出 **Persona Card V2 JSON**（`card_v2_export`）→ 别人能导入 SillyTavern 用；也能导出 **MiniMax system prompt**（把 `persona.description` + `boundaries` + `relationship` 拼成 `messages[0].role=system`，§4.2 已核实该位置可用）。

### 6.6 资产许可清单（抄 TalkingHead 的教训，§3.11）

`assets_manifest` 每条记：`{path, license, source, commercial_use, attribution_required}`。
⭐ **为什么重要**：我们将来给 320×240 表情屏做美术资源，**每张图可能来自不同来源**（Twemoji 是 **CC-BY 4.0**，见 `78__xiaozhi-fonts/font_emoji.py` 文件头原文："Graphics License: CC-BY 4.0"）—— **混用时必须逐个记录**。

⭐ **结论（必须写进我们的协议层）**：
1. **官方固件只认 8 个情绪串**（`neutral/happy/laughing/angry/sad/crying/sleepy/doubtful`），**其余一律静默退化成 Neutral**（只打一条 `ESP_LOGW`）。
2. `ControlAvatar`（0x03）走的是**几何参数**路径 —— 要做"细粒度表情"必须自己算 `leftEye/rightEye/mouth` 的 x/y/rotation/weight/size，**不能指望发个情绪名就有表情**。
3. **因此我们的后端必须有两条发送通道**：① 情绪串（走 `SetEmotion`，需找到触发它的调用点）；② 几何 JSON（走 `ControlAvatar` 0x03，可实现枚举之外的 14 个 mood）。
4. ⚠️ **待确认**：路径 B 的 `SetEmotion` 在固件里的**调用入口**（谁调它、是不是也在某个 WS 消息类型下）—— 本轮 grep 只在 `stackchan_display.cc` 找到**定义**，**未找到调用方**（`hal_ws_avatar.cpp` 里只有 `onWsAvatarData.emit(payload)` 走 JSON 路径）。**这一项记为"未取得"，见 §11**。

## 八、主动陪伴的调度参考

> **现状基线（实读 `experience_store.py`）**：
> - `cue(kind, ...)`（`:180`）产出**一个动作包**：`{kind, enabled, say, emotion, motion, face, voice, reaction, category, interval_minutes, priority, ...}`。已实现的 kind：`water` / `ielts` / `supervision` / `birthday_countdown` / `startup`。
> - `due_cues(now, consume)`（`:296`）按 `interval_minutes` 用 `_cue_elapsed()`（`:326`）判断是否到期；`consume=True` 时写 `runtime.last_cues[kind]`。
> - `reminders` 三档间隔：water 120min / ielts 240min / supervision 25min；生日倒计时 7 天内每天一次。
> - ⚠️ **现状缺口**：`due_cues` **只按时间间隔触发，没有"用户最近在不在/忙不忙/是不是刚说过话"的判断**，也没有"每天最多几次"的上限 → **会变成催促**。

### 8.1 ⭐ 什么时候说话 / 什么时候沉默

**说话的条件（全部满足才说）**：

| # | 条件 | 判定 | 依据 |
|---|---|---|---|
| 1 | 该 cue 自己 `enabled` | `cue["enabled"]` | 现有代码已有 |
| 2 | **距上次同类间隔已过** | `_cue_elapsed(kind, now, interval)` | 现有代码已有 |
| 3 | ⭐ **距上次"机器人主动说话"已过静默期** | `now - runtime.last_spoke_at >= quiet_period` | **新增**（§8.3） |
| 4 | ⭐ **不在静默时段** | 不在 `proactivity.quiet_hours` | **新增** |
| 5 | ⭐ **今天主动次数未超上限** | `runtime.spoke_today < max_cues_per_day` | **新增** |
| 6 | ⭐ **设备当前状态允许** | 不在"充电中 / OTA 中 / 用户正在专注倒计时 / 相机使用中" | **新增** |
| 7 | ⭐ **不是"刚被问完还没走"的场景** | 距用户最后一条消息 ≥ `reaction.simple_delay_ms`×N | **新增** |

**沉默的条件（命中任一就闭嘴）**：

| # | 条件 | 行为 |
|---|---|---|
| 1 | 用户正在说话（VAD 检出） | **不插话**，等 `SetEmotion` 的语义轮次判定（§3.9 livekit 思路）说用户说完了 |
| 2 | 距用户最后一条消息 < 静默期 | 等 |
| 3 | 处在静默时段（默认 23:00–07:00） | 只做**不打扰的姿态**（表情/呼吸灯），不说话 |
| 4 | 今天已经主动说过 N 次 | 停 |
| 5 | 上一次主动说话**用户没有回应** | ⭐ **连续 2 次无回应 → 该 cue 自动降频**（间隔 ×2） |

⭐ **第 5 条是"反催促"的核心**：用户没理你，就该**更少**说话，而不是更多。

### 8.2 ⭐ "反催促"的具体做法（不打扰 / 不指标 / 不催促震动）

| 反催促原则 | 具体做法（可落地） | 依据 |
|---|---|---|
| **不指标** | ⭐ **界面上永远不出现**"连续 N 天""已提醒 N 次""亲密度 87""本周坚持 3 次" | 我们的硬约束（§1.3）；Gentler Streak 的非暴力设计范式（`00-总纲` §0.9） |
| **不催促震动** | ⭐ **cue 触发时设备不震动**。震动只在**用户主动交互**（按键、NFC 贴卡）时用 | 00-总纲 §0.9 "没有催促震动" |
| **不用红色未达标** | 错过提醒**不显示任何"未完成"标记** | 同上 |
| **不升级强度** | 提醒**不递进**（第 3 次不改成"更急的语气"）。⭐ 现状 `experience_store.py:241-244` 的 supervision 文案已符合（"先不追求完美"），**要保持** | 现有代码 |
| **降频而非升频** | 用户无回应 → 间隔 ×2（§8.1 沉默条件 5） | 本节设计 |
| **可一键静音** | 人格包里 `proactivity.max_cues_per_day` 与 `quiet_hours` **用户可改**，改完立即生效（§6.2 热更新） | §6.2 |
| ⭐ **不"代打卡"** | ⭐ **不记录"已完成"状态** —— 用户说"我喝了"是我们**知道**，不是**我们判定他完成了**。不要出现"✓ 今日饮水已完成" | 不编造数据 |
| **错过不补** | 错过的时间点**不追补**（不"你今天 3 点该喝水没喝，现在补一下"） | 00-总纲 §0.9 |

### 8.3 ⭐ 可借鉴参数（抄 SillyTavern 的 `Talkativeness`，§3.4）

| 参数 | 语义 | 默认 | 落点 | 作用 |
|---|---|---|---|---|
| **`talkativeness`** | 0–100% 的"说话意愿" | **50**（SillyTavern 默认语义；⚠️ 其 README 未含该参数，原文未取得，见 §11.2 —— **默认值沿用任务书给定口径**） | `personas/enfp.yaml` → `proactivity.talkativeness` | ⭐ **单一旋钮**：调高 = 更频繁主动；调低 = 更安静。**用它替掉一堆零散阈值** |
| `max_cues_per_day` | 每天主动说话上限 | 4 | 同上 | 防打扰的**硬闸门** |
| `quiet_hours` | 静默时段 | `["23:00-07:00"]` | 同上 | 夜间不主动 |
| `quiet_period_minutes` | 两次主动之间的最小间隔 | 30 | 同上 | 静默期 |
| `idle_silence_scale` | 无回应后的降频倍率 | 2.0 | 同上 | ⭐ 越被忽略越安静 |
| `reaction.simple_delay_ms` | 回应前的思考延迟 | 120（**现有值**，`experience_store.py:27`） | 现有代码 | 已有，别丢 |
| `reaction.liveliness_level` | 活跃度 0–3 | 2（现有值，`:30`） | 现有代码 | 已有 |
| `proactivity.enabled` | 总开关 | true | 同上 | 一键关掉所有主动行为 |

⭐ **用法**：用户说"小栈你话太多了" → **只改一个数**（`talkativeness: 50 → 25`），不碰任何代码，不需要重启（§6.2 热更新）。**这是把"陪伴感调节"从开发任务变成用户任务的关键。**

### 8.4 ⭐ 与 `due_cues()` 的最小改造（不重写）

```
due_cues(now, consume)  # 现有签名不变
  ↓ 在 for 循环内、append 之前加 4 个闸门：
  ① if now 在 quiet_hours: continue
  ② if runtime.spoke_today >= max_cues_per_day: break
  ③ if now - runtime.last_spoke_at < quiet_period: continue
  ④ if 该 cue 上次触发后用户无回应: interval *= idle_silence_scale
  ↓ append 后：
  runtime.spoke_today += 1
  runtime.last_spoke_at = now
```

⭐ **注意 `consume` 语义要保留**（`:296` 的 `consume=True` 才写 `last_cues`）—— **"试算"（`consume=False`）不能污染状态**，这是现有代码的好设计，改动时别破坏。

### 8.5 ⭐ "沉默时自己思考"（sleep-time compute，抄 Letta 的概念，§3.1）

Letta 的 sleep-time compute 是"没有用户交互时，agent 自己整理记忆"。**我们不引入 Letta 框架，但可以抄这个动作**：

- **触发**：VPS 上一个低频定时任务（如每 30 分钟，或每天凌晨 3 点）。
- **做什么**（**不产生任何 KPI 数字**）：
  1. 把本周 `episodes` 蒸馏成 `facts`（session distillation，§3.5）；
  2. 合并/去重 `facts`（同 key 取最新，冲突留痕）；
  3. 清理过期 `episodes`（TTL，§5.4）；
  4. ⭐ **生成"明天想主动聊什么"的内部草稿**（**存在 `private/`，不入库**，§6.4）——比如"她上周说在准备雅思口语，可以明天问一句练得怎么样"。
- **边界**：⭐ **这个任务只能写 `private/` 和 `facts`，绝不能产生"指标"**；⭐ **它不许自发对外说话**（说话仍走 `due_cues` 的闸门）。
