# 54 · 韵律特征提取与端侧实时可行性（ESP32-S3 / iOS）

> 研究员：worker（research）｜任务编号 R54｜状态：**已完成**（2026-10-24）
> 目标：为「韵律 → 舵机/关键帧」这条链路确定**端侧实时可得的韵律特征**，产出可直接进技术方案的结论。
> 硬性规则：所有结论必须有实际抓取的来源 URL；区分「官方实测 / 第三方声称 / 本人推断」三档；无实测来源的数字一律标「未取得」。

## §0 一句话结论

**能跑，但不该在 ESP32-S3 上跑 —— 这一版应该在服务端算。**

- **ESP32-S3 端**：官方语音栈（esp-sr / esp-dsp / esp-dl-audio / dl_fft）**完全没有任何 F0、pitch、共振峰、语速实现**（528 个 esp-sr 文件全树 grep：`prosody`=0、`formant`=0、`autocorrelation`=0；`pitch` 仅 1 处，在中文 TTS 的时间伸缩器内部且不导出）。官方白送的是**响度**（AFE `data_volume`，dBFS）与**停顿**（AFE `vad_state`）。自研 F0 的积木（定点 FFT、相关/互相关、biquad、窗函数）**全部官方 Apache-2.0 齐备**，官方实测 512 点定点实数 FFT 仅 **3873 cycles**（≈16 µs）⇒ **算力上极宽裕**。
- **但算力不是问题，载体才是**：05 号红线 1「不改固件」意味着 ESP32-S3 上**没有我们代码的载体**；官方 AFE 的 `data_volume`/`vad_state` 也只在固件进程内，拿不到。
- **iPhone 端**：**Apple 官方没有任何音高 API**（SoundAnalysis 7 个公开类 + Speech 20 个公开类，穷举确认）；能拿到的是响度（`averagePower` / `vDSP_rmsqv`）和原始 PCM 入口（iOS 26+ `SpeechAnalyzer`/`AnalyzerInput`）。F0 要自己算或用 MIT 的 `Tuna`（默认 YIN，SwiftPM，iOS 可用）。
- **中间件**：**不存在可部署的「轻量韵律→动作」模型**（GitHub 检索 0 命中；arXiv 命中的全是扩散 Transformer / GPU 级：ECHO-G、DuoGesture、Gelina 等）。**规则层 + 关键帧插值才是对的抽象层级**（55 号正在做的那个）。
- **⭐ 结论**：**在服务端算**。服务端本来就同时握着**用户上行 PCM** 和 **TTS 下行 PCM**（31 号目标架构），而 05 号 P0-6 的「关键帧动作合成器」本来就在服务端 ⇒ **零固件改动、零 App 改动、零协议改动**（韵律只作为服务端内部编排输入，不传给设备），且韵律分析与关键帧天然在同一时间轴上。

> 取证方式：`git clone --depth 1 https://github.com/espressif/esp-sr.git`（本地实克隆，master 提交 `78a923d29a45e4e1433b909d3da12ab5b0f994fc`，2026-10-13）+ `gh api search/code` + 全树递归 grep。

> 来源 URL：https://github.com/espressif/esp-sr ｜ https://github.com/espressif/esp-sr/blob/master/README.md

### 1.1 esp-sr 的模块清单（官方 README 原文）

README 的 "ESP-SR framework includes the following modules" 列表只有 5 项：

1. Audio Front-end AFE
2. Wake Word Engine WakeNet
3. VAD VADNet
4. Speech Command Word Recognition MultiNet
5. Speech Synthesis

**没有任何 pitch / F0 / prosody / formant 模块。** AFE 的官方描述为 "integrates AEC (Acoustic Echo Cancellation), VAD (Voice Activity Detection), BSS (Blind Source Separation) and NS (Noise Suppression), NSNET(Deep noise suppression) and other functions" —— 全部是「让语音识别更准」的前端/后端算法，**没有一个是描述「说话人怎么说话」的韵律分析**。

### 1.2 全树代码取证：esp-sr 无任何韵律特征提取实现

在克隆到本地的 esp-sr 仓库中，对 528 个 `.h/.c/.cpp/.rst/.md/.txt/.py` 文件做递归 grep（排除 `.git`）：

| 检索词 | 命中数 | 命中位置 / 说明 |
| --- | --- | --- |
| `pitch` | 1 | 仅 `esp-tts/esp_tts_chinese/include/esp_tts_stretcher.h:13`，注释 "This library performs time domain harmonic scaling **with pitch detection**" |
| `prosody` | 0 | 全树零命中 |
| `formant` | 0 | 全树零命中 |
| `fundamental` | 0 | 全树零命中 |
| `autocorrel` | 0 | 全树零命中（无自相关基频检测实现） |
| `f0` | 2059 | 全部是十六进制采样字面量 `0xf0` 等，**非基频特征**，不计数 |

来源 URL：https://github.com/espressif/esp-sr/blob/master/esp-tts/esp_tts_chinese/include/esp_tts_stretcher.h

**结论（官方代码实证）**：Espressif 官方语音组件 **不提供** F0/pitch 检测、共振峰、语速、停顿分布等任何韵律特征提取 API。韵律必须在我们的固件里自己实现，或在手机端算。

### 1.3 但官方白送一个「响度」特征：`data_volume`

`include/esp32s3/esp_afe_sr_iface.h` 的 `afe_fetch_result_t` 结构体里有一个现成的能量字段：

```c
float data_volume;  // VAD input mean square energy in dBFS, calculated before AGC. With VadNet
                    // enabled, the window covers vad_min_speech_ms; otherwise, one fetch frame is used.
```

来源 URL：https://github.com/espressif/esp-sr/blob/master/include/esp32s3/esp_afe_sr_iface.h

这是**每次 fetch 直接给出的 dBFS 均方能量**（AGC 之前算的，等于麦克风原始响度，不受自动增益污染）。配套还有：

- `esp_afe_sr_iface_op_set_vad_energy_threshold_t` / `..._get_vad_energy_threshold_t` —— VAD 能量阈值，单位 dBFS，范围 [-100, 0]。
- `vad_state_t vad_state` —— 逐帧语音/静音判定 → **停顿分布（pause/hesitation）可直接由 VAD 状态机时间序列导出**，不需要自己做能量门限。

**结论（官方 API 实证）**：响度（dBFS）与停顿分布这两项韵律特征，**用官方 AFE 现成拿，零额外算力**；pitch / 语速必须自己算或外移。

### 1.4 官方音频前端的能力边界与输入格式

- AFE 输入格式（`esp_afe_sr_iface.h` 的 `feed` 注释原文）："The input data should be arranged in the format of channel interleaving. The last channel is reference signal if it has reference data." + "only support **signed 16-bit @ 16 KHZ**"。→ **官方链路就是 PCM int16 / 16 kHz**，与我们 M5Stack CoreS3 的麦克风采样率一致。
- `esp_afe_sr_iface_op_get_samp_chunksize_t` / `..._get_samp_rate_t` —— 可查询每帧样本数与采样率。
- `esp_afe_sr_iface_op_fetch_with_delay_t` —— 带超时的取帧（默认超时 2000 ms）。

### 1.5 官方给了「自己写基频检测」的 DSP 积木（esp_speech_features.h）

`include/esp32s3/esp_speech_features.h` 公开了完整的谱分析原语：

| 函数 | 作用 | 对我们的用处 |
| --- | --- | --- |
| `esp_fft_init(int nfft)` / `esp_fft_deinit` | FFT 表初始化（注释："For ESP-PLATFORM, use dl_fft"） | 自研基频检测的 FFT 底座 |
| `esp_fftr(float *x, int nfft, void *fft_table)` | 实数 FFT | 自研基频检测 |
| `esp_spectrum_step(float *x, int nfft, bool use_power, void *fft_handle)` | 幅度谱 / 功率谱 | 自研基频检测的谱分析 |
| `esp_preemphasis_step(float *x, unsigned int len, float coeff, float last)` | 预加重 | 自研基频检测标准前处理 |
| `esp_win_func_init(char *win_type, ...)` | 窗函数：hanning / hamming / sine / povey / rectangular / wn9 | 自研基频检测加窗 |
| `esp_mel_filter_init(...)` / `esp_mel_dotprod_step(...)` | Mel 滤波器组 | 可选：共振峰近似 / 谱质心 |
| `esp_mfcc_malloc(size, from_psram)` | 可选从 PSRAM 分配 | 8 MB PSRAM 下不是瓶颈 |

`include/esp32s3/esp_mfcc_iface.h` 的 `esp_mfcc_opts_t` 给出官方默认帧参数：`winstep_ms`（步进，默认注释 10）、`winlen_ms`（窗长，默认注释 25）、`nfilter`、`nfft`、`samp_freq`、`low_freq`/`high_freq`、`preemph`（0.97）、`win_type`。→ **官方帧约定就是 16 kHz / 25 ms 窗 / 10 ms 步进**，自研基频跟踪直接沿用这个约定即可与 AFE 对齐。

来源 URL：https://github.com/espressif/esp-sr/blob/master/include/esp32s3/esp_speech_features.h ｜ https://github.com/espressif/esp-sr/blob/master/include/esp32s3/esp_mfcc_iface.h

### 1.6 官方 TTS 组件里藏着一个 BSD 许可的基频检测实现（但接口不暴露 F0）

`esp-tts/esp_tts_chinese/include/esp_tts_stretcher.h` 是 David Bryant 的 **SoundTouch / Time Domain Harmonic Scaler**（BSD 许可）的 `stretch.h`。其头注释写明 "This library performs time domain harmonic scaling **with pitch detection** to stretch the timing of a 16-bit PCM signal"。其内部用**互相关（correlation）法做周期检测**。

但公开 API 只有 `stretch_init(shortest_period, longest_period, num_chans, fast_mode)` / `stretch_samples(...)` / `stretch_flush` / `stretch_deinit` —— **检测出的 pitch 不对外暴露**。

- 对我们的价值：**这是一份在 ESP32 上跑得动的 BSD 许可相关法基频检测参考实现**，可作为我们自研 F0 的算法蓝本与代码来源（需自行确认 lib 内的 .c 是否随仓库提供，以及是否允许复用）。
- 不能直接用的原因：二进制库在 `lib/` 目录内，且不导出 F0；把它接到「说话人韵律」上还需要自己的标定。

### 1.7 Espressif 的 FFT / DSP 组件归属（README 指向）

README 末尾的 "Documentation and Resources" 明确：

- Fbank/MFCC → https://github.com/espressif/esp-dl/tree/master/esp-dl/audio
- FFT → https://components.espressif.com/components/espressif/dl_fft/versions/0.3.1/readme （即 `dl_fft` 组件 0.3.1）
- AI 推理框架 → https://github.com/espressif/esp-dl

即：**官方把 DSP 能力放在 esp-dl（audio 子目录）与 dl_fft，而不是放在 esp-sr 里**。esp-sr 只是消费者。这解释了为什么 esp-sr 里搜不到任何 pitch 实现。

**结论（官方代码实证）**：Espressif 官方 DSP 栈里**积木齐全**——定点与浮点 FFT、相关/互相关、biquad、窗函数、Mel 滤波器组，许可证宽松（esp-dsp 为 Apache-2.0）；但**没有任何一个 F0/pitch 检测器**。

⇒ 自研基频检测在 ESP32-S3 上属于「**有积木、没积木房**」：积木（Apache-2.0）都有了，房子（YIN / 自相关 / 谱峰插值那几十行）要我们自己盖。工程量是**百行级**，不是研究级问题。

> **【第三方声称】**= 第三方仓库或论文自己声称的数字，未见独立复现；
> **【本人推断】**= 我基于官方数字做的算术推算，无直接实测。

| # | 方案 | 平台 | 能给的韵律特征 | 延迟 / 帧率 | 内存 | 来源 | 可信度档 |

### 2.1 逐特征小结：哪些能真拿到

| 韵律特征 | ESP32-S3 端 | iPhone 端 | 服务端 | 结论 |

### 2.2 关于「官方到底有没有 pitch」的最终裁决

**Espressif 官方语音栈（esp-sr + esp-dsp + esp-dl/audio + dl_fft）里没有任何 F0/pitch/formant/语速实现。** 这是 528 个 esp-sr 文件全树 grep + 757 个 esp-dsp 路径清单 + esp-dl/audio 目录树的穷举结论（§1.2、§1.9）。
任何「Espressif 有现成 F0 库」的说法都与源码不符；官方 TTS 里那个唯一叫 pitch 的东西是**时间伸缩器的内部实现，不对外暴露**。

### 3.3 iPhone 端「实时 F0」能不能做？——能做，但有两个必须诚实标注的点

1. **技术上能做**：Tuna 默认 YIN + `AVAudioEngine` tap + Accelerate RMS，在 iPhone 上跑 16~32 ms 一帧的 F0/能量跟踪没有原理性障碍。

### 3.4 「iPhone 算完通过 WS 下发」这条路的可行性判定

| 判据 | 结论 |
| --- | --- |

| 判定 | **技术上可行，但架构上是绕远路**。除非有「离线/无服务端时也要有身体表达」这类硬需求，否则不建议作为主路径 |

### 4.3 ⭐ 由此得出的工程裁决：韵律→动作必须是**我们自己写的规则层**，不是模型

| 事实 | 依据 |
| --- | --- |
| 没有任何开源的「轻量韵律→动作」模型 | §4.1 检索（GitHub 0 命中，arXiv 全是重型模型） |
| 唯一成熟的「韵律→动作」范式是**规则/查表 + 关键帧插值** | 53 号 §5.4 已确认官方 0x14 通道就是「关键帧时间轴」；55 号做的就是插值层 |
| 学术模型的重心已从「纯韵律」转向「韵律 + 语义」 | 2609.36685 明确指出纯声学韵律会忽略语义、需语义补充 —— 说明**纯韵律驱动动作有上限**，我们要早做打算 |
| 我们的动作自由度很小（颈 2 舵机 + 脸 3 元素 + 双灯） | 53 号 §5.2/§5.3 —— 这种低维输出**不需要神经网络**，规则层足够且可控可调 |

⇒ **建议路线**：不要找模型，**直接把「韵律描述符 → 关键帧」写成一组可标定的查表/曲线**（55 号的插值层就是这个），并把「标定数据」当作可积累资产。这既符合 05 号 P0-6「关键帧动作合成器」已有的规划，也符合我们的 05 号红线 1（不改固件）。

### 4.4 可选增强：服务端用轻量 SER 补「情绪」维度

韵律描述符（F0 轮廓 / 能量 / 语速 / 停顿）本身**不含情绪语义**（升调可以是疑问，也可以是惊讶，也可以是噪声）。若要「韵律→情绪」，可选：
- **零成本版**：直接复用已有的情绪抽取（31 号已设计 LLM 情绪标签 + `[[emotion:xxx]]` 兜底标记），韵律只用于**表达强度**（同一情绪下，F0 跨度大 → 动作幅度大）。
- **轻量模型版**：服务端跑 DistilHuBERT / AMRD 类轻量 SER，输出情绪概率作为韵律之外的第二路输入。**代价**：需引入模型推理依赖与 GPU/CPU 预算，且 05 号红线 3 强调个人数据不入库，SER 的隐私口径要单独审。
- **建议**：P2 阶段先走**零成本版**，把模型留到有真实需求时再上。

⇒ **只要坚持红线 1，ESP32-S3 上跑我们的 F0 代码就没有载体**（官方固件里没有我们的代码；要跑就得刷自己的固件 = 违反红线 1 = 05 号 §3 已经在方案 A 里否决过的路径）。
⇒ 结论：**韵律特征不在 ESP32-S3 上算。** 算力不是瓶颈（§1.10 显示还很宽裕），**载体/架构才是**。

### 5.2 决定性事实：服务端本来就已经握着两段 PCM

31 号已定的目标架构是「用我们的 server 取代小智服务器，音频上下行都过我们」：

| 方向 | 音频流 | 服务端是否持有 PCM | 来源 |
| --- | --- | --- | --- |
| **上行**（用户 → 机器人） | 机器人麦克风 → PCM 16 kHz / 60 ms 帧 → `esp_opus_enc` → Opus → WS → server | ✅ server 收 Opus → 解码 PCM → 送 STT | 31 号 §3.5 表格：「server 侧 ASR（server 收 Opus → 解码 PCM → 送 STT）」；`firmware/xiaozhi-esp32/main/audio/audio_service.cc:81,409-411`（`encoder_sample_rate_ = 16000`、`frame_duration = 60`、`channels = 1`） |
| **下行**（机器人说话） | MiniMax TTS → Ogg/Opus → server 拆包 → 裸 Opus → WS → 设备播放 | ✅ server 侧就有 TTS 音频字节流（31 号 §3.4 要求 server 做 Ogg de-mux） | 31 号 §3.4 / §3.5 |

⇒ **两路韵律都能在服务端拿到解码后的 16 kHz 单声道 PCM**：
- **机器人自己的韵律**（下行）→ 驱动它的身体表达（自我表达 / embodied）——这是「韵律驱动桌面表情机器人」这条线的正解，也是 CHI EA 2026 论文那类工作做的同一件事。
- **用户的韵律**（上行）→ 驱动它的**反应**（用户语调上扬 → 机器人歪头）。

### 5.3 ⭐ 建议方案（这一版就是能进 05 号 P2 的那一版）

**一句话**：**在服务端流式算韵律，用它编译出 0x14 关键帧；ESP32-S3 与 iPhone 都不动。**

| 项 | 决定 | 理由 |
| --- | --- | --- |
| **谁在哪算** | **服务端**，紧贴 TTS 流（下行） | ① 服务端已有 PCM（§5.2）；② 05 号 P0-6「关键帧动作合成器」本来就在服务端（把「情绪 + 韵律」编译成 0x14 序列）；③ 零固件改动、零 App 改动、**不动 03 号数据契约**；④ 韵律分析与关键帧在**同一时间轴**，天然对齐 |
| **传什么** | **什么都不传给设备**。韵律特征只作为**服务端内部的编排输入** | 设备侧零感知 ⇒ 不改 0x14 schema ⇒ 不改固件 ⇒ 不违反红线 1。韵律只改变「服务端生成什么关键帧」 |
| **算哪些特征** | 第一版**只要 3 个**：① 归一化 F0 轮廓（半音，相对说话人中位基线）② 能量包络（dBFS，相对中位数）③ 停顿/节奏（VAD 状态机导出的静音段与语速） | 这三个覆盖了「高低起伏 / 强弱 / 快慢迟疑」，足够驱动「点头幅度 / 歪头 / 停顿前倾」等身体表达。**共振峰与精细语速先不做**（§2.1：全链路都要自研，收益最低） |
| **怎么标定** | **全部用相对值，不用绝对 Hz/dB** | 见 §5.4 |

### 5.4 标定方案：用相对值，因为 TTS 音色与音量会炸掉绝对阈值

这是本方案最容易做错、也最决定成败的一点。

**问题**：同一段文字，TTS 的基频取决于音色（MiniMax 每个 `voiceID` 的 F0 基线不同）、音量取决于 `audio_setting`、语速取决于模型版本。**绝对阈值（"F0 > 250 Hz 就算高"）在换音色/换音量后立刻失效。**

**做法**（全部可在服务端离线完成，不需要真机）：

| 步骤 | 做法 | 产出 |
| --- | --- | --- |
| 1. 建参考集 | 用我们实际会用的音色 × 6 种情绪 × N 句典型台词，跑一遍 TTS，把 PCM 存下来 | 一批带标签的 TTS 音频样本 |
| 2. 提特征 | pyworld / librosa 提 F0 轮廓、能量包络、停顿 | 每个样本的特征向量 |
| 3. 求每音色的基线 | 对每个 `voiceID` 求 F0 中位数 `m` 与 MAD（median absolute deviation） | 音色级基线表 |
| 4. 归一化 | F0 特征转成**半音相对基线**：`12·log2(f0 / m)`；能量转成 **dB 相对该句中位数**；节奏转成**该句语速相对全局均值的比值** | 与音色/音量无关的可比特征 |
| 5. 定动作阈值 | 在归一化空间里手工看散点，定「F0 半音 > +2 ⇒ 抬头」「能量 > +6 dB ⇒ 身体前倾」这类规则；每条规则挑 3~5 个样本做回归测试 | 规则表 + 回归测试集 |
| 6. 在线计算 | 流式：每 16~32 ms 一帧，算 F0/能量/停顿；用**滑窗中位数**做在线基线（代替离线的全局中位数），随情绪切换缓慢重估 | 实时归一化特征流 |

⚠️ **在线基线的冷启动问题**：一句话开头的前几百毫秒还没有足够样本估基线 ⇒ 这段时间的归一化值不可信。**处理办法**：这段窗口直接不发韵律驱动的动作（回落到情绪模板），等基线稳定（建议 ≥ 300 ms 有声段）再启用。

### 5.5 兜底与降级（这一版必须一开始就写好）

| 情况 | 降级行为 |
| --- | --- |
