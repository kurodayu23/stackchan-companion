# 79 · E-4 结构化输出实测：MiniMax 云端能不能一次产出 reply+emotion+motion+intensity

> 建立日期：2026-10-25（第三轮夜间，07:20 后）
> 测量工具：`tools/probe_minimax_json.py`（自检 15/15，已进 CI）
> 被测对象：`docs/spec/00` §9 的 **O-3** 开放项 + §3 E-4 的「**待复核**」技术约束
> 真实 API：`https://api.minimaxi.com` ／ 模型 `MiniMax-M3.1-Flash`（生产同款）

---

## 一、结论先行

1. ⛔ **`response_format: json_schema` 在 `MiniMax-M3.1-Flash` 上被「接受但未生效」。**
   ⇒ `docs/spec/00` §3 E-4 写的那条约束**成立**：云端不能靠 schema 约束输出。
   ⇒ **必须自己写「解析 + 校验 + 重试 + 兜底」**，不能依赖服务端 schema。
2. ✅ **但 E-4 本身可行** —— **靠提示词就够了**（`plain` 模式）。
   用**生产环境的真实 ENFP 人格提示词**（`personas/enfp.json`）实测 **8/8 通过**。
   ⇒ 「云端结构化输出可能没有现成实现」这句话是对的，
   但它的**推论**（「情绪状态机没法做」）是错的 ⇒ **开放项 O-3 可以销账**。
3. ⭐ **顺带暴露一个规格歧义（之前没人写下来）**：`emotion` 字段**指谁的情绪**？
   实测里模型给出的 `emotion` 是**小灯自己**的状态（用户抱怨时它道歉 ⇒ `sad`），
   而规格从头到尾**没说清**这个字段是谁的 ⇒ 已登记为 **Q20**。

---

## 二、三种模式的实测

口径：一次调用算「通过」要同时满足
① HTTP 200 且 `base_resp.status_code == 0`（⚠️ MiniMax 失败时也可能返回 HTTP 200）
② 剥掉 `<think>…</think>` 后能解析出 JSON 对象
③ 四个字段齐全且类型正确：`reply`(非空 str) / `emotion`(枚举内) / `motion`(枚举内) / `intensity`(0.0–1.0 的数字)

| 模式 | 请求里加什么 | 次数 | HTTP 200 | base_resp=0 | 抠出 JSON | 四字段齐全 | **通过率** |
|---|---|---|---|---|---|---|---|
| `plain` | 什么都不加，只在 system prompt 里要求输出 JSON | 3 | 3 | 3 | 3 | 3 | **100%** |
| `json_object` | `response_format: {"type":"json_object"}` | 3 | 3 | 3 | 3 | 3 | **100%** |
| `json_schema` | `response_format: {"type":"json_schema", ...}` | 3 | 3 | 3 | 3 | 3 | **100%** |

### ⭐ 但「三种都 100%」这件事本身**证明不了 schema 起了作用**

因为 `plain`（纯提示词）也是 100% ⇒ 「输出是合法 JSON」这件事，
**无法区分**「schema 被执行」与「提示词起了作用」。

⇒ 必须做**冲突探针**。

---

## 三、⭐ 冲突探针：schema 到底被执行还是被忽略

**做法**：故意让 schema 与提示词**互相矛盾**：

- schema 说 `emotion` 只能是 `neutral`、`motion` 只能是 `idle`；
  提示词却让模型从 6 个情绪 / 7 个动作里挑；
- schema 额外要求一个提示词里**根本没提**的字段 `must_be_present`。

**观测（6 次）**：

| 观测 | 值 |
|---|---|
| HTTP 200 | 6 / 6 |
| 观测到的 `emotion` 分布 | `['happy', 'sad', 'sad', 'happy', 'sad', 'sad']` |
| 出现 `must_be_present` 的次数 | **0 / 6** |

⇒ **emotion 仍随提示词变化、schema 额外要求的字段一次都没出现**
⇒ **schema 被 API 接受但未生效**，实际由提示词决定输出。

⚠️ 这就是「**所有模式都 100% 通过**」背后的真相：
**`response_format` 在 M3.1-Flash 上是一个被容忍、被忽略的参数。**

---

## 四、用**生产真实人格包**再压一轮（这才是决策依据）

`personas/enfp.json` 的 `system_prompt` 是「中文口语、短句、先共情、不要念思考过程」——
风格上**鼓励**自然对话输出 ⇒ 它可能和「只输出 JSON」打架
⇒ 只用通用 JSON 指令测出来的 100% 说服力不够。

**做法**：人格提示词原文 + 追加 JSON 硬要求 ⇒ `plain` 模式跑 8 次。

| 模式 | 次数 | HTTP 200 | base_resp=0 | 抠出 JSON | 四字段齐全 | **通过率** |
|---|---|---|---|---|---|---|
| `plain` + **生产 ENFP 人格提示词** | 8 | 8 | 8 | 8 | 8 | **100%** |

### 实际产出抽样（看内容质量，不只看格式）

| 输入 | 期望 emotion | 实际 emotion | intensity | reply |
|---|---|---|---|---|
| 今天真开心啊，见到你真好。 | happy | happy ✅ | 0.9 | 我也很开心呀，见到你真的很好。哈哈，今天有什么好事让你这么开心？ |
| 我有点难过，不太想说话。 | sad | sad ✅ | 0.75 | 嗯，听起来你现在很难受。不想说话也没关系，我就在这儿安静陪你。 |
| 你怎么这么慢！我都等半天了。 | angry | **sad** ⚠️ | 0.7 | 抱歉让你等这么久！刚刚卡住了，现在我在这儿呢。 |
| 我有点难过，不太想说话。 | sad | sad ✅ | 0.45 | 嗯，我听见了。先不用说话，我陪你安静待一会儿。 |

- ✅ `reply` **质量很好**：中文口语、短句、先共情、不念思考过程 ⇒ **人格没被 JSON 要求破坏**。
- ✅ `intensity` 有区分度（0.45 / 0.7 / 0.75 / 0.9）。
- ⚠️ **emotion 与「用户情绪」一致 4/6**：两次不一致都是用户抱怨的场景
  ⇒ 模型给的是**小灯自己的情绪**（它在道歉 ⇒ sad），不是镜像用户情绪。

## 五、⭐ 由此暴露的规格歧义（新增开放项 Q20）

`docs/spec/00` §3 E-4 只写「一次产出 reply + emotion + motion + intensity」，
**从没说过 `emotion` 是谁的**：

| 读法 | 含义 | 设备脸上的表情 | 观察到的实测行为 |
|---|---|---|---|
| **A. 小灯自己的情绪** | 它此刻的状态（开心/低落/生气） | 小灯的脸 | ✅ 实测就是这个（抱怨时它道歉 ⇒ sad） |
| **B. 镜像用户的情绪** | 用户此刻的情绪 | 小灯的脸变成用户的情绪 | ❌ 实测不是这个 |

⇒ **两种读法会做出完全不同的产品**：
读法 A 是「有自己状态的角色」，读法 B 是「情绪镜子」。
⇒ 与 Q17（「小栈不永远甜」是否作为基线）**直接耦合**：
若小栈不永远甜 ⇒ 它的脸应当是自己的状态（A）⇒ 读法 B 与之矛盾。

⇒ 已登记 **Q20**（见 `docs/spec/07` §3.5），并给出建议：**读法 A（小灯自己的情绪）**，
用户的情绪只作为**诱因**（用户难过 ⇒ 小灯先共情，但脸显示的是小灯此刻的状态）。

## 六、对 E-4 验收标准的修订建议

`docs/spec/00` §3 E-4 原文：「任一 provider 下，emotion 必落在枚举内、motion 必落在动作库内，
非法输出自动重试 ≤2 次后降级。」

**本轮实测补三条**（都是实测逼出来的，不是想当然）：

1. ⚠️ **不能用服务端 schema 当护栏** ⇒ 护栏必须在我们自己这一侧
   （`extract_json_object` + `validate_turn`，见 `tools/probe_minimax_json.py` 的纯函数部分）。
2. ⚠️ **必须处理模型的"多说"**：实测里输出可能带 ```` ```json ```` 包裹、前后有闲聊、
   `<think>` 内联推理 ⇒ 抠取逻辑要覆盖这三种形态（探针里已实现并有自检覆盖）。
3. ⭐ **intensity 要当连续量用**：实测 0.45–0.9 有分布 ⇒ 不该拍成 6 档离散。

## 七、未验证 / 诚实边界

- ❌ **样本量小**：主测 3×3 + 人格包 8 次 + 冲突探针 6 次 ⇒ 合计 23 次调用。
  「100%」的**置信区间很宽**，**不能**据此声称「生产环境 100% 可靠」。
- ❌ **只测了 `MiniMax-M3.1-Flash`** ⇒ `MiniMax-M3` / `MiniMax-Text-01` 是否不同，**未测**。
- ❌ **未测长回复**（本轮 reply 都是短句）⇒ 长回复时 JSON 是否仍完整，**未测**。
- ❌ **未测多轮对话**（带 history 时模型是否还守 JSON 格式），**未测**。
- ❌ **未测 `function calling`**（备选 2）⇒ MiniMax 是否支持，**未测**。
- ❌ **未测重试与降级路径**（探针只测了单次，不测「非法输出 ⇒ 重试 ⇒ 降级」这条链）。
- ✅ **已验证**：在**生产同款人格提示词**下，8/8 稳定产出四字段齐全的合法 JSON。
- ✅ **已验证**：`response_format: json_schema` 在本模型上**未生效**（冲突探针 6/6 证明）。
