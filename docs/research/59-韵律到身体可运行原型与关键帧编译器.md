   │
   ▼

### 3.1 7 维韵律 → 映射目标（55 号）

| 韵律维度 | 映射到 | 本原型实现 |
|---|---|---|
| F0 均值 | 头部俯仰基线 | 半音偏移 × `f0PitchGain`（参考基频 220 Hz） |
| F0 重音峰 | 点头幅度 | `base_pitch - f0AccentNodGain × gain` |
| 能量 | 眼睛 weight、灯亮度 | 嘴 weight `+45×gain`；眼 weight `+12×gain`（**weight 越大 = 越睁开**，能量高应更睁开 ⇒ 取正，见 §11 B1） |
| 语速 | **只映射时间轴缩放** | 锚点时刻整体 × `1/rateTimeScale`；**锚点角度值一个都不改**（§11 B3） |
| 停顿 | **落定**，不是「不动」 | 停顿中点插入「缓缓回到中位 + 眼神放松」锚点 |
| HNR | 眼睑柔和度 | 停顿锚点的 eye weight **下调**（weight 越小越闭 ⇒ 更柔和） |
| 谱质心 | 灯色冷暖 | Oklab 空间插值，H 通道按 CSS Color 4 §13.5 显式走 shortest 路径 |

## 5. ⭐ 抓到的 6 个 bug（4 个是静默错误）

这一节是本号最有价值的部分：**三个 bug 都不抛异常，输出的数字看起来完全合理，但结果是错的。**

### 5.1 Bug 1 · YIN 差函数的「后缀和」用错表 ⇒ F0 掉到 0.007 Hz

- **症状**：整段 F0 恒为 `0.0067 Hz`，自检直接 FAIL。
- **根因**：
  ```python
  # ❌ 错：tail[τ] 实际是「最后 N-τ+1 项的能量和」
  tail = np.concatenate(([0.0], np.cumsum(x2[::-1])[::-1]))
  # ✅ 对：suffix[k] = sum(x2[k:])，长度 N+1；tail[τ] = suffix[N-τ]
  suffix = np.concatenate((np.cumsum(x2[::-1])[::-1], [0.0]))
  ```
  差函数 `d(τ) = Σ(x[j]-x[j+τ])²` 依赖「窗口切片和」，用错表 ⇒ `d` 全错 ⇒ `cmnd` 全错。
- **通用形式**：**自相关/差函数类算法的「窗口切片和」必须用后缀和表，前缀和表错位一格就全错。**

### 5.2 Bug 2 · 平滑时把未浊音帧的 0 一起平均 ⇒ F0 塌成一个值

- **症状**：所有浊音帧的 F0 恒为同一个值（150 Hz 信号在 200 Hz 段也报 150）。
- **根因**：未浊音帧被填成 `0.0`（= 1 Hz），`medfilt(33)` 与 Butterworth 把这些 0 当成真实值一起平均/滤波。
- **修法**：未浊音帧先**线性插值**再滤波，最后用 `voiced` 掩码还原为 0。
- **通用形式**：**「稀疏信号 → 平滑」必须先补齐再滤，最后按原掩码还原**；直接对含 0 的数组做滤波是最常见的静默错误。

### 5.3 Bug 3 · Butterworth 归一化截止频率用了**音频采样率**而非**帧率** ⇒ 滤波器退化成均值滤波器

- **症状**：F0 恒等于全段直流；`f0_smooth` 每个元素完全相同。
- **根因**：
  ```python
  # ❌ 错：sr = 16000（音频率），但 F0 轮廓的采样率是 100 Hz
  butter(5, 8 / (sr / 2))        # 归一化截止 = 0.001 ⇒ 截止 0.08 Hz
  # ✅ 对：滤波器的采样率 = 该序列自己的采样率
  frame_rate = 1.0 / hop_sec      # = 100 Hz
  butter(5, 8 / (frame_rate / 2)) # 归一化截止 = 0.16  ⇒ 截止 8 Hz
  ```
  截止 0.08 Hz 时滤波时间常数（≈ 1/(2π·0.08) ≈ 2 s）**大于整段时长** ⇒ 输出恒为 DC。
- **通用形式**：**任何施加在「派生序列」上的滤波器，归一化截止频率必须用该序列的采样率**；用错不会报错，只会静默退化成均值滤波器。
- **可复用判据**：滤波器输出若出现「异常整齐的常数」，先查归一化截止频率与该序列采样率的比值。

### 5.4 Bug 4（设计级）· 情绪基线 `pitch` 超出舵机物理上限 ⇒ 情绪差异被钳掉

- **症状**：`Happy_pitch = 92°` / `Neutral_pitch = 88°` 均超过物理上限 87°，被钳到软限位 85° ⇒ Happy 与 Neutral 的俯仰差异消失。
- **修法**：所有基线 `pitch` 落到软限位内（现为 52°~80°）。
- **通用形式**：**情绪基线必须先过一遍设备限位再定值**，否则「情绪映射」会被限位静默压平。

### 5.5 Bug 5（假通过）· `rateTimeScale` 的「不映射角度」断言恒为真

> ⚠️ **本条已在独立复核中被推翻并重做**，见 §11 B3。这里保留原始记录作为教训。

- **症状（第一版）**：自检「改语速不改变角度轨迹」恒为真 —— 因为该参数**在代码里从未被使用**，改了自然没影响。
- **第一版修法（已被复核推翻）**：
  - 重新定义为「每音节核产生 `round(rateTimeScale)` 个微动作，**幅度恒定 1.5°**」⇒ 语速改变的是**时间轴密度**，不是角度语义。
  - 断言改成三条：**锚点数变密** + **重音点头深度不变** + **yaw 上界不变**。
- **复核发现的真相**：这个「修法」**本身也是错的**。
  - 那个「音节微锚点」带**非中性 pitch**（`base_pitch - 1.5 × gain`）⇒ 语速**确实改了角度**：实测 rate 1.0→3.0 时 59 帧里 **24 帧 pitch 不同**，最大差 **1.9°**。
  - 新断言同样**结构上测不到** —— 「锚点数变密」比较的量**必然**随 `round(rateTimeScale)` 变；「yaw 上界不变」「重音点头深度不变」都落在微锚点影响不到的量上 ⇒ 仍是假通过。
- **最终修法**：语速改为**纯时间轴压缩**（锚点时刻整体 × `1/rateTimeScale`，锚点角度值一个都不改）；断言改为「**锚点 pitch/yaw/eye 取值集合完全一致**」+「**锚点到达时间确实被压缩**」+「重音点头深度不受影响」。
- **通用形式**：**「参数 X 不影响 Y」这类断言，若 X 未被接线则恒真 —— 必须先断言 X 确实改变了某项可观测量。**
  这条与已有记忆 `enum-failure-first-hypothesis-is-wrong-source-set` 同源：**先证明「我改的东西真的被用到了」，再断言它的影响。**
  补充（本轮新增）：**配套断言的「可观测量」必须与 X 在同一条因果链上** —— 「锚点数变密」不满足，「锚点到达时间变早」才满足。

### 5.6 Bug 6（复核阶段补抓）· 眼睛 `weight` 极性反了 ⇒ 眨眼时反而睁眼

- **症状**：输出数字完全正常（`weight` 全在 0~100），但表情语义是反的。
- **根因**：旧实现假设「`weight` 越大 = 眼睑越下沉（100 = 全闭）」。固件事实相反：
  - `eyes.cpp:47` 构造函数 `setWeight(100)` ⇒ 默认是**睁眼**；
  - `eyes.cpp:71-78` `_eyelid_offset_y = -map_range(_weight, 0, 100, 0, eyelid_height)` ⇒ `weight=100` 眼睑上移一个身位 ⇒ **全开**；`weight=0` ⇒ **全闭**；
  - `eyes.cpp:103-122` 官方情绪表 Neutral=100 / Happy=72 / Angry=70 / Sad=70 / Doubt=75 / Sleepy=35 —— 全是「睁眼程度」。

- **修法**：情绪眼基线改用**固件官方情绪表**；眨眼改为把 `weight` **压到 0**；能量调制方向取**正**。
- **通用形式**：**「量纲 / 极性」这类语义必须回固件取，不能靠命名猜。** 构造函数里的默认值（`setWeight(100)`）和官方情绪表是判定极性的**最廉价证据**，比读 100 行渲染代码更快也更可靠。

### 11.2 四个阻断项：错在哪 → 怎么改 → 用哪条断言证明

#### B1 · 眼睛 `weight` 极性反了

**错在哪**

旧实现假设「`weight` 越大 = 眼睑越下沉（100 = 全闭）」，并据此把能量调制写成**取负**（「能量高 ⇒ 眼睛更闭」）。固件事实正相反：

- `eyes.cpp:47` 构造函数 `setWeight(100)` —— 默认状态是**睁眼**，不是闭眼。
- `eyes.cpp:71-78` `setWeight()`：`_eyelid_offset_y = -map_range(_weight, 0, 100, 0, (int)_eyelid->getHeight())`。
  `weight = 100` ⇒ 眼睑上移一个身位、让出眼睛 ⇒ **全开**；`weight = 0` ⇒ 眼睑落回眼中 ⇒ **全闭**。
- `eyes.cpp:103-122` 官方情绪表：Neutral=100、Happy=72、Angry=70、Sad=70、Doubt=75、Sleepy=35 —— 全都是「睁眼程度」，`Sleepy` 最小。

⇒ 旧实现把「睁眼」写成了「闭眼」：**眨眼时反而把眼睛睁开，常态反而半闭**；能量调制方向也反了。

**怎么改**

1. 情绪眼基线**直接采用固件官方情绪表**（`eyes.cpp:103-122`），不再自造。
2. 眨眼改为把 `weight` **压到 0**（闭眼），再回到原值。
3. 能量调制方向取**正**：`eye_w += energyEyeGain × 12 × e_norm`（嘴相反，嘴 `weight` 越大越张开）。

**用哪条断言证明修好了**（自检 2，全部 PASS）

- 「眼睛基线 == 固件官方情绪表（`eyes.cpp:103-122`，值不漂移）」—— 断言的是**值相等**，比只比大小顺序更强。
- 「眼睛 weight 极性 = 固件（越大越睁开：Sleepy < Happy < Neutral）」。
- 「常态眼睛是睁开的（weight 高）」—— 静息中位 `weight ≥ 50`。
- 「眨眼时 weight 压到接近 0（闭眼）」。

#### B2 · `0x14` 的 MAC 前缀：模拟器加了、云剥了，两头都错

**错在哪**

旧原型假设「所有走 App → 云 → 设备的控制类消息都带 12 字节 MAC 前缀，云会剥掉前 12 字节再转发」。固件事实是**分类剥前缀**：

| 云端分支 | 位置 | 是否剥 12 字节 |
|---|---|---|
| `Opus` | `server/internal/web_socket/web_socket.go:523` | ✅ 剥 |
| `Jpeg` | 同上 `:537` | ✅ 剥 |
| `ControlAvatar` + `ControlMotion` | 同上 `:553` | ✅ 剥 |
| `TextMessage` | 同上 `:569` | ✅ 剥 |
| `RequestCall` | 同上 `:588` | ✅ 剥 |
| **`Dance`** | 同上 `:740` | ❌ **原样转发，不剥** |

官方 App 侧也**不加**前缀：`app/lib/view/home/dance.dart:193` 直接发 `jsonEncode(DanceData.listToJson(danceDataList))` 的裸 JSON 数组。

⇒ 旧原型**两头都错**：模拟器给 `0x14` 加了前缀，云不剥 ⇒ 设备侧 `json.loads` 直接失败（这正是 §6.3 记录的「dance payload 不是关键帧数组」）。

**怎么改**

1. App 侧 `0x14` **不加** MAC 前缀。
2. 云侧只对上述 6 类剥前缀，新增常量 `CLOUD_STRIP_MAC`（`tools/protocol_sim.py:82-83`），其余（含 `Dance`）原样转发。

**怎么验证修好了**

- 静态：`protocol_sim.py` 的 `CLOUD_STRIP_MAC` 集合**不含** `DANCE`；`CONTROL_AVATAR = 0x03`（`:42`）、`DANCE = 0x14`（`:57`）。
- 端到端：设备侧能正常解析出关键帧数组并打印帧数（§6.2 的 `[device] dance 收到 59 个关键帧`）。
- ⚠️ **这一条不在 `prosody_to_motion.py` 的自检范围内** —— 自检只负责产出 JSON，不负责发包；它的验证面在 `protocol_sim.py` 与端到端链路。

#### B3 · `rateTimeScale` 实际会改角度，但文档与自检都声称「不映射角度」

**错在哪**

旧实现用「每音节核产生 `round(rateTimeScale)` 个微动作、幅度恒定 1.5°」表达语速。问题在于**这个微锚点带非中性 pitch**（`base_pitch - 1.5 × gain`）⇒ 语速实际上**改了角度**，与 §3.1 和 §7 的「语速只映射时间轴缩放」自相矛盾。

复核实测：rate 1.0 → 3.0 时，**59 帧里 24 帧 pitch 不同，最大差 1.9°**。更糟的是旧自检**结构上测不到** —— 它只比 `accentNodDegrees` 与 max yaw，微锚点的 pitch 变化根本不在比较范围内 ⇒ 假通过。

**怎么改**

改为**纯时间轴压缩**，锚点角度值一个都不改：

```
time_scale = 1 / max(0.25, rateTimeScale)
at   = anchor_t   × time_scale     # 只有时刻被压缩
ayaw / apitch / aeye 原样送进插值器  # 角度值不动
```

**用哪条断言证明修好了**（自检 3，全部 PASS）

- 「锚点 pitch 取值集合完全一致（角度语义未变）」。
- 「锚点 yaw 取值集合完全一致」。
- 「锚点 eye 取值集合完全一致」。
- 「锚点到达时间被压缩（时间轴确实变了）」—— **这条是必需的配套断言**，否则上面三条会空转（详见 §11.3 类型 2）。
- 「重音点头深度不受语速影响」。
- 「帧数与音频时长绑定（语速不改总时长）」。

#### B4 · 消息类型号写错：`0x13` 应为 `0x03`

**错在哪**

原型把表情通道写成 `0x13`。固件 `hal_ws_avatar.cpp:52` 是 `ControlAvatar = 0x03`；`:66` 的 `0x13` 是 `VideoModeOff`（关闭视频模式）。⇒ 把 `0x13` 当表情发出去，设备根本不解析。

**怎么改**

`0x13` → `0x03`。已落到 `tools/protocol_sim.py:42`（`CONTROL_AVATAR = 0x03`）、`:56`（`OFF_PHONE_SCREEN = 0x13`）、`:57`（`DANCE = 0x14`）；原型侧 `build_avatar()` 的说明也改成 `0x03 ControlAvatar`。

**怎么验证修好了**

- 静态：与 `hal_ws_avatar.cpp:52` 的枚举值逐字对齐。
- ⚠️ **这一条同样不在 `prosody_to_motion.py` 的自检范围内**（自检只产出 JSON，不发包）；验证面在协议层。

### 11.3 三类假通过的断言模式（可复用团队规范）

> 这一节的价值不在本项目。**任何自检 / 单元测试 / 验收脚本都适用。**
> 复核在本次原型里一次抓出 **3 处假通过**，它们都能稳定地「PASS」，却什么也没验证。

#### 模式 1 · 自证型断言（tautology）：断言内容就是被测代码自己的计算结果

**本次实例**

| 旧断言 | 为什么恒真 |
|---|---|
| 「帧数 == 时长 / 40 ms」 | `keyframeCount` 本来就是 `ceil(duration_s × 25)` 算出来的，断言只是把同一个式子写了两遍 |
| 「眼睛位置在 ±16 内」 | 编译器里已经 `_clamp` 过，断言的是**代码自己刚保证过**的事 |

**团队规范**

1. **期望值必须来自被测代码之外的输入**。帧数的期望值要在断言处**独立**用「音频时长 × 25」重算，不能引用编译器的输出。
2. **限幅断言要断言「值确实贴到了边界」**，而不是「值没越界」。只断言「没越界」= 断言「clamp 生效」；真正要防的是「clamp 把差异吃掉了」。
3. **自检问句**：*把被测函数改成永远返回同一个常数，这条断言会失败吗？* 不会 ⇒ 它是自证的，必须重写。

**本次修法**：拆成两条真断言 ——「帧数 == ceil(音频时长 × 25)」（独立算）+「关键帧总时长与音频时长对齐（±1 帧）」（对齐而非恒等）。

#### 模式 2 · 断言「X 不影响 Y」，但 X 根本没接线

**本次实例**

旧断言「改语速不改变角度轨迹」恒真，原因有两层：
① `rateTimeScale` 只影响微锚点的**个数**，断言比较的 `accentNodDegrees` 与 max yaw 都不受它影响；
② 更根本 —— 旧实现里那个微锚点带非中性 pitch，**语速确实改了角度**，但改的那部分不在断言的比较范围内。

**团队规范**

1. **凡有「A 不影响 B」的断言，必须同时存在一条「A 确实影响了 C」的断言**，且 C 必须是**可观测且非平凡**的。
2. 「A 影响了 C」里的 C 要选**与 A 在同一条因果链上**的量。拿「语速 → 锚点时刻」当 C 是有效的；拿「语速 → 锚点个数」当 C 是无效的（个数变化是定义的必然，不是行为证据）。
3. **自检问句**：*把 A 改成另一个值，B 真的没变吗？* 如果 B 没变是因为**比较对象选错了**，这条断言就是假通过。

**本次修法**：「锚点到达时间被压缩（时间轴确实变了）」+「锚点 pitch/yaw/eye 取值集合完全一致（角度语义未变）」成对出现。集合相等比逐帧相等更强，且**任何一处角度漂移都会被抓出来**。

#### 模式 3 · 单位错导致断言恒真

**本次实例**

旧断言「眼睛 x/y 在 ±16 内」：**±16 是像素限幅**（`eyes.cpp:12-16`），而 JSON 通道是 **±100**（`element.h:26-30`）。拿 JSON 值和像素限幅比，永远过 —— 而且原型当时正是按 JSON 语义在设计，**整个眼睛位移通道偏了 6.25 倍**（JSON 16 实际只有 2.56 px）。

**团队规范**

1. **每个限幅断言必须写清量纲**，且限幅的来源要与被断言对象**同量纲**。
2. **做一次换算往返**：JSON → 像素 → JSON，两端都断言（既断「不超过限幅」，也断「换算系数本身对」）。
3. **固件里凡是出现 `map_range` 的地方，都是量纲陷阱的高发点** —— 固件内部一律用「目标量纲」思考（像素、度、0.1 度），线上协议却是归一化值。
4. **自检问句**：*这个数字的单位，和被断言对象的单位一致吗？* 不一致 ⇒ 断言恒真。

**本次修法**：「换算回像素后不超过设备限幅 ±16」+「JSON 100 恰好对应像素 16（换算系数正确）」。第二条尤其关键 —— 它把**系数本身**也纳入断言，防止有人把 6.25 又改错。

#### 附：强度类断言必须带对照组

复核还发现一类弱断言：**「yaw 有变化」**。它能过，是因为原型里有一段**与音频无关**的缓慢「张望」漂移（`yaw += drift`）—— **静音输入同样能过**。

**团队规范**：任何「输出随输入变化」的断言，都要配一条**对照组断言**：用**静音 / 零输入**跑同一管线，断言「有输入时的变化幅度显著大于对照组」。本次修法：「yaw 变化幅度：语音输入显著大于静音输入」（实测 voice_span=35 vs silent_span=20）。

> ⭐ **这三条可以压缩成一句话**：*一条断言如果在被测代码被破坏时仍然会通过，它就不是断言，是装饰。*
