### 2.1 逐条判断

#### ① 大字标题加整宽大图列表
**结构**：`宽体大写标题 → 搜索栏 → 分类 → 整宽大图 → 名字 + 参数 → 箭头按钮`
**视觉高级感的来源**：① 超大字重（font-weight 700+）与超大字号的标题；② 标题占据的**行宽**本身是装饰；③ 分类是一排纯文字，没有胶囊底色。

**对我们的取舍**：
- ✅ **可抄**：**"大图 + 一行元信息 + 一个箭头"的列表条目结构** —— 这正是 iOS 系统列表的原生结构，iOS 端**不需要抄**（原生自带），但**设备端 320×240 值得抄**（设备端没有系统列表）。
- ❌ **不可抄**：**顶部宽体大写字母标题**。理由不止审美 —— `hallmark` 的 Floor 第 9 条把「眉标题 / 全大写字距标签 / small caps」直接列为**不可豁免的 Floor 违例**（"Never an eyebrow, and never a label in tracked capitals or small caps"）。这条与我们的设计宪法方向完全一致：**大写加宽字距的"标签眉"是 AI 味的头号来源**。
- ⭐ **落地**：iOS 端首屏**不设独立大标题区**，靠**大标题（Large Title）由系统提供**；设备端用「小栈的脸」占据视觉主体，不放文字标题。

#### ② 大图头块叠信息
**结构**：`大图头块 → 目的地倒计时 + 按钮 → 白底天气块 → 日期块 → 温度曲线`
**视觉高级感的来源**：**同屏多层信息，但用"块"和"底色差"分层，而不是用线或卡片边框**。

**对我们的取舍**：
- ✅ **可抄（设备端强相关）**：**"倒计时"这个模块**。我们的语境不是行程，而是**陪伴的时间感** → 可迁移为「距上次见面」「今天我们聊了 12 分钟」这类**温和的时间锚点**。
- ⚠️ **需要克制**：**温度曲线 = 情绪随时间曲线**。这是"情绪可视化"，也是 KPI 面的边缘。我们目前的裁决是「不做 KPI 考核面」，所以：
  - ❌ 不做「连续 7 天亲密度曲线」
  - ✅ 可以做**单点的、当下的**状态表达（如"小栈现在心情不错"），不做趋势曲线
- ⭐ **落地**：**同屏多层信息 + 底色差分层**（而不是边框/卡片套卡片）→ 这与 hallmark Floor 第 11 条「card inside a card」互为正反面，可以直接写进我们的规范。

#### ③ 黑白两档主次 ⭐⭐ 本轮最重要的一条
**结构**：`浅灰打底 → 黑色主角块 → 白字 → 分类选中变黑 → 黑色横幅`
**视觉高级感的来源**：**只用两档明度建立层级，页面里几乎没有第三种颜色。**

**对我们的取舍**：
- ⭐⭐ **直接升级为设计宪法的显式表述**。我们此前的裁决是「iOS 端 = 系统语义色 + 唯一暖色强调」，但没说明"主次怎么建立"。抖音第 ③ 条给出了更本质的答案：
  > **主次靠明度两档建立，不靠色相多。**
  > 一个页面里如果同时出现「系统蓝 + 暖粉 + 青 + 紫」，即使每个色都达标，层级也会糊掉。
- ⭐ **落地（iOS 端）**：
  - 背景 = `Color(.systemGroupedBackground)`（浅）/ `Color(.systemBackground)`（深）
  - 主体内容 = `Color(.label)` / `Color(.secondaryLabel)`（**两档**）
  - 唯一暖色只出现在 **`.tint`** 一处（品牌强调）
  - 设备端保留深色底（脸要看清），青 `#00D2FF` **降级为状态色**，不再当品牌色
- ⚠️ **注意 Apple 文化差异**：HIG 明确「中文用红表示涨」（Stocks App），我们**不能把红当错误色**用 —— 这条已在 `10-AppleHIG官方核实` 记录，与本条的「两档明度」不冲突但要一起遵守。

#### ④ 大色块网格
**结构**：`亮黄大块数字 → 浅灰底 → 圆环完成度 → 超粗中英标题 → 四列小格`
**视觉高级感的来源**：**大面积高饱和色块 + 极端字号对比**（超粗标题 vs 超大数字）。

**对我们的取舍**：
- ❌ **不可抄**：`四列小格` = 功能宫格 = **我们的六宫格禁令**（`00-总纲` 宪法已禁）。`圆环完成度` = KPI 考核面 = **已禁**。
- ⭐ **但"大色块 + 极端字号对比"这个手法本身可抄**，用在**设备端 320×240**：
  - 设备端小屏上，"一个巨大的字/数字 + 一个色块"比"一行 12pt 小字"更能在 2 英寸屏上被看清
  - 例：设备端显示**电量档位**（大色块 3 档）或**情绪词**（一个字超粗）
- ⭐ **落地**：设备端「状态层」用**单色块 + 超大字**；iOS 端不用（iOS 上系统排版更合适）。

#### ⑤ 海报大字加半圆转盘
**结构**：`方块大字标题 → 半圆转盘 → 超大数字 + 黑色按钮 → 撞色底栏`
**视觉高级感的来源**：**半圆转盘**（半圆仪表盘）—— 非传统的控件形状自带"被精心设计过"的观感。

**对我们的取舍**：
- ⭐⭐ **强烈建议抄到设备端**。理由：
  - 设备端是 **320×240 触摸屏**，转盘/旋钮是**最自然的粗手势控件**（手指划过弧线，误触率低）
  - 转盘天然表达**档位/连续量**：亲密度、情绪强度、音量、亮度
  - 半圆转盘在小屏上的**信息密度远高于滑块**（转盘能同时显示刻度 + 当前值 + 可选范围）
  - ⭐ **与舵机天然同构**：小栈的 pitch/yaw 就是"旋钮"，转盘 = 舵机的手势映射，两者在心智上统一
- ⭐ **落地**：设备端新增「**半圆转盘**」控件原型（转盘 → 舵机角度 或 转盘 → 情绪档位），需用户确认后进设计稿。
- ⚠️ **iOS 端不用**：iOS 上系统 `Slider` 更符合原生感，刻度盘在 iOS 上显得"自作聪明"。

#### ⑥ 叠放堆栈
**结构**：`细长宽体字标题 → 分类 → 大图 → 堆栈 → 页码`
**视觉高级感的来源**：**卡片有轻微偏移地叠放**（层叠感）+ 页码给出"这是第几张"的秩序。

**对我们的取舍**：
- ✅ **可抄（设备端）**：**叠卡堆栈** = 第14集交互里的「叠卡展开」在静态形态上的体现。设备端"记忆/回顾"场景可用叠卡表示**一组同源的记忆**（比如"上周的 5 个片段"）。
- ⚠️ **iOS 端慎用**：Apple 原生风格是**平铺列表**，叠卡是刻意的"非原生"表达，与我们"iOS 端 = Apple 原生骨架"的裁决冲突。最多用在**空状态**或**回顾页顶部**做一次视觉锚点，不做主导航。

| 布局 | 设备端 320×240 | iOS 端 | 理由 |
|---|---|---|---|

## 三、评论区：最重要的一条反向意见

第 14 集（6 种精致交互）评论区出现的高赞反对意见，**比视频内容本身更值得抄进设计宪法**：

> 「实用性 app，交互效果越少越好」
> 「动画越多，一些手机不行的越卡，实用就好」

**这条与我们的产品判断高度吻合**，并且给出了我们此前没有的**第三种量化维度**：

此前我们的"陪伴型界面"判据是「单屏可点 0–4 个 + 留白 50–80%」（来自 `06-设计方法论`）。
现在可以加上**第三条**：

> ⭐ **动效预算**：单屏**同时运行的持续动效 ≤ 1 处**；一次性反馈动效 ≤ 2 处；总时长 ≤ 400 ms（与 `baseline-ui` 的 "NEVER exceed 200ms for interaction feedback" 同向但更宽松，因为我们的场景需要"被感知到"）。

**落地产出（待并入宪法）**：
- ❌ 禁「跳动波形」（已在 `00-总纲` 定案：不用文字标签、不用波形）
- ❌ 禁「多元素同时呼吸/发光」（霓虹辉光已在 AI 味清单里）
- ✅ 允许**唯一的持续动效** = 小栈的脸（它是 AI 的化身，动的应该是它，不是界面）
- ⚠️ 必须支持 `prefers-reduced-motion`（iOS 有 `accessibilityReduceMotion`）→ 见 §5.1 Floor 第 7 条

**其他评论区信号**（第 12 集）：
- 高频正向词：「看起来很高级」
- 高频索取：「可以付费求 AI 设计 UI 的 skill」「总结一下 ai 描述词发我」→ **说明这类"AI 描述词 + Skill"是有真实市场需求的，也印证我们收集情报的方向正确**
- 内容型请求：「请问有餐饮业的页面布局吗？」「下期能不能出一期悬浮球的方案」→ 说明**布局方案要按行业成体系**，不是通用模板

### 4.1 `Nutlope/hallmark` — 「反 AI 味」设计技能包 ⭐⭐ 本轮最高价值发现

**是什么**：Together AI 出品的 Claude Code / Codex / Cursor / OpenCode 设计技能包，MIT 许可，v2.0.0。
**一句话**：*"一个让编码助手生成的 UI 看起来像被设计过、而不是被生成出来的技能包。"*

**架构（实测自 `SKILL.md` + jsdelivr 文件清单）**：

├── references/
│   ├── gates.md                    Reflex / Finish 分级门禁  ← ⚠️ 本轮 main 分支取不到（见下）
│   ├── layout.md / anatomy.md / imagery.md / craft.md

**⭐ 核心机制：Floor / Reflex / Finish 三层门禁**

| 层 | 含义 | 能否豁免 |
|---|---|---|
| **Floor** | 硬底线：对比度、焦点、减动效、编造事实、手机布局崩坏 | **不可豁免**（"none of it waivable"） |
| **Reflex** | 模型默认会犯的毛病；**有理由可以书面豁免** | 可豁免，需记录理由 |
| **Finish** | 工艺细节检查 | 不阻塞发布 |

**Floor 16 条硬规则（原文逐条摘录，本轮实测取得）**：

| # | 规则 | 对我们的适用性 |
|---|---|---|
| 1 | 每个颜色和字体都必须走 `:root` 里声明的 token；token 块之外不得出现字面量颜色或 `font-family` | ✅ **完全适用** → SwiftUI：`Color`/`Font` 全部进 Design Token 枚举，禁止字面量 |
| 2 | 永不 `transition: all`；永不动画 `width`/`height`/`top`/`left` | ✅⭐ **完全适用且高价值** → SwiftUI：不改 `frame`，只动 `transform`/`opacity` |
| 3 | 永不在正体标题里放一个斜体词 | ✅ 适用（我们不做混排） |
| 4 | `html`/`body` 用 `overflow-x: clip`，不用 `hidden`、不用 `100vw` | 🟡 iOS 无横向滚动，但对应"不要用固定宽度撑出屏幕" |
| 5 | 带图的网格轨道用 `minmax(0, 1fr)`；大标题容器 `overflow-wrap: break-word; min-width: 0` | ✅ 适用（中文长词/长表情名不撑破布局） |
| 6 | 每个可交互元素都要有 `:focus-visible`，且立刻出现 | 🟡 iOS 无键盘，但 **Mac Catalyst / 外接键盘 / 灵动岛交互**需要 |
| 7 | 每个动画都要有 `prefers-reduced-motion: reduce` 兜底；关脚本时内容仍可见 | ⭐⭐ **完全适用且是重大发现** → iOS：`@Environment(\.accessibilityReduceMotion)` 必须支持；SwiftUI 动画都要有 reduce-motion 分支 |
| 8 | 永不编造指标、证言、logo 墙、案例数量 | ⭐⭐ **完全适用** → 陪伴产品最容易造假（假"亲密度 87"、假"已陪伴 128 天"）。**这正是我们要防的 AI 味** |
| 9 | 永不设眉标题（eyebrow）；标签/说明/表头/标签页/导航链接用正文字体或主题 label 字体，小一号，句式或小写，**不加字距** | ⭐⭐ **完全适用** → 直接命中抖音第 ① 条布局的「顶部宽体大写标题」 |
| 10 | 永不中点连接的元信息串、箭头贴链接文字、装饰性状态圆点 | ✅ 适用 → 设备端避免 `A · B · C` |
| 11 | 永不紫→蓝渐变、卡片套卡片、emoji 当图标、手绘浏览器/OS 窗口 | ⭐⭐ **完全适用** → "卡片套卡片" = 六宫格禁令；"emoji 当图标" = 不能拿 emoji 冒充小栈表情 |
| 12 | 首屏的主标题、一句话说明、主操作，在 1280×800 下**不滚动就全部可见** | 🟡 iOS 端等价："首屏不用滚就能看到脸和主操作" |
| 13 | 任何一屏约 80 词；首屏文字 = 标题 + 一句话 + 操作 | ⭐ **完全适用** → **iOS 端一屏 ≈ 80 字上限**（很好用的密度标尺） |
| 14 | 容器定宽居中；1920 时只加边距，度量与网格不变 | 🟡 弱适用 |
| 15 | CSS 第一行是 hallmark 印记，然后是评语行，然后是豁免行 | 🟡 可改造为我们的"设计稿存根"格式 |
| 16 | 有 Node 就跑 `sloplint.mjs --render`，修完所有 FAIL，FIX 或豁免每条 REFLEX | ✅ **方法论直接可用**（见下） |

**⭐⭐ 三个可直接搬走的"方法论"（比规则本身更值钱）**：

1. **"Hero first, review cold, then the rest."**
   > *"Write the nav and the hero, nothing below them yet, run sloplint --stage hero, then the hero review in fresh context. Build the sections once the hero ships."*
   → **对我们**：iOS 设计稿**先只出首页**（小栈的脸 + 一句话 + 一个主操作），**渲染出来冷评**（子代理盲审 / 新上下文评审），通过后再出其余页面。**这直接解决了我们"设计稿一次性铺 6 屏 → 全部平庸"的风险**。
   → 与我们已有的"子代理 verifier 独立审核"完全同构，Hallmark 把它做成了流程。

2. **"Mirror test" — 避免 AI 味的真正判据**
   > *"Would a neighbouring prompt in the same category get this exact combination? If yes, change one decision and say which."*
   → ⭐⭐ **这是本轮最深刻的一条**。**AI 味不是"用了 AI"，而是"换了参数也换不出独特性"**。检查方法：把我们的设计换成任何同品类产品（比如换成天气 App、记账 App），如果**只换文案不换决策**，那它就是 AI 味。
   → **我们的差异化决策是什么？** 答案应该只有一条：**"屏幕上唯一会动、唯一被注视的东西是小栈的脸；其他一切都是背景。"** 如果换成别的 App 这条不成立，说明设计还不够定制。

3. **"One idea per screen, set big." + "Fullness comes from scale and pictures, never from more words."**
   → 与我们已有宪法「每屏一动作」「不堆功能」同源，但 "set big"（把它做大）是我们缺的一半：**简约 ≠ 元素少，而是元素少且其中一个大**。

**其他可抄的机制**：
- **48 主题 = 材质（material）不是布局（plan）** → "同一个主题做两次会得到两个不同的页面"。设计系统的类比：**令牌与语汇固定，布局可派生**。
- **Genre 静默推断**：AI 工具/音乐/视频/暗色 → atmospheric；SaaS/API/开发者 → modern-minimal；趣味/游戏/家庭 → playful；**其余 → editorial**。
  → ⭐ **我们的产品落在哪？** 小栈 = 陪伴 + 宠物 + 家庭向 + 交互玩具 → **`playful` 与 `modern-minimal` 的混合**（外壳 modern-minimal，材质 playful）。这印证了我们"iOS 走 Apple 原生骨架 + 小栈的脸是唯一自绘"的方向。
- **"Show, do not describe"** → 页面要展示真东西，不描述它。→ **我们的 iOS 端要显示小栈的真实表情帧，不是画一个"小栈图标"**。
- **"Pictures take at most a third of the page below the hero, never two photograph-led sections in a row"** → 图片占比上限 + 禁止连续两个图主导区块。
- **照片库**：755 张 Wikimedia Commons 开放许可照片，**明确不用 Unsplash/Pexels/Pixabay（其条款禁止 AI 工具选图）** → ⭐ 这是一条**可直接落地的合规约束**：我们若用 AI 生成图片，不能用图库站的图；用官方表情 PNG 是零风险路径。

**❌ 不可抄 / 需改造的部分**：

| 部件 | 为什么不能直接用 | 我们的改造 |
|---|---|---|
| Floor 的 CSS 语法判定 | 我们的 iOS 是 SwiftUI + 设备端是 LVGL/C++，**不是 CSS** | 转成**平台无关的判据**，用我们自己的 `design-floor` 文档 + 检查脚本承载 |
| `sloplint.mjs`（Node + Puppeteer） | 它渲染 HTML 检查 DOM；我们若用 HTML/CSS 做设计稿（已定 B 路线），**可以复用它检查 HTML 稿** | ⭐ **保留 `sloplint` 检查我们的 HTML 设计稿**；SwiftUI 端另写规则检查（颜色字面量、动画属性、Reduce Motion 覆盖） |
| 48 主题 | 是**网页**主题（字体/材质/配色），不是 iOS 主题 | 只借鉴"主题=材质"这个**概念** |
| 21 种 macrostructure | 是**网页页面骨架**（hero/bento/manifesto/letter…） | ⭐ **可借鉴 3–4 个**：`05-workbench`（工作台）、`06-conversational-faq`（对话式）、`07-manifesto`（宣言式）、`14-narrative-workflow`（叙事流）→ 映射到"陪伴型 App 的 4 种骨架"，但**结论仍以我们的 IA 定案为准（Tab 只 2 个）** |

**⭐ `baseline-ui` 的可转译条款（去 Tailwind 后仍然成立的判断）**：

| 原条款 | SwiftUI 对应 |
|---|---|
| MUST use accessible component primitives（Base UI / React Aria / Radix）；键盘/焦点行为不手搓 | ⭐ iOS 用系统原生控件（`Button`/`Slider`/`Toggle`）即自动满足；**不要自绘可交互控件** |
| MUST add `aria-label` to icon-only buttons | → `accessibilityLabel`（设备端无障碍暂时不适用） |
| NEVER use `h-screen`, use `h-dvh` | → iOS 无此问题；但**设备端必须按 320×240 实际尺寸设计，不按逻辑像素外推** |
| MUST respect `safe-area-inset` for fixed elements | ⭐⭐ **完全适用** → iOS `safeAreaInset` / `.safeAreaPadding`；**灵动岛与底部 Home 指示条必须避让**（上一轮 `YYC.html` 已用 `env(safe-area-inset)`） |
| MUST show errors next to where the action happens | ⭐ 适用（错误就地提示，不弹 toast） |
| MUST use `AlertDialog` for destructive actions | ⭐ iOS 用 `confirmationDialog`；设备端无破坏性操作 |
| MUST use structural skeletons for loading states | ⭐ 适用（骨架屏，不是转圈菊花） |
| NEVER block paste in `input`/`textarea` | 🟡 弱 |
| MUST use `text-balance` for headings / `text-pretty` for body | ⭐ **完全适用且很实用** → SwiftUI `.multilineTextAlignment` 不够，需用 `AttributedString` + 自定义断行算法；中文场景尤其需要（**中文没有词边界，标题断行比英文难**） |
| MUST use `tabular-nums` for data | ⭐ 适用 → SwiftUI `.monospacedDigit()` |
| MUST give empty states one clear next action | ⭐⭐ **完全适用** → 空状态只给**一个**动作（我们的宪法已有） |
| SHOULD limit accent color usage to one per view | ⭐⭐ **完全适用** → 印证"唯一暖色强调" |
| SHOULD use theme color tokens before introducing new ones | ⭐⭐ 完全适用 → 印证"系统语义色优先" |
| NEVER use gradients unless explicitly requested | ⭐ 适用 → 我们已禁装饰渐变球 |
| NEVER use purple or multicolor gradients | ⭐ 适用 |
| NEVER use glow effects as primary affordances | ⭐⭐ **完全适用** → **glow-fi 光晕是 AI 味四大元凶之一**（`06-设计方法论` 已量化：18 张图里 4 张叠霓虹辉光） |
| MUST use a fixed `z-index` scale | ⭐ 适用 → SwiftUI `.zIndex` 定级表 |
| SHOULD use `size-*` for square elements | 🟡 弱 |

**⭐⭐ `fixing-motion-performance` 的 9 类规则（完全适用，是本轮最实用的动效规范）**：

先确立**渲染成本分级**（这三个词就是我们后续讨论动效时的通用语言）：

```
composite（合成层）: transform, opacity              ← 最便宜
paint（绘制层）   : color, borders, gradients, masks, images, filters
layout（布局层）  : size, position, flow, grid, flex   ← 最贵
```

| 优先级 | 类别 | 规则 | 对我们的落地 |
|---|---|---|---|
| 1 | never patterns | 不要在同一帧里交错读布局与写布局 | 设备端 LVGL 同理：**不要在动画里反复 `get_` 尺寸** |
| 1 | never patterns | 不要在大面积/有意义的表面上持续动画布局属性 | ⭐ 设备端 320×240 小屏上，**改 width/height 会触发整屏重绘**，比 iOS 贵得多 |
| 1 | never patterns | 不要用 `scrollTop`/`scrollY`/scroll 事件驱动动画 | iOS → 用 `ScrollView` 的 `scrollTargetBehavior` / `visualEffect` / `onScrollGeometryChange`（iOS 18+），不用监听 offset |
| 1 | never patterns | 没有停止条件的 rAF 循环禁止 | ⭐ 设备端：舵机/呼吸动画必须有停止条件，不能是死循环 |
| 2 | mechanism | 默认 transform + opacity；只有交互需要才用 JS 驱动 | ⭐ 与 hallmark Floor 第 2 条同源，互为印证 |
| 2 | mechanism | 一次性效果比持续动效更可接受；**优先降级技术而非删掉动效** | ⭐⭐ 这句话很关键：**不要"为了性能砍掉质感"，要"换个更便宜的技术实现质感"** |
| 3 | measurement | 量一次，然后用 transform/opacity 动；DOM 读批量在写之前 | iOS → 避免在 `body` 里反复读 `layoutRect` |
| 4 | scroll | 用 Scroll/View Timeline 做滚动联动；用 IntersectionObserver 管可见性与暂停 | iOS → `ScrollView` + `LazyVStack` + `.onAppear/.onDisappear` 暂停动画 |
| 5 | paint | 绘制触发型动画只允许在小而孤立元素上 | ⭐ 设备端：**只有小栈的脸（320×240 里的一块）可以做绘制型动画** |
| 5 | paint | 不要动画 CSS 变量来做 transform/opacity/position | 设备端同理：**不要动画一个"全局透明度变量"** |
| 6 | layers | 合成层动画需要层提升，不能假设 | ⭐ 设备端 LVGL：双缓冲代价高，**尽量单缓冲 + 只重绘变化区域** |
| 7 | blur | blur 动画幅度 ≤8px；只做短时一次性效果；不在大面积上持续模糊 | ⭐⭐ **iOS 直接对应**：`.ultraThinMaterial` 不能持续动；HIG 也要求玻璃不滥用 |
| 8 | view transitions | 只用于导航级切换；交互密集界面不用 | ⭐ iOS → `matchedTransitionSource` 只用于跨页元素 |

**⭐ 这 9 类规则解决了我们一个一直没解决的设备端问题**：
设备端 320×240 用 ESP32-S3 + LVGL，**性能预算比 iOS 紧一个数量级**。以前我们只有"设备端少做动画"这种模糊纪律，现在有了**按渲染成本分级的判据**：
> 设备端动效默认只允许 **composite 级**（移动一个已有的位图 / 改一个已有矩形的位置）；
> paint 级（重绘像素）**仅限小栈的脸这块区域**；
> layout 级（改尺寸触发重排）**原则上禁止**，必须用两个预渲染位图切换替代。

| `cangjie-skill` | ⏸ 待评估 | 本轮未取原文 |

**为什么不整体安装 Hallmark**（避免踩坑）：
1. 它的 Floor / 门禁是**围绕 HTML/CSS 的**，我们的交付物是 **SwiftUI + LVGL**；装进来大部分规则会以"不适用"的形式稀释注意力。
2. 它会与已有的 `user-defaults`、`superpowers:*`、本项目 `AGENTS.md` 规则**叠加**，产生"多个技能同时要求先提问/先加载文件"的冲突成本。
3. 它的 `theme.mjs deal` 是**随机发牌**机制 —— 对"每次生成不同页面"有效，对**一个需要高度统一的定制产品**反而有害（我们要的是一致性，不是多样性）。
4. ⭐ **它的价值恰好在"规则"而非"引擎"** → 所以正确姿势是：**把 Floor 抄成我们自己的规范，而不是把技能装进工作流。**

## 七、一句话总结

> 抖音这 6 集真正给我们的不是"布局模板"，而是**一个反例集**：它们演示的 6 种布局里有 4 种（眉标题 / 宫格 / 完成度圆环 / 趋势曲线）正是我们宪法要禁的东西。
> 而 `hallmark` 的 Floor 第 9、11 条**逐字命中**了这 4 种里的 3 种 —— 说明我们的禁令**不是拍脑袋**，行业里确实有人在用同一套判据对抗 AI 味。
> **最有价值的产出不是新样式，是新判据**：Mirror test（一屏一个决策）、Floor 16 条、渲染成本 9 级 —— 这三样能把"看起来高级"变成**可复现、可检查、可否决**的东西。
