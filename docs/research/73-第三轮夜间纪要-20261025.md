## 二、缺陷 1 详记：CSS 自定义属性的「静默失败模式」

### 2.1 怎么发现的

给 4 套方案**出图**（Playwright 点切换器按钮后截真图）时，肉眼看到深色方案那张图的
**Tab Bar 选中项「陪伴」几乎看不见**。

### 2.2 定位过程（不猜，逐层测）

| 步骤 | 手段 | 结果 |
|---|---|---|
| 1 | 看深色截图 | 选中项文字是黑的，底也是黑的 |
| 2 | Playwright 量计算样式 | `--label` = `#ECECEE`（**正确**），但 `.tab-label` 的 `color` = `rgb(0,0,0)` |
| 3 | 对照另一处用同一变量的元素 | `.nav-title` 用 `var(--label)` ⇒ **正常显示白色** ⇒ 变量本身没问题 |
| 4 | 查 CSSOM 里命中的规则 | `.tab-item[aria-selected="true"]{color:var(--tint)}` —— **命中的是这条** |
| 5 | 查 `--tint` 到底定义没有 | `grep --tint`：**被引用 8 次，定义 0 次** |

⇒ 根因确定：**`--tint` 未定义 ⇒ `color:var(--tint)` 在计算值阶段非法 ⇒ 该属性退回继承值**。

### 2.3 为什么它能溜过去（这是最值得记的部分）

| 原因 | 说明 |
|---|---|
| **浏览器不报错** | CSS 规范规定：自定义属性未定义 ⇒ 该声明作废 ⇒ 属性取**继承值**或初始值。**没有 console 警告** |
| **DOM 里看不出来** | `getAttribute('style')` 是空的；只有 `getComputedStyle` 才看得到 |
| **浅色方案下「不显眼」** | 黑字在浅底上看着正常，只是「不像设计稿」⇒ 肉眼判读容易放过 |
| **深色方案才致命** | 深底黑字 = 不可读 |
| **原有的对比度门禁看不见它** | `tools/check_contrast.py` 只读 `prototype/variants/`，**根本没看 iOS 原型**；而且它做的是「两个**有值**的变量之间的比值」，压根不关心「被引用的变量有没有定义」 |

### 2.4 修法（不新造一套命名）

| 旧 | 新 | 理由 |
|---|---|---|
| `--tint`（未定义） | `--accent` | Swift `Tokens.swift` 的 token 就叫 `accent`；`prototype/variants/` 也用 `--accent` |
| 方案块里的 `--bubble-out` | `--accent` | 每个方案只声明**一对**强调色 token |
| 方案块里的 `--bubble-out-text` | `--on-accent` | 同上 |
| `:root` 的 `--bubble-out:var(--tint)` | `--bubble-out:var(--accent)` | 冒泡色由强调色派生 ⇒ 不会再漂移 |

改动文件：`prototype/ios/ios-light.html`、`prototype/ios/ios-dark.html`
（`--bubble-out` / `--bubble-out-text` / `--label` / `--tint` 相关的 6 处引用 + 4 个方案块 + `:root`）。

### 2.5 验证（不是「看截图觉得对了」）

- 4 套方案 × 2 轮复测 `.tab-item` 的计算色：

| 方案 | `--label` | 修复前 `itemColor` | 修复后 `itemColor` | 应为 |
|---|---|---|---|---|
| paper-terracotta | `#241F1B` | `rgb(0,0,0)` | **`rgb(175,76,55)`** | `#AF4C37` ✓ |
| pure-white-blank | `#1D1D1F` | `rgb(0,0,0)` | **`rgb(183,67,50)`** | `#B74332` ✓ |
| warm-paper-serif | `#2A231C` | `rgb(0,0,0)` | **`rgb(158,59,38)`** | `#9E3B26` ✓ |
| tuck-dark-calm | `#ECECEE` | `rgb(0,0,0)` | **`rgb(227,168,87)`** | `#E3A857` ✓ |

- 出图复看：深色方案下「陪伴」标签与图标已是琥珀色，清晰可读。

### 2.6 顺带查出的第二处：`--on-accent` 漂移

`prototype/variants/01-paper-terracotta.html` 的 `--on-accent:#FFF8F4`，
而 Swift `Tokens.swift` 与 iOS 原型都是 `#FFFFFF` ⇒ **三处不一致**。
已把 variants 改成 `#FFFFFF`（视觉差不可察，但三方必须一致）。

### 3.1 `tools/check_ci.py`（CI 自身的体检）

| 检查码 | 判什么 |
|---|---|
| CI-01 | YAML 可解析 |
| CI-02 | `run:` 里 `python <path>` 指向的脚本必须存在 |

| CI-09 | 同一 workflow 内 `python-version` 必须唯一 |
| CI-10 | 每个 job 必须声明 `runs-on` |

> CI-07 必须扫**原始文本** —— 「本地复现：」是 YAML 注释，PyYAML 会把注释丢掉。
> CI-05 的路径字符类要用 `\w`（Unicode）才能覆盖本仓大量的中文文件名。

### 3.2 `tools/check_css_vars.py`（原型 CSS 变量体检）

| 检查码 | 判什么 |
|---|---|
| CSV-01 | **被引用但从未定义**的 CSS 变量 → FAIL |
| CSV-02 | 4 套方案的 token **集合不一致** → FAIL |

自检 **4/4**（坏夹具：未定义变量 / 方案 token 不一致 / 健康文件零 FAIL / `@property` 注册过的变量不算未定义）。

### 3.3 `fetch_literature.py --merge / --check`

- `--merge`：把多份留痕**反向解析**回结构，合并去重后重新渲染（**无损**：同一 arXiv ID 跨文件出现时按字段择优合并，与 `dedupe()` 同一套规则）。
- `--check`：重算并集 vs 已落盘文件，判**条目集合**是否一致（不能逐字节 —— 落盘文件头部带「取证时间」，重算必然不同）。少一条 = 有人删了证据；多一条 = 并集没重算。
- 负向实测：拿只含 3 主题的 69 号当「已落盘文件」⇒ 报出 **7 个主题不一致**并 exit 1。

## 六、README 首页那张脸是真的（`tools/make_readme_hero.py`）

新增工具：生成 README 首页用的「小栈的脸」**真实动图**（GIF）+ 静帧。

```
真实 MiniMax TTS → 韵律提取(7 维) → 42 参数 → 0x14 关键帧 → 固件几何 → 320×240 像素
```

实测：`female-shaonv` / 2.473 s ⇒ **62 关键帧** ⇒ 渲染 60 帧 ⇒ GIF 回读 **45 帧 / 总时长 2400 ms**
（PIL 会合并相邻相同帧 —— 脸不会每 40 ms 都变 ⇒ **总时长不变，这是对的**）。
产物 20 KB（纯黑白 ⇒ GIF 压得极好）。

### 关键决定：几何**复用**而不是**复制**

工具直接 `import tools/check_face_geometry.py` 的固件复刻函数
（`fw_eye_diameter` / `fw_eyelid_offset` / `fw_mouth_size` / `fw_position_offset` …），
**不另写一份** —— 那份已经过「同口径校验」（逐条对过 `map_range`、C++ 整数除法、眼睑极性），
复制一份就等于多一个可能漂移的副本。

### 自检 14/14 里最关键的三条

| 断言 | 为什么必须有 |
|---|---|
| 眼睑极性：weight=0 偏移 0（全闭）/ weight=100 偏移 -眼径（全睁） | 这条最容易搞反；搞反了整张脸就是「睁眼变闭眼」 |
| 相邻帧有变化（不是静止图） | 防「产物存在但内容是死的」 |
| GIF 写出后**回读帧数**一致 | 防「文件生成了但打不开/帧不对」 |

实测抽帧确认：weight=0 → 全闭（眼白被眼睑全盖）、50 → 半睁（下方留白）、
100 → 全睁（完整圆）⇒ **极性正确**。

## 七、DeepSeek 派单：**两次都失败**，这一轮不再重派

| 轮次 | 派单 | 结果 |
|---|---|---|
| night4 | 4 任务（readme-hero / security-audit / face-review / audio-transport），`-MaxParallel 2 -Fanout 2` | **全部被掐断**：后台 bash 撞上 **1 小时上限**（`maxRunMs=3600000`），4 份 `report.md` 全是 537~835 B 的骨架 |

### 根因（不是模型不行，是通道不行）

- 中转站 `zean2.bbroot.com` **RPM ≈ 15/分钟**，而且**本机同时有 3 个别的会话在派 DeepSeek**

- `retryPolicy=always` ⇒ 429 表现为「变慢」而不是「失败」⇒ 表现为**超时**而非报错。

### 结论与教训（比派单本身更重要）

1. **DeepSeek 的 `report.md` 可能是骨架，scratch 工作区才是本体** —— 上一轮已踩过，这轮再踩一次。
2. **任务书里写「开工第一件事就建 report.md 并持续更新」不够** —— 它确实建了、也确实每步都写了，
   但**被掐断时留下的仍是占位稿** ⇒ 必须有「**结论段落**」先落地，而不是先落地骨架。
3. **长研究任务在当前通道下不可靠** ⇒ 夜间自主推进**不应把关键交付押在 DeepSeek 上**。
   这一轮的全部实质产出（CSS 变量门禁、CI 体检、文献并集、hero 动图、4 套方案出图）
   都是**我自己做的**，没有一件依赖 DeepSeek。

⇒ **本轮决定不再重派 DeepSeek**。Q10 的方案 A 规格本就在 `docs/spec/07` §3.6.1，
