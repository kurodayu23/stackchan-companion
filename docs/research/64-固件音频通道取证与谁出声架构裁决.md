# 64 · 固件音频通道取证与「谁出声」架构裁决

> 建立日期：2026-10-25（夜间）
> 起因：夜间任务清单里有一项「音频下发通道（0x18 + Opus）—— 设备现在不会出声」。
> 本轮逐行核对固件源码后**发现这个任务的前提是错的** ⇒ 本文档是取证与订正。
> 取证方式：只读官方固件 git 仓库 `D:\jss18\AI\StackChan\StackChan2`
> （1.5.1 = `94856a7^`，1.6.0 = `origin/main` = `eff0d6b`），**未做任何修改、未刷机**。

---

## 一、结论先行

1. ⛔ **官方固件没有「服务器 → 设备」的音频通道。** `0x01`(Opus) / `0x18` / `0x19`
   在设备侧**全部是空实现**，Opus 解码代码**整段被注释掉**，
   而且它引用的 `AudioStreamPacket` / `_audio_service` **在整个固件树里根本不存在**。
2. ⭐ **官方的声音是在手机上放的。** 官方 iOS App 用 `AVAudioEngine` + `AVAudioPlayerNode`
   自己解码并播放（16 kHz 单声道）。**设备在音频链路里根本不出声** —— 它只做身体（表情 + 动作）。
3. ⇒ **裁决：手机出声，设备做身体。**
   这是「官方固件零改动、只读不 fork」前提下**唯一可落地**的路径，
   而且**与官方 App 的实际行为一致**，不是我们的独创妥协。
4. ⇒ 连带结论：**我们不需要 Opus 编码器，也不需要 Opus 解码器。**
   官方用 Opus 是因为要传**麦克风实时流**（带宽敏感）；
   我们的 TTS 是**一次性、非实时**的 ⇒ 直接用 PCM 更简单、零依赖。
5. ⇒ 之前的任务项「0x18 + Opus 音频下发通道」**作废**，
   换成「**iOS 端 PCM 流式播放 + 与 0x14 动作时间轴对齐**」。

## 三、裁决

### 3.1 架构：手机出声，设备做身体

```
┌────────────┐   ① 文本        ┌──────────────┐   ② 回复文本 + 关键帧   ┌──────────┐
│  iOS App   │ ──────────────► │  云端服务端   │ ────────────────────► │  设备     │
│ (用户界面) │                 │ (LLM/TTS/韵律) │                        │ (身体)   │
│            │ ◄───────────── │                │                        │          │
│ ② PCM 音频 │   ③ PCM 音频流  │                │                        │          │
│ ④ 0x14 帧  │ ──────────────────────────────────────────► 0x14 动作+表情  │          │
└────────────┘                                             ⑤ 嘴部跟着动    └──────────┘
```

- **声音**：云端把 TTS 的 PCM 分片推给 App，App 用 `AVAudioEngine` 播。
- **身体**：同一段 PCM 推出的 0x14 关键帧给设备，**嘴部动作与声音同源**。
- **对齐保证**：关键帧与音频来自同一段 PCM ⇒ 时间轴同源；
  关键帧量化到 25 fps 栅格（`durationMs = 40`）⇒ 误差 **≤ 一帧 = 40 ms**。

### 3.2 已落地的机器校验

`tools/demo_offline.py` 已新增 **4 项音画对齐断言**（自检从 27 项增加到 **31 项，全绿**）：

| 断言 | 含义 |
|---|---|
| 音画对齐误差 ≤ 1 帧（40 ms） | 关键帧总时长 − 音频时长 的绝对值 ≤ `OUT_DT_MS` |
| 关键帧总时长 = 帧数 × `durationMs` | 时间轴是算出来的，不是写死的 |
| 加长文本后误差仍在 1 帧内 | 时长随输入解析变化，不是常数 |
| 加长文本后总时长确实变长 | 同上（反向验证） |

实测（离线替身语音，"今天真开心啊！"）：音频 **1.81 s** vs 关键帧 **1840 ms（1.84 s）** ⇒ 误差 **+30 ms**，在一帧内。

### 3.3 不需要 Opus（省掉的复杂度）

| | 官方为什么用 Opus | 我们为什么不需要 |
|---|---|---|
| 场景 | **麦克风实时流**（每 20 ms 一帧，8 字节状态头 + 载荷） | **TTS 一次性音频**（非实时） |
| 带宽 | 实时、连续、必须压 | 一次性、可整段传 |
| 代价 | 要编解码器（官方用 Flutter 插件） | **0**：TTS 直接给 PCM，iOS 直接播 PCM |

⇒ 我们的 iOS 端不需要引入任何 Opus 库，也不需要服务器侧编码器。
（官方 App 的 `opus_codec` 是 Flutter 插件；我们写原生 Swift，**不引入第三方 Opus 依赖**。）

### 4.1 三种承载方式（**待拍板**，DeepSeek 风险评估也会独立给一份）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. WS 二进制分片** | App↔云继续走现有 WS 帧 `[Type(1)][Length(4)][Payload]`，新增一个**自研扩展类型**承载 PCM 分片 | 一条连接、实时、与现有协议同构 | 要新增消息类型；远端单帧 256 KB 上限 ⇒ PCM 16 kHz/16-bit = 32 KB/s ⇒ **必须分片**（如 100 ms/片 = 3.2 KB） |
| **B. HTTP 拉取** | 云端把整段音频落到临时 URL，App 用 `URLSession.download` 取回再播 | 实现最简单；不受 WS 帧上限约束 | 多一次往返；起播延迟大；**弱网体验差**；且需要云端有 HTTP 静态服务（我们的替身服务端有 HTTP，但生产要另配） |
| **C. App 自己请求 TTS** | App 直接调 MiniMax TTS 拿音频（**密钥不能进 App** ⇒ 不可行） | —— | ⛔ **不可行**：API Key 不能进客户端 |

⭐ **推荐 A**：
理由：① 保持「App↔云 一条 WS 连接」的架构一致性；② 现有帧编解码器（`server/stackchan_ai/protocol.py`
与 `ios/.../CoreProtocol`）可直接复用，只需**加一个类型 + 一个分片协议**；
③ 分片粒度可以做到 20~160 ms，**起播延迟可控**（⭐ 2026-10-25 07:00 订正：具体规格后来取 **160 ms = 4 帧 = 5120 B**，对齐关键帧分组边界 ⇒ 见 `docs/spec/07` §3.6.1）；④ 弱网时能边收边播（体验优于 B）。

⚠️ 扩展类型编号的取舍：
用 **0x01(Opus) 但改载荷语义**会破坏「与官方 MsgType 完全对齐」这个卖点 ⇒ **不推荐**；
建议新增 **`0x1C`**（设备侧 `isKnownType` 不认，**永远不会误发给设备**），
并在 `docs/spec/03` §2.2 明确标注「0x1C = App↔云私有扩展，设备侧不使用」。
⚠️ 这条会改动 `docs/spec/03` 的 25 项消息类型表 ⇒ **等用户拍板后再动**。
