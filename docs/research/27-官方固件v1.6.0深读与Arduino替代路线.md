#### 改了什么（v1.5.1 → v1.6.0）

v1.6.0 把这个文件从「单通道云 WS」改成 **「云 WS + 局域网 WS」双通道架构**，重写幅度远超 369 行：

1. **通道抽象**：新增 `enum class Channel : uint8_t { Remote, Local }`（`hal_ws_avatar.cpp:74-77`），`ReceivedMessage` 增加 `channel` + `generation` 两个字段（`:79-84`）。
2. **远端连接搬进独立 FreeRTOS 任务**：新增 `startRemoteTask()`（`:495-522`），任务名 `avatar_remote`，栈 8192，优先级 2，每 250 ms 一轮；未连上时每 **5000 ms** 重试一次（`:505-510`）。v1.5.1 是在主 worker 的 `update()` 里同步 `connect()`（diff 段 `- if (millis() - _last_reconnect_attempt > 5000) connect();`），v1.6.0 后者**不再阻塞主循环**。
3. **自研 WS 客户端**：从 `network->CreateWebSocket(1)`（v1.5.1）换成 `local_network::AvatarSocket`（`:131`），带 bounded TCP + 发送超时 + 32 KB 分片（见 §1.3）。
4. **generation 机制**：每次重连 `++_remote_generation`（`:132`）；所有回调先校验 `generation != _remote_generation` 就丢弃（`:136`、`:142`、`:146`）；出队时二次校验（`:194-196`）。旧连接的迟到消息不会污染新会话。
5. **队列限流**：`enqueueMessage()` 限制 **最多 16 条 / 合计 256 KB**（`:486-493`），防媒体帧把堆吃光。
6. **新增两种 MsgType**：`AimedTakePhoto = 0x1A`、`AppLanAddress = 0x1B`（`:70-71`）。
7. **心跳语义修正**：`handleMessage()` 每次收到任何消息就刷新 `_last_heartbeat_time`（`:205`），且只有 **Remote 通道**的 HeartbeatPing 才刷新（`:289-291`）——LAN 忙不再被误判成云端超时。
8. **双通道发送**：`sendPacket(channel, type, ...)`（`:563-571`）显式指定通道；`sendPacket(type, ...)`（`:573-578`）**优先 LAN，失败回落云端**。
9. **JPEG 质量自适应**：按 20 → 10 → 5 逐级降质，保证 LAN 帧不超过 `MaxPayloadSize`（`:445-455`）。
10. **端点公告机制**：`applyAnnouncedEndpoint()`（`:399-410`）——App 通过云通道把自己的局域网 WS 端点广播给设备，设备收到后立刻连。
11. **呼叫通道跟踪**：新增 `_call_channel`（`:478`），`AcceptCall`/`DeclineCall`/`EndCall` 回发到呼叫发生的那条通道（`:97-122`）。
12. **Opus 接收分支被注释掉**（`:212-220`），注释写 "Opus handled in OnData Fast Path"，但 `OnData` 里**没有** fast path 逻辑了 —— 见下方「音频」小节。

#### WS 连接 / 断开 / 重连 / 心跳完整流程

**连接（远端 / 云）**

- `init()`（`:86-125`）构造 URL：`fmt::format("{}/stackChan/ws?deviceType=StackChan", secret_logic::get_server_url())`（`:88`）——**固定 `deviceType=StackChan`**，query 参数只有这一个。
- 远端任务循环（`:504-512`）：`!_remote_connected && (first_attempt || now - last_attempt >= 5000)` → `connect()`。
- `connect()`（`:127-163`）逐字流程：
  1. `const auto token = secret_logic::generate_auth_token();`（`:129`）——鉴权 token 由本机生成。
  2. `auto socket = std::make_shared<local_network::AvatarSocket>(*Board::GetInstance().GetNetwork(), 1);`（`:131`）——连接 id = **1**。
  3. `socket->SetHeader("Authorization", token.c_str());`（`:134`）——**鉴权走 HTTP 头 `Authorization`，不是 query**。
  4. 注册 `OnConnected` / `OnDisconnected` / `OnData` 三个回调（`:135-148`）。
  5. 在 `_remote_mutex` 下把旧 socket 换出并 `old.reset()`（`:149-155`）。
  6. `socket->Connect(_url.c_str())`（`:156`）；**失败只打日志**，不 emit `onWsLog`，不阻塞，5 秒后重试（`:156-158`）。
  7. 成功后**立刻发一条文本帧**：`{"type":"hello", "msg":"Hello from StackChan!"}`（`:161`）。
- 注意：`connect()` 里**没有** `OnConnected` 回调之外的心跳发送——**心跳是服务端发 ping、设备回 pong**，设备不主动发起。

**断开**

- `OnDisconnected`（`:141-144`）→ `_remote_connected = false`（仅当 generation 仍匹配）。
- `sendRemotePacket()` 发送失败也会强制 `_remote_connected = false`（`:558-560`），下次 update 即触发重连。

**心跳**

- 收到 `HeartbeatPing (0x10)` → 回 `HeartbeatPong (0x11)`（`:287-294`）。
- `update()`（`:171-174`）：`_remote_connected && millis() - _last_heartbeat_time > 10000` → `GetHAL().onWsLog.emit(CommonLogLevel::Error, "Heartbeat Timeout")`，并**把时间戳重置**。
- ⚠️ **重要**：心跳超时**只打日志，不主动断开**，`_remote_connected` 仍为 true，不会触发重连。真正掉线靠 TCP 层 `OnDisconnected`。这是官方实现里的一个弱点，**我们 fork 时应改成超时即断开并重连**。
- `HeartbeatPong (0x11)` 在 switch 里**没有分支**（落到 `default: break;`，`:389-390`），即设备收到 pong 什么都不做。

#### `controlMotion (0x04)` 走哪条通道 + 报文格式

**通道**：**云端和局域网都走**。远端帧直接进 `handleMessage()`；LAN 帧先被 `decodeToRemoteFrame()` 解包成 `[type:1][length:4][payload]`（`local_network_protocol.h:85-88`），再进同一个 `handleMessage()` → 同一个 `ControlMotion` 分支。**设备端没有"只支持某一条通道"的逻辑。**

**远端（云 WS）报文格式**——`sendRemotePacket()`（`:549-561`）：

```
[ Type : 1 byte ][ Length : 4 bytes, Big-Endian ][ Payload : Length bytes ]
```

- `packet[0] = type`（`:555`）
- `local_network::writeBigEndian(packet.data() + 1, len, 4)`（`:556`）——长度 **4 字节大端**
- payload 拷到 offset 5（`:557`）
- 整体以 **WebSocket 二进制帧**发出（`socket->SendBinary`，`:558`）

⚠️ **长度是 4 字节，不是 LAN 的 2 字节**。两条通道的帧头长度不同，这是最容易踩的坑。

**LAN 报文格式**——见 §1.2。

**接收端是死的。** `DataType::Opus` 的 case 被整段注释（`:212-220`），注释说 "Opus handled in OnData Fast Path"，但 `OnData`（`:145-148`）只是把原始字节塞进队列，**没有任何 fast path**。全仓库 grep `Opus` / `AudioStreamPacket` / `PushPacketToDecodeQueue` 只命中 `hal_ws_avatar.cpp` 里的这 5 行（全是注释）+ 两行枚举/二进制资产误匹配。
→ **结论：v1.6.0 固件收不到云端下发的语音。**

**发送端：WS 通道没有音频上行。** `sendPacket()` 的所有调用点只有 JPEG、呼叫类、GetDeviceName 三类（`:104`、`:107`、`:121`、`:283`、`:451`），**没有任何音频发送路径**。
→ 语音上行/下行走的是**小智 SDK 那条独立通道**（见 §1.7），不是这个 WS。

**分片/缓冲逻辑**：设备→App 的 LAN 帧，`MaxPayloadSize = UINT16_MAX`（`local_network_protocol.h:18`），所以载荷最大 65535 字节；`encode()` 拒绝超限（`:53`）。JPEG 发送前用 20→10→5 三档质量自适应压到上限内（`:445-455`）。**没有音频分片/重组代码**——因为音频不走这条通道。

**我们要不要保留 Opus 分支？**
→ **不保留，直接删**。我们要接 MiniMax，TTS 音频流必须由我们自己的通道（服务器→设备）承载，格式我们自己定（建议 PCM/Opus 单包定长），不跟官方 WS 通道混。官方这个分支是死代码，留着只会误导。

### 1.2 `firmware/main/hal/utils/local_network/local_network_protocol.h`（新增 314 行，全文已读）

#### 完整帧格式（20 字节头 + 载荷）

`encode()`（`:50-64`）逐字节构造，帧长 = `HeaderSize(20) + len`：

| 偏移 | 长度 | 含义 | 取值 / 编码 | 佐证 |
|---|---|---|---|---|
| 0 | 1 | **Magic 高字节** | 固定 `0x53`（ASCII `'S'`） | `:55` |
| 1 | 1 | **Magic 低字节** | 固定 `0x43`（ASCII `'C'`） | `:56` |
| 2 | 1 | **Version** | 固定 `1` | `:57` |
| 3 | 1 | **Type** | MsgType（见 §1.1 全表） | `:58` |
| 4 | 2 | **保留 / 标志** | `frame.assign(..., 0)` 后**从不写入** → 恒为 0 | `:54`（全零初始化） |
| 6 | 8 | **Session** | uint64 **Big-Endian**，设备侧 = `(esp_random() & 0x7fffffff) << 32 \| esp_random()` | `:59`；生成处 `local_avatar_client.cpp:202` |
| 14 | 4 | **Sequence** | uint32 **Big-Endian**，每次发送 `++_sequence`（从 1 开始） | `:60`；`local_avatar_client.cpp:203, 247` |
| 18 | 2 | **Length** | uint16 **Big-Endian**，载荷长度 | `:61` |
| 20 | len | **Payload** | 见下 | `:62` |

**没有校验和 / CRC / magic 之外的任何完整性校验。** `decodeToRemoteFrame()` 的校验只有 4 项（`:71-75`）：
1. `len >= HeaderSize`
2. `data[0]==0x53 && data[1]==0x43 && data[2]==1`
3. `isKnownType(data[3])`（`:39-43`：`0x01-0x07`、`0x09-0x0E`、`0x10-0x1B`）
4. `payload_size == len - HeaderSize`（`payload_size` 由 `data[18]<<8 | data[19]` 算出，`:74`）

**坑**：长度字段虽然存在，但**接收端不信任它做分片重组**——它只用来校验「声明长度 == 实际剩余字节」。真正的 TCP 流边界由 WebSocket 帧边界提供。

#### `hasTargetPrefix` 的语义

`hasTargetPrefix(type)`（`:45-48`）：`type ∈ [0x02, 0x06] ∪ {0x12, 0x13}` → **该类型的 payload 开头带 12 字节目标设备 MAC**。

即：Jpeg(0x02)、ControlAvatar(0x03)、ControlMotion(0x04)、StartCameraStream(0x05)、StopCameraStream(0x06)、VideoModeOn(0x12)、VideoModeOff(0x13) —— 这 7 种消息**是路由消息**，payload 前 12 字节是目标 MAC。

MAC 规范化规则 `normalizeMac()`（`:20-29`）：去掉 `:` 和 `-`，转小写，必须正好 12 个 hex 字符，否则返回空串。

**路由校验逻辑**（`decodeToRemoteFrame`，`:77-84`）：
```cpp
if (hasTargetPrefix(data[3])) {
    const auto expected = normalizeMac(factory_mac);
    if (payload_size < 12 || expected.empty() ||
        normalizeMac(std::string_view(reinterpret_cast<const char*>(payload), 12)) != expected)
        return false;
    payload += 12;
    payload_size -= 12;
}
```
→ **MAC 不匹配的帧被整帧丢弃**，解包后交给 HAL 的是去掉 12 字节 MAC 前缀的 `[type:1][length:4 BE][payload]`（`:85-88`），**复用远端 WS 的同一套 handler**。这就是 LAN 和云两条通道能在设备端共用一套业务代码的关键。

注意：路由只对**入向**生效。**出向**（设备→App）的 `encode()` **不加 MAC 前缀**（`:50-64` 没有这段逻辑），App 靠连接本身知道设备身份。

#### 有没有心跳 / 保活 / 重连

**协议层没有心跳帧类型**——`local_network_protocol.h` 里**没有** ping/pong 定义，`isKnownType` 的白名单也不含任何心跳值。

保活在**传输层**：
- 依赖 **WebSocket 协议自带的 ping/pong**：`local_avatar_client.cpp:123-125` 注释明确写「A connected App sends WebSocket ping every five seconds. The network component replies pong itself; a missed notification must not tear the link down.」→ **App 每 5 秒发 WS ping，设备侧由 WS 库自动回 pong**。
- **重连**：`AvatarClient::run()`（`local_avatar_client.cpp:94-129`）——WiFi 断开就 `disconnect()` 并复位 `first_attempt`（`:100-102`）；未连上时每 `RetryInterval = 2000` ms 重试一次（`:20`, `:107`）；App 公告新端点时 `_endpoint_revision` 变化会**立即**触发一次连接（`:105-109`）。
- **WiFi 没连上就不连 LAN**（`:100`），因为 LAN 要求同子网。

#### 我们的 iOS 端要复用这个协议（局域网直连 / 手势控舵机），需要写哪几个函数 + 坑

**iOS 侧作为 App（服务端）需要实现：**

1. **WebSocket 服务端**（监听端口），接受设备连接。设备端固定连 `ws://<host>:<port>/ws`（`local_avatar_client.cpp:193`）。
2. **帧封装 `encode(type, payload, len, session, sequence)`** —— 20 字节头，magic `0x53 0x43`、version `1`、type、2 字节 0、session u64 BE、sequence u32 BE、length u16 BE。**长度字段是 2 字节**，上限 65535。
3. **帧解析 `decodeToRemoteFrame()`** —— 校验 magic/version/type/长度；对 0x02-0x06 & 0x12 & 0x13 **先比 12 字节 MAC**，不匹配丢弃。
4. **端点公告 `parseEndpointAnnouncement()` 的逆操作** —— 设备端用 `parseEndpointAnnouncement` 解析（`:261-312`），支持格式 `{"port":45678,"path":"/ws","ip":["192.168.1.5","10.0.0.3"]}`（注释示例 `:255-256`）。**只用到 `port` 和 `ip` 数组，`path` 被忽略**（`:281-288` 的 key 分支里没有 `path` → 落 `skipJsonValue`）。**注意它是自研的迷你 JSON 解析器**，不认 `\u` 转义（`:114-120`）、只认扁平对象。
5. **握手鉴权** —— 设备在 WS 握手的 HTTP 头带 `Authorization: <token>`（`local_avatar_client.cpp:183`），token 由 `secret_logic::generate_handshake_token("stackchan-lan-v1")` 生成（`hal_ws_avatar.cpp:91`）。**iOS 端必须校验这个头**，但**校验算法在 `secret_logic` 里，不在本地仓库中**——见 §五。

**坑清单：**

| # | 坑 | 说明 |
|---|---|---|
| 1 | **长度字段宽度不一致** | 云通道 4 字节 BE（`hal_ws_avatar.cpp:556`），LAN 通道 2 字节 BE（`local_network_protocol.h:61`）。写代码时极易混。 |
| 2 | **MAC 前缀只对 7 种类型生效** | 其余类型（0x01/0x07/0x09/0x0D/0x0E/0x10/0x14/0x1B）**不能**加 MAC 前缀，加了会被当成 payload 内容。 |
| 3 | **MAC 格式严格** | 12 位小写 hex，无分隔符。设备侧是 `GetHAL().getFactoryMacString()` 规范化后的值（`hal_ws_avatar.cpp:91`）。iOS 拿到的是**冒号大写**格式的 MAC，必须 `normalizeMac` 后再比。 |
| 4 | **无校验和** | 帧完整性只靠 TCP + WS 保证，丢位不会被发现（但也不会出错，因为长度字段会先对不上）。 |
| 5 | **Payload 上限 65535** | JPEG 大概率超限——官方为此写了 20→10→5 降质循环（`hal_ws_avatar.cpp:445-455`）。iOS 端也要有同样策略，否则大图被丢。 |
| 6 | **session 是 64 位随机数** | `(esp_random() & 0x7fffffff) << 32 \| esp_random()`（`local_avatar_client.cpp:202`）——**每次 TCP 重连都换新 session**。iOS 端可用它区分「同一连接的连续帧」和「重连后的新会话」。 |
| 7 | **sequence 每连接从 0 开始** | `++_sequence`（`:247`），首帧 seq = 1。**发送方向和接收方向各用各的计数器**（协议里没有明确方向位，靠 session 区分）。 |
| 8 | **App 必须每 5 秒发 WS ping** | 否则设备的 `BoundedTcp` 收超时不会主动断（依赖 TCP keepalive），iOS 端（尤其跨 NAT/热点）要自己保活。 |
| 9 | **同子网前提** | 设备端 `WifiManager::GetInstance().IsConnected()` 才尝试（`:100`）；且注释说 "The App and this device must share one IPv4 subnet"（`:27-28`）。iOS 用蜂窝/P2P 时不可用。 |
| 10 | **iOS 的 AWDL/link-local 地址** | 官方明确处理了：`local_avatar_client.cpp:148-149`「iOS can report a link-local AWDL address besides the Wi-Fi one, so the first reachable address wins」→ `ip` 数组要**按顺序试**，不能只取第一个。 |
| 11 | **设备端用 WS id=2，连云用 id=1** | `local_avatar_client.cpp:177` 用 id 2；`hal_ws_avatar.cpp:131` 用 id 1。注释说「networks whose underlying implementation identifies connections by this value」（`:175-176`）。iOS 侧无需关心，但 fork 时别混。 |
| 12 | **`path` 字段被忽略** | 设备端固定连 `/ws`（`local_avatar_client.cpp:193`），公告里的 `path` 不起作用。 |

### 1.3 `avatar_socket.cpp` / `local_avatar_client.cpp`（新增 401 + 256 行）

#### 谁是服务端谁是客户端？

**设备端是客户端，App 端是服务端。**

- 设备端：`local_avatar_client.cpp` 的 `AvatarClient::connect()`（`:168-209`）主动 `socket->Connect(url)`，URL 是 `ws://<host>:<port>/ws`（`:193`），**host/port 来自 App 通过云通道广播的公告**（`hal_ws_avatar.cpp:375-382` → `applyAnnouncedEndpoint()` `:399-410` → `_local_client->setEndpoint()` `:409`）。
- **设备端不监听任何 LAN 端口**，也没有 mDNS/广播发现。App 必须先能通过云通道联系到设备，才能告知自己的局域网地址。
- App 端（官方 Flutter App）在本仓库里**没有源码**（App 是独立仓库），只在 `local_avatar_client.cpp` 的注释和 `parseEndpointAnnouncement` 的示例里体现其行为。

**WS 握手鉴权**：设备端在 HTTP 头带 `Authorization: <token>`（`local_avatar_client.cpp:183`），token = `secret_logic::generate_handshake_token("stackchan-lan-v1")`（`hal_ws_avatar.cpp:91`）。

#### LAN 优先 / 云回落的切换判据

**不是探测，是「谁先连上谁生效 + 逐级回落」。**

1. `sendPacket(type, ...)`（`hal_ws_avatar.cpp:573-578`）：**先试 LAN**（`_local_client->send()`），成功就 return；**失败才走云**（`sendRemotePacket()`）。
2. `sendPacket(channel, type, ...)`（`:563-571`）：**显式指定通道**，用于呼叫应答这类「必须回原通道」的场景。
3. `isConnected()`（`:412-415`）：`_local_client->isConnected() || _remote_connected` —— **任一通即可**。
4. 抓帧时（`captureAndSendFrame`）用**不带 channel 的** `sendPacket(DataType::Jpeg, ...)`（`:451`），所以 JPEG 走 LAN 优先。
5. **没有超时/探测式的「探测 App 在不在局域网」**——判据完全依赖：
   - **云通道**：App 公告了 `AppLanAddress (0x1B)` → 设备端才可能连 LAN；
   - **LAN 通道**：公告里的 IP **TCP 连不上**（`connectAnnouncedEndpoint()` 逐个试，`:150-166`；`BoundedTcp::Connect` 超时 `ConnectTimeoutMs = 2000`，`avatar_socket.cpp:27, 75`）→ 保持云通道。

**重要含义**：**纯局域网场景（没有云）时，设备端永远连不上 App**，因为 App 的地址必须经云通道告知。这对我们的意义见 §四。

#### 对我们的影响：fork 后这套 LAN 直连要不要保留？

**建议：保留协议，但重写拓扑。**

- **保留**：`local_network_protocol.h` 的 20 字节帧格式很干净，且 `hasTargetPrefix` 的 MAC 路由已经解决了「同一局域网多台 StackChan」的寻址问题——这是我们做「手势控舵机」的现成基础。
- **要改**：把「App 公告端点」换成**我们的 App 主动发现/连接**。最干净的改法是让**设备端做服务端**（监听一个端口 + 广播 mDNS `_stackchan._tcp`），iOS 主动连——这样纯局域网可用，不依赖云。
- **不要照抄**：`BoundedTcp` 手写 TCP + 自造 `SocketNetwork` 适配器（`avatar_socket.cpp:251-288`）这套是**为了给官方 WebSocket 库加超时**而做的绕行方案，代码量大且脆（手写 select 循环、跨线程 fd 生命周期）。我们如果自己写 iOS 端 + ESP-IDF 端，可以直接用 ESP-IDF 的 `esp_websocket_client` / `esp_http_client` 省掉这一坨。

**实现细节（对我们有参考价值的部分）**：

- `AvatarSocket::SendBinary()` 按 **32 KB 分片**发送，所有分片共享**同一个 deadline**（`avatar_socket.cpp:370-384`；分片大小 `:377`，deadline 检查 `:376`）。发送锁用 `std::timed_mutex`，拿不到锁就**直接 Abort 连接**（`:326-331`）。
- `BoundedTcp::Send()` 明确「零写/部分写不算成功」（`:148`）。
- `AvatarClient` 的 `generation` 机制和 `markDisconnected()`（`:211-220`）在断线时 `++_generation`，**立刻作废队列里已排队的控制消息**——这是防「断线前的旧动作在新连接上重放」的好设计。
- `AvatarClient::disconnect()`（`:222-237`）**故意不在锁外等待 socket 析构**——注释说「Socket destruction may wait for the receive task and its callbacks. Never hold a mutex those callbacks or the sender might need here.」

### 1.6 `firmware/main/hal/hal_ble.cpp`（120 行）—— BLE 配网加固后的消息格式

#### 消息方向与载体

设备在配网态起一个**自定义 GATT 服务**（`stackchan_ble_is_connected()` / `ble_init(true)`），App 与设备之间是**双向 JSON 文本**。两个方向的消息都用同一个 `cmd` 字段区分。

#### App → 设备

**1) `handshake`**

- 设备收到后回 `notify_state(4, token.c_str())`（`hal_ble.cpp` diff 段 `handle_handshake`）。
- 即 **`type = 4` 的 notifyState 里，`state` 字段装的是设备生成的 token**。
- 这个 token 就是后续 HTTP/WS 鉴权用的东西（官方实现里 `secret_logic::generate_auth_token()` / `generate_handshake_token()`）。

**2) `setWifi`**（`on_config_data`）

JSON 字段（**严格校验**）：

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `ssid` | string | **是** | WiFi SSID，1-32 字节，不得含 NUL |
| `password` | string | **是** | 密码，≤64 字节；开放网络传空串 |
| `frequency` | int | 否 | App 侧测到的频段（MHz）；**≥ 4900 判定为 5 GHz** |
| `currentNetwork` | bool | 否 | 该 SSID 是否是手机当前连接的网（**仅上下文，不作判据**） |

**校验规则**（diff 段 `on_config_data`）：
```cpp
if (!data["ssid"].is<const char*>() || !data["password"].is<const char*>()) {
    notify_failure("", {"invalid_configuration",
        "Wi-Fi configuration must contain an SSID and a password string (empty for an open network)."});
    return;
}
```
→ **缺 ssid 或缺 password 一律拒收**（对应上游提交 `d2e9548 fix(firmware): reject setWifi messages without an ssid or password`）。注意 `is<const char*>()` 判的是「**字符串**」，不是「非空」——空密码合法（开放网络）。

`frequency` / `currentNetwork` 是**可选扩展字段**（"Older Apps simply do not send them."），缺失或类型不对就忽略（`band.reported_5ghz = frequency.is<int>() && frequency.as<int>() >= 4900`）。

#### 设备 → App

统一格式：`notifyState`
```json
{
  "cmd": "notifyState",
  "data": {
    "type": 1,
    "state": "wifiConnected",
    "errorCode": "authentication_failed",
    "errorMessage": "Wi-Fi authentication failed. ...",
    "reason": 15,
    "sdkError": 0,
    "ssid": "MyRouter"
  }
}
```
- `type` / `state` 恒有；`errorCode` / `errorMessage` / `reason` / `sdkError` / `ssid` **仅在失败时出现**（`notify_state` 的 `if (failure)` 分支）。
- `type` 枚举（从代码反推）：`0 = wifiConnecting`、`1 = wifiConnected`、`2 = wifiConnectFailed`、`3 = wifiDisconnected`、`4 = <token>`。

`state` 字符串常量：`"wifiConnecting"`、`"wifiConnected"`、`"wifiConnectFailed"`、`"wifiDisconnected"`。
失败时 `state` 仍是 `"wifiConnectFailed"`，细节在 `errorCode`/`errorMessage` 里。

**busy 码**：`{"busy", "The device is already connecting to Wi-Fi. Wait for the current attempt to finish."}`。

#### 线程模型改进

- v1.5.1 在 **ESP WiFi 事件回调里直接**发 BLE 通知 + 发 UI 信号。
- v1.6.0 改成：ESP 回调只 `push` 到 `_results` 队列（`ConnectionResult{success, ssid, failure}`），由 `update()`（worker 线程）取出来再发 BLE 和 UI 信号。注释写明 "ESP Wi-Fi callbacks only queue results; BLE sends and UI signals stay on this worker rather than blocking the ESP event loop."
- `_app_config_server_started` 静态标志防重复启动 `startAppConfigServer()`。

**对我们的影响**：**这套 BLE 协议我们要照抄**（我们的 App 要能配网 + 看错误原因）。但 `errorCode` 的 18 个取值来自 §1.5 的表，**我们的 App 要按这套 code 映射文案**。`frequency`/`currentNetwork` 是可选的，我们可以**先不做**（不影响主流程）。

```
[设备侧]
 1. 启动 → app_launcher.onLauncherOpen()
      ├─ consumeAppSetupRequest() == true  → WifiSetupWorker（网络/绑定失败后的恢复路径，app_launcher.cpp:29-31）

            → requestAppSetup()  ← 重启回 App 配网页

      服务端返回 activation.code → requires_app_binding_ = true
      → GetHAL().requestAppSetup() → 重启回 App 配网页（App 完成绑定）

```

**App 必须提供什么（我们要复刻的）**：
1. BLE GATT 通道：连设备 → 发 `handshake` → 收 `type:4` 的 token。
2. 发 `setWifi`（**必须带 ssid 和 password 两个字符串**）。
3. 解析 `notifyState`，把 `type=2` 时的 `errorCode` / `errorMessage` **直接展示给用户**（官方 App 就是这么做的，18 个 code 都有现成文案）。
4. 完成**账号绑定**流程 → 设备下次 OTA 检查时不再返回 `activation.code`。

```cpp
[[noreturn]] void Hal::requestAppSetup()
{
    // A deliberate reboot for provisioning must not roll back a working OTA
    // image merely because credentials or App binding are missing.
    const auto* running = esp_ota_get_running_partition();
    esp_ota_img_states_t state;
    if (running && esp_ota_get_state_partition(running, &state) == ESP_OK && state == ESP_OTA_IMG_PENDING_VERIFY) {
        ESP_ERROR_CHECK(esp_ota_mark_app_valid_cancel_rollback());
    }
    {
        Settings settings("warm_boot", true);
        settings.SetInt("app_setup", 1);
        settings.SetInt("app_index", 6);
    }
    esp_restart();
}

bool Hal::consumeAppSetupRequest()
{
    Settings settings("warm_boot", true);
    const bool requested = settings.GetInt("app_setup", 0) != 0;
    if (requested) settings.SetInt("app_setup", 0);
    return requested;
}
```

**关键设计**：配网失败 = **重启回 App 配网页**（`app_index = 6`），而不是弹个错误框。重启前先 `esp_ota_mark_app_valid_cancel_rollback()`，**避免「因为没配网就把好镜像回滚了」**。

1. `ota.cc`（patch 后）**丢弃**服务器给的 `activation.code` / `activation.message` 字符串，只留 `requires_app_binding_` 布尔量（patch `main/ota.cc` 段）。

**关键帧系统**：`firmware/main/stackchan/animation/animation.h` 定义 `Keyframe / FeatureKeyframe / ServoKeyframe / KeyframeSequence`，**只依赖 uitk 的 `Vector2i`**（`animation.h:7-11`、`:19-60`），本身**是可移植的**（约 200 行）。但它驱动的是 avatar 的 `leftEye/rightEye/mouth` 三个 Feature —— **没有 avatar，keyframe 就是空转**。

**移植难度评估（avatar → Arduino）**：
- 依赖 `<lvgl.h>` + `<smooth_lvgl.hpp>`（M5Stack 的 LVGL C++ 封装，见 `skins/default/default.h:8-9`、`decorators/decorators.h:5-6`）。Arduino 侧 M5GFX 有 LVGL 支持，但 **`smooth_lvgl.hpp` 要么一起搬、要么重写一层适配**。
- `avatar.h` 依赖 `uitk` 的 `Vector2i`、元素池（`ObjectPool`）、`uitk_intl::ui_hal`（tick/delay）——BSP 的 uitk 移植版**已经提供了 `core/hal/hal.hpp`**（`on_get_tick` / `on_delay` 注入），这一层是通的。
- 装饰器素材是 **C 数组**（`decorator_*.c`），可直接编。
- **净迁移量 ≈ 1900 行 C++ + 1 层 LVGL 适配，不是「白拿」。**

→ **结论：Arduino 路线下，表情引擎要么自己搬（1900 行 + 解 LVGL 依赖 + 重做 skin 渲染层），要么从零重写。**

### 2.3 UiFlow2 是什么

M5Stack 的 **Web 版 Blockly 可视化编程**（https://uiflow2.m5stack.com/），设备端跑 **MicroPython 固件**。官方有专门的 "StackChan UiFlow2 Quick Start"（`/en/uiflow2/stackchan/program`），流程是：

1. 用 **M5Burner** 烧 StackChan 的 UiFlow2 固件（烧录时填 COM / 波特率 / **Server 服务器地址** / WiFi SSID+密码 / SNTP / 时区 / 启动选项）；
2. 在 Web IDE 里拖 **Blockly 积木**；
3. 「Burn」把生成的 `.py` 烧进设备 / 或直接 Run。

**能不能满足「固件外科式改造 + 自定义交互」？→ 不能。**
- Blockly 图形化**无法做 C++ 级固件改造**：改不了 `hal_ws_avatar.cpp`、改不了分区表、改不了 `secret_logic` 的 RSA token 生成。
- **没有 MiniMax / 自建后端的接入能力**：MicroPython 侧没有可用的成熟 TLS+WebSocket 栈，官方 server 的 `[type:1][len:4 BE][payload]` 二进制协议在积木里表达不了。
- **OTA 不是 OTA**：只有 M5Burner 整包烧录。
- 优点是**上手最快**（拖积木、烧录 1 分钟出效果），适合**原型验证和演示**。

### 2.4 三条路线对比表

| 维度 | **ESP-IDF 改 C++（我们当前）** | Arduino + BSP | UiFlow2 |
|---|---|---|---|
| **表情引擎可得性** | ✅ **原样拿到**：`firmware/main/stackchan/`（3057 行）已在仓库里，含 6 情绪枚举、程序化脸、keyframe、skin、decorator、modifier 全套 | ❌ **拿不到**（BSP 无 avatar）；要搬 ≈1900 行 + 解 `smooth_lvgl` 依赖，或从零重写 | ❌ 没有；只能做静态图 / 简单 UI 组件 |
| **后端对接** | ✅ 自由改 `hal_ws_avatar.cpp` / 新写 `protocols/`；能接 MiniMax TTS WS、能换账号体系 | ⚠️ 能写 WS，但**要连带重做 OTA / 协议层 / 账号层**（BSP 一个都没有）；16 MB Flash 里塞 LVGL+表情+WS+OTA 余量紧张 | ❌ 基本不可能 |
| **OTA** | ✅ 官方 `ota.cc` + `OTA_URL`（Kconfig）可改 | ⚠️ **BSP 不含 OTA**，要从零写 | ⚠️ 只有 M5Burner 整包烧录，不是 OTA |
| **体积与内存** | ✅ 官方已调优（`CONFIG_COMPILER_OPTIMIZATION_SIZE=y`、8 MB PSRAM、16 MB Flash） | ⚠️ Arduino+LVGL+M5Unified+NFC+IR 体积显著变大，且无 PSRAM 优化经验 | ❌ MicroPython 解释器占 Flash |
| **迭代速度** | ⚠️ ESP-IDF 编译慢（分钟级），但 C++ 表达力强 | ✅ 编译快（秒级）、API 简单 | ✅✅ 最快（拖积木） |
| **社区** | 中（M5Stack 官方 + 中文社区活跃，v1.6.0 刚发布） | 中（BSP 1.1.1，examples 齐全，有 Arduino-Build-Check CI） | 高（UiFlow2 是 M5Stack 主推平台） |
| **求职作品可展示性** | ✅✅ 高：能讲「**改官方工业固件 + 自建后端 + 自研 iOS App**」的完整工程故事 | ⚠️ 中：像「用官方 BSP 写了个 demo」 | ❌ 低：像「玩了个积木」 |

### 2.5 结论与推荐：**不换路线，留在 ESP-IDF**

**推荐：继续走 ESP-IDF 改 C++。** 三条理由：

1. **表情引擎是本项目的产品核心，而它只在 ESP-IDF 固件里。** Arduino 路线拿不到它 —— BSP 只到「舵机 + LED + 触摸 + motion 运动学」这一层，表情要自己重写。我们重写表情 = 主动放弃官方工业级资产，**在求职作品里是净负分**。
2. **我们要做的三件事（接 MiniMax / 自建后端 / 换账号体系），Arduino 一件都不省。** 这三件都是 C/C++ 级工作量：官方 `hal_ws_avatar.cpp` 620 行 + `ota.cc` + `application.cc` 对话循环，在 Arduino 上不但要重写，还要额外补 Arduino 侧**完全没有**的 OTA 层、协议层、账号层。**净新增工作量，不是节省。**
3. **Arduino 唯一划算的用法是「不拿它当主固件」。** BSP 极好，我们可以把它当作：
   - **舵机标定 / 产线测试工具**（`HomeCalibration` 示例直接可用）；
   - **舵机协议（FEETECH 总线）的快速实验台**；
   - **独立小应用固件**——官方工厂固件本来就有 App Store 机制（`GET /stackChan/apps` + `firmwareUrl` 字段，`server/README.MD:882`、`:898-915`），我们的服务器也能发布「Arduino 编译出来的独立小固件」当扩展 App。

**如果（仅作参考）非要用 Arduino 做主固件，迁移成本**：
| 工作项 | 成本 |
|---|---|
| 搬 `firmware/main/stackchan/motion/` | **≈ 0**（BSP 同 API，已含） |
| 搬 `firmware/main/stackchan/avatar/`（≈1900 行） | **中-大**：需解 `smooth_lvgl` 依赖 + 重做 skin 渲染层 + 适配 Arduino 侧 uitk |
| 搬 `firmware/main/stackchan/modifiers/`（blink/breath/dance/head_pet/idle_expression/idle_motion/imu/speaking/timed） | 中：依赖 `modifiable.h` + `ObjectPool`，可移植但依赖 avatar |
| 重写 WS 协议层 + MiniMax TTS + OTA + 账号 | **大，且和 ESP-IDF 路线的这部分工作完全重叠**（不省） |
| **净结论** | **严格劣于 ESP-IDF 路线** |

### 3.1 连接 URL / 参数 / 鉴权头

**设备端**（`firmware/main/hal/hal_ws_avatar.cpp:88`）：
```
{server_url}/stackChan/ws?deviceType=StackChan
```
**App 端**（`server/README.MD:922`）：
```
ws://<host>:12800/stackChan/ws?deviceType=App&deviceId=<app-device-id>
```

**鉴权头（两者相同）**：`Authorization: <rsa-mac-token>`（`server/README.MD:927`、`:803`）。

**token 生成**（`server/README.MD:615-627`）：
```
plainText = "<MAC>|<nonce>|<unix_timestamp_seconds>"      // 例："AA:BB:CC:DD:EE:FF|random_nonce|1710000000"
cipher    = RSA-OAEP-SHA256-Encrypt(plainText, rsa.server.public)
header    = Base64(cipher)
```

**服务端校验**（`server/internal/web_socket/web_socket.go:79-109` `GetMac`）：
1. `base64.StdEncoding.DecodeString(token)`（`:81`）
2. `utility.RSADecrypt(decodedToken)`，用 `rsa.server.private`（`:86`）
3. `strings.Split(tokenStr, "|")`，取 `parts[0]`=MAC、`parts[2]`=时间戳（`:92-101`）
4. **时间戳与服务端时间差 > 10 秒 → 拒绝**（`:102-105`，`now-ts > 10 || ts-now > 10`）
5. `GetMac` 失败或 MAC 为空 → **HTTP 401**（`:114-119`）
6. `deviceType` 缺失 → 拒绝（`:120-124`）
7. `deviceType=App` 时 `deviceId` 必填（`:204-208`）

**RSA 密钥共 4 把**（`server/README.MD:294-313`）：`server_public/server_private`（设备→服务器请求）、`client_public/client_private`（服务器→客户端响应加密）。**设备侧只需要 `server_public`。**

**⚠️ 关键设计**：**App 端也用「设备自己的 MAC token」连接**（`GetMac` 对两个 deviceType 分支都执行，`:114`）。所以服务端的数据模型是 **1 个 MAC = 1 台设备（`stackChanClientPool[mac]`）+ N 个 App 客户端（`appClientPool[mac][]`）**，所有路由都按 MAC 走。

### 3.2 消息封装格式

**服务端生成**（`web_socket.go:820-834` `createMessage`）：
```go
msg := make([]byte, 1+4+dataLen)
msg[0] = msgType
binary.BigEndian.PutUint32(msg[1:5], uint32(dataLen))
copy(msg[5:], data)
```
→ **`[type:1][len:4 Big-Endian][payload]`**，与设备侧 `hal_ws_avatar.cpp:549-561`（`writeBigEndian(packet.data()+1, len, 4)`）**逐字节一致**。

**服务端解析**（`web_socket.go:308-324` `parseBinaryMessage`）：
- `len(msg) < 5` → 丢弃（`:309-312`）
- `dataLen = BigEndian.Uint32(msg[1:5])`（`:315`）
- `payload = msg[5 : 5+dataLen]`（`:316`）
- **`len(msg)-5 != dataLen` → 丢弃**（`:318-321`，日志 "Length mismatch: header says %d, actual is %d"）

**WS 帧类型**：一律 `websocket.BinaryMessage`。**唯一例外**：设备连上后主动发的一条**文本帧** `{"type":"hello", "msg":"Hello from StackChan!"}`（`hal_ws_avatar.cpp:161`）—— 服务端在 `readStackChanMessage` 的 `websocket.TextMessage` 分支**原样转发给该 MAC 的所有 App**（`web_socket.go:476-482`），**服务端不解析 hello**。

**⚠️ 长度字段宽度必须分清**：
| 通道 | 长度字段 | 佐证 |
|---|---|---|
| 云 WS（设备↔server↔App） | **4 字节 BE** | `web_socket.go:829`、`hal_ws_avatar.cpp:556` |
| 局域网 WS（设备↔App 直连） | **2 字节 BE**（且 20 字节自定义头） | `local_network_protocol.h:61`、`:50-64` |

1. **带 12 字节 MAC 前缀**：`Opus / Jpeg / ControlAvatar / ControlMotion / TextMessage / RequestCall`
2. **payload 整体就是 MAC 字符串（12 字节）**：`OnAudio / OffAudio / OnCamera / OffCamera / OnPhoneScreen / OffPhoneScreen`
3. **无 MAC**：设备→服务端方向的所有消息

而**局域网直连协议**（`local_network_protocol.h:45-48` `hasTargetPrefix`）判定为「带 target 前缀」的类型是 `0x02-0x06 ∪ {0x12, 0x13}`——**与服务端的 MAC 前缀集合并不完全一致**：
- 服务端给 0x01/0x07/0x09 加 MAC 前缀，局域网协议**不加**（`hasTargetPrefix(0x01/0x07/0x09) == false`）；
- 服务端给 0x05/0x06/0x12/0x13 的 payload 是「整个 MAC」，局域网协议却把它们判为「带前缀」→ **局域网与云端在这几种类型上不兼容**。
→ **我们做局域网直连时必须自己统一这两套约定**（建议：局域网一律采用「12 字节 MAC 前缀」，与云端对齐）。

### 3.4 设备端与 App 端的角色差异

| 维度 | 设备（`deviceType=StackChan`） | App（`deviceType=App`） |
|---|---|---|
| query 参数 | `deviceType=StackChan` | `deviceType=App&deviceId=<id>`（`deviceId` 必填，`:204-208`） |
| 鉴权 token | 设备自己的 MAC token | **同一台设备的 MAC token** |
| 服务端存储 | `stackChanClientPool[mac]`（单例） | `appClientPool[mac][]`（同 MAC 多 App） |
| `deviceId` 用途 | — | 仅用于**重连去重**（同 mac+deviceId 复用连接，`:213-221`） |
| 音频方向 | → App：**麦克风上行**；← App：**喇叭下行** | 同 |
| 相机 | → App 推 JPEG | → 设备发 Jpeg（**仅 phoneScreen 开启**） |
| 连接即推送 | 推 `DeviceOnline(0x17)` 给所有 App（`:168-174`）；若之前有 `callAppClient` → 额外推 `TextMessage "The equipment has been reconnected."`（`:144-147`）；若已有 camera/audio 订阅 → 补发 `OnCamera`/`OnAudio`（`:148-155`） | 设备在线 → 推 `DeviceOnline(0x17)`；否则推 `DeviceOffline(0x16)`（`:229-236`） |
| 15 s 超时清理 | 从池中删除 + 推 `DeviceOffline(0x16)` 给所有 App（`socket_task.go:235-283`） | 从池中删除 + 给设备发 `OffCamera`/`OffAudio`（`socket_task.go:114-212`） |
| 心跳 | 服务端每 **5 秒**发一次 `ping(0x10)` 给所有客户端（`socket_task.go:28-101`） | 同 |

**超时常量**：`ClientExpireTimeout = 15 * time.Second`（`socket_task.go:24`）；README 亦写 "every 15 seconds: clean expired connections"（`README.MD:973`）。
**注意**：设备端 `handleMessage` 里收到任何消息都会刷新心跳时间戳（`hal_ws_avatar.cpp:205`），所以 15 s 清理实际是「15 s 没有任何报文」。

### 3.5 服务端要做的最小实现（我们只做：设备通道 + 表情控制 + 文本消息 + 音频）

**必须实现：**

| # | 模块 | 要点 |
|---|---|---|
| 1 | **WS 端点** | `GET /stackChan/ws?deviceType=StackChan`（+ 我们自研 App 需要时再加 `deviceType=App&deviceId=`） |
| 2 | **鉴权中间件** | Base64 解码 → RSA-OAEP-SHA256 解密（`rsa.server.private`）→ 解析 `mac\|nonce\|ts` → 校验 `\|Δt\| ≤ 10 s` → 提取 MAC；失败 401 |
| 3 | **连接池** | `devicePool[mac]`（单例）+ `appPool[mac][]`；每条连接维护 `lastTime`；**15 s 心跳清理** + 清理时发 `DeviceOffline(0x16)` / `OffCamera` / `OffAudio` |
| 4 | **帧编解码** | `[type:1][len:4 BE][payload]`；**长度必须严格等于 `len-5`**，否则丢弃 |
| 5 | **路由表（最小集）** | ① App→设备 `ControlAvatar(0x03)` / `ControlMotion(0x04)`：**剥 12B MAC 前缀**后转发<br>② App→设备 `TextMessage(0x07)`：剥 MAC 后转发<br>③ App→设备 `Opus(0x01)`：剥 MAC 后转发（下行音频）<br>④ 设备→App `Opus(0x01)`：转发给该 MAC 的订阅者（上行音频）<br>⑤ 设备→App `TextMessage(0x07)`：转发<br>⑥ 设备→服务端 `GetDeviceName(0x0E)`：查库回包<br>⑦ 在线状态 `DeviceOnline(0x17)` / `DeviceOffline(0x16)`<br>⑧ 服务端每 5 s 发 `ping(0x10)` |
| 6 | **写协程 + 有界队列** | 每连接一个 writer goroutine + `sendChan`（容量 100，`web_socket_model.go:58`、`:76`），**队列满时丢弃并打日志**（`web_socket.go:784-786`）——不要阻塞读循环 |
| 7 | **数据库（最小）** | 设备表（mac / name / 绑定用户）；`GET /stackChan/device/info`（设备自检用，26 号已核实） |

**我们不需要实现**（官方有、我们砍掉）：呼叫（0x09-0x0C）、相机订阅与 JPEG 转发（0x05/0x06）、手机投屏（0x12/0x13）、舞蹈（0x14）、拍照（0x1A）、App Store、社区（post/comment/friend/pano）、文件上传、Admin 后台、`/stackChan/xiaozhi/*`。

**如果我们同时自研 iOS App**，服务端还要加：`deviceType=App` 分支 + `deviceId` + `appPool[mac][]` + App 方向那套「12B MAC 前缀 / 整个 payload 是 MAC」的解析规则。

### 3.6 TTS 音频从哪来、服务端怎么推给设备 —— **官方 server 根本不做 TTS**

**证据（三条）**：
1. `server/internal/web_socket/` 目录**只有 3 个文件**（`web_socket.go`、`socket_task.go`、`web_socket_model.go`），**没有任何 TTS / STT / LLM 代码**。
2. `server/README.MD` 第 11 章对 `0x01` 的定义只有一句 "Audio frame"，**不区分「麦克风上行」和「TTS 下行」**——因为服务端只是**转发器**。
3. 设备端 `hal_ws_avatar.cpp` **没有任何 Opus 发送路径**（§1.1 已证：所有 `sendPacket` 调用点只有 JPEG / 呼叫 / GetDeviceName），且 **Opus 接收分支被整段注释**（`:212-220`）。

`server/api/xiaozhi/v1/xiaozhi.go` + `README:883-885` 的 `/stackChan/xiaozhi/token` 等接口，只是**帮设备去小智平台换 token**（`README:315-322` 的 `xiaozhi` 配置节），**不是 TTS 服务**。

**真实的官方语音链路**：
```
设备麦克风 ──► xiaozhi SDK (protocols/websocket_protocol.cc) ──► 小智云 (MQTT/WS)
小智云 TTS ──► xiaozhi SDK ──► audio_service ──► 设备喇叭
App 音频   ──► 官方 M5Stack server ──► 设备      （旁路：App 播放的音效 / 通话音频）
设备麦克风 ──► 官方 M5Stack server ──► App      （旁路：远程收音）
```

**→ 我们对接 MiniMax TTS WebSocket 时，要替换的是「小智协议层」这一环，不是官方 server。**

| 官方环节 | 我们的替换动作 |
|---|---|
| `xiaozhi-esp32/main/protocols/websocket_protocol.cc`（小智 WS 协议：hello / 打断 / STT / TTS 事件） | **新写 `protocols/minimax_protocol.cc`**，实现 MiniMax 的 WS 协议（建链、录音上行、STT/TTS/LLM 事件、打断） |
| `xiaozhi-esp32/main/application.cc` 的对话循环（`InitializeProtocol` / `ContinueOpenAudioChannel` / `ContinueWakeWordInvoke` / `ResetProtocol`） | **改造为我们的**：唤醒 → 建 WS → 发音频 → 收 STT → 送 LLM → 收 TTS 音频 → 播 |
| `xiaozhi-esp32/main/audio/audio_service.cc` 的 TTS 解码播放 | **保留其播放能力**，但输入改为我们的协议层直喂；或我们直接调 `Board::GetInstance().GetAudioCodec()->OutputAudio(...)` 绕开 `audio_service`（`audio_service` 只留提示音 `PlaySound`） |
| `xiaozhi-esp32/main/ota.cc` 拉小智的 `mqtt`/`websocket` 配置 | **换掉**：`OTA_URL` 指向我们自己的配置接口（26 号已核实 `OTA_URL` 是 Kconfig 可配的） |
| **官方 M5Stack server** | **TTS 部分不用动（本来就没有）**；我们只复用它做 **App↔设备的控制面**（表情 / 舵机 / 文本 / 通话音频） |

**一句话结论**：**TTS 音频不走官方 server，走我们自己的 MiniMax 通道；官方 server 我们只复用「App↔设备控制面」这一层。** 因此 §四 的改动清单里要新增的是「**自写 MiniMax 协议层 + 自己的设备注册/激活后端**」，而**不是**去改官方 server 的 WS 实现。

## §五 未核实与风险

### 5.1 ⭐ 最高风险：Opus 帧格式不匹配（**必须实测，不能推断**）

- **风险**：MiniMax TTS 直出 opus 的**封装格式 / 采样率 / 帧长**与设备侧解码器期望不一致 → 设备播出噪音、变速、或直接不播。
- **为什么是最高风险**：这是"云端 TTS 直出 opus、设备侧解码路径不变"这一整条路线的**单点故障**。方案成立与否全押在它上面。
- **缓解**：① 36 号已把 opus 链路列为专项；② 兜底方案存在（设备端不解码，改由后端转 PCM/WAV 下发，代价是带宽与延迟上升）；③ **不实现 C-1 之前先做 1 小时实验**：抓一段 MiniMax TTS 的 opus 字节流，和设备解码器期望格式逐项比对。
- **当前状态（2026-10-23 更新）**：**协议层已定死，风险大幅下降**（见 `36-端侧感知与声学技术栈调研.md`）：
  - 控制面帧格式 = `[Type=0x01][4B 大端长度][裸 opus 包]`
  - 设备端解码器 = 官方 `espressif/esp_codec_dev` 的 `esp_opus_dec`（**已在依赖树内，复用成本 ≈ 0**）
  - 语音面走 **OGG 容器**（须含 OpusHead+OpusTags，否则整包丢弃）；官方 SFX 脚本已证明该路线可行
  - ⚠️ **剩余的真实选型**：我们的自研协议层走 OGG 还是裸包（→ 规格书 O-9），以及**板级 24 kHz 与语音面 16 kHz 的显式对齐**
  - ⚠️ 仍需在构建产物（`xiaozhi-esp32` 不在 git 里，由 `firmware/repos.json` 拉取）中核对解码器入参期望

### 5.2 表情是否支持连续插值（morph）—— 决定 A-3 能否做渐变

- **影响**：「回来时别过头再慢慢转过来 + 眼睛从闭到睁」这类**连续渐变**需要表情插值；若官方只有离散切换，只能做"瞬间换表情 + 身体缓动"的折中。
- **当前状态**：**未核实**（37 号 §二正在解剖 `skins/default/` 与 `elements/`）。

### 5.3 300+ 表情 / 动作的完整命名清单未取全

- 情绪与装饰器已确认（§六），但**动作**侧的完整 ID 清单（点头/摇头/看别处/前倾/睡觉…）尚未逐个列出 → 动作库（功能 B-4）还不能定稿。
- **当前状态**：**部分核实**（38 号 §9.4 待补）。

### 5.4 已发布版固件 / App 是否比我们的基线更新

- 官方 README 自述"仓库比已发布固件/App 滞后" → **我们同步的 `origin/main`（`eff0d6b`, 2026-10-22）有可能仍落后于商店里的发布版**。
- GitHub Releases / Tags **未取到**（`api.github.com` 配额耗尽，core 0/60）；版本号只能从 commit 消息推断。
- **影响**：若发布版已含我们没有的改动（例如新的表情或协议），需要二次对齐。
- **缓解**：发正式固件前，用 `git fetch` + `git log origin/main` 重新核对一次；必要时比对 OTA 接口返回的版本号。

### 5.5 设备端算力约束

- ESP32-S3：16MB Flash / 8MB PSRAM / 5MB SRAM。**在设备端跑人脸存在检测 / 唤醒词 / 声学特征提取是否可行未验证**。
- 若不可行 → 感知必须移到 iPhone 端（会带来"手机不在身边就失去在场感知"的限制，与"持续在场"的产品承诺冲突）。**这是需要尽早验证的架构分叉点**（36 号专项）。
