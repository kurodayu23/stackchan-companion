# StackChan · 设计情报库

> 这个目录是 **StackChan 桌面 AI 陪伴机器人**（自研软件栈 + 原生 iOS App）的**前期设计情报库**。
> **99 份档案，约 5.6 MB**，全部产出自**实际抓取 / 实测 / 实读源码** —— 不用记忆复述，不用二手转述充当结论。
>
> 采集日期：2026-07 ~ 2026-10 ｜ 最后更新：2026-10-30

## 怎么读这份情报库

**只想要结论 → 读 [`00-总纲`](00-总纲-设计情报总汇与方向裁决.md)。**
其余各份都是它的证据来源。

**想知道"为什么" → 按下面的分层索引跳。**

**想知道"我们凭什么这么判" → 每份文档末尾都有「未取得 / 失败记录」一节。**
抓不到的东西我们如实留空，不补数字。

**想快速进入状态 → 读仓库根目录的 [`PRODUCT.md`](../../PRODUCT.md)（产品真相层）与 [`DESIGN.md`](../../DESIGN.md)（视觉系统层）。**

```
Apple HIG 原文
```

## 本情报库的四条方法论

### 1. 「好看」必须能被判定

`impeccable detect`（62 条确定性规则，Rust，**不需要 LLM / API key**）与
`nongeneric audit`（82 条 + 0–100 分 + P0–P3 整改计划）**两个独立实现**已列入设计稿流程。

但**分数不是质量证书**：检测器通过只是必要条件，**人工冷评必须**。
并且**伪造通过本身就是 AI 味** —— 所以每份报告都要如实写"哪条没验证"。

### 2. 镜像测试

> 换成任何同品类 App，若**只换文案不换决策**仍然成立 → AI 味，必须改一个决策。

我们的差异化决策只有一条：

> **屏幕上唯一会动、唯一被注视的东西是小栈的脸；其他一切都是背景。**

### 3. 短视频是灵感与反例源，不是规范源

抖音上被奉为"高级"的做法，**有相当一部分恰好命中我们的禁止项**
（深色 + 流光渐变 + 霓虹光感 + 3D 粒子卡片 = 我们已量化的 AI 味四大元凶）。
但**它同时也是找到 `impeccable` 的线索来源** —— 这部分价值是真实的。

### 4. 只读核验优先于动手改

我们已有的资产（初稿 `ios/prototype/index.html`、官方固件、官方 server）
**先读源码、先跑工具、先取证，再决定改什么**。
本轮对初稿只做了只读核验（`node --check` 定位到一处 `let`/`function` 同名导致整块 JS 失效），
**没有改任何产品文件** —— 需求未定不动手。
