# 85 · 隐私工程证据补齐：Q5「本地加密后再发」的最终判定与数据分级表的现成骨架

## 一、⭐⭐ Q5「本地加密后再发」：582 条全量判定 = **零证据**

81 号 §八.6 写的是「55 条里没有一条涉及 TEE / 同态加密 / 机密计算」⇒ 拍板时不要把它当选项。
语料从 55 条扩到 **582 条（25 主题）** ⇒ **该结论必须重测**，不能沿用。

**判定方法**：对 83 号（当前权威并集留痕）**每一条记录**的「标题 + 摘要正文」做关键词匹配，**7 组**：

| 关键词组 | 命中 / 582 |
|---|---|
| 机密计算 / TEE：`TEE`、`enclave`、`confidential comput`、`trusted execution`、`attestation`、`secure boot` | **0** |
| 同态加密 / 安全多方计算：`homomorphic`、`MPC`、`multi-party computation`、`garbled circuit` | **0** |
| 端到端加密 / 本地保留：`end-to-end encryption`、`E2EE`、`local-only`、`on-device storage` | **0** |
| 差分隐私：`differential privacy`、`privacy budget` | **0** |
| 联邦学习 / 分布式训练：`federated learning`、`federated` | **0** |
| 客户端加密 / 端侧推理：`client-side encryption`、`encrypted inference`、`privacy-preserving inference` | **0** |
| 数据最小化 / 可携带性：`data minimization`、`data portability`、`right to be forgotten` | **5** |

⇒ **结论（比 81 号更强）**：
1. **「本地加密后再发」这条路线在 582 条、25 个主题的语料里零证据** ⇒ **Q5 拍板时不要把它列为选项**（不是「文献不支持」，是「我们这个主题范围内根本没检索到相关工作」）。
2. ⚠️ **诚实边界**：这说明的是「**我们没找到**」，**不是**「这条路不存在」。它可能是真实存在但**不在 arXiv / 这 25 个主题**里（私有工程博客、专利、企业白皮书都不在语料内）。
3. ⇒ **对 Q5 的直接影响**：Q5 的选项里**不要出现「端侧加密推理」**；要出现的是**可落地的工程契约**（分级表 + 导出 + 可审计），而不是密码学方案。

## 二、⭐⭐ 数据分级表的现成骨架（不必自创字段）

`privacy-data-lifecycle.13`（arXiv `2606.23696`，*Privacy Engineering: A Systematic Literature Review*）：

> 我们综合了 **2018–2025 年的 90 项研究**，用系统综述 + 主题综合梳理隐私工程。
> **十三个维度构成两个递归核心**：
> **PETs（隐私增强技术）+ PM（隐私度量）与 VT（验证与测试）**；
> **GA（治理与问责）与 TC（透明与沟通）及 OM（组织措施）**。
> **MS（建模与规约）在两个核心之间起中介作用**。
> 生命周期映射显示，**需求与设计阶段**的集中度最高。

⇒ **这条直接回答了 84 号 §八 提的「数据分级表要做成可机检的」**：
**文献里对应的就是「PETs + 隐私度量 + 验证与测试」这一支** ⇒ 我们的分级表不该只是「哪些字段敏感」的清单，而应当**每一条敏感值都挂三样东西**：

| 挂载项 | 含义 | 落到我们哪里 |
|---|---|---|
| **PETs** | 用什么隐私增强技术处理它（本地保留 / 脱敏 / 不采集） | 采集与存储策略 |
| **PM（隐私度量）** | 怎么**量化**风险（不是「敏感」与否，而是**泄露影响面 × 可逆性**） | 分级表的分级列 |
| **VT（验证与测试）** | 怎么**自动验证**这条策略没被破坏 | ⭐ **落到门禁**（我们已有 38 项，这是第 39 项的候选） |
| **GA / TC / OM** | 谁负责、怎么跟用户说、组织上怎么兜 | 隐私文案 + 责任划分 |
| **MS（建模与规约）** | 把上面这些**写成规约**，让运行时能对齐 | ⭐ 分级表本身的载体 |

⇒ ⭐ **直接的动作**：我们 `docs/spec/05` §2.1 的数据分级表**应当按这五列改写**，而不是自创字段。
（**当前状态：还没改** —— 下面 §四 说明这属于「要你拍板 Q5 读法之后才能落地」的事。）

## 三、⭐⭐ 两条**可验收**判据（不是理念）

### 3.1 每一段都问「这一步**严格必需**吗」

- `privacy-data-lifecycle.12`（arXiv `2603.26354`，*Only What's Necessary: Pareto Optimal Data Minimization*）：
  > GDPR 要求个人数据**限于特定处理目的所严格必需的范围**（`limited to what is strictly necessary for a specified processing purpose`）；
  > 该文提出 **Pareto 最优数据最小化**的 privacy-by-design 框架。

- `privacy-data-lifecycle.15`（arXiv `2607.20190`，*Multiparty Session Types for GDPR Purpose Compliance*）：
  > **目的限制（purpose limitation）是 GDPR 的根本约束**：个人数据必须**按明确声明的目的**收集、存储、处理；
  > 系统不仅要在**声明**目的上合规，还要确保**运行时行为与声明的目的保持一致**；
  > 原文点名现状：实践中目的常被当成**与系统行为脱钩的非正式声明**。

⇒ ⭐ **对我们的两条硬判据**：
1. **「存 / 取 / 用 / 展示 / 导出」每一段**都必须能回答「**这一步对当前目的是严格必需的吗**」—— 答不上来 ⇒ 这段不该存在。
   （注意：这**恰好**印证 81 号 §三 的「按敏感值的生命周期切，而不是按字段切」—— 字段是静态的，**必要性是按段判的**。）
2. ⭐ **运行时一致性检查**：声明的目的必须**与运行时行为对齐**。⇒
   ⇒ **分级表如果只是文档，它就只是文档** —— 需要在**每次取/用敏感值时校验它所属的目的**。
   ⇒ 这条与 84 号 §八 的「分级表要能机检」**完全同构**，而且更具体：**校验点 = 取/用两段**（这正是 81 号 §三 指出的「我们此前完全没写取、用两段」）。

### 3.2 「可导出」不等于「数据主体能真的用起来」

- `privacy-data-lifecycle.7`（arXiv `2305.03471`）：数据主体访问请求（DSAR）**至今仍主要靠手工执行**，`has so far only seen marginal technical reflection`。
- `privacy-data-lifecycle.8`（arXiv `2407.04470`）：即使拿到数据，**「实际使用它们的可能性严重受限」**（`severely limited so far`）。

⇒ ⭐ 对我们「可导出」这条承诺的**收紧**：
**光能导出不够，导出物要能被用户/工具真正用起来** ⇒
导出物至少要满足：① **机器可读**（不是二进制 dump）② **带语义**（字段含义/时间/来源可解释）③ **不依赖我们的服务端**才能读懂。
⇒ 这三条正好是「个人数据永不入库」读法 B 里「可导出」三个字的**可验收展开**。

### 3.3 一记反面教训：加密方案不是「用了就安全」

`privacy-data-lifecycle.14`（arXiv `2606.20760`）：公有账本的「完全透明」与「数据最小化」存在张力；**ZKP 提供理论解，但现有构造常忽略对抗约束**（链下证明生成与链上提交的异步解耦 ⇒ 引入抢跑与证明复用风险）。

⇒ ⇒ **这一条与 §一 配套使用**：既然「本地加密」连**文献证据都没有**，那么**将来若有人提它**，也要连带问「**这个方案的攻击面是什么**」（别把「上了密码学」当成隐私已解决）。
