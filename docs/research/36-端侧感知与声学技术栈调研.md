## §一 结论摘要

> 本节为阶段性结论，§二~§十 落盘后同步修订。**所有结论的证据 URL / 文件路径+行号见各章。**

1. **Opus 链路没有未知的黑盒**：官方协议（设备↔App↔后端）已经把 Opus 帧格式定死为 `[Type=0x01][4B 大端长度][裸 opus 包]`，官方 iOS App 已有可运行的「PCM→Opus→WS→播放」参考实现。**TTS 直出 opus → ESP32 播放在协议层完全可行**，缺的是设备端解码分支（被官方注释掉）和后端 TTS 接入点。
2. **设备端 Opus 解码器不需要自研**：官方固件已依赖 Espressif 官方组件 `espressif/esp_codec_dev`（含 Opus 解码器 `esp_opus_dec`），xiaozhi 侧亦然。**复用成本 ≈ 0**，只需把注释分支接通。
3. **唤醒词不必自造模型**：官方固件 `sdkconfig.defaults` 已开 `CONFIG_SR_WN_WN9_HISTACKCHAN_TTS3=y`，且 xiaozhi 依赖 `espressif/esp-sr ~2.3.0`——**「HiStackChan」唤醒词模型已在官方构建里**。
4. **esp-sr / esp_codec_dev / bmi270_sensor 三件套都已在官方依赖树内**（xiaozhi `idf_component.yml`），复用不引入新的供应链。
5. **必须自造**：摄像头行为理解（视线/在场/多人）、IMU 语义化（被拿起/被拍打）、设备侧情绪声学特征——这三项**没有现成开源栈可直接套用**，需在上述信号之上自造算法层。
6. **iPhone 端是感知主力**：MediaPipe Tasks / Apple Vision / AVFoundation 在设备端做「人脸朝向、是否在看屏幕、眨眼、多人、离开/返回」成本极低且延迟可接受；ESP32-S3 上的 0.3MP 摄像头做同样的事不现实。
7. **ESP32-S3 上做不到的**：连续大模型推理、多目标人脸跟踪、声纹级说话人识别（受 8MB PSRAM 与无 NPU 限制）。
8. **Opus 容器格式有两条**：xiaozhi 语音面走 **OGG 容器**（OpusHead+OpusTags 必须存在，否则整包丢弃）；StackChan 自建控制面走**裸 opus 包**。两者不能混用。
9. **官方 SFX 已证明 OGG-Opus 路线可行**：`firmware/main/assets/sfx/convert_cmd.sh` = `ffmpeg -i xxx.mp3 -c:a libopus -b:a 24k -ar 16000 xxx.ogg`。
10. **设备板级采样率是 24 kHz**（`firmware/main/hal/board/config.h:9-10`），与 xiaozhi 语音面的 16 kHz **不是同一套**，自研协议层必须显式对齐。

| 接入方式 | ESP-IDF Component Manager（`idf_component.yml` 声明），**无需手工 CMake** | 同上 |
| 是否已在官方构建内 | **是**。官方固件 `sdkconfig.defaults` 已开 `CONFIG_SR_WN_WN9_HISTACKCHAN_TTS3=y` | `firmware/sdkconfig.defaults`（origin/main @ eff0d6b） |
| 模型来源 | esp-sr 组件自带 `model/` 目录；xiaozhi 用 `find_component_by_pattern("espressif__esp-sr" ...)` 定位并以 `--esp_sr_model_path` 传给模型转换工具 | `firmware/xiaozhi-esp32/main/CMakeLists.txt:943-946, 1019` |

**可替代自造的**：唤醒词模型训练与量化、AFE 前端（VAD+AEC+降噪+唤醒）整条流水线。**采用决策：复用。**
理由——唤醒词模型是官方资产（`WN9_HISTACKCHAN_TTS3`），自研的识别率与误唤醒率不可能优于官方在同一 SoC 上调优过的模型；而 ESP32-S3 8MB PSRAM 也没有余量再塞一套自训模型。

**注意**：`CONFIG_SR_WN_WN9_HISTACKCHAN_TTS3` 这一 Kconfig 项在官方 firmware 仓库内**没有对应的模型文件**（`git ls-tree -r origin/main -- 'firmware/*'` 中无 `.tflite`/`.nb`/srmodel 文件）。模型来源推测为 esp-sr 组件自身或构建期拉取——**此项标记为未取得，见 §十**。

## §六 ⭐ Opus 链路专项

> 本章是本轮调研的最大未知数项。结论：**协议层无黑盒，格式已被官方三方（固件 / server / App）共同锁定；缺的是设备端被注释掉的解码分支，以及后端 TTS 的接入点。**

### 6.1 官方协议的三方一致定义

**（a）官方 server 的二进制帧格式（权威定义）**
`server/README.MD:931-937`（origin/main @ eff0d6b）：

```text
1 byte  : msgType
4 bytes : payload length (big endian)
N bytes : payload
```

`server/README.MD:943` 消息类型表：`| 0x01 | Opus | Audio frame |`。

`server/internal/web_socket/web_socket.go:29-63` 常量表：`Opus byte = 0x01`。

**（b）Go 实现的收发两处，严格校验长度**
`server/internal/web_socket/web_socket.go:308-324`：

```go
func parseBinaryMessage(ctx context.Context, msg *[]byte) (byte, int, []byte, bool) {
	if len(*msg) < 1+4 { ... return 0, 0, nil, false }
	msgType := (*msg)[0]
	dataLen := int(binary.BigEndian.Uint32((*msg)[1:5]))
	payload := (*msg)[5 : 5+dataLen]
	if len(*msg)-5 != dataLen { ... return 0, 0, nil, false }
	return msgType, dataLen, payload, true
}
```

`server/internal/web_socket/web_socket.go:820-834` `createMessage` 为完全对称的封装。

**（c）App → 设备 的 Opus 转发（剥 MAC）**
`server/internal/web_socket/web_socket.go:523-536`：

```go
case Opus:
    if payload == nil || len(payload) < 12 { ...return }
    macAddrBytes := payload[:12]
    data := payload[12:]
    macAddr := string(macAddrBytes)
    newMsg := createMessage(msgType, data)          // ← 重新封成 [0x01][len][opus]
    stackChanClient := getStackChanClient(macAddr)
    if stackChanClient != nil { stackChanSendMessage(ctx, stackChanClient, messageType, newMsg) }
```

**（d）设备 → App 的 Opus 转发**
`server/internal/web_socket/web_socket.go:417-435`：设备来的 Opus 按订阅列表转发给 App 订阅者。

### 6.2 设备端接收分支：确认为死代码

`firmware/main/hal/hal_ws_avatar.cpp`（origin/main @ eff0d6b）：

- `:49-71` —— 枚举存在，`Opus = 0x01`（`Opus` 在 `:50`）。
- `:211-220` —— **case 被完整注释掉**：

```cpp
switch (type) {
    // Opus handled in OnData Fast Path
    // case DataType::Opus: {
    //     if (msg.data.size() > 5) {
    //         auto packet = std::make_unique<AudioStreamPacket>();
    //         packet->payload.assign(msg.data.begin() + 5, msg.data.end());
    //         _audio_service.PushPacketToDecodeQueue(std::move(packet));
    //     }
    //     break;
    // }
```

- `:132-135` —— `OnData` 回调**只是入队**（`_msg_queue.push`），并无所谓 "Fast Path"；`:176-190` `processMessages()` → `:192` `handleMessage()` 是唯一消费路径。**注释里说的 "OnData Fast Path" 在本版本中不存在。**
- 全仓库检索：`PushPacketToDecodeQueue` / `AudioStreamPacket` / `_audio_service` 在 `firmware/**` 中**只出现在这段注释里**（`git grep -n 'PushPacketToDecodeQueue\|AudioStreamPacket\|_audio_service' origin/main -- 'firmware/*'`）——即官方 StackChan 固件**连音频服务对象都没有**，这是从 xiaozhi 移植时留下的残骸。

**➡ 结论（可直接写进实现方案）**：设备端 Opus 接收帧格式 = `[0x01][4B 大端 payload 长度][裸 opus 包字节]`，
payload 起点 = `msg.data.begin() + 5`（与注释代码一致），**不是 OGG 容器**。

**（d）⚠ 板级采样率不一致（自研协议必须处理）**

| 位置 | 输入采样率 | 输出采样率 |
| --- | --- | --- |
| 官方 StackChan 固件 | `AUDIO_INPUT_SAMPLE_RATE 24000` | `AUDIO_OUTPUT_SAMPLE_RATE 24000` | 
| 证据 | `firmware/main/hal/board/config.h:9-10` | 同 |

**➡ 关键可行性结论**：
官方 App 已经实现了一条 **「实时 PCM → Opus(16k/mono/voip/20ms) → WS 二进制帧 → 远端播放」** 的完整通路。

**协议层零改造，只需写设备端那个被注释掉的 case + 后端 TTS 桥接。**

### 6.5 「TTS 直出 opus」的真实约束与未解项

| 问题 | 状态 | 证据 / 缺口 |
| --- | --- | --- |
| 设备端能否吃 MiniMax 原始 opus？ | **取决于 MiniMax 返回的是 OGG 还是裸包** | 未取得 MiniMax TTS 接口文档原文（见 §十） |
| OGG 路线可行？ | **可行，官方 SFX 已是 OGG-Opus @16k/24kbps** | `firmware/main/assets/sfx/convert_cmd.sh:1` |
| 裸包路线可行？ | **可行，但需保证帧长/采样率与解码器配置一致**（16k mono 20ms 或 60ms 均可，只要 `self_delimited=false` 且非自界定帧） | `main/audio/audio_service.cc:16-23` |
| 裸包路线的坑 | `esp_opus_dec` 打开时 `.sample_rate` 固定为板级输出采样率，**与 TTS 实际采样率不匹配会导致变调/降速** | `main/audio/audio_service.cc:67` |
| 最小改动方案 | 走 OGG：后端把 TTS opus 包成 OGG（OpusHead + OpusTags + 包），设备复用 `OggDemuxer` → `esp_opus_dec`，**与 xiaozhi 语音面完全同构**，零协议分歧 | `main/audio/demuxer/ogg_demuxer.cc:269-274`；`main/audio/audio_service.cc:646-668` |
| 官方 `opus_demo` 示例位置 | **未取得**（本次未定位到具体文件；xiaozhi 内未见 opus_demo 目录） | 见 §十 |

### 6.6 §六 行动清单（可直接拆任务）

1. **设备端**：在自研协议层新建 opus 分支，帧格式 `[0x01][4B BE len][裸 opus]`，或 `[0x01][len][OGG 字节流]` 二选一；解码器复用 `esp_opus_dec`（`esp_codec_dev` 已依赖）。
2. **设备端**：补一个「解码输出 → 24 kHz → I2S」的播放任务（官方固件**没有**这个任务，需新写；xiaozhi 的 `AudioService::OpusCodecTask` 可作模板，见 `main/audio/README.md:40-56, 69-83`）。
3. **后端**：MiniMax TTS → opus → 封帧 → 推设备；或 TTS → PCM → ffmpeg/libopus 现场编码（一致性更好，代价是 ~50ms 编码延迟）。
4. **对齐**：设备端 24 kHz 与 App/编码侧 16 kHz 的重采样点必须显式确定（建议整链统一 16 kHz，设备端再上采样到 24 kHz 给 I2S）。
