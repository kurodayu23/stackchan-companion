### 3.4 `78/xiaozhi-esp32` — 我们正在用的官方语音栈（D/E）

- **实测依据**：GitHub API 实测 **31805★ / 7436 forks**，MIT，默认分支 `main`，2026-10-23 仍在 push，171 个 release 变体；本地 `StackChan2/firmware/xiaozhi-esp32/main/` 即其源码（`application.cc` 43KB、`mcp_server.cc` 22KB、`ota.cc` 22KB、`assets.cc` 34KB、138 板卡目录含 CoreS3）。

- **⭐ 可复用方案**：`assets.cc` 里的 **A/B 资源槽机制**（`ASSET_SLOT_LABELS = {"assets_a","assets_b"}`）+ `AssetSlotMetadata{ magic, version, active_slot, sequence, image_size, sha256[32], asset_version, crc32 }` = **官方自己给出的"资源可热更新 + 回滚"设计**。

- **⭐ 落地**：**M8 SERVER_URL / M8 联网**。
- ⭐ **实测发现的矛盾（须在 M8 解决）**：本地 `StackChan2/firmware/partitions.csv` 只有**一个** 4MB 的 `assets, data, spiffs, 0xA00000, 4M` 分区，**没有 `assets_a` / `assets_b` 两个槽**；而 `assets.cc:43` 却按两个槽写死。→ 这正是 M8「分区表 assets_a/b 各 3MB → 恢复图标」的落点：**分区表必须与 `assets.cc` 的槽位命名对齐**，否则开机读不到资源。

### 3.5 `lvgl/lvgl` — 渲染预算的权威依据（A）⭐⭐

- **一句话**：官方固件用的 UI 框架本体；也是我们"动效按渲染成本分级"的量化标尺。
- **实测依据**（README 原话）：
  - 「For a *typical* UI, you need only **~100kB RAM, ~200–300kB flash, and a buffer size of 1/10 of the screen** for rendering.」
  - 「At a bare minimum needs only **32kB RAM and 128kB Flash**, a frame buffer, and at least a **1/10 screen-sized buffer** for rendering.」
  - 局部刷新示例：`lv_display_set_buffers(display, buf, NULL, sizeof(buf), LV_DISPLAY_RENDER_MODE_PARTIAL);`
- **许可**：MIT（API 实测），24990★ / 4408 forks，默认分支 `master`。
- **硬件门槛（换算到我们这块板）**：
  - 320×240 的 **1/10 屏缓冲 = 7680 px**。RGB565 下 **15 KB**；放 PSRAM 即可。
  - **双缓冲 = 30 KB**。按 `19-设计底线` §4.2「双缓冲代价高，尽量单缓冲 + 只重绘变化区域」→ **我们选 1/10 屏单缓冲（15KB，PSRAM）**。
  - 全屏 RGB565 双缓冲 = 320×240×2×2 = **307 KB** → 放得进 8MB PSRAM，但没必要。
- **⭐ 可复用方案**：**`LV_DISPLAY_RENDER_MODE_PARTIAL` + 1/10 屏缓冲**。这是"脸部区域 paint 级动效、其余区域 composite 级"的物理前提：脸部以外的任何变化都不该触发整屏重绘。
- **采用决策**：**复用（已是基线）**。理由：我们不改 UI 框架；我们只改**用它的方式**（动效分级）。
- **⭐ 落地**：**M8 分区表**（PSRAM 分配）；**M2/M3 情感**（脸部独立对象 + 脏矩形刷新）。

### 4.4 ⭐ 结论与我们的表情资产策略

1. **默认路线：程序化表情（官方路线），位图只做装饰器。**
   官方固件已证明这条路可行且省 Flash：6 个参数化情绪 + 5 个装饰器位图（130.9 KB）。
   → **我们 M2/M3 新增情绪时，优先扩 `Emotion` 枚举 + 参数表，而不是加 PNG。**
2. **若必须用位图表情（我们自己的角色），统一走「64 色调色板 PNG」。**
   → 300 张 @64px = **303 KB**，只占 4MB 分区的 7.6%；16 色可再降到 238 KB。
   → 保留 alpha（调色板 + tRNS），禁用 WebP（LVGL 无解码器）、禁用 JPEG（丢 alpha）。
3. **GIF 一律不用**（21.7 MB @300 张，且单张解码量 = 41 张 PNG）。动效用「多张静态 PNG + 关键帧切换」实现，**这与官方 `animation.h` 的关键帧模型天然吻合**。
4. **背景图用裸 RGB565**（官方 assets-generator 就这么做：「带 64 字节的 header，内容为 `lv_image_dsc_t`」），320×240 = **150 KB**，零解码。
5. **热表情（idle / 眨眼 / 说话嘴型）用裸 RGB565 常驻 PSRAM**；冷表情（情绪切换时偶发）用 PNG 存分区、按需解码 → **符合 4.2「优先降级技术而非删掉动效」**：不是砍掉动效，是换个更便宜的技术实现。
6. ⚠️ **本轮未测**：MCU 上真实的 PNG 解码耗时、LVGL 各配置的 Flash 占用实测、assets 分区实际剩余容量（需刷机后读 `spi_flash_mmap_get_free_pages` 日志）。

## 六、明确不采用的（写清原因）

| 项目 | 不采用原因 |
|---|---|
| **WebP 表情格式** | ⭐ **LVGL 无内置 WebP 解码器**（实测：无 decoder）。要支持就得自己引 libwebp，Flash + CPU 都不划算。实测 WebP lossless 只比 PNG 调色板小一点（64px：454.6 KB vs 303.1 KB @300 张） |
| **JPEG 表情** | ❌ **丢 alpha**（表情必须有透明背景）。虽然 M5GFX 自带 TjpgDec 且 ESP32-S3 有硬件 JPEG 解码器（解码最便宜），但透明是硬需求 → **背景可以用 JPEG 试，表情不行** |
| **GIF 表情（任何尺寸）** | ❌ 实测 64px GIF 单张 73.95 KB → **300 张 = 21.7 MB**（16MB Flash 的 1.36 倍）；仅 21 张就吃掉 4MB 分区的 38%。且 41 帧 GIF 的解码量 ≈ 41 张 PNG。**三组独立证据**（官方 noto-emoji 组 / fairy-stackchan 的「2 个 GIF ≈ 2MB」/ 我们的 GIF 实测）指向同一结论 |
| **全屏 GIF 皮肤路线**（fairy-stackchan 的 `Fairy` 皮肤） | ❌ 同上，Flash 不可行。**但"双皮肤切换机制"可抄**（M8/M2-1） |
| **PWM / LEDC / PCA9685 舵机方案** | ❌ ⭐ **前提错误**：我们的舵机是 **Feetech SCS0009 半双工串行总线舵机**，不是 PWM 舵机。本地 `main/hal/hal_servo.cpp:16` 实测 `static SCSCL _scs_bus;`，用 `WritePos/ReadPos/ReadMove/EnableTorque/WritePWM`。官方 HAL 已经能用，**引入任何 PWM 舵机库都是错的** |
| **`ros2_control` / micro-ROS**（`rostack-chan`） | ❌ Ubuntu 22.04 + ROS2 + Docker 专有；README 自承「micro-ROS の関係上、S3・C3 系のビルドが通らない可能性があります」；本机 Windows 跑不了；2023-08 后停更。仅作舵机型号佐证 |
| **Moddable XS 栈**（`stack-chan/stack-chan` 本体） | ❌ 会推翻我们 M5/M6/M8 全线（我们要保留官方 xiaozhi 语音栈与 ESP-IDF）。**只借鉴"用参数描述脸"与"Web 仿真器"两点** |
| **「300+ 官方 PNG 表情资产」这个前提** | ❌ **未在任何官方来源证实**。官方 v1.5.1 实测是「6 个参数化情绪 + 5 个装饰器位图（130.9 KB）」；官方 assets 工具的预设表情集**只有 21 张**。→ 我们的压缩方案要按「我们自己新增的表情」来做，不是按 300+ 来做 |
| **sherpa-onnx 跑在设备端** | ❌ 设备端 16MB Flash 放不下 ONNX 模型（**未实测具体占用**），且 ESP32-S3 不在 sherpa-onnx README 的目标矩阵内。**放服务端** |
| **`lvgl/lv_port_esp32` 作为依赖引入** | ❌ 会与官方固件自带的 LVGL 配置冲突。**只借鉴它的 `manifests/` 组织方式** |
| **`lvgl/lv_port_esp32` 的 ESP-IDF v6.x 路径** | ❌ 本机是 v5.5.4（`D:\idf`），用 README 里的 v5.x 命令：`$ . /path/to/esp-idf/export.sh` → Windows 下用 `export.ps1` |
| **`esp-lottie` / SVG / Rive 表情** | ❌ `espressif/esp-lottie` 仓库路径本轮 404（未取得）；SVG/Rive 在 ESP32-S3 上的渲染成本远超「禁 layout 级动画 + paint 仅限脸部」的预算。**且官方脸已经是程序化绘制，不需要矢量动画引擎** |
| **上游代码对外再分发** | ❌ ⚠️ **实测：`m5stack/StackChan` 根目录没有 LICENSE 文件（main/master 两分支都 404），API `license.spdx_id = null`**。→ 我们只在自己设备上用；对外只发自己的 patch/脚本/文档。**这也是为什么 M8-11「独立仓库 + patch」是必须的** |
| **`fairy-stackchan` 的 Fairy 表情素材** | ❌ README 明写「**个人非商业使用**」+「版权属原版权方」。**代码 MIT，素材不可用** |
| **任何布局级动画**（改 size/position 触发布局重排） | ❌ 违反 `19-设计底线` F11；320×240 上改 width/height 会触发整屏重绘，比 iOS 贵得多。**替代方案：两个预渲染位图切换**（正是 `animation.h` 的关键帧模型） |
| **表情区以外的持续动效** | ❌ 违反 F12「单屏持续动效 ≤1 处」。**唯一允许的持续动效 = 小栈的脸**（脸部是 paint 级；其余一律 composite 级：移动已有位图 / 改已有矩形位置） |
| **用圆环/进度环表达养成数值** | ❌ 宪法 R18（圆环 = 完成度 = KPI 面）；设备端禁用 |
| **全屏模糊/glow/渐变装饰** | ❌ 宪法 F13 / F17；LCD 屏上模糊是帧率杀手 |
| **ESP-NOW 遥控与联网并发** | ❌ `ronron-gh/AI_StackChan_Ex` 实测「ESP-NOW 使用中は Wi-Fi 接続が切断されます」→ 我们的三区触摸/遥控走 ESP-NOW 时必须避开联网窗口 |

### 7.3 ⭐ `i41-eu/i41eu-StackChan` —— 唯一值得抄的 fork（README 原话）

- **一句话**：给 StackChan 加「**Embody Mode**」，让机器人成为**家里服务器的轻客户端**，local first / privacy first。
- **实测依据**（README 原话）：
  - 「**Embody Mode: your StackChan becomes the body of many apps, local first and privacy first.**」
  - 「**One click to set up:** plug the robot in over USB and open [m.i41.eu](https://m.i41.eu) in Chrome or Edge.」
  - 「**Your own home server:** run the apps and the manager on a computer at home, so the **camera, microphone and sensors stay on your network**.」
  - 「**Encrypted camera and microphone:** end-to-end encryption to the browsers you pair with the robot's QR code; they stream only while you watch or listen, with a LIVE badge on the screen.」
  - 「**Branches:** `embody` (ours, the default) and `main` (upstream's, as it is). `embody` is based on upstream's 1b57655 … To sync: `git remote add upstream https://github.com/m5stack/StackChan.git`, `git fetch upstream`, then `git merge upstream/main` into `embody`.」
  - 「**Upstream: Embody Mode is meant to be offered to upstream as an official mode (an app of the launcher), so its changes are kept apart in a few commits on top of upstream.**」
  - 「**The owner rebuilds each release to the same bytes and signs its `SHA256SUMS`**」
  - 「**License:** MIT, as upstream (M5Stack's copyright kept, [firmware/LICENSE](firmware/LICENSE)).」← ⚠️ **它自称上游是 MIT 并自带 `firmware/LICENSE`；我们实测上游根目录无 LICENSE（404）** → 二者矛盾，**以我们的实测为准：上游无许可**。
- **许可**：fork 自称 MIT（自带 LICENSE）；**上游无许可**。
- **硬件门槛**：CoreS3 + 舵机（我们的机器）。
- **⭐ 可复用方案（五条，全部直接落我们的改造点）**：
  1. ⭐⭐ **「改动集中在少数 commit + 独立分支 + 明确 sync 流程」** —— 这是「外科式改造」最干净的范式。我们的 M8-11 照抄。
  2. ⭐⭐ **「机器人 = 家里服务器的轻客户端，摄像头/麦克风数据不出网」** —— 我们的 M8 SERVER_URL + M1/M9 记忆「本地优先」的定位由此有了现成范式。
  3. ⭐ **「USB + 浏览器一键配置」** —— 与 `stackchan-atama` 的 USB CDC 通道同构 → M6-3。
  4. ⭐ **「QR 配对 + 端到端加密的摄像头/麦克风」** → M7 iOS 侧。
  5. ⭐ **「可复现构建 + SHA256SUMS 签名」** → M8-12。
- **采用决策**：**复用（范式，不引代码）**。理由：它的目标与我们不同（做通用平台 vs 做陪伴产品），但**工程纪律**（分支纪律、sync 流程、可复现构建、local-first 定位）是我们 M1/M9 最缺的。
- **⭐ 落地**：**M1/M9 记忆（local-first 定位）**；**M8（分支纪律 + 可复现构建）**；**M6（USB 一键配置）**；**M7 iOS（QR 配对 + 加密流）**。

### 7.5 ⭐ 生态结论（3 条）

1. ⭐⭐ **StackChan 的 fork 生态是「量大、质低」的：395 个 fork 里，独立分支只有 1 个，有独立 README 的只有 1 个，有 star 的只有 3 个。**
   → **对我们的含义：没有可直接抄的社区实现**。我们必须自己承担 M8/M6/M5 的集成工作，**不能指望"社区已经做过了"**。
2. ⭐⭐ **fork 的真实成本几乎全在二进制资源上（增量 2.8–21.7 MB），不在代码上。**
   → **对我们的含义：Flash/资源体积预算就是我们的第一工程约束**（这与 §四 的压缩结论、与 M8-3 的「3MB 槽位」算术是同一件事的三个侧面）。
3. ⭐⭐ **「不改上游、只加一个 app」的分支纪律，是生态里唯一被验证可长期维护的做法（`i41-eu`）。**
   → **对我们的含义：M8 必须走「独立仓库 + patch + 明确 sync 流程」**，不要直接在官方树里改。这同时解决了「上游无许可证，不能再分发」的法律问题。

## 十、本轮结论一句话汇总

> **StackChan 的开源生态没有现成答案可抄**（395 fork 里只有 1 个有分支纪律、3 个有 star）；
> **真正的工程约束不是代码，是 Flash**（社区 fork 的真实成本是 2.8–21.7 MB 的二进制资源，官方表情是程序化绘制而非 PNG）；
> **官方 v1.5.1 已经给了我们最值钱的三样东西**：程序化表情 + 统一关键帧（眼/嘴/舵机/灯色）+ 表情引擎 6 情绪枚举；
> **我们的 M8 应该做的是「对齐官方已有的 A/B 资源槽契约 + 走 patch 分支纪律 + 把 assets 槽放大到 ≥3MB」，而不是重造资源管线。**
