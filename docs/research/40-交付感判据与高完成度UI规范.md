## §一 结论摘要：交付感 = 哪几件事

1. **质感不是颜色，是"一致性 + 完成度"**。交付感 ≈ 一致性 × 完成度，二者相乘，任一为 0 则整体为 0。
2. **动效只有一套**：一个曲线家族 + 一张时长阶梯表 + 高频路径不加动效。
3. **每个数据位都有状态**：加载 / 空 / 错误 / 离线 / 权限拒绝 / 首次 / 设备不在线，7 态齐备才算做完。
4. **排版是一张阶梯表**：只用 iOS 11 档系统 text style，字重只有 3 档。
5. **图标是一套网格**：尺寸 / 细节度 / 笔触粗细 / 透视 4 项全一致。
6. **色彩只有一条主线**：系统色优先；强调色只给主操作，且只给一处背景。
7. **间距是一套 scale**：所有间距出自同一张 4pt 栅格表。
8. **触感与动作一一对应**：同一语义永远同一 haptic 类型。
9. **可见即可用**：屏幕上没有一个点了没反应的元素。
10. **首屏有预算**：首帧与可交互时间有明确上限，超预算即不合格。
11. **四种适配全过**：动态字体 / 深色模式 / 减弱动效 / 增强对比。
12. **主次靠折叠实现，不靠堆功能**：一级可见元素有硬上限，次要功能一律进 More 菜单 / 长按 / 搜索 / 通知。

> **最核心的 3 条**（若只能改 3 件事）：① **状态完整性**（7 态齐备）→ 决定「像没做完」；② **折叠与一级元素上限** → 决定「杂乱」；③ **动效/间距/图标的一致性** → 决定「有没有质感」。

### 2.1 动效统一性 —— 一个曲线家族、一张时长阶梯、减弱的数量

**规则**
全 App 只允许存在**一个动画曲线家族**和**一张时长阶梯表**；任何不在表内的动效时长即视为破规范。

**量化参数**〔项目自定〕

| 档位 | 用途 | 时长 | 曲线 |
|---|---|---|---|
| T0 反馈 | 按下态、开关切换、勾选 | 0.10–0.15 s | `spring(response:0.25, dampingFraction:0.9)` |
| T1 元素级 | 元素出现/消失、图标替换、展开行 | 0.20 s | 同上 |
| T2 页面级 | push / pop 转场、Tab 切换 | 0.30 s | `spring(response:0.35, dampingFraction:1.0)` |
| T3 布局级 | 分段切换、Sheet 展开、折叠区 | 0.35–0.40 s | 同上 |
| T4 循环 | 呼吸/待机/加载指示 | 1.5–2.0 s / 周期 | `easeInOut` 往返 |

- **曲线家族数量上限 = 2**（交互反馈 + 线性循环）。超出即破规范。
- **时长档位数量上限 = 5**。
- **同时运动的元素数量 ≤ 3**（屏幕上不得有 4 个以上元素各自独立运动）。
- **高频路径动效豁免**：Tab 切换、列表滚动、输入框聚焦这三类高频交互**不加自定义转场动效**，用系统默认。
- **减弱动效（Reduce Motion）**：开启后，位移类动画一律替换为 fade，时长压到 ≤ 0.20 s，弹簧 bounce 归零。

**验收方法**
1. 导出全部动画参数（代码搜 `withAnimation` / `Animation` / `transition` / `duration`），把每处时长归入上表 5 档之一。**出现表外时长 → 不过**。
2. 统计不同缓动函数种类（`.easeInOut` / `.linear` / `.spring` / 自定义）。**> 2 种曲线家族 → 不过**。
3. 录屏逐帧数"同一时刻运动的元素数"，峰值 **> 3 → 不过**。
4. 设置 → 辅助功能 → 动态效果 → 减弱动态效果 打开，再走一遍全部转场：**仍有缩放/位移 → 不过**。

**依据**
- 〔HIG〕Motion："**Aim for brevity and precision in feedback animations.** When animated feedback is brief and precise, it tends to feel lightweight and unobtrusive, and it can often convey information more effectively than prominent animation."
  — https://developer.apple.com/design/human-interface-guidelines/motion.md
- 〔HIG〕Motion："**In apps, generally avoid adding motion to UI interactions that occur frequently.** The system already provides subtle animations for interactions with standard interface elements."
  — 同上
- 〔HIG〕Motion："**Let people cancel motion.** As much as possible, don't make people wait for an animation to complete before they can do anything, especially if they have to experience the animation more than once."
  — 同上
- 〔HIG〕Accessibility："When this setting is active, ensure your app or game responds by reducing automatic and repetitive animations, including zooming, scaling, and peripheral motion."，并列出替代做法："Tightening animation springs to reduce bounce effects / Tracking animations directly with people's gestures / Avoiding animating depth changes in z-axis layers / **Replacing transitions in x-, y-, and z-axes with fades to avoid motion** / Avoiding animating into and out of blurs"
  — https://developer.apple.com/design/human-interface-guidelines/accessibility.md
- ⚠️ **未取得**：HIG Motion 页**不提供任何时长数值表**（已逐字通读全文，无 duration 数字）。上表 5 档时长为〔项目自定〕，无 HIG 背书。

### 2.2 状态完整性 —— 7 个状态各自有设计

**规则**
App 中**每一个能取到数据的位点**，必须同时设计了 7 个状态；缺任一状态即视为"没做完"。

**量化参数**
必备状态清单（**7 个，缺一不可**）：

| # | 状态 | 必须包含 | 验收判定 |
|---|---|---|---|
| S1 | 加载中 | 骨架屏或占位符 + 进度指示器 | 不出现纯白/纯黑空白屏 |
| S2 | 空 | 标题 + 说明 + 引导动作 | 空态文案必须说明「为什么空」和「下一步做什么」 |
| S3 | 错误 | 人话描述 + 可执行的恢复按钮 | 必须有「重试」按钮，不能只有一句错误 |
| S4 | 离线/设备不在线 | 明确说明 + 降级可用内容 | **桌面机器人场景核心状态** |
| S5 | 权限被拒 | 解释用途 + 跳转系统设置的入口 | 必须有去设置的按钮 |
| S6 | 首次使用 | 引导 + 示例数据 + 一句话价值说明 | 空库时也要有可见内容 |
| S7 | 权限/能力受限 | 降级可用 + 说明缺什么 | 例如无摄像头时表情功能降级 |

- **加载中**：HIG 口径为「超过 a moment or two」才显示进度指示器 → **本项目阈值：请求发起后 300 ms 未返回才显示进度指示器**，300 ms 内不显示（避免闪烁）。
- **空态文案长度**：≤ 20 字（说明）+ ≤ 12 字（按钮）。
- **错误文案**：不得出现错误码、HTTP 状态、类名。

**验收方法**
1. 列出所有数据位点（列表、会话、设置项、设备状态、消息流），逐一对照 7 态清单打勾。**任一位点缺态 → 不过**。
2. 抓包把网络切到「超时 / 断网 / 403 / 500」四种，逐位点截图核对。
3. 拒绝一次麦克风/相机/蓝牙权限，进入 App 截图核对 S5。
4. 设备未配网/机器人离线状态下进入 App，核对 S4。
5. 全新安装、清空数据后首次启动，核对 S6。

**依据**
- 〔HIG〕Loading："**Show something as soon as possible.** ... Instead, consider showing placeholder text, graphics, or animations as content loads, replacing these elements as content becomes available."
- 〔HIG〕Loading："**Let people do other things in your app or game while they wait for content to load.**"
- 〔HIG〕Loading："**If loading takes an unavoidably long time, give people something interesting to view while they wait.** ... Gauge the remaining loading time as accurately as possible"
- 〔HIG〕Progress indicators："**Clearly communicate that content is loading and how long it might take to complete.** Ideally, content displays instantly, but for situations where loading takes more than a moment or two, you can use system-provided components — called *progress indicators*"
- 〔HIG〕Progress indicators："**Keep progress indicators moving so people know something is continuing to happen.** People tend to associate a stationary indicator with a stalled process or a frozen app."
- 〔HIG〕Feedback："**Show people when a command can't be carried out and help them understand why.**"
- 〔HIG〕Tab bars："**Don't disable or hide tab bar buttons, even when their content is unavailable.** ... If a section is empty, explain why its content is unavailable."
  — https://developer.apple.com/design/human-interface-guidelines/loading.md / progress-indicators.md / feedback.md / tab-bars.md

### 2.3 排版节奏 —— 字号阶梯、字重阶梯、行高、数字、截断

**规则**
全 App 只使用 **iOS 11 档系统 text style**、**3 档字重**；不得出现自造字号。

**量化参数**
〔HIG〕iOS / iPadOS Dynamic Type（Large / 默认档），来自 typography.md 规格表：

| Style | Weight | Size (pt) | Leading (pt) | Emphasized weight |
|---|---|---|---|---|
| Large Title | Regular | 34 | 41 | Bold |
| Title 1 | Regular | 28 | 34 | Bold |
| Title 2 | Regular | 22 | 28 | Bold |
| Title 3 | Regular | 20 | 25 | Semibold |
| Headline | Semibold | 17 | 22 | Semibold |
| Body | Regular | 17 | 22 | Semibold |
| Callout | Regular | 16 | 21 | Semibold |
| Subhead | Regular | 15 | 20 | Semibold |
| Footnote | Regular | 13 | 18 | Semibold |
| Caption 1 | Regular | 12 | 16 | Semibold |
| Caption 2 | Regular | 11 | 13 | Semibold |

- **字号种类上限 = 11 档**（HIG 全集），**本项目建议实际启用 ≤ 6 档**〔项目自定〕：Large Title 34 / Title 2 22 / Headline 17 / Body 17 / Subhead 15 / Caption 1 12。
- **字重阶梯 = 3 档**：Regular / Semibold / Bold。〔HIG〕emphasized weight 可为 medium / semibold / bold / heavy，本项目**禁用 Medium 与 Heavy**〔项目自定〕。
- **行高**：一律使用 text style 自带 leading，**不手动改 lineHeight**；正文行高 ≥ 1.29×字号（17→22 即 1.29）〔HIG 表格推算〕。
- **数字等宽**：所有会跳变的数字（电量、时长、计数、计时、传感器读数）必须用**等宽数字**（SF Mono / `.monospacedDigit()`），避免宽度跳动。
- **截断规则**〔项目自定〕：单行标签 → `tail` 截断；正文说明 → 最多 3 行后 `tail`；**禁止**中段截断；标题永不截断（改换行）。
- **中英混排**：中文正文与 SF Pro 混排时行高取 text style leading，不额外加 0。

**验收方法**
1. 抓 Design Tokens / 代码中的 `.font(...)`，统计不同 `.font` 组合数。**出现非上述 11 档之一 → 不过**。
2. 统计字重使用：出现 Medium / Heavy / Black → 不过。
3. 全局搜索 `lineHeight(`：存在手动行高 → 不过。
4. 播放一段会跳数的界面（电量/时间），录屏逐帧看数字宽度：**宽度变化 → 不过**。
5. 开启「超大字体」后遍历所有文案：**出现截断的正文说明（且不是设计上的 tail 截断）→ 不过**。

**依据**
- 〔HIG〕Typography："A *text style* specifies a combination of font weight, point size, and leading values for each text size."
- 〔HIG〕Typography 规格表："### iOS, iPadOS Dynamic Type sizes" — https://developer.apple.com/design/human-interface-guidelines/typography.md
- 〔HIG〕Typography："**Make sure text looks good and remains legible when people scale it.** Use a text style that makes the text look good at full scale, then test it for legibility at different scales."
- 〔HIG〕Typography："Variable fonts support *optical sizing* ... On all platforms, the system fonts support *dynamic optical sizes*"
- 〔HIG〕Typography："<doc://com.apple.documentation/documentation/Human-Interface-Guidelines/sf-symbols> provides a comprehensive library of symbols that integrate seamlessly with the San Francisco system font, automatically aligning with text in all weights and sizes."
- 〔HIG〕Layout："**Be prepared for text-size changes.** ... horizontally adjacent views may need to stack vertically to provide more space for text; table rows or other containers may need to grow in height so that text isn't cropped or doesn't overlap other content"

### 2.4 图标一致性 —— 网格、笔触、端点、圆角

**规则**
全 App 图标共享**同一套网格**与**同一笔触粗细**；与系统图标混用时，自定义图标必须对齐到 SF Symbols 的权重体系。

**量化参数**
- 〔HIG〕图标四一致项：**尺寸、细节层级、笔触粗细（weight）、透视方向**必须一致。
- 〔项目自定〕图标网格：**24×24 pt 画布**，图形主体占 **20×20 pt**（约 83%），四周留 2 pt；与文字对齐用光学对齐（底部基线对齐）。
- 〔项目自定〕描边宽度：**1.5 pt**（Regular 档），图标尺寸每翻一档描边不随之缩放（避免视觉变细）。
- 〔项目自定〕圆角：所有方形图标容器圆角统一 **12 pt**（iOS 连续曲率风格）；圆形图标容器用 **胶囊**。
- 〔项目自定〕图标与相邻文字：图标**视觉高度 = 文字 x-height 的 1.0–1.2 倍**，与相邻文字**字重对应**（Semibold 文字配 Semibold 图标）。
- 〔项目自定〕可点图标命中区 **≥ 44×44 pt**（图形可以更小，命中区不可）。
- 〔HIG〕文字类图标必须本地化（字符型图标必须随语言变化）。
- 〔HIG〕方向性图标必须提供 RTL 版本。

**验收方法**
1. 把所有图标导出叠到一张网格上（24×24，2 pt 步进）。**任何图形越出 20×20 安全框 → 不过**。
2. 放大到 400% 检查描边：**出现粗细不一 → 不过**。
3. 图标 + 文字并排截图，比较视觉字重：**图标明显更粗或更细 → 不过**。
4. 用 Accessibility Inspector 或 Xcode 调试器读每个图标的 frame：**命中区 < 44×44 pt → 不过**。
5. 切系统语言到阿拉伯语 / 希伯来语：**出现未镜像的方向图标 → 不过**。

**依据**
- 〔HIG〕Icons："**Maintain visual consistency across all interface icons in your app.** Whether you use only custom icons or mix custom and system-provided ones, all interface icons in your app need to use a consistent size, level of detail, stroke thickness (or weight), and perspective. Depending on the visual weight of an icon, you may need to adjust its dimensions to ensure that it appears visually consistent with other icons."
- 〔HIG〕Icons："**In general, match the weights of interface icons and adjacent text.** Unless you want to emphasize either the icons or the text, using the same weight for both gives your content a consistent appearance and level of emphasis."
- 〔HIG〕Icons："**If necessary, add padding to a custom interface icon to achieve optical alignment.**"
- 〔HIG〕Icons："An effective icon is a graphic asset that expresses a single concept in ways people instantly understand."
- 〔HIG〕Icons："**Include text in your design only when it's essential for conveying meaning.** ... If you need to display individual characters in your icon, be sure to localize them."
  — https://developer.apple.com/design/human-interface-guidelines/icons.md

### 2.5 色彩层级纪律 —— 中性阶数量、强调色只一处、分隔只一种手法

**规则**
**同一屏内被强调的视觉焦点不得超过 1 个**；分隔信息**只用一种手法**。

**量化参数**
- 〔项目自定〕中性色阶使用 **≤ 4 档**（如 label / secondaryLabel / tertiaryLabel / quaternaryLabel 对应的语义色），且**必须使用系统动态色**，不硬编码色值。
- 〔项目自定〕强调色（accent / tint）**每屏最多出现 1 处背景着色**；系统 HIG 明文："Refrain from adding color to the background of multiple controls."
- 〔项目自定〕同一屏内强调色着色的控件数 **≤ 1 个**（例如只有主按钮）。
- 〔项目自定〕分隔手法**同一屏只用 1 种**：分隔线 / 背景色块 / 阴影 / 留白，四选一。混用 ≥2 种 → 不过。
- 〔HIG〕自定义颜色必须提供 **light + dark + increased contrast 三套变体**；即使只发布单一外观，也必须提供 light/dark 两套。
- 〔HIG〕彩色背景下，toolbar / tab bar 应**单色化**（monochromatic）。
- 〔HIG〕同一颜色不得表达不同语义；系统动态色的语义不得重定义。

**验收方法**
1. 用取色器/Design Inspector 统计单屏出现的**不同色相数量**：彩色内容区 **≤ 2 个色相**（品牌色 + 内容色）〔项目自定〕。
2. 逐屏截图，圈出所有强调色着色的控件：**数量 > 1 → 不过**。
3. 逐屏记录分隔手法种类：**> 1 种 → 不过**。
4. 开「增强对比度」后逐屏复检：**对比度未升高 → 不过**（HIG 硬性要求）。
5. 浅色/深色/浅色+增强对比 三个模式截图并排：任一模式某元素"消失" → 不过。

**依据**
- 〔HIG〕Color："**Avoid using the same color to mean different things.** Use color consistently throughout your interface, especially when you use it to help communicate information like status or interactivity."
- 〔HIG〕Color："**Make sure all your app's colors work well in light, dark, and increased contrast contexts.** ... If you define a custom color, make sure to supply light and dark variants, and an increased contrast option for each variant that provides a significantly higher amount of visual differentiation."
- 〔HIG〕Color："**Avoid hard-coding system color values in your app.** Documented color values are for your reference during the app design process. The actual color values may fluctuate from release to release, based on a variety of environmental variables."
- 〔HIG〕Color："**Apply color sparingly to the Liquid Glass material, and to symbols or text on the material.** ... reserve it for elements that truly benefit from emphasis, such as status indicators or primary actions. To emphasize primary actions, apply color to the background rather than to symbols or text. ... **Refrain from adding color to the background of multiple controls.**"
- 〔HIG〕Color："**Avoid using similar colors in control labels if your app has a colorful background.** ... prefer a monochromatic appearance for toolbars and tab bars"
- 〔HIG〕Color："**Consider choosing a limited color palette that coordinates with your app logo.** Subtle use of color can help you communicate your brand while deferring to the content."
- 〔HIG〕Color："**Avoid redefining the semantic meanings of dynamic system colors.** ... don't use the *separator* color as a text color, or *secondary text label* color as a background color."
  — https://developer.apple.com/design/human-interface-guidelines/color.md

### 2.6 间距体系 —— 一套 scale

**规则**
全 App 所有间距、留白、内边距**只能取自同一张间距表**；出现表外数值即破规范。

**量化参数**〔项目自定，HIG 未规定 iOS 间距 scale〕
- 间距 scale（4 pt 栅格）：**2 / 4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 / 64**
- **屏幕左右安全边距 = 16 pt**（紧凑布局起点）
- **内容块之间 = 16 / 24 pt**；**内容块内部 = 8 / 12 pt**；**图标与文字 = 8 pt**
- **列表行高 = 44 pt 起**（与最小触控高度对齐）；行内图文左间距 16 pt
- **列表组之间 = 32 / 40 pt**（用分组间距而非分隔线，是"分隔只一种手法"的落地方式）
- **可点击区域间距**：有 bezel 的控件之间 ≥ 12 pt；无 bezel 的元素之间 ≥ 24 pt〔HIG〕
- **同一屏内"间距取值种类" ≤ 4 档**〔项目自定，防杂乱】

**验收方法**
1. 用 Xcode View Debugger 或 Figma 红线，把全 App 出现的间距值导出成集合。**集合中含 scale 外的值 → 不过**。
2. 同一屏内统计出现的不同间距值数量：**> 4 档 → 不过**。
3. Accessibility Inspector 逐控件读 frame，验证命中区 ≥ 44×44 pt 且相邻控件间距达标。
4. 对照"分隔只一种手法"：逐屏确认没有同时出现分隔线 + 阴影 + 背景色块。

**依据**
- 〔HIG〕Accessibility："**Consider spacing between controls as important as size.** Include enough padding between elements to reduce the chance that someone taps the wrong control. In general, it works well to add **about 12 points of padding around elements that include a bezel**. For elements without a bezel, **about 24 points of padding** works well around the element's visible edges."
- 〔HIG〕Buttons："As a general rule, a button needs a hit region of at least 44x44 pt"
- 〔HIG〕Layout："The system includes predefined layout guides that make it easy to apply standard margins around content and restrict the width of text for optimal readability."
- 〔HIG〕Layout："Respecting the safe area is essential to make sure system UI and hardware features like the Dynamic Island don't obstruct content and controls."
  — https://developer.apple.com/design/human-interface-guidelines/accessibility.md / buttons.md / layout.md

### 2.7 触感同步 —— 哪些动作配 haptic、用哪种、时机

**规则**
**每一类语义只对应一种 haptic**；同一个动作在任何页面触发同一种触感；无意义处一律不触发。

**量化参数**〔HIG 系统分类，全部可直接用 UIFeedbackGenerator 实现〕
| 语义 | haptic 类别 | 具体 pattern | 触发时机 |
|---|---|---|---|
| 操作成功（任务完成） | notification | `.success` | 动作真正完成、状态已落库 |
| 警告（可继续但不理想） | notification | `.warning` | 有风险但未失败（如电量低、对话超时前提醒） |
| 失败 | notification | `.error` | 动作失败且用户需改变行为 |
| 轻量反馈（吸附到位、选项切换） | impact | `.light` | 拖拽吸附、轻点切换 |
| 中等力度（模态出现、确认） | impact | `.medium` | Sheet 弹出、关键状态落定 |
| 重反馈（大件碰撞、机器人本体动作） | impact | `.heavy` | 机器人本体发生位移/机械动作 |
| 硬/脆质感 | impact | `.rigid` | 硬质开关、锁定 |
| 软质感 | impact | `.soft` | 柔性材质、软性回弹 |
| 值在变化 | selection | `.selection` | 滑杆、步进器、Tab 内切换（值变化时） |

- 〔HIG〕**短促 haptic 优先**：默认用 transient 类，不用 continuous。
- 〔HIG〕**haptic 必须可选**：能关掉，且关掉后功能不受影响。
- 〔项目自定〕**单次交互最多 1 个 haptic**；同时发 2 个 → 不过。
- 〔项目自定〕**同一次连续手势内最多 1 次**（如滚动列表不逐项触发 selection）。
- 〔HIG〕**haptic 与动画/音效强度要匹配**，并作为视觉反馈的补充而非替代。

**验收方法**
1. 列出手势 → haptic 映射表（一张表，穷举全部手势）。**同一手势在不同页面映射到不同 pattern → 不过**。
2. 关闭「系统触感」后走通全部主流程：**功能受影响 → 不过**（HIG 硬性）。
3. 录屏 + 录设备音频/触感日志，统计单次交互的 haptic 触发次数：**> 1 → 不过**。
4. 逐条核对语义映射是否符合上表（成功≠失败≠警告混用）。

**依据**
- 〔HIG〕Playing haptics："**Use system-provided haptic patterns according to their documented meanings.** ... If the documented use case for a pattern doesn't make sense in your app or game, avoid using the pattern to mean something else."
- 〔HIG〕Playing haptics："**Use haptics consistently throughout your app or game.** It's important to build a clear, causal relationship between each haptic and the action that causes it"
- 〔HIG〕Playing haptics："**Avoid overusing haptics.** ... Often, the best haptic experience is one that people may not be conscious of, but miss when it's turned off."
- 〔HIG〕Playing haptics："**In most apps, prefer playing short haptics that complement discrete events.**"
- 〔HIG〕Playing haptics："**Make haptics optional.** Let people turn off or mute haptics, and make sure people can still enjoy your app or game without them."
- 〔HIG〕Playing haptics："**Prefer using haptics to complement other feedback in your app or game.** ... you generally want to match the intensity and sharpness of a haptic with the intensity and sharpness of the animation it accompanies."
- 〔HIG〕Playing haptics（iOS 分类）：Notification = Success / Warning / Error；Impact = Light / Medium / Heavy / Rigid / Soft；Selection。
  — https://developer.apple.com/design/human-interface-guidelines/playing-haptics.md

### 2.8 无未接线元素 —— 可见即可用

**规则**
**屏幕上出现的每一个可点元素，要么真的能做它看起来该做的事，要么明确说明为什么现在不能做。**

**量化参数**
- 〔HIG〕"可见即可用"：**未接线的按钮数 = 0**。
- 〔HIG〕**不得禁用/隐藏 Tab Bar 按钮**，即使其内容不可用；空section 要解释原因。
- 〔项目自定〕不可用元素必须**可见但变暗（disabled）**，且**附一句原因**（tooltip / 说明文案 / alert）；禁止"点了没反应"。
- 〔项目自定〕占位内容（TODO、Lorem、"Coming soon"、示例假数据）**在 Release 构建中可见数 = 0**。
- 〔项目自定〕**所有图标按钮必须有 accessibilityLabel**，且 label 是可读的动词短语。

**验收方法**
1. 全 App 遍历所有可点元素，逐一实点。**无反应 → 不过**。
2. 走一遍所有"数据为空 / 权限被拒 / 设备离线"路径，确认按钮变暗**且有原因说明**。
3. Release 构建全局搜索 `TODO` / `FIXME` / `Coming soon` / `Lorem`：**有命中 → 不过**。
4. Accessibility Inspector 扫描：**存在空 accessibilityLabel 的可点元素 → 不过**。

**依据**
- 〔HIG〕Tab bars："**Don't disable or hide tab bar buttons, even when their content is unavailable.** Having tab bar buttons available in some cases but not others can make your app's interface appear unstable and unpredictable. If a section is empty, explain why its content is unavailable."
- 〔HIG〕Feedback："**Show people when a command can't be carried out and help them understand why.**"
- 〔HIG〕Menus："**Show people when a menu item is unavailable.** An unavailable menu item often appears dimmed and doesn't respond to interactions. If all of a menu's items are unavailable, the menu itself needs to remain available so people can open it and learn about the commands it contains."
  — https://developer.apple.com/design/human-interface-guidelines/tab-bars.md / feedback.md / menus.md

### 2.9 首帧 / 可交互时间预算

**规则**
App 启动后必须在预算内呈现**可交互的首屏**；启动屏不得用于掩盖慢加载。

**量化参数**〔项目自定，HIG 只给定性要求，未给数字〕
| 指标 | 预算 | 测量方式 |
|---|---|---|
| 冷启动 → 首帧可见 | ≤ 1.0 s | Instruments App Launch / MetricKit `AppLaunch` |
| 冷启动 → 可交互（可响应输入） | ≤ 1.5 s | Instruments / 冷启动后立即点主按钮，测量响应延迟 |
| 启动后 **3.0 s** 内必须出现**有意义内容**（非纯加载态） | ≤ 3.0 s | 录屏看第一帧非占位内容的时间 |
| 二次热启动（回到前台） | ≤ 0.3 s | Instruments |
| 关键路径网络请求（首屏数据） | P95 ≤ 800 ms | 自建埋点 |

- 〔HIG〕"**The best content-loading experience finishes before people become aware of it.**"
- 〔项目自定〕**超过预算的降级方案**：3 s 未拿到数据 → 显示"有意义的骨架 + 1 句说明"，而不是转圈。
- 〔项目自定〕**启动屏**：不超过 1 个 logo + 1 行字；不使用启动屏做品牌宣言页。

**验收方法**
1. 真机（不是模拟器）冷启动 ≥ 10 次，取中位数与最差值。**中位数超预算 → 不过**。
2. Instruments App Launch 模板跑一次，读取 "App Launch" 时间。
3. 弱网（Network Link Conditioner "3G"）下测 3 s 规则。
4. 切后台再切回前台，测热启动时间。

**依据**
- 〔HIG〕Loading："**The best content-loading experience finishes before people become aware of it.**"
- 〔HIG〕Loading："**Show something as soon as possible.**"
- 〔HIG〕Loading："**Improve installation and launch time by downloading large assets in the background.**"
- 〔HIG〕Launching（缓存页，2026-10-23 读取中断）— ⚠️ 见 §七「未取得」。
  — https://developer.apple.com/design/human-interface-guidelines/loading.md

### 2.10 边界与安全区 —— 刘海、灵动岛、Home Indicator、键盘

**规则**
**任何内容都不得被系统硬件或系统 UI 遮挡**；键盘出现时，正在编辑的内容必须可见。

**量化参数**
- 〔HIG〕必须尊重 **safe area**：灵动岛、状态栏、Home Indicator、toolbar、tab bar 覆盖区均排除。
- 〔项目自定〕**屏幕左右边距 = 16 pt**；**底部固定操作条**必须额外避开 Home Indicator 区域（使用 `safeAreaInset`）。
- 〔项目自定〕**键盘处理**：出现键盘时，输入框及其上下文（标签/错误提示）必须在键盘上方可见；使用 `keyboardLayoutGuide`；**不得手动猜键盘高度**。
- 〔项目自定〕**横竖屏**：竖屏必过；横屏在 iPhone 上若支持，必须同样遵守 safe area（若有横屏专属布局，需单独走查）。
- 〔HIG〕tvOS 安全区（作为量级参照）：上下 60 pt、左右 80 pt。
- 〔HIG〕visionOS：按钮中心间距 ≥ 60 pt。

**验收方法**
1. Xcode 打开 `debugViewHierarchy` 或 View Debugger，检查所有固定定位元素是否落在 safe area 内。
2. 真机刘海机型 + 灵动岛机型各截一张首屏：**有任何元素被切 → 不过**。
3. 每个输入框：点击后录屏，**输入框被键盘遮挡 → 不过**。
4. iPhone SE（3.375"）/ iPhone 16 Pro Max / iPad 各截一轮，**文字截断或元素重叠 → 不过**。
5. VoiceOver 开启后走主流程，确认元素不会因避开刘海而被推走。

**依据**
- 〔HIG〕Layout："A *safe area* defines the area within a window that isn't covered on the edge by a hardware feature or another view within the window, like a toolbar, tab bar, or status bar. **Respecting the safe area is essential to make sure system UI and hardware features like the Dynamic Island don't obstruct content and controls.**"
- 〔HIG〕Layout："**Design a layout that adapts gracefully and consistently.** ... by respecting system-defined safe areas, margins, and guides (where available)"
- 〔HIG〕Layout："**Determine layout based on size classes, not device type or orientation.**"
- 〔HIG〕Layout（tvOS）："**Adhere to the screen's safe area.** Inset primary content 60 points from the top and bottom of the screen, and 80 points from the sides."
  — https://developer.apple.com/design/human-interface-guidelines/layout.md

### 2.11 四种适配全过 —— 动态字体 / 深色模式 / 减弱动效 / 增强对比

**规则**
**四项系统级适配必须全部通过**，任一不过即视为未完成。

**量化参数**
| 适配项 | 硬指标 | 依据 |
|---|---|---|
| **动态字体** | 放大到 **200%** 仍不裁切、不重叠、不丢失操作 | HIG：Ideally, give people the option to enlarge text by at least 200 percent |
| **深色模式** | 自定义色必须提供 light + dark 两套变体；**即使只发布单一外观也要提供两套**（Liquid Glass 适配） | HIG Color |
| **减弱动效** | 位移/缩放 → fade；时长 ≤ 0.20 s；bounce 归零 | HIG Accessibility |
| **增强对比** | 正文 ≤17 pt 需 **4.5:1**；≥18 pt 或粗体需 **3:1**；开启后对比度必须**升高** | HIG Accessibility |

**验收方法**
1. 设置 → 辅助功能 → 显示与文字大小 → 更大字体 → 拉到最大（200%+），遍历全部页面。
2. 浅色 / 深色 / 浅色+增强对比 / 深色+增强对比，四种组合截图并排复检。
3. 减弱动效开/关各录一轮全流程，转场形态差异必须肉眼可辨。
4. 用对比度计算器（或 Accessibility Inspector 内置检查）逐个前景/背景组合量比值，**低于阈值 → 不过**。
5. VoiceOver + 全键盘/全语音控制跑一遍主流程。

**依据**
- 〔HIG〕Accessibility："**Support larger text sizes.** ... Ideally, give people the option to enlarge text by **at least 200 percent** (or 140 percent in watchOS apps)."
- 〔HIG〕Accessibility："**Strive to meet color contrast minimum standards.** ... <doc://com.apple.documentation/documentation/Accessibility/accessibility-inspector> uses the following values from **WCAG Level AA** as guidance" —— 表格：`Up to 17 pts / All / 4.5:1`、`18 pts / All / 3:1`、`All / Bold / 3:1`
- 〔HIG〕Accessibility："**If your app doesn't provide this minimum contrast by default, ensure it at least provides a higher contrast color scheme when the system setting Increase Contrast is turned on.** If your app supports Dark Mode, make sure to check the minimum contrast in both light and dark appearances."
- 〔HIG〕Color："**Make sure all your app's colors work well in light, dark, and increased contrast contexts.** ... If you define a custom color, make sure to supply light and dark variants, and an increased contrast option for each variant that provides a significantly higher amount of visual differentiation. **Even if your app ships in a single appearance mode, provide both light and dark colors to support Liquid Glass adaptivity in these contexts.**"
- 〔HIG〕Accessibility（Assistive Access）："**Identify the core functionality of your app and consider removing noncritical workflows and UI elements.**" / "**Break up multistep workflows so people can focus on a single interaction per screen.**"
  — https://developer.apple.com/design/human-interface-guidelines/accessibility.md / color.md

### 2.12 图标与文案的一致性 —— 命名、语气、大小写

**规则**
**同一个概念，图标、标题、按钮文案必须用同一个词**；全 App 文案遵循一套语气与大小写规则。

**量化参数**
- 〔HIG〕Tab 标签：**能用单个词就用单个词**。
- 〔HIG〕按钮/菜单项标签：**用动词开头**，描述动作（"Add to Cart" 式），用 title-style capitalization。
- 〔HIG〕菜单项标签：**去掉冠词** a / an / the（View Settings，不是 View the Settings）。
- 〔HIG〕菜单项**需要更多信息才能完成时才加省略号 …**。
- 〔HIG〕同一菜单组内，图标**要么全给要么全不给**。
- 〔项目自定〕**术语表**：App 内每个概念只允许 1 个名字（如"对话/会话/聊天"三选一），文档化并全量替换。
- 〔项目自定〕**大小写规则**：正文与说明句用句首大写（sentence case）；Tab 标签、导航标题、按钮标题用 title case；专有名词除外。
- 〔项目自定〕**语气**：全 App 统一第二人称、主动语态；错误文案说明原因 + 给出下一步，不用"哎呀/糟糕"。

**验收方法**
1. 导出全 App 所有可见字符串（`.strings` / `Localized.strings`），生成词表。**同一概念出现 ≥2 个同义词 → 不过**。
2. 检索菜单/按钮标签：**以名词开头而非动词 → 不过**；**含冠词 → 不过**；**该加省略号没加/不该加却加了 → 不过**。
3. 检索 Tab 标签：**非单词（两词以上）→ 不过**。
4. 通读全部字符串列表，检查大小写规则一致性：**同类元素大小写不一致 → 不过**。
5. 用 VoiceOver 连读一遍全部文案：**有读起来不通顺/歧义的 → 不过**。

**依据**
- 〔HIG〕Tab bars："**Include tab labels to help with navigation.** ... **Use single words whenever possible.**"
- 〔HIG〕Buttons："**Consider using text when a short label communicates more clearly than an icon.** To use text, write a few words that succinctly describe what the button does. Using [title-style capitalization](https://help.apple.com/applestyleguide/#/apsgb744e4a3?sub=apdca93e113f1d64), **consider starting the label with a verb**"
- 〔HIG〕Menus："**For each menu item, write a label that clearly and succinctly describes it.** In general, label a menu item that initiates an action **using a verb or verb phrase**"
- 〔HIG〕Menus："**Remove articles like *a*, *an*, and *the* from menu-item labels to save space.**"
- 〔HIG〕Menus："**Append an ellipsis to a menu item's label when the action requires more information before it can complete.**"
- 〔HIG〕Menus："**Apply a uniform visual treatment across menu items in the same group.** ... provide icons for all menu items in a group, or none of them."
- 〔HIG〕Segmented controls："**Use nouns or noun phrases for segment labels.** Write text that describes each segment and uses title-style capitalization."
  — https://developer.apple.com/design/human-interface-guidelines/tab-bars.md / buttons.md / menus.md / segmented-controls.md

### 3.1 动效（Motion）
> https://developer.apple.com/design/human-interface-guidelines/motion.md
> （本次新抓取；HIG 更新日志：September 9, 2025 "Added guidance for Liquid Glass."）

- "Beautiful, fluid motions bring the interface to life, conveying status, providing feedback and instruction, and enriching the visual experience of your app or game."
- "**Add motion purposefully, supporting the experience without overshadowing it.** Don't add motion for the sake of adding motion. Gratuitous or excessive animation can distract people and may make them feel disconnected or physically uncomfortable."
- "**Make motion optional.** Not everyone can or wants to experience the motion in your app or game, so it's essential to avoid using it as the only way to communicate important information. To help everyone enjoy your app or game, supplement visual feedback by also using alternatives like haptics and audio to communicate."
- "**Strive for realistic feedback motion that follows people's gestures and expectations.** ... if someone reveals a view by sliding it down from the top, they don't expect to dismiss the view by sliding it to the side."
- "**Aim for brevity and precision in feedback animations.** When animated feedback is brief and precise, it tends to feel lightweight and unobtrusive, and it can often convey information more effectively than prominent animation."
- "**In apps, generally avoid adding motion to UI interactions that occur frequently.** The system already provides subtle animations for interactions with standard interface elements."
- "**Let people cancel motion.** As much as possible, don't make people wait for an animation to complete before they can do anything, especially if they have to experience the animation more than once."
- "**Consider using animated symbols where it makes sense.**"
- 游戏帧率："maintaining a consistent frame rate of 30 to 60 fps typically results in a smooth, visually appealing experience"
- watchOS 注："All layout- and appearance-based animations automatically include built-in easing that plays at the start and end of the animation. **You can't turn off or customize easing.**"
- ⚠️ **本节无任何时长数值** —— HIG Motion 页不提供 duration ladder。

### 3.2 加载（Loading）
> https://developer.apple.com/design/human-interface-guidelines/loading.md

- "The best content-loading experience **finishes before people become aware of it**."
- "**Show something as soon as possible.** If you make people wait for loading to complete before displaying anything, they can interpret the lack of content as a problem with your app or game. Instead, consider showing placeholder text, graphics, or animations as content loads, replacing these elements as content becomes available."
- "**Let people do other things in your app or game while they wait for content to load.**"
- "**If loading takes an unavoidably long time, give people something interesting to view while they wait.** ... Gauge the remaining loading time as accurately as possible to help you avoid giving people too little time to enjoy your placeholder content or having so much time that you need to repeat it."
- "**Improve installation and launch time by downloading large assets in the background.**"

### 3.3 进度指示器（Progress indicators）
> https://developer.apple.com/design/human-interface-guidelines/progress-indicators.md

- "All progress indicators are **transient**, appearing only while an operation is ongoing and disappearing after it completes."
- "**When possible, use a determinate progress indicator.**"
- "**Be as accurate as possible when reporting advancement in a determinate progress indicator.** Consider evening out the pace of advancement ... Showing 90 percent completion in five seconds and the last 10 percent in 5 minutes can make people wonder if your app is still working and can even feel deceptive."
- "**Keep progress indicators moving so people know something is continuing to happen.** People tend to associate a stationary indicator with a stalled process or a frozen app."
- "**When possible, switch a progress bar from indeterminate to determinate.**"
- "**Don't switch from the circular style to the bar style.** Activity indicators (also called spinners) and progress bars are different shapes and sizes, so transitioning between them can disrupt your interface and confuse people."
- "**If it's helpful, display a description that provides additional context for the task.** Be accurate and succinct. **Avoid vague terms like *loading* or *authenticating* because they seldom add value.**"
- "**Display a progress indicator in a consistent location.**"
- "**When it's feasible, let people halt processing.** ... include a Cancel button."
- Podcasts 刷新控件标题示例："a refresh control in Podcasts ... uses a title to tell people when the last podcast update occurred"

### 3.4 反馈（Feedback）
> https://developer.apple.com/design/human-interface-guidelines/feedback.md

- "The most effective feedback tends to **match the significance of the information to the way it's delivered**. For example, it often works well to display status information in a passive way ... In contrast, a warning about possible data loss needs to interrupt people so they have a chance to avoid the problem."
- "**Make sure all feedback is accessible.** When you use multiple ways to provide feedback, you reach more people and give them the opportunity to receive feedback in ways that work for them. For example, when you provide feedback using color, text, sound, and haptics, people can receive it whether they silence their device, look away from the screen, or use VoiceOver."
- "**Consider integrating status feedback into your interface.** When status feedback is available near the items it describes, people get important information without having to take action or leave their current context. For example, **Mail in iOS and iPadOS describes the most recent update and displays the number of unread messages in the toolbar of the mailbox screen, making the information unobtrusive but easy for people to check when they're interested.**"
- "**Use alerts to deliver critical — and ideally actionable — information.** By design, alerts disrupt the current context ... **Alerts can lose their impact if you use them too often or to deliver unimportant information.**"
- "**Warn people when they initiate a task that can cause data loss that's unexpected and irreversible.** In contrast, don't warn people when data loss is the expected result of their action. For example, **the Finder doesn't warn people every time they throw away a file because deleting the file is the expected result.**"
- "**When it makes sense, confirm that a significant action or task has completed.** ... it's generally best to reserve this type of confirmation for activities that are sufficiently important — because people typically expect their action or task to succeed, **they only need to know when it doesn't.**"
- "**Show people when a command can't be carried out and help them understand why.** For example, if people request directions without specifying a destination, **Maps tells them it can't provide directions to and from the same location.**"

### 3.5 触感（Playing haptics）
> https://developer.apple.com/design/human-interface-guidelines/playing-haptics.md

- "**Use system-provided haptic patterns according to their documented meanings.** ... If the documented use case for a pattern doesn't make sense in your app or game, avoid using the pattern to mean something else."
- "**Use haptics consistently throughout your app or game.** It's important to build a clear, causal relationship between each haptic and the action that causes it so people learn to associate certain haptic patterns with certain experiences."
- "**Avoid overusing haptics.** ... **Often, the best haptic experience is one that people may not be conscious of, but miss when it's turned off.**"
- "**In most apps, prefer playing short haptics that complement discrete events.**"
- "**Make haptics optional.** Let people turn off or mute haptics, and make sure people can still enjoy your app or game without them."
- iOS 三大类（**可直接映射为代码**）：
  - Notification → Success / Warning / Error
  - Impact → Light / Medium / Heavy / Rigid / Soft
  - Selection → "Indicates that a UI element's values are changing"
- transient vs continuous："Transient events are brief and compact, often feeling like taps or impulses." / "Continuous events feel like sustained vibrations."

### 3.6 排版（Typography）
> https://developer.apple.com/design/human-interface-guidelines/typography.md

- "A *text style* specifies a **combination of font weight, point size, and leading values** for each text size."
- "Text styles also allow text to **scale proportionately when people change the system text size** or make accessibility adjustments, like turning on Larger Text in Accessibility settings."
- "**Make sure text looks good and remains legible when people scale it.** Use a text style that makes the text look good at full scale, then test it for legibility at different scales."
- "**Maximize the contrast between text and the background of its container.**"
- "On all platforms, the system fonts support **dynamic optical sizes**, which merge discrete optical sizes (like Text and Display) and weights into a single, continuous design."
- SF Symbols："integrate seamlessly with the San Francisco system font, **automatically aligning with text in all weights and sizes**."
- 规格表（iOS / iPadOS Dynamic Type，Large 默认档）—— 见 §2.3 表。

### 3.7 辅助功能（Accessibility）
> https://developer.apple.com/design/human-interface-guidelines/accessibility.md

- "**Support larger text sizes.** ... Ideally, give people the option to enlarge text by **at least 200 percent** (or 140 percent in watchOS apps)."
- "**Strive to meet color contrast minimum standards.** ... <doc://com.apple.documentation/documentation/Accessibility/accessibility-inspector> uses the following values from **WCAG Level AA** as guidance"

  | Text size | Text weight | Minimum contrast ratio |
  |---|---|---|
  | Up to 17 pts | All | 4.5:1 |
  | 18 pts | All | 3:1 |
  | All | Bold | 3:1 |

- "**If your app doesn't provide this minimum contrast by default, ensure it at least provides a higher contrast color scheme when the system setting Increase Contrast is turned on.** If your app supports Dark Mode, make sure to check the minimum contrast in both light and dark appearances."
- 控件尺寸表：

  | Platform | Default control size | Minimum control size |
  |---|---|---|
  | iOS, iPadOS | **44x44 pt** | 28x28 pt |
  | macOS | 28x28 pt | 20x20 pt |
  | tvOS | 66x66 pt | 56x56 pt |
  | visionOS | 60x60 pt | 28x28 pt |
  | watchOS | 44x44 pt | 28x28 pt |

- "**Consider spacing between controls as important as size.** ... **about 12 points of padding around elements that include a bezel**. For elements without a bezel, **about 24 points of padding** works well around the element's visible edges."
- "**Support simple gestures for common interactions.** ... **avoid custom multifinger and multihand gestures**"
- "**Offer alternatives to gestures.** ... if you use a swipe gesture to dismiss a view, also make a button available"
- 减弱动效清单（见 §2.1 依据）。
- Assistive Access："**Identify the core functionality of your app and consider removing noncritical workflows and UI elements.**" / "**Break up multistep workflows so people can focus on a single interaction per screen.**"

### 3.8 图标（Icons）
> https://developer.apple.com/design/human-interface-guidelines/icons.md

- "An effective icon is a graphic asset that **expresses a single concept** in ways people instantly understand."
- "an *interface icon* typically uses **streamlined shapes and touches of color** to communicate a straightforward idea."
- "**Maintain visual consistency across all interface icons in your app.** ... all interface icons in your app need to use a consistent **size, level of detail, stroke thickness (or weight), and perspective**."
- "**In general, match the weights of interface icons and adjacent text.**"
- "**If necessary, add padding to a custom interface icon to achieve optical alignment.**"
- "**Include text in your design only when it's essential for conveying meaning.** ... If you need to display individual characters in your icon, be sure to localize them." / "include a flipped version of the icon to use when the context is right-to-left."
- 文档图标："Your document icon can display as small as **16x16 px**" / "**Define a margin that measures about 10% of the image canvas** and keep most of the image within it ... it's best when the image occupies about **80% of the image canvas**."

### 3.9 色彩（Color）
> https://developer.apple.com/design/human-interface-guidelines/color.md

- "The system defines colors that look good on various backgrounds and appearance modes, and can automatically adapt to vibrancy and accessibility settings. **Using system colors is a convenient way to make your experience feel at home on the device.**"
- "**Avoid using the same color to mean different things.**"
- "**Make sure all your app's colors work well in light, dark, and increased contrast contexts.** ... If you define a custom color, make sure to supply light and dark variants, and an increased contrast option for each variant ... **Even if your app ships in a single appearance mode, provide both light and dark colors to support Liquid Glass adaptivity in these contexts.**"
- "**Avoid hard-coding system color values in your app.** Documented color values are for your reference during the app design process. **The actual color values may fluctuate from release to release**, based on a variety of environmental variables."
- "**Apply color sparingly** ... reserve it for elements that truly benefit from emphasis, such as status indicators or primary actions. To emphasize primary actions, apply color to the background rather than to symbols or text. ... **Refrain from adding color to the background of multiple controls.**"
- "**Avoid using similar colors in control labels if your app has a colorful background.** ... prefer a **monochromatic appearance for toolbars and tab bars**"
- "**Consider choosing a limited color palette that coordinates with your app logo.** Subtle use of color can help you communicate your brand while **deferring to the content**."

### 3.10 Tab Bar / Toolbar / 菜单（导航与折叠的官方依据）
> https://developer.apple.com/design/human-interface-guidelines/tab-bars.md / toolbars.md / menus.md / segmented-controls.md / gestures.md

- Tab："**Use a tab bar to support navigation, not to provide actions.**"
- Tab："**Use the appropriate number of tabs required** ... it's generally easier to navigate among **fewer tabs**."
- Tab："**Avoid overflow tabs.** ... the trailing tab becomes a **More** tab in iOS and iPadOS ... **The More tab makes it harder for people to reach and notice content on tabs that are hidden, so limit scenarios in your app where this can happen.**"
- Tab："**Don't disable or hide tab bar buttons**, even when their content is unavailable."
- Tab："**Include tab labels** ... **Use single words whenever possible.**"
- Tab（自定义）："If you let people select their own tabs, **aim for a default list of five or fewer** to preserve continuity between compact and regular view sizes."
- Tab（tvOS）："The height of a tab bar is 68 points, and its top edge is 46 points from the top of the screen; **you can't change either of these values.**"
- Toolbar："**Choose items deliberately to avoid overcrowding.** People need to be able to distinguish and activate each item, so you don't want to put too many items in the toolbar. To accommodate variable view widths, **define which items move to the overflow menu** as the toolbar becomes narrower."
- Toolbar："**Add a More menu to contain additional actions. Prioritize less important actions for inclusion in the More menu.** Try to include all actions in the toolbar if possible, **and only add this menu if you really need it.**"
- Toolbar（macOS/iPadOS）："**The system automatically adds an overflow menu** when items no longer fit. **Don't add an overflow menu manually**"
- Toolbar："**Prioritize only the most important items** for inclusion in the main toolbar area."
- 菜单："**Prefer listing important or frequently used menu items first.** People tend to start scanning a menu from the top."
- 菜单："**Consider grouping logically related items.** ... To help people visually distinguish such groups, use a **separator**."
- 菜单："**Be mindful of menu length.** People need more time and attention to read a long menu ... If a menu is too long, consider **dividing it into separate menus**. Alternatively, you might be able to use a **submenu** to shorten the list."
- 菜单："**Apply a uniform visual treatment across menu items in the same group.** ... provide icons for all menu items in a group, or none of them."
- 分段控件："**Limit the number of segments in a control.** ... **Aim for no more than about five to seven segments in a wide interface and no more than about five segments on iPhone.**"
- 手势："**Use shortcut gestures to supplement standard gestures, not replace them.** ... people also need simple, familiar ways to navigate and perform actions, even if it means an extra tap or two."
- 手势："**Avoid conflicting with gestures that access system UI.**"

### 3.11 布局（Layout）
> https://developer.apple.com/design/human-interface-guidelines/layout.md

- "**Order content by relative importance.** People often start by viewing content in reading order — that is, **from top to bottom and from the leading to trailing side** — so place the most important items near the top and leading side."
- "**Determine layout based on size classes, not device type or orientation.**"
- "**Keep functionality the same as size classes change** ... you can change the amount of functionality that's visible onscreen as the amount of space changes. Consider ... **expose functionality that might otherwise be grouped into an overflow menu.**"
- "**Design a layout that adapts gracefully and consistently.**"
- "**Be prepared for text-size changes.** ... horizontally adjacent views may need to stack vertically ... table rows ... may need to grow in height so that text isn't cropped or doesn't overlap other content."
- "The system includes predefined **layout guides** that make it easy to apply standard margins around content and restrict the width of text for optimal readability."
- "**Adhere to the screen's safe area.** Inset primary content 60 points from the top and bottom of the screen, and 80 points from the sides."（tvOS）

3. **静音失败永远不行**——不成功要说明原因（Maps）。

5. **导航层级随空间变化，功能集合不变**（Music 的 tab↔sidebar）。
6. **「确认」是稀缺资源**——只在预期失败时给（Apple Pay）。
7. **界面稳定 > 内容齐全**：空 section 解释原因，而不是隐藏 tab（Tab bars）。

## §五 ⭐ 主次与折叠规范

> 本节是用户核心痛点（「不要堆功能，把需要体现的功能都体现出来，把一些功能进行折叠」）的落地规则。
> 规则本身为〔项目自定〕，凡有 HIG 支撑处均已注明。

### 5.1 一级可见元素上限

| 层级 | 对象 | 上限 | 依据 |
|---|---|---|---|
| L0 | Tab Bar 项数 | **≤ 5** | 〔HIG〕"aim for a default list of **five or fewer**"（tab-bars.md:90）；"easier to navigate among fewer tabs" |
| L0 | 分段控件段数（iPhone） | **≤ 5**（宽界面 ≤ 7） | 〔HIG〕segmented-controls.md:46 |
| L0 | 单屏**主操作按钮**（填充色强调按钮） | **= 1** | 〔HIG〕"Refrain from adding color to the background of multiple controls."（color.md） |
| L1 | 单屏 Primary 层级卡片/列表行 | **≤ 5** | 〔项目自定〕，依据〔HIG〕"reading order — from top to bottom"（layout.md:26），超过 5 项视觉主次失效 |
| L1 | 单屏可交互元素总数（不含 Tab Bar 与导航栏） | **≤ 7** | 〔项目自定〕，超出即触发"杂乱"（见 §5.4） |
| L2 | 导航栏右侧 + 工具栏可见项 | **≤ 4**，其余进 More | 〔HIG〕"Choose items deliberately to avoid overcrowding" + "Prioritize only the most important items"（toolbars.md:32/170） |
| L2 | 悬浮按钮 | **≤ 1** | 〔项目自定〕 |
| L3 | 上下文菜单（长按）项数 | **≤ 5** | 〔HIG〕"a context menu lets people access a **small number** of frequently used actions"（menus.md:22）+ 菜单长度建议 |
| L3 | 单个菜单（More 菜单）项数 | **≤ 8**；超出用 separator 分组或 submenu | 〔HIG〕"Be mindful of menu length ... consider dividing it into separate menus ... use a submenu"（menus.md:72） |

### 5.2 三层信息层级定义 + 收纳方式

| 层 | 定义 | 判断标准 | 收纳方式 | 数量约束 |
|---|---|---|---|---|
| **Primary（主）** | 使用这个 App 的**主要目的**本身 | 去掉它，App 失去存在意义 | 永久可见：Tab / 首屏主区 / 底部主按钮 | 每屏 1 个焦点；Tab ≤ 5 |
| **Secondary（次）** | **高频但非目的**的支撑操作 | 日/周频使用；不常驻也能活 | 一级可见但降权：工具栏、分段控件、列表行内 | 单屏 ≤ 5–7 |
| **Tertiary（次次要）** | 低频、一次性、可配置、可逆 | 月频以下；错过不致命；可被替代 | **折叠**：More 菜单 / 长按菜单 / 设置页 / 命令面板 / 快捷键 / 搜索 | 不常驻；不可见可发现 |

**归属铁律**：
1. Tertiary **绝不**进入 Tab Bar、**绝不**占据首屏主区、**绝不**与 Primary 同屏同权重。
2. 一个功能只要满足「**不常驻也能被找到**」+「**有兜底路径**」（搜索/命令面板/设置），就可以被折叠。
3. 折叠后的功能**必须有发现路径**：至少满足「More 菜单」或「长按」或「搜索」三者之一，否则等于删除。

### 5.3 功能该放哪：收纳方式对照表

| 功能特征 | 应该放到 | 具体形态 | 不该放到 |
|---|---|---|---|
| 顶级分区、日/周频、有独立内容集合 | **Tab** | ≤5 个，单词标签 | 更多 |
| 顶级分区但低频 | **侧栏 / 设置内列表 / 搜索** | iPad 用 sidebar，iPhone 用设置页分组 | Tab（会挤爆 5 个上限） |
| 需要独立上下文、超过一屏、要返回 | **独立 Scene（push 全屏页）** | 导航栈 | Sheet（内容超一屏） |
| 轻量编辑、二次确认、≤1 屏 | **Sheet / 弹窗** | `presentationDetents` 可下拉消解 | 全屏 push |
| 对当前列表项的操作（重命名/归档/删除） | **长按上下文菜单 / 侧滑** | 侧滑露出 1–2 个主动作 + 更多进 ⋯ | 独立页面 |
| 同一屏的同类视图切换 | **分段控件** | ≤5 段（iPhone） | Tab |
| 跨层级、低频、需要额外参数的高级操作 | **命令面板 / 快捷键** | 唤起即输入 | 一级按钮 |
| 不打断、可延后、用户不必马上看 | **通知 / Live Activity / 角标** | 只给"摘要 + 一键进入" | Alert（打断） |
| 高度个性化、影响其他功能行为的配置 | **设置页**（分组列表） | 二级入口 | 首屏 |
| 机器人硬件行为（音量、灯光、动作、姿态） | **常驻控制面板 / 悬浮控件** | 独立可折叠面板 | 混进设置深处 |
| 危险 / 不可逆 / 会丢数据 | **二次确认 Alert** | 明确动词 + 影响范围 | 静默执行 / 一键撤销 |
| 失败兜底、诊断、日志 | **App 内"诊断/关于"页** | 仅调试构建可见 | 用户主界面 |

### 5.4 ⭐ 「看起来杂乱」的 6 个可检测成因

> 每个成因都有**可机械执行的检测方法**——设计/实现可自测，验收方可复核。

| # | 成因 | 可检测特征 | 检测方法 | 判定阈值 |
|---|---|---|---|---|
| **C1 同层级竞争** | 一屏内出现 ≥2 个视觉权重相当的焦点 | 多个填充色按钮 / 多个大标题 / 多个彩色卡片 | 逐屏截图，统计"强调色着色控件数"与"最大字号元素数" | 同屏强调色控件 **>1** 或 最大字号元素 **>1** → 不过 |
| **C2 一致性破缺** | 同屏混用 ≥2 套间距/圆角/字重/描边体系 | 一半卡片 16pt 圆角、一半 8pt；一半圆头字体 | 导出该屏全部间距值/圆角值/字重值，统计**不同取值数** | 任一维度取值种数 **>2** → 不过 |
| **C3 分隔手段过多** | 同一区域混用分隔线 + 阴影 + 背景色块 + 留白 | 列表项既描边又有投影又有底色 | 逐屏标注分隔手法种类 | 手法种数 **>1** → 不过 |
| **C4 强调色滥用** | 强调色出现在多个不相关区域 | 蓝色同时用于链接、图标、背景、按钮 | 逐屏统计强调色像素面积占比 + 出现区域数 | 强调色面积占比 **>10%** 或 出现区域 **>2** → 不过 |
| **C5 密度不均 / 节奏断裂** | 同屏元素间距分布无规律，块与块之间没有稳定节奏 | 有的 8pt 有的 40pt；分组间距 = 组内间距 | 计算同屏所有相邻间距值的**标准差/最大值比** | 组内间距 ≥ 组间间距，或 组内间距种类 **>2** → 不过 |
| **C6 兜底缺失** | 元素"看起来能点但不知道是什么 / 点了没反应" | 无标题的图标按钮、无说明的开关、空区域无文案 | Accessibility Inspector 扫描空 accessibilityLabel；人工遍历「空/错/离/拒」4 条路径 | 空 label 可点元素 **>0**，或 4 条路径任一出现无解释 → 不过 |

**补充检测（整体观感）**：把任意两个页面并排放大到同一尺寸，**能在 3 秒内说出哪个是主页面** —— 说不出即触发 C1。

### 5.5 ⭐ 5 问决策表（给任意一个功能，问 5 个问题决定它放哪）

> **用法**：拿到一个待安置的功能，依次问 Q1→Q5；**第一个答"否"的问题就决定它去哪**。

| 问 | 问题 | 判据 | 答"是"→ 去哪 |
|---|---|---|---|
| **Q1** | **它是不是"使用这个 App 的主要目的"？** | 删掉它，App 就没有存在意义了吗？ | → **Primary**：Tab / 首屏主区 / 主按钮 |
| **Q2** | **它日频/周频被使用吗？** | 日均 ≥1 次或周 ≥3 次 | → **Secondary**：一级可见（工具栏 / 分段控件 / 行内按钮），但降权 |
| **Q3** | **它需要"不进入就能看到当前状态"吗？** | 用户必须一眼看到它的状态/数值/进度 | → **常驻可见**：常驻状态位（角标 / 状态条 / 常驻小部件）；否则不必常驻 |
| **Q4** | **折叠后还能被找到吗？** | 有没有至少一条兜底路径（More 菜单 / 长按 / 搜索 / 命令面板 / 设置）？ | 有 → **Tertiary**：折叠到 More 菜单 / 长按 / 搜索 / 设置<br>没有 → **不折叠**，升级为 Secondary 一级可见 |
| **Q5** | **放进一级会稀释主操作吗？** | 同屏/同层是否会出现第二个同等权重的视觉焦点？ | 会 → **折叠**（或与主操作合并）；不会 → 可放一级 |

**决策速查**：

```
Q1 是 → Primary（Tab / 首屏主区）
Q1 否 & Q2 是 → Secondary（一级可见，降权）
Q1 否 & Q2 否 & Q4 有 → Tertiary（折叠）
Q1 否 & Q2 否 & Q4 无 → 强制升为 Secondary（可发现性优先）
Q3 是 → 追加"常驻状态位"（不占用功能入口）
Q5 是 → 再降一级 / 合并 / 移出屏幕
```

**硬性兜底规则**（无论五问结果如何）：
- 危险 / 不可逆 / 会丢数据 → **Alert 二次确认**（不论层级）。
- 机器人硬件的直接控制（音量、灯光、动作、姿态）→ **常驻可折叠控制面板**（桌面机器人的核心动作不能藏在三级）。
- 任何"可见即可用"要求：折叠项在被折叠前**必须**在父级有可见入口（More / 长按 / 角标）。

### 5.6 本项目（桌面 AI 陪伴机器人）的一次落地演算

> 用一个假想 App 演示 5 问表怎么用。**角色/功能为示例，非产品既定事实**。

| 功能 | Q1 | Q2 | Q3 | Q4 | Q5 | 结论 |
|---|---|---|---|---|---|---|
| 实时对话（语音/文字） | 是 | 是 | — | — | 否 | **Primary** → 首页主区 + 常驻输入条 |
| 机器人表情/动作切换 | 否 | 是 | 是（当前表情需可见） | — | 否 | **Secondary + 常驻状态位** → 常驻控制面板 + 顶部状态条 |
| 音量 / 静音 | 否 | 是 | 是 | — | 是（会稀释对话） | **Secondary 折叠** → 控制面板内一行；不放首屏主按钮区 |
| 灯光颜色 | 否 | 否 | 否 | 是（面板内 + 设置） | 是 | **Tertiary** → 控制面板 ⋯ / 设置页 |
| 对话历史 | 否 | 是 | — | — | 是 | **Secondary** → Tab 或首页分段控件切换（≤5 段） |
| 配网 / 设备管理 | 否 | 否 | 是（设备状态需可见） | — | 是 | **常驻状态位 + 设置页**；设备不在线 → 空/离线状态 |
| 固件升级 | 否 | 否 | 否 | 是 | 是 | **Tertiary** → 设置页 + 通知（非 Alert，除非会中断） |
| 导出/诊断日志 | 否 | 否 | 否 | 是 | 是 | **Tertiary** → 设置页最底 + 仅调试构建 |
| 新建对话 | 否 | 是 | — | — | 否 | **Secondary** → 导航栏右侧（工具栏 ≤4 项） |

> 结论：Tab 只需 **2 个**（对话 / 历史）—— 这正是"减法"落地后的样子；其余 7 项全部进入「控制面板 + 设置 + 通知」三条折叠通道。
